# Отчётность

Техническая часть оценки — лишь половина всего процесса. Конечный результат — хорошо написанный и информативный отчёт. Он должен быть понятным и выделять все риски, обнаруженные при оценке. Отчёт должен быть полезен как высшему руководству, так и техническим специалистам.

## Об этом разделе

Это руководство предлагает лишь один из возможных подходов к отчётности; его не следует считать набором строгих обязательных правил. Рассматривая любую из рекомендаций ниже, всегда спрашивайте себя, улучшит ли она ваш отчёт.

Эти рекомендации лучше всего подходят для отчётов по консалтинговым работам. Для внутренних отчётов или сообщений в программах вознаграждения за уязвимости они могут быть избыточны.

Независимо от аудитории рекомендуется защитить и зашифровать отчёт, чтобы воспользоваться им мог только получатель.

Хороший отчёт помогает заказчику понять обнаруженные проблемы и подчёркивает качество технического тестирования. Если заказчик не понимает результаты, качество технического тестирования теряет всякое значение.

## 1. Введение

### 1.1. Управление версиями

Фиксирует изменения отчёта, обычно в виде таблицы, подобной следующей.

| Версия | Описание | Дата | Автор |
|:-------:|-------------|------|--------|
| 1.0 | Первоначальный отчёт | DD/MM/YYYY | J. Doe |

### 1.2. Оглавление

Страница с оглавлением документа.

### 1.3. Команда

Список участников команды с подробным описанием их компетенций и квалификации.

### 1.4. Область работ

Границы и потребности работ, согласованные с организацией.

### 1.5. Ограничения

Ограничения могут включать:

- области, исключённые из тестирования;
- неработающую функциональность;
- недостаток сотрудничества;
- нехватку времени;
- отсутствие доступа или учётных данных.

### 1.6. Сроки

Продолжительность работ.

### 1.7. Заявление об ограничении ответственности

Вы можете включить заявление об ограничении ответственности за свои услуги. Для создания юридически обязывающего документа всегда консультируйтесь с юристом.

Следующий пример приведён только для иллюстрации. Его не следует использовать без изменений; он не является юридической консультацией.

*Это тестирование представляет собой оценку на определённый момент времени, поэтому после его проведения среда могла измениться. Нет гарантии, что выявлены все возможные проблемы безопасности; после проведения тестов могли быть обнаружены новые уязвимости. Таким образом, этот отчёт служит ориентиром, а не гарантией полноты представления рисков, угрожающих рассматриваемым системам.*

## 2. Краткое изложение для руководства

Это краткая презентация сути отчёта, предоставляющая руководителям:

- Цель тестирования.
  - Опишите бизнес-потребность, лежащую в основе проверки безопасности.
  - Опишите, как проверки помогли организации понять свои системы.
- Ключевые результаты в бизнес-контексте: например, возможные проблемы соответствия требованиям, ущерб репутации и т. д. Сосредоточьтесь на последствиях для бизнеса, пока не затрагивая технические подробности.
- Стратегические рекомендации по предотвращению повторения проблем. Опишите их без технических подробностей, пока не включая конкретные технические рекомендации.

Изложение должно быть конструктивным и содержательным. Избегайте жаргона и негативных предположений. Если используются рисунки, графики или иллюстрации, убедитесь, что они передают мысль яснее, чем текст.

## 3. Обнаруженные проблемы

Этот раздел предназначен для технической команды. Он должен содержать все сведения, необходимые для понимания, воспроизведения и устранения уязвимости. Логическое разделение помогает улучшить читаемость отчёта. Например, можно выделить разделы «Внешний доступ» и «Внутренний доступ».

При повторном тестировании можно создать подраздел с итогами предыдущей проверки, актуальным состоянием ранее выявленных уязвимостей и перекрёстными ссылками на текущую проверку.

### 3.1. Сводка обнаруженных проблем

Список обнаруженных проблем с уровнями риска. Для удобства обеих команд можно использовать таблицу.

| Идентификатор | Название | Уровень риска |
|:------------:|--------|------------|
| 1 | Обход аутентификации пользователя | Высокий |

### 3.2. Подробности обнаруженных проблем

Для каждой проблемы следует подробно указать:

- Идентификатор для общения между сторонами и перекрёстных ссылок в отчёте.
- Название уязвимости, например «Обход аутентификации пользователя».
- Вероятность эксплуатации или возможность эксплуатации с учётом различных факторов:
  - Насколько легко её эксплуатировать.
  - Существует ли работающий код эксплойта.
  - Какой уровень доступа требуется.
  - Насколько злоумышленник мотивирован её эксплуатировать.
- Последствия уязвимости для системы.
- Риск уязвимости для приложения.
  - Возможные значения: информационный, низкий, средний, высокий и критический. Обязательно подробно определите используемые значения в приложении к отчёту. Это позволит читателю понять, как определяется каждая оценка.
  - Для некоторых работ требуется оценка [CVSS](https://www.first.org/cvss/). Если она необязательна, иногда её полезно включить, а иногда она лишь усложняет отчёт.
- Подробное описание уязвимости, способа её эксплуатации и возможного ущерба. Любые потенциально конфиденциальные данные, например пароли, персональные сведения или реквизиты кредитных карт, следует маскировать.
- Подробные шаги по устранению уязвимости, возможные улучшения защищённости и недостающие практики безопасности.
- Дополнительные материалы, помогающие понять уязвимость: изображение, видео, CVE, внешнее руководство и т. д.

Оформите этот раздел так, чтобы наилучшим образом передать суть.

Всегда убеждайтесь, что описания дают читающему отчёт инженеру достаточно информации для действий. Подробно объясните проблему и приведите столько технических сведений, сколько необходимо для её устранения.

## Приложения

Можно добавить несколько приложений, например:

- Использованная методология тестирования.
- Пояснения к оценкам серьёзности и риска.
- Существенные результаты работы инструментов.
  - Обязательно обработайте вывод, а не просто вставляйте его целиком.
- Контрольный список всех выполненных проверок, например [контрольный список WSTG](https://github.com/OWASP/wstg/tree/master/checklist). Такие материалы можно предоставлять отдельными вложениями к отчёту.
