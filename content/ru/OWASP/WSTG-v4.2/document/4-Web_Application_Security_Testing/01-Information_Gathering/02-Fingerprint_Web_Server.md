# Определение типа и версии веб-сервера

|ID          |
|------------|
|WSTG-INFO-02|

## Краткое описание

Определение типа и версии веб-сервера (web server fingerprinting) позволяет установить, какой веб-сервер и какой его версии используется на целевой системе. Хотя эта функция часто встроена в инструменты автоматизированного тестирования, исследователям важно понимать, как эти инструменты пытаются распознать программное обеспечение и какую пользу это приносит.

Точное определение типа веб-сервера, на котором работает приложение, может помочь специалистам по тестированию безопасности установить, уязвимо ли приложение для атаки. В частности, серверы с устаревшими версиями программного обеспечения без актуальных исправлений безопасности могут быть подвержены известным эксплойтам для конкретных версий.

## Цели тестирования

- Определить версию и тип работающего веб-сервера для последующего выявления известных уязвимостей.

## Методика тестирования

К методам определения веб-сервера относятся [получение баннера сервера](https://en.wikipedia.org/wiki/Banner_grabbing), получение ответов на некорректные запросы и использование автоматизированных инструментов для более основательного сканирования, сочетающего несколько приёмов. Все эти методы основаны на одном принципе: получить от веб-сервера ответ, который затем можно сравнить с базой известных ответов и вариантов поведения и тем самым сопоставить с известным типом сервера.

### Получение баннера сервера

Для получения баннера серверу отправляют HTTP-запрос и исследуют [заголовок ответа](https://developer.mozilla.org/en-US/docs/Glossary/Response_header). Для этого подходят различные инструменты, включая `telnet` для HTTP-запросов и `openssl` для запросов через SSL.

Например, ниже приведён ответ сервера Apache на запрос.

```http
HTTP/1.1 200 OK
Date: Thu, 05 Sep 2019 17:42:39 GMT
Server: Apache/2.4.41 (Unix)
Last-Modified: Thu, 05 Sep 2019 17:40:42 GMT
ETag: "75-591d1d21b6167"
Accept-Ranges: bytes
Content-Length: 117
Connection: close
Content-Type: text/html
...
```

Ниже приведён другой ответ, на этот раз от nginx.

```http
HTTP/1.1 200 OK
Server: nginx/1.17.3
Date: Thu, 05 Sep 2019 17:50:24 GMT
Content-Type: text/html
Content-Length: 117
Last-Modified: Thu, 05 Sep 2019 17:40:42 GMT
Connection: close
ETag: "5d71489a-75"
Accept-Ranges: bytes
...
```

Ответ lighttpd выглядит следующим образом.

```sh
HTTP/1.0 200 OK
Content-Type: text/html
Accept-Ranges: bytes
ETag: "4192788355"
Last-Modified: Thu, 05 Sep 2019 17:40:42 GMT
Content-Length: 117
Connection: close
Date: Thu, 05 Sep 2019 17:57:57 GMT
Server: lighttpd/1.4.54
```

В этих примерах тип и версия сервера раскрываются явно. Однако приложения, в которых уделяют внимание безопасности, могут скрывать сведения о сервере, изменяя заголовок. Например, ниже приведён фрагмент ответа на запрос к сайту с изменённым заголовком:

```sh
HTTP/1.1 200 OK
Server: Website.com
Date: Thu, 05 Sep 2019 17:57:06 GMT
Content-Type: text/html; charset=utf-8
Status: 200 OK
...
```

Если сведения о сервере скрыты, тестировщики могут предположить его тип по порядку полей заголовка. Обратите внимание: в приведённом выше примере Apache поля следуют в таком порядке:

- Date
- Server
- Last-Modified
- ETag
- Accept-Ranges
- Content-Length
- Connection
- Content-Type

Однако и в примере nginx, и в примере со скрытыми сведениями о сервере общие поля следуют в таком порядке:

- Server
- Date
- Content-Type

На основании этой информации тестировщики могут предположить, что сервер со скрытыми сведениями — nginx. Однако разные веб-серверы могут использовать одинаковый порядок полей, а сами поля можно изменять или удалять, поэтому этот метод не даёт однозначного результата.

### Отправка некорректных запросов

Веб-серверы можно распознавать по ответам об ошибках и, если они не изменены, по стандартным страницам ошибок. Один из способов заставить сервер выдать такой ответ — отправить заведомо неверный или некорректно сформированный запрос.

Например, ниже приведён ответ сервера Apache на запрос с несуществующим методом `SANTA CLAUS`.

```sh
GET / SANTA CLAUS/1.1


HTTP/1.1 400 Bad Request
Date: Fri, 06 Sep 2019 19:21:01 GMT
Server: Apache/2.4.41 (Unix)
Content-Length: 226
Connection: close
Content-Type: text/html; charset=iso-8859-1

<!DOCTYPE HTML PUBLIC "-//IETF//DTD HTML 2.0//EN">
<html><head>
<title>400 Bad Request</title>
</head><body>
<h1>Bad Request</h1>
<p>Your browser sent a request that this server could not understand.<br />
</p>
</body></html>
```

Ниже приведён ответ nginx на тот же запрос.

```sh
GET / SANTA CLAUS/1.1


<html>
<head><title>404 Not Found</title></head>
<body>
<center><h1>404 Not Found</h1></center>
<hr><center>nginx/1.17.3</center>
</body>
</html>
```

Ниже приведён ответ lighttpd на тот же запрос.

```sh
GET / SANTA CLAUS/1.1


HTTP/1.0 400 Bad Request
Content-Type: text/html
Content-Length: 345
Connection: close
Date: Sun, 08 Sep 2019 21:56:17 GMT
Server: lighttpd/1.4.54

<?xml version="1.0" encoding="iso-8859-1"?>
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Transitional//EN"
         "http://www.w3.org/TR/xhtml1/DTD/xhtml1-transitional.dtd">
<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="en" lang="en">
 <head>
  <title>400 Bad Request</title>
 </head>
 <body>
  <h1>400 Bad Request</h1>
 </body>
</html>
```

Стандартные страницы ошибок содержат множество признаков, различающих типы веб-серверов, поэтому их исследование может быть эффективным способом определения сервера даже при скрытых полях заголовка со сведениями о нём.

### Использование автоматизированных средств сканирования

Как отмечалось выше, определение веб-сервера часто входит в функциональность автоматизированных средств сканирования. Эти инструменты умеют отправлять запросы, подобные показанным выше, а также другие пробы, более специфичные для отдельных серверов. Автоматизированные инструменты сравнивают ответы веб-серверов значительно быстрее, чем при ручном тестировании, и пытаются распознать сервер с помощью больших баз известных ответов. Поэтому они с большей вероятностью дают точные результаты.

Ниже перечислены некоторые распространённые средства сканирования с функцией определения веб-сервера.

- [Netcraft](https://toolbar.netcraft.com/site_report) — онлайн-инструмент, сканирующий сайты для получения информации, в том числе о веб-сервере.
- [Nikto](https://github.com/sullo/nikto) — инструмент сканирования с открытым исходным кодом, работающий из командной строки.
- [Nmap](https://nmap.org/) — инструмент с открытым исходным кодом для командной строки, у которого есть и графический интерфейс — [Zenmap](https://nmap.org/zenmap/).

## Рекомендации по устранению

Раскрытие сведений о сервере само по себе не обязательно является уязвимостью, однако эти сведения могут помочь злоумышленникам эксплуатировать другие существующие уязвимости. Они также могут подсказать злоумышленникам уязвимости конкретной версии сервера, позволяющие атаковать серверы без исправлений. Поэтому рекомендуется принять некоторые меры предосторожности, в том числе:

- Скрывать сведения о веб-сервере в заголовках, например с помощью [модуля mod_headers](https://httpd.apache.org/docs/current/mod/mod_headers.html) Apache.
- Использовать [обратный прокси-сервер](https://en.wikipedia.org/wiki/Proxy_server#Reverse_proxies) с усиленной защитой как дополнительный уровень безопасности между веб-сервером и Интернетом.
- Поддерживать веб-серверы в актуальном состоянии, устанавливая последние версии программного обеспечения и исправления безопасности.
