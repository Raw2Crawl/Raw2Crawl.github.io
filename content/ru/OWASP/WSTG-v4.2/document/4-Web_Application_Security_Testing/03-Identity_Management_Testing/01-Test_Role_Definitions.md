# Тестирование определений ролей

## Краткое описание

Приложения предоставляют разные функции и сервисы, для которых требуются разрешения доступа в соответствии с потребностями пользователя. Пользователь может быть:

- администратором, управляющим функциями приложения;
- аудитором, проверяющим операции приложения и предоставляющим подробный отчёт;
- инженером поддержки, помогающим клиентам диагностировать и устранять проблемы с их учётными записями;
- клиентом, взаимодействующим с приложением и использующим его сервисы.

Для поддержки этих и других сценариев использования приложения определяют роли; этот подход более известен как [RBAC](https://en.wikipedia.org/wiki/Role-based_access_control). На основе этих ролей пользователь получает возможность выполнять требуемые задачи.

## Цели тестирования

- Выявить и документировать роли, используемые приложением.
- Попытаться переключиться на другую роль, изменить роль или получить к ней доступ.
- Проверить детализацию ролей и обоснованность предоставленных разрешений.

## Методика тестирования

### Выявление ролей

Тестировщику следует начать с выявления ролей проверяемого приложения любым из следующих способов:

- Документация приложения.
- Разъяснения разработчиков или администраторов приложения.
- Комментарии в приложении.
- Фаззинг возможных ролей:
  - переменная cookie-файла, *например* `role=admin`, `isAdmin=True`;
  - переменная учётной записи, *например* `Role: manager`;
  - скрытые каталоги или файлы, *например* `/admin`, `/mod`, `/backups`;
  - переключение на известных пользователей, *например* `admin`, `backups` и т. д.

### Переключение на доступные роли

После выявления возможных векторов атаки тестировщику необходимо проверить и подтвердить возможность доступа к имеющимся ролям.

> Некоторые приложения определяют роли пользователя при создании, применяя строгие проверки и политики либо защищая роль подписью, созданной серверной частью. Само обнаружение ролей не означает наличия уязвимости.

### Анализ разрешений ролей

Получив доступ к ролям в системе, тестировщик должен разобраться в разрешениях каждой из них.

Инженер поддержки не должен иметь возможности выполнять административные функции, управлять резервными копиями или проводить какие-либо операции вместо пользователя.

Администратор не должен обладать неограниченными полномочиями в системе. Для критически важных административных функций следует применять принцип разделения инициатора и проверяющего (maker-checker) либо многофакторную аутентификацию (MFA), чтобы убедиться, что операцию выполняет именно администратор. Наглядный пример — [инцидент с Twitter в 2020 году](https://blog.twitter.com/en_us/topics/company/2020/an-update-on-our-security-incident.html).

## Инструменты

Описанные проверки можно провести без каких-либо инструментов, кроме того, который используется для доступа к системе.

Для упрощения работы и более полного документирования можно использовать:

- [Расширение Autorize для Burp](https://github.com/Quitten/Autorize)
- [Дополнение ZAP для тестирования управления доступом](https://www.zaproxy.org/docs/desktop/addons/access-control-testing/)
