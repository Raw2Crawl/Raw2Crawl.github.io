## Резюме

[OAuth2.0](https://oauth.net/2/) (далее именуемый OAuth) представляет собой фреймворк авторизации, позволяющий стороннему клиенту получать доступ к ресурсам от имени своего пользователя.

Для реализации этого процесса OAuth активно использует токены для взаимодействия между различными сущностями, каждая из которых наделена определенной [ролью](https://datatracker.ietf.org/doc/html/rfc6749#section-1.1):

- **Resource Owner (Владелец ресурса):** Сущность, предоставляющая доступ к ресурсу; владелец, в большинстве случаев являющийся самим пользователем.
- **Client (Клиент):** Приложение, запрашивающее доступ к ресурсу от имени владельца ресурса. Клиенты подразделяются на два [типа](https://oauth.net/2/client-types/):
    - **Public (Публичные):** клиенты, не способные обеспечить конфиденциальность секрета (*например*, фронтенд-приложения, такие как SPA, мобильные приложения и т. д.).
    - **Confidential (Конфиденциальные):** клиенты, способные безопасно аутентифицироваться на сервере авторизации за счет надежного сохранения зарегистрированных секретов (*например*, бэкенд-сервисы).
- **Authorization Server (Сервер авторизации):** Сервер, хранящий информацию об авторизации и предоставляющий права доступа.
- **Resource Server (Сервер ресурсов):** Приложение, предоставляющее доступ к контенту, запрашиваемому клиентом.

Поскольку задача OAuth заключается в делегировании клиенту прав доступа владельцем ресурса, этот протокол является крайне привлекательной целью для злоумышленников, а некорректная реализация приводит к несанкционированному доступу к ресурсам и конфиденциальной информации пользователей.

Для предоставления доступа клиентскому приложению OAuth использует несколько [типов предоставления авторизации (grant types)](https://oauth.net/2/grant-types/) для генерации токена доступа (access token):

- [Authorization Code](https://oauth.net/2/grant-types/authorization-code/): используется как конфиденциальными, так и публичными клиентами для обмена кода авторизации на токен доступа, однако рекомендуется исключительно для конфиденциальных клиентов.
- [Proof Key for Code Exchange (PKCE)](https://oauth.net/2/pkce/): PKCE расширяет механизм Authorization Code, обеспечивая повышенную безопасность при его использовании публичными клиентами и усиливая защищенность конфиденциальных клиентов.
- [Client Credentials](https://oauth.net/2/grant-types/client-credentials/): используется для межмашинного взаимодействия (machine-to-machine, M2M), где в роли «пользователя» выступает сама машина, запрашивающая доступ к собственным ресурсам на сервере ресурсов.
- [Device Code](https://oauth.net/2/grant-types/device-code/): применяется для устройств с ограниченными возможностями ввода данных.
- [Refresh Token](https://oauth.net/2/grant-types/refresh-token/): токены, выдаваемые сервером авторизации и позволяющие клиентам обновлять токены доступа пользователей после того, как они становятся недействительными или истекают. Данный тип предоставления используется в сочетании с одним из других grant types.

Два потока авторизации признаны устаревшими (deprecated) в спецификации [OAuth2.1](https://oauth.net/2.1/), и их применение не рекомендуется:

- [Implicit Flow*](https://oauth.net/2/grant-types/implicit/): надежная реализация механизма PKCE сделала данный поток устаревшим. До появления PKCE поток Implicit использовался клиентскими приложениями (такими как [одностраничные приложения (Single Page Applications, SPA)](https://en.wikipedia.org/wiki/Single-page_application)), поскольку [механизм совместного использования ресурсов между разными источниками (Cross-Origin Resource Sharing, CORS)](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) ослабил [политику единого источника (Same-Origin Policy)](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy) для взаимодействия между сайтами. Подробные сведения о том, почему поток Implicit не рекомендуется к использованию, см. в [данном разделе](https://datatracker.ietf.org/doc/html/rfc9700#section-2.1.2).
- [Resource Owner Password Credentials](https://oauth.net/2/grant-types/password/): использовался для передачи учетных данных пользователя напрямую клиенту, который затем отправлял их на сервер авторизации для обмена на токен доступа. Информация о причинах отказа от этого потока представлена в [данном разделе](https://datatracker.ietf.org/doc/html/rfc9700#section-2.4).

\*: Поток Implicit является устаревшим исключительно в OAuth, однако по-прежнему остается допустимым решением в протоколе OpenID Connect (OIDC) для получения `id_tokens`. Важно точно понимать контекст использования потока Implicit: его можно идентифицировать в ситуациях, когда для получения токена доступа используется только эндпоинт `/authorization`, без какого-либо обращения к эндпоинту `/token`. Пример приведен [здесь](https://auth0.com/docs/get-started/authentication-and-authorization-flow/implicit-flow-with-form-post).

*Обратите внимание, что потоки OAuth являются сложной комплексной темой, и приведенное выше описание содержит лишь обзор ключевых областей. Ссылки в тексте содержат дополнительную подробную информацию о конкретных потоках.*

## Цели тестирования

- Определить, является ли реализация OAuth2 уязвимой, использует ли устаревшие методы или нестандартную (кастомную) реализацию.

## Методика тестирования

### Устаревшие типы разрешений (Grant Types)

Устаревшие типы предоставления (grant types) были выведены из эксплуатации по соображениям безопасности и функциональности. Выявление факта их использования позволяет оперативно проверить, подвержено ли приложение угрозам, связанным с их эксплуатацией. Некоторые из них могут находиться вне досягаемости внешнего атакующего (например, способ обработки учетных данных пользователя клиентом). Данные факты необходимо документировать и эскалировать внутренним командам разработки.

Для публичных клиентов определить тип предоставления, как правило, можно по запросу к эндпоинту `/token`. Он указывается в запросе на обмен токена параметром `grant_type`.

В следующем примере показан поток Authorization Code с расширением PKCE:

```http
POST /oauth/token HTTP/1.1
Host: as.example.com
[...]

{
  "client_id":"example-client",
  "code_verifier":"example",
  "grant_type":"authorization_code",
  "code":"example",
  "redirect_uri":"https://client.example.com"
}
```

Значения параметра `grant_type` и соответствующие им типы предоставления:

- `password`: указывает на тип предоставления ROPC.
- `client_credentials`: указывает на тип предоставления Client Credentials.
- `authorization_code`: указывает на тип предоставления Authorization Code.

Поток Implicit Flow не содержит параметра `grant_type`, поскольку токен возвращается непосредственно в ответе на запрос к эндпоинту `/authorization`, и вместо этого его можно идентифицировать по параметру `response_type`. Ниже приведен пример:

```http
GET /authorize
  ?client_id=<some_client_id>
  &response_type=token 
  &redirect_uri=https%3A%2F%2Fclient.example.com%2F
  &scope=openid%20profile%20email
  &state=<random_state>
```

Следующие параметры URL указывают на используемый поток OAuth:

- `response_type=token`: указывает на поток Implicit Flow, так как клиент напрямую запрашивает возвращение токена от сервера авторизации.
- `response_type=code`: указывает на поток Authorization Code, так как клиент запрашивает от сервера авторизации возвращение кода, который впоследствии будет обменян на токен.
- `code_challenge=sha256(xyz)`: указывает на расширение PKCE, поскольку ни один другой поток не использует этот параметр.

Ниже приведен пример запроса на авторизацию для потока Authorization Code с расширением PKCE:

```http
GET /authorize
    ?redirect_uri=https%3A%2F%2Fclient.example.com%2F
    &client_id=<some_client_id>
    &scope=openid%20profile%20email
    &response_type=code
    &response_mode=query
    &state=<random_state>
    &nonce=<random_nonce>
    &code_challenge=<random_code_challenge>
    &code_challenge_method=S256 HTTP/1.1
Host: as.example.com
[...]
```

#### Публичные клиенты

Для публичных клиентов рекомендуется использовать механизм Authorization Code с расширением PKCE. Запрос на авторизацию для потока Authorization Code с PKCE должен содержать параметры `response_type=code` и `code_challenge=sha256(xyz)`.

Запрос на обмен токена должен содержать тип предоставления `authorization_code` и параметр `code_verifier`.

Недопустимыми типами предоставления для публичных клиентов являются:

- Authorization Code без расширения PKCE
- Client Credentials
- Implicit Flow
- ROPC

#### Конфиденциальные клиенты

Для конфиденциальных клиентов рекомендуется использовать механизм Authorization Code. Также допустимо применение расширения PKCE.

Недопустимыми типами предоставления для конфиденциальных клиентов являются:

- Client Credentials (за исключением сценариев межмашинного взаимодействия — см. ниже)
- Implicit Flow
- ROPC

##### Межмашинное взаимодействие (M2M)

В ситуациях, когда взаимодействие с пользователем отсутствует и все взаимодействующие клиенты являются исключительно конфиденциальными, может использоваться тип предоставления Client Credentials.

Если вам известны параметры `client_id` и `client_secret`, можно получить токен, передав тип предоставления `client_credentials`:

```bash
$ curl --request POST \
  --url https://as.example.com/oauth/token \
  --header 'content-type: application/json' \
  --data '{"client_id":"<some_client_id>","client_secret":"<some_client_secret>","grant_type":"client_credentials"}' --proxy https://localhost:8080/ -k
```

### Утечка учетных данных

В зависимости от используемого потока OAuth передает различные типы учетных данных в качестве параметров URL.

К учетным данным, подверженным утечке, относятся следующие токены:

- токен доступа (access token)
- токен обновления (refresh token)
- код авторизации (authorization code)
- параметры PKCE code challenge / code verifier

В силу принципов работы OAuth код авторизации `code`, а также параметры `code_challenge` и `code_verifier` могут передаваться в составе URL. Поток Implicit Flow передает токен авторизации в URL-адресе, если для параметра `response_mode` не установлено значение [`form_post`](https://openid.net/specs/oauth-v2-form-post-response-mode-1_0.html). Это может приводить к утечке запрошенного токена или кода в заголовке `Referer`, в файлах журналов и на прокси-серверах, поскольку эти параметры передаются либо в строке запроса (query), либо во фрагменте URL (fragment).

Риск утечки токенов при использовании Implicit Flow значительно выше, чем риск утечки `code` или любых параметров `code_*`, поскольку последние привязаны к конкретным клиентам и ими сложнее злоупотребить в случае компрометации.

Для проверки данного сценария используйте перехватывающий HTTP-прокси, такой как OWASP ZAP, и перехватывайте трафик OAuth:

- Выполните процесс авторизации по шагам и идентифицируйте любые учетные данные, присутствующие в URL.
- Если на страницах, задействованных в потоке OAuth, подключаются внешние ресурсы, проанализируйте исходящие к ним запросы. Учетные данные могут утекать в заголовке Referer.

После прохождения потока OAuth и взаимодействия с приложением в истории запросов перехватывающего HTTP-прокси сохранится ряд запросов. Выполните поиск HTTP-заголовка Referer (например, `Referer: https://idp.example.com/`), содержащего URL сервера авторизации и клиента, в истории запросов.

Анализ meta-тегов HTML (хотя данный тег [поддерживается не всеми браузерами](https://caniuse.com/mdn-html_elements_meta_name_referrer)) или заголовка [Referrer-Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy) поможет оценить вероятность утечки учетных данных через заголовок `Referer`.

## Рекомендации по устранению

- При внедрении OAuth всегда учитывайте используемую технологию и то, является ли приложение серверным (способным скрывать секреты) или клиентским (неспособным хранить секреты в тайне).
- Практически во всех случаях используйте поток Authorization Code с расширением PKCE. Единственным исключением могут быть сценарии межмашинного взаимодействия (machine-to-machine).
- Для передачи секретов используйте POST-параметры или значения HTTP-заголовков.
- Если другие возможности отсутствуют (например, в унаследованных приложениях, которые невозможно модернизировать), внедрите дополнительные заголовки безопасности, такие как `Referrer-Policy`.
