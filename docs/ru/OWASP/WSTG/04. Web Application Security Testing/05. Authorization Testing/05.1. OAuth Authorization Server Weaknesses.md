# Уязвимости сервера авторизации OAuth

## Резюме

OAuth хранит идентификаторы пользователей и соответствующие им права доступа на сервере авторизации (Authorization Server, AS). Сервер авторизации играет ключевую роль в процессе выполнения потока OAuth, предоставляя клиентам доступ к ресурсам. Для безопасного выполнения этой задачи он обязан надлежащим образом валидировать все параметры, являющиеся частью потока OAuth.

Недостаточная валидация параметров может привести к захвату учетной записи (Account Takeover), несанкционированному доступу к ресурсам и повышению привилегий.

## Цели тестирования

- Выявить недостатки и уязвимости в сервере авторизации.

## Методика тестирования

При тестировании сервера авторизации на наличие уязвимостей преследуются следующие цели:

1. Извлечь учетные данные или токены, используемые для авторизации.
2. Предоставить себе доступ к произвольным ресурсам с помощью принудительного перехода (forced browsing).
3. Обойти механизмы авторизации.

### Недостаточная валидация URI перенаправления

Если параметр `redirect_uri` не валидируется должным образом, атакующий может сформировать ссылку с URL-адресом, указывающим на контролируемый им сервер. Это позволяет заставить сервер авторизации отправить код авторизации на сервер злоумышленника. В следующем примере в качестве поддельного `redirect_uri` используется `client.evil.com`:

```text
https://as.example.com/authorize?client_id=example-client&redirect_uri=http%3A%2F%client.evil.com%2F&state=example&response_mode=fragment&response_type=code&scope=openid&nonce=example
```

Если пользователь перейдет по этой ссылке в браузере (user agent), сервер авторизации выполнит перенаправление на вредоносный URL.

Злоумышленник может перехватить значение `code`, переданное в поддельном URL, и затем отправить его на токен-эндпоинт сервера авторизации.

Следующий запрос иллюстрирует запрос на авторизацию, передающий `redirect_uri` на сервер авторизации. Клиент `client.example.com` отправляет запрос авторизации на сервер `as.example.com` с URL-закодированным URI перенаправления `http%3A%2F%2Fclient.example.com%2F`:

```http
GET /authorize
    ?redirect_uri=http%3A%2F%2Fclient.example.com%2F
    &client_id=example-client
    &errorPath=%2Ferror
    &scope=openid%20profile%20email
    &response_type=code
    &response_mode=query
    &state=example
    &nonce=example
    &code_challenge=example
    &code_challenge_method=S256 HTTP/1.1
Host: as.example.com
```

Сервер авторизации отвечает перенаправлением, содержащим код авторизации. Этот код можно обменять на токен доступа при запросе токена. Как показано ниже, URL в заголовке `Location` совпадает с URI, переданным ранее в параметре `redirect_uri`:

```http
HTTP/1.1 302 Found
Date: Mon, 18 Oct 2021 20:46:44 GMT
Content-Type: text/html; charset=utf-8
Content-Length: 340
Location: https://client.example.com/?code=example&state=example
```

Для проверки сервера авторизации на уязвимость к недостаточной валидации redirect URI перехватите трафик с помощью HTTP-прокси, например OWASP ZAP:

1. Запустите поток OAuth и приостановите его на этапе запроса авторизации.
2. Измените значение параметра `redirect_uri` и проанализируйте ответ.
3. Исследуйте ответ и проверьте, был ли произвольный параметр `redirect_uri` принят сервером авторизации.

Если сервер авторизации перенаправляет браузер пользователя на указанный вами `redirect_uri`, значит, AS не валидирует этот параметр должным образом.

Дополнительно обратитесь к разделу `Common Filter Bypass` в руководстве [Server-Side Request Forgery](../07.%20Injection%20Testing/19.%20Server-Side%20Request%20Forgery.md) для изучения распространенных способов обхода валидации redirect URI.

### Инъекция кода авторизации

В процессе обмена кодами в потоке Authorization Code сервер авторизации выдает код клиенту, после чего клиент отправляет его на токен-эндпоинт для получения токена авторизации и токена обновления.

Выполните следующие тесты против сервера авторизации:

1. Отправьте валидный код, выданный для другого `client_id`.
2. Отправьте валидный код, выданный для другого владельца ресурса (resource owner).
3. Отправьте валидный код, связанный с другим `redirect_uri`.
4. Отправьте один и тот же код повторно несколько раз (воспроизведение кода, code replay).

#### Публичные клиенты

Запрос, отправляемый на токен-эндпоинт, содержит код авторизации, который обменивается на токен. Перехватите этот запрос с помощью перехватывающего HTTP-прокси (например, ZAP) и отправьте его повторно с модифицированными значениями.

```http
POST /oauth/token HTTP/1.1
Host: as.example.com
[...]

{
    "errorPath":"/error",
    "client_id":"example-client",
    "code":"INJECT_CODE_HERE",
    "grant_type":"authorization_code",
    "redirect_uri":"https://client.example.com"
}
```

Если сервер авторизации возвращает `access_token`, инъекция кода прошла успешно.

#### Тестирование конфиденциальных клиентов

Поскольку поток OAuth для конфиденциальных клиентов дополнительно защищен секретом клиента (`client_secret`), отправить код авторизации напрямую на токен-эндпоинт невозможно. Вместо этого внедрите код авторизации в клиент. Этот внедренный код затем будет отправлен в запросе токена самим конфиденциальным клиентом вместе с его клиентским секретом.

Сначала перехватите код авторизации от сервера авторизации:

1. Запустите поток Authorization Code от имени пользователя Алисы. Приостановите процесс при получении кода от сервера авторизации.
2. Не отправляйте код клиенту, сохранив значение кода и соответствующий параметр `state`.

Затем выполните внедрение кода:

 1. Запустите поток Authorization Code от имени пользователя Мэллори и внедрите в процесс ранее полученные значения кода и `state` пользователя Алисы.
 2. В случае успешной атаки клиент получит `authorization_token`, предоставляющий доступ к ресурсам Алисы.

```http
GET /callback?code=INJECT_CODE_HERE&state=example HTTP/1.1
Host: client.example.com
[...]

```

### Атака понижения уровня защиты PKCE

При определенных обстоятельствах расширение PKCE может быть удалено из потока кода авторизации. Это может сделать публичные клиенты уязвимыми перед атаками, которые должно было предотвращать расширение PKCE.

Это происходит в следующих случаях:

- Сервер авторизации не поддерживает PKCE.
- Сервер авторизации не выполняет должной валидации PKCE.

Оба сценария можно протестировать с помощью перехватывающего HTTP-прокси, такого как ZAP. Проведите следующие тесты:

1. Отправьте запрос авторизации без параметров `code_challenge=sha256(xyz)` и `code_challenge_method`.
2. Отправьте запрос авторизации с пустым значением параметра `code_challenge=sha256(xyz)`.
3. Отправьте запрос авторизации с поддельным значением параметра `code_challenge=sha256(xyz)`.

В приведенном ниже примере выделены параметры, подлежащие модификации:

```http
GET /authorize
    ?redirect_uri=http%3A%2F%client.example.com
    &client_id=example-client
    &errorPath=%2Ferror
    &scope=openid%20profile%20email
    &response_type=code
    &response_mode=web_message
    &state=example-state
    &nonce=example-nonce
    &code_challenge=MODIFY_OR_OMIT_THIS
    &code_challenge_method=MODIFY_OR_OMIT_THIS
    &prompt=none HTTP/1.1
Host: as.example.com
[...]

```

Сервер авторизации должен проверять значение `code_verifier` при обмене токенов. Для тестирования:

1. Отправьте запрос токена без параметра `code_verifier`.
2. Отправьте запрос токена с пустым параметром `code_verifier`.
3. Отправьте запрос токена с валидным значением `code_verifier`, относящимся к другому коду авторизации.

```http
POST /oauth/token HTTP/1.1
Host: as.example.com
[...]

{
"client_id":"example-client",
"code_verifier":"MODIFY_OR_OMIT_THIS",
"code":"example",
"grant_type":"authorization_code",
"redirect_uri":"https://client.example.com"
}
```

### Подделка межсайтовых запросов (CSRF) на странице согласия

Атаки класса CSRF подробно описаны в руководстве [CSRF](../06.%20Session%20Management%20Testing/05.%20Cross%20Site%20Request%20Forgery.md). Протокол OAuth также может подвергаться атакам CSRF.

Для предотвращения CSRF-атак в OAuth используется параметр `state` в роли anti-CSRF токена.

Защиту от CSRF могут обеспечивать и другие механизмы: поток PKCE снижает риск CSRF, а значение `nonce` также может выступать в качестве anti-CSRF токена.

Протестируйте каждый запрос, содержащий параметры защиты от CSRF в OAuth, согласно тестам, описанным в разделе [CSRF](../06.%20Session%20Management%20Testing/05.%20Cross%20Site%20Request%20Forgery.md).

Страница согласия (consent page) отображается пользователю для подтверждения его согласия на доступ клиента к ресурсам от его имени. Атака на страницу согласия методом CSRF может позволить произвольному клиенту получить доступ к ресурсам от имени жертвы. Этапы этого процесса:

1. Клиент генерирует параметр `state` и передает его вместе с запросом согласия.
2. Браузер (User Agent) отображает страницу согласия.
3. Владелец ресурса предоставляет доступ клиенту.
4. Подтверждение согласия отправляется на сервер авторизации вместе с одобренными областями доступа (scopes).

Используйте перехватывающий HTTP-прокси (например, ZAP), чтобы проверить, надлежащим ли образом валидируется параметр `state`:

```http
POST /u/consent?state=Tampered_State HTTP/1.1
Host: as.example.com
[...]

state=MODIFY_OR_OMIT_THIS
&audience=https%3A%2F%2Fas.example.com%2Fuserinfo
&scope%5B%5D=profile
&scope%5B%5D=email
&action=accept
```

### Кликджекинг

Методология атак кликджекинга описана в разделе [Clickjacking](../11.%20Client-side%20Testing/09.%20Clickjacking.md). Если страница согласия уязвима к кликджекингу, а злоумышленник располагает `client_id` (для публичных клиентов или клиентским секретом для конфиденциальных), он может сфальсифицировать согласие пользователя и получить доступ к запрашиваемому ресурсу через вредоносного клиента.

#### Методика тестирования

Для успешного проведения атаки злоумышленнику необходимо загрузить страницу авторизации во фрейм (`iframe`).

Следующий HTML-код можно использовать для загрузки страницы авторизации во фрейм:

```html
<html>
    <head>
        <title>Clickjack test page</title>
    </head>
    <body>
        <iframe src="https://as.example.com/auth/realms/example/login-actions/required-action?execution=OAUTH_GRANT&client_id=example-client" width="500" height="500"></iframe>
    </body>
</html>
```

Если страница успешно загружается во фрейме, ресурс уязвим к кликджекингу.

Подробное руководство по реализации данной атаки см. в разделе [Clickjacking](../11.%20Client-side%20Testing/09.%20Clickjacking.md).

### Время жизни токена

В OAuth существует два типа токенов: токен доступа (access token) и токен обновления (refresh token). Токен доступа должен иметь ограниченный срок действия. Это означает, что он должен быть короткоживущим: оптимальное время жизни зависит от специфики приложения и обычно составляет от 5 до 15 минут.

Токен обновления должен действовать дольше. При этом он должен быть одноразовым и заменяться на новый при каждом использовании (ротация refresh-токенов).

#### Проверка валидации времени жизни токена доступа (Access Token)

Если в качестве токена доступа используется JSON Web Token (JWT), срок его действия можно извлечь из декодированного JWT. Это описано в разделе [JSON Web Tokens](../06.%20Session%20Management%20Testing/10.%20JSON%20Web%20Tokens.md). Сервер авторизации может некорректно проверять срок жизни JWT.

Для проверки времени жизни токена доступа используйте перехватывающий HTTP-прокси, например ZAP. Перехватите запрос к эндпоинту, содержащий токен доступа. Направьте этот запрос в модуль повторной отправки (Repeater) и выждите установленное контрольное время. Срок действия access-токена должен составлять от 5 до 15 минут в зависимости от чувствительности ресурсов.

Такие запросы могут выглядеть следующим образом (токен также может передаваться другими способами, например в cookie):

```http
GET /userinfo HTTP/1.1
Host: as.example.com
[...]
Authorization: Bearer eyJhbGciOiJkaXIiL[...]

```

Проверьте валидацию времени жизни, отправляя запрос через различные интервалы времени, например через 5 минут, 10 минут и 30 минут.

Этот процесс можно оптимизировать путем автоматизации шагов и логирования ответов сервера. Получение ответа со статусом HTTP 403 (вместо HTTP 200) указывает на то, что токен доступа более недействителен.

#### Проверка валидации времени жизни токена обновления (Refresh Token)

Токены обновления имеют больший срок действия, чем токены доступа. В силу длительного срока действия они должны становиться недействительными сразу после использования при обмене на новый токен доступа.

Токены обновления выдаются в том же ответе на запрос токена, в котором клиенту возвращается токен доступа.

Используйте перехватывающий HTTP-прокси (например, ZAP). Подготовьте тест следующим образом:

1. Получите валидный токен обновления.
2. Перехватите запрос, используемый для обмена токена обновления на новый access token.
3. Отправьте перехваченный запрос в Repeater.

В следующем примере токен обновления передается в теле POST-запроса:

```http
POST /token HTTP/1.1
Host: as.example.com
Cookie: [...]
[...]

grant_type=refresh_token
&refresh_token=eyJhbGciOiJIUz[...]
&client_id=example-client

```

Проведите следующие тесты:

1. Отправьте токен обновления и определите, возвращает ли сервер авторизации новый токен доступа.
2. Повторите эти шаги с тем же токеном обновления, чтобы оценить, сколько раз принимается один и тот же refresh token.

Если в качестве refresh token используется JWT, срок его действия можно прочитать из декодированного токена. Это описано в разделе [JSON Web Tokens](../06.%20Session%20Management%20Testing/10.%20JSON%20Web%20Tokens.md). Токен обновления может быть действителен длительное время, но обязательно должен содержать дату истечения срока действия (`exp`).

Дополнительный уровень безопасности обеспечивает механизм обнаружения кражи токенов (Token Theft Detection). Если токен обновления используется для обмена сверх своего срока действия (или после того, как он уже был однократно применен), сервер авторизации должен аннулировать всю цепочку выданных токенов обновления. Для проверки этого механизма:

1. Отправьте токен обновления и проверьте, выдает ли сервер авторизации токен доступа.
2. Повторяйте отправку с тем же токеном обновления до тех пор, пока он не будет отклонен.
3. Попробуйте применить свежий токен обновления, полученный из последнего успешного ответа сервера.

Если все refresh-токены, выданные данному клиенту для этого владельца ресурса, оказываются аннулированы, значит, на сервере авторизации реализован механизм обнаружения кражи токенов.

## Рекомендации по устранению

Большинство атак на сервер авторизации OAuth можно предотвратить с помощью строгой валидации наличия и содержимого параметров при обмене кодами авторизации и токенами.

Ограничьте срок жизни и допустимое число использований для таких учетных данных, как код авторизации и токен обновления. Это снижает вероятность успешных атак и ограничивает возможности злоумышленника в случае компрометации данных.

Корректная настройка средств защиты, таких как CORS, токены anti-CSRF и заголовки против кликджекинга, позволяет нейтрализовать угрозы или минимизировать их последствия.

- Всегда проверяйте обязательное присутствие всех параметров и валидируйте их значения.
- Используйте расширение PKCE для надлежащей защиты обмена кодами авторизации и токенами.
- Запретите возможность отката (fallback) для механизмов безопасности, таких как PKCE.
- Ограничивайте время жизни учетных данных и токенов.
- Используйте учетные данные только однократно там, где это применимо (например, код авторизации).
- Настройте доступные средства защиты, включая CORS, anti-CSRF токены и заголовки противодействия кликджекингу.
