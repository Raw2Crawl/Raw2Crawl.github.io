# Небезопасные прямые ссылки на объекты

| ID |
| --- |
| WSTG-ATHZ-04 |

## Резюме

Небезопасные прямые ссылки на объекты (Insecure Direct Object References, IDOR) возникают, когда приложение предоставляет прямой доступ к объектам на основе входных данных, переданных пользователем. В результате этой уязвимости злоумышленники могут обойти авторизацию и получить прямой доступ к ресурсам в системе, например к записям базы данных или файлам.
Небезопасные прямые ссылки на объекты позволяют злоумышленникам обходить авторизацию и напрямую обращаться к ресурсам путем изменения значения параметра, используемого для прямого указания на объект. Такими ресурсами могут быть записи базы данных, принадлежащие другим пользователям, файлы в системе и многое другое. Причиной является то, что приложение принимает входные данные пользователя и использует их для извлечения объекта без проведения достаточных проверок авторизации.

## Цели тестирования

- Выявить точки приложения, в которых используются прямые ссылки на объекты.
- Оценить механизмы контроля доступа и проверить их уязвимость к IDOR.

## Методика тестирования

Для тестирования этой уязвимости тестировщику сначала необходимо составить карту всех мест в приложении, где пользовательский ввод используется для прямого обращения к объектам. Например, места, где данные пользователя используются для доступа к строке базы данных, файлу, страницам приложения и т. д. Затем тестировщику следует изменить значение параметра, используемого для ссылки на объекты, и оценить возможность извлечения объектов, принадлежащих другим пользователям, или иного способа обхода авторизации.

Лучший способ тестирования прямых ссылок на объекты — использование как минимум двух (а зачастую и более) учетных записей пользователей для охвата различных объектов владения и функций. Например, два пользователя, каждый из которых имеет доступ к различным объектам (таким как информация о покупках, личные сообщения и т. д.), и (при необходимости) пользователи с разными привилегиями (например, администраторы), чтобы проверить наличие прямых ссылок на функциональность приложения. Наличие нескольких учетных записей экономит ценное время тестирования на подбор различных идентификаторов объектов, так как тестировщик может попытаться обратиться к объектам, заведомо принадлежащим второму пользователю.

Ниже приведено несколько типичных сценариев возникновения этой уязвимости и методы тестирования для каждого из них:

### Использование значения параметра напрямую для извлечения записи из базы данных

Пример запроса:

```text
https://foo.bar/somepage?invoice=12345
```

В данном случае значение параметра *invoice* используется в качестве индекса (первичного ключа) в таблице счетов в базе данных. Приложение берет значение этого параметра и подставляет его в запрос к базе данных. Затем приложение возвращает пользователю информацию о счете.

Поскольку значение *invoice* напрямую передается в запрос, изменив значение параметра, можно получить любой объект счета независимо от того, какому пользователю он принадлежит. Для тестирования этого случая тестировщику следует получить идентификатор счета, принадлежащего другому тестовому пользователю (убедившись, что по бизнес-логике приложения доступ к нему запрещен), а затем проверить возможность доступа к объекту без авторизации.

### Использование значения параметра напрямую для выполнения операции в системе

Пример запроса:

```text
https://foo.bar/changepassword?user=someuser
```

В данном случае значение параметра `user` используется для указания приложению, для какого именно пользователя следует изменить пароль. Во многих случаях этот шаг является частью мастера настройки (wizard) или многоэтапной операции. На первом шаге приложение получает запрос с указанием целевого пользователя для смены пароля, а на следующем шаге пользователь вводит новый пароль (без запроса текущего пароля).

Параметр `user` используется для прямой ссылки на объект пользователя, над которым будет выполнена операция смены пароля. Для проверки данного сценария тестировщику следует попытаться передать имя другого тестового пользователя (отличное от текущего авторизованного) и проверить возможность изменения пароля чужой учетной записи.

### Использование значения параметра напрямую для извлечения ресурса файловой системы

Пример запроса:

```text
https://foo.bar/showImage?img=img00011
```

В данном случае значение параметра `file` используется для указания приложению, какой именно файл намеревается получить пользователь. Указав имя или идентификатор другого файла (например, `file=image00012.jpg`), злоумышленник сможет получить объекты, принадлежащие другим пользователям.

Для тестирования этого сценария тестировщик должен получить ссылку на ресурс, к которому у текущего пользователя не должно быть доступа, и попытаться запросить его через параметр `file`. Примечание: данная уязвимость часто эксплуатируется в сочетании с уязвимостью обхода каталога (см. [Path Traversal](01.%20Directory%20Traversal%20File%20Include.md)).

### Использование значения параметра напрямую для доступа к функциональности приложения

Пример запроса:

```text
https://foo.bar/accessPage?menuitem=12
```

В данном случае значение параметра `menuitem` указывает приложению, к какому пункту меню (и, следовательно, к какой функциональности приложения) пытается обратиться пользователь. Предположим, что права пользователя ограничены, и ему доступны ссылки только на пункты меню 1, 2 и 3. Изменяя значение параметра `menuitem`, можно обойти авторизацию и получить доступ к дополнительным возможностям приложения. Для тестирования этого сценария тестировщик находит место, где функциональность определяется ссылкой на пункт меню, сопоставляет доступные для данного тестового пользователя значения пунктов меню и затем пробует обращаться к другим пунктам меню.

В приведенных выше примерах достаточно модификации одного параметра. Однако иногда ссылка на объект может быть распределена между несколькими параметрами, и методологию тестирования следует скорректировать соответствующим образом.
