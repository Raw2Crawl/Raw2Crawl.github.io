# Передача конфиденциальной информации по незашифрованным каналам

| ID |
| --- |
| WSTG-CRYP-03 |

## Резюме

Конфиденциальные данные должны быть защищены при передаче по сети. Если данные передаются по протоколу HTTPS или защищаются другим криптографическим методом, этот защитный механизм не должен иметь ограничений или уязвимостей, как описано в общей статье [Weak Transport Layer Security](01.%20Weak%20Transport%20Layer%20Security.md) и в других руководствах OWASP:

- [A04:2025 Cryptographic Failures](https://owasp.org/Top10/2025/A04_2025-Cryptographic_Failures/)
- [OWASP ASVS — Проверка V9](https://github.com/OWASP/ASVS/blob/master/4.0/en/0x17-V9-Communications.md)
- [Transport Layer Protection Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Protection_Cheat_Sheet.html)

Как общее правило: если данные требуют защиты при хранении (at rest), они обязательно должны защищаться и в процессе передачи по сети (in transit). Примерами чувствительных данных являются:

- Данные, используемые для аутентификации (например, логины и пароли, PIN-коды, идентификаторы сессий, токены, cookie и т. д.).
- Информация, защищаемая законами, нормативными актами или регламентами конкретной организации (например, номера банковских карт, медицинские записи, персональные данные и т. д.).

Если приложение передает конфиденциальную информацию по незашифрованным каналам (таким как обычный HTTP), это считается серьезным риском безопасности. Злоумышленники могут захватывать учетные записи пользователей путем [прослушивания сетевого трафика](https://owasp.org/www-community/attacks/Manipulator-in-the-middle_attack) (network sniffing). В качестве примеров можно привести базовую HTTP-аутентификацию (Basic Authentication), передающую учетные данные в открытом виде, формы входа, отправляющие пароли через HTTP, или открытую передачу любой другой информации, признанной чувствительной в соответствии с законодательством, политиками безопасности или бизнес-логикой приложения.

К персональным идентифицирующим данным (Personally Identifiable Information, PII) относятся:

- Номера социального страхования
- Номера банковских счетов
- Паспортные данные
- Сведения о состоянии здоровья
- Данные медицинского страхования
- Сведения об успеваемости и студенческие билеты
- Номера кредитных и дебетовых карт
- Данные водительских удостоверений и государственных удостоверений личности

## Цели тестирования

- Идентифицировать конфиденциальную информацию, передаваемую по различным сетевым каналам.
- Оценить уровень конфиденциальности и защищенности используемых каналов связи.

## Методика тестирования

Различные типы информации, требующие защиты, могут непреднамеренно передаваться приложением в открытом виде. Чтобы проверить, передаются ли эти сведения по незащищенному HTTP вместо HTTPS, перехватите трафик между клиентом и сервером веб-приложения при отправке учетных данных. Для каждого сообщения, содержащего конфиденциальные данные, убедитесь, что передача происходила исключительно по протоколу HTTPS. Дополнительную информацию о небезопасной передаче учетных данных см. в разделах [A04:2025 Cryptographic Failures](https://owasp.org/Top10/2025/A04_2025-Cryptographic_Failures/) и [Transport Layer Protection Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Protection_Cheat_Sheet.html).

### Базовая аутентификация (Basic Authentication) по HTTP

Типичный пример — использование базовой HTTP-аутентификации (Basic Authentication) поверх открытого протокола HTTP. При использовании Basic-аутентификации учетные данные пользователя лишь кодируются (Base64), а не шифруются, и передаются в HTTP-заголовках. В приведенном ниже примере тестировщик использует утилиту [curl](https://curl.se/) для проверки этой проблемы. Обратите внимание, что приложение запрашивает Basic-аутентификацию по HTTP вместо HTTPS:

```bash
$ curl -kis http://example.com/restricted/
HTTP/1.1 401 Authorization Required
Date: Fri, 01 Aug 2013 00:00:00 GMT
WWW-Authenticate: Basic realm="Restricted Area"
Accept-Ranges: bytes Vary:
Accept-Encoding Content-Length: 162
Content-Type: text/html

<html><head><title>401 Authorization Required</title></head>
<body bgcolor=white> <h1>401 Authorization Required</h1>  Invalid login credentials!  </body></html>
```

### Аутентификация на основе форм по протоколу HTTP

Другим классическим примером являются формы аутентификации, передающие учетные данные пользователя по незашифрованному протоколу HTTP. В приведенном ниже фрагменте видно использование префикса `http://` в атрибуте `action` HTML-формы. Эту проблему также можно легко зафиксировать путем анализа трафика через перехватывающий прокси-сервер.

```html
<form action="http://example.com/login">
    <label for="username">User:</label> <input type="text" id="username" name="username" value=""/><br />
    <label for="password">Password:</label> <input type="password" id="password" name="password" value=""/>
    <input type="submit" value="Login"/>
</form>
```

Если прямой переход по HTTP-эндпоинту невозможен в браузере (например, из-за включенного механизма HSTS или кэширования редиректов), выполните запрос к этому же эндпоинту с помощью [curl](https://curl.se/) и изучите полученный ответ. Корректно защищенный эндпоинт должен незамедлительно возвращать ответ 3XX, перенаправляющий на HTTPS-адрес:

```bash
$ curl -kis -o /dev/null -D - http://example.com/login
HTTP/1.1 301 Moved Permanently
Location: https://example.com/login
```

Если сервер возвращает код 200, отдает контент по HTTP или перенаправляет на другой HTTP-эндпоинт, конфиденциальные данные могут оказаться под угрозой раскрытия из-за незашифрованного транспортного соединения.

### Передача cookie с идентификатором сессии по HTTP

Cookie-файл идентификатора сессии должен передаваться исключительно по защищенным каналам связи. Если для cookie не установлен флаг [Secure](../06.%20Session%20Management%20Testing/02.%20Cookies%20Attributes.md), приложение будет передавать его в открытом виде при любом HTTP-запросе. Обратите внимание, что в примере ниже установка cookie производится без флага Secure, а весь процесс аутентификации выполняется по протоколу HTTP, а не HTTPS:

```http
https://secure.example.com/login

POST /login HTTP/1.1
Host: secure.example.com
[...]
Referer: https://secure.example.com/
Content-Type: application/x-www-form-urlencoded
Content-Length: 188

HTTP/1.1 302 Found
Server: Apache
Set-Cookie: JSESSIONID=BD99F321233AF69593EDF52B123B5BDA; expires=Fri, 01-Jan-2014 00:00:00 GMT; path=/; domain=example.com; httponly
[...]
```

```http
http://example.com/private

GET /private HTTP/1.1
Host: example.com
[...]
Referer: https://secure.example.com/login
Cookie: JSESSIONID=BD99F321233AF69593EDF52B123B5BDA;

HTTP/1.1 200 OK
[...]
```

### Сброс пароля, смена пароля и другие операции с учетной записью по HTTP

Если в веб-приложении предусмотрены функции изменения учетной записи или отправки учетных данных в сторонние сервисы, убедитесь, что все эти взаимодействия происходят строго по протоколу HTTPS. Проверяемые сценарии включают формы, которые:

- Позволяют пользователям восстанавливать забытый пароль или другие учетные данные.
- Позволяют редактировать текущие пароли и параметры аутентификации.
- Требуют от пользователя прохождения аутентификации у стороннего провайдера (например, обработка платежей).

### Проверка наличия паролей и конфиденциальной информации в исходном коде или журналах

Используйте следующие методы для поиска конфиденциальной информации:

Проверка наличия жестко закодированных паролей или ключей шифрования в исходном коде или файлах конфигурации:

`grep -r -E "Pass | password | pwd |user | guest| admin | encry | key | decrypt | sharekey " ./PathToSearch/`

Проверка логов или исходного кода на предмет содержания номеров телефонов, адресов электронной почты, идентификаторов или любых других персональных данных (PII). Скорректируйте регулярное выражение в зависимости от формата искомых PII:

`grep -r " {2\}[0-9]\{6\} "  ./PathToSearch/`

## Рекомендации по устранению

Используйте протокол HTTPS для всего веб-сайта целиком и принудительно перенаправляйте любые входящие HTTP-запросы на HTTPS.
