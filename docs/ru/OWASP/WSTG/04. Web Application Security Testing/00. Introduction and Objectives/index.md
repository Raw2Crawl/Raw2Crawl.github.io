# Введение и цели

В данном разделе описывается методология тестирования безопасности веб-приложений OWASP и объясняется, как выявлять признаки наличия уязвимостей в приложении, вызванных недостатками внедренных механизмов контроля безопасности.

## Что такое тестирование безопасности веб-приложений?

Тестирование безопасности — это метод оценки защищенности компьютерной системы или сети путем методичной валидации и проверки эффективности механизмов контроля безопасности приложений. Тестирование безопасности веб-приложений сфокусировано исключительно на оценке безопасности веб-приложения. Процесс включает активный анализ системы на предмет любых недостатков, технических изъянов или уязвимостей. Все обнаруженные проблемы безопасности представляются владельцу системы вместе с оценкой их потенциального воздействия, предложениями по нейтрализации рисков или готовым техническим решением.

## Что такое уязвимость?

Уязвимость — это изъян или слабое место в архитектуре, реализации, эксплуатации или администрировании системы, которое может быть использовано для нарушения целей безопасности системы.

## Что такое угроза?

Угроза — это любое обстоятельство или сущность (внешний злоумышленник, внутренний пользователь, системный сбой и т. д.), способное нанести ущерб активам приложения (ценным ресурсам, таким как данные в базе данных или файлы в файловой системе) путем эксплуатации уязвимости.

## Что такое тест?

Тест — это действие, направленное на демонстрацию того, что приложение соответствует требованиям безопасности заинтересованных сторон.

## Подход к написанию данного руководства

Подход OWASP основан на открытости и сотрудничестве:

- Открытость (Open): каждый эксперт по безопасности может внести свой вклад, опираясь на практический опыт. Все материалы проекта бесплатны.
- Совместная работа (Collaborative): перед написанием статей проводится совместное обсуждение, что позволяет авторам делиться идеями и формировать единое видение проекта. Это обеспечивает консенсус экспертов, широкий охват аудитории и высокий уровень вовлеченности профессионального сообщества.

Такой подход позволяет сформировать четко определенную методологию тестирования, которая является:

- Последовательной (Consistent)
- Воспроизводимой (Reproducible)
- Строгой (Rigorous)
- Находящейся под постоянным контролем качества (Under quality control)

Рассматриваемые проблемы подробно документируются и проверяются. Важно использовать различные методы для проверки всех известных уязвимостей и скрупулезно документировать любые действия по тестированию безопасности.

## Что представляет собой методология тестирования OWASP?

Тестирование безопасности никогда не станет точной наукой с раз и навсегда зафиксированным исчерпывающим перечнем проверок. По сути, тестирование безопасности — лишь одна из нескольких методик, применимых для оценки защищенности веб-приложений в конкретных условиях. Цель данного проекта — собрать воедино все доступные техники тестирования, детально разъяснить их и поддерживать руководство в актуальном состоянии. Методология тестирования веб-приложений OWASP базируется на подходе «черного ящика» (black-box testing). Тестировщик располагает минимальными сведениями об исследуемой системе либо не имеет их вовсе.

Модель тестирования состоит из следующих элементов:

- Тестировщик: специалист, непосредственно выполняющий тестовые проверки
- Инструменты и методология: ядро настоящего руководства по тестированию (Testing Guide)
- Приложение: исследуемый «черный ящик»

Тестирование разделяется на пассивное и активное:

### Пассивное тестирование

В процессе пассивного тестирования специалист изучает логику работы приложения и исследует его поведение в роли обычного конечного пользователя. Для сбора информации применяются специализированные утилиты. Например, перехватывающий HTTP(S)-прокси используется для наблюдения за всеми исходящими HTTP(S)-запросами и входящими ответами сервера. К концу данной фазы тестировщик должен составить общее представление обо всех точках доступа и функциональных возможностях системы (заголовки HTTP, передаваемые параметры, файлы cookie, интерфейсы API, используемые технологические паттерны и т. д.). В разделе [Information Gathering](../01.%20Information%20Gathering/index.md) подробно описывается методика проведения пассивного тестирования.

Например, тестировщик может обнаружить страницу со следующим адресом: `https://www.example.com/login/auth_form`

Это указывает на наличие формы аутентификации, в которой приложение запрашивает имя пользователя и пароль.

Следующие параметры представляют собой две точки доступа к приложению: `https://www.example.com/appx?a=1&b=1`

В данном случае приложение имеет две точки входа (параметры `a` и `b`). Все выявленные на этой фазе входные точки становятся непосредственными целями для последующего тестирования. Фиксация карты каталогов, дерева вызовов приложения и всех точек доступа чрезвычайно полезна при переходе к фазе активного тестирования.
