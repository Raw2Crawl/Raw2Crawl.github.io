# Перенаправление URL на стороне клиента

| ID |
| --- |
| WSTG-CLNT-04 |

## Резюме

В данном разделе описывается методика проверки перенаправления URL на стороне клиента (Client-side URL Redirection), также известного как открытое перенаправление (Open Redirection). Это дефект валидации входных данных, возникающий в тех случаях, когда приложение принимает контролируемый пользователем ввод, задающий ссылку на внешний URL, потенциально являющийся вредоносным. Подобный тип уязвимости может использоваться для проведения фишинговых атак (phishing) или перенаправления жертвы на страницу заражения вредоносным ПО.

Уязвимость возникает, когда приложение принимает недоверенный ввод, содержащий значение URL, и не выполняет его санитарную обработку. Это значение URL может принудительно перенаправить пользователя на стороннюю страницу — например, на вредоносный ресурс, контролируемый злоумышленником.

Данная уязвимость позволяет атакующему успешно организовать фишинговую атаку и похитить учетные данные пользователя. Поскольку исходное перенаправление инициируется легитимным приложением, фишинговая ссылка вызывает значительно больше доверия у жертвы.

Ниже приведен пример URL для фишинговой атаки:

```text
https://www.target.site?#redirect=www.fake-target.site
```

Жертва, перешедшая по данному адресу, будет автоматически перенаправлена на `fake-target.site`, где атакующий может развернуть поддельную страницу, внешне неотличимую от целевого ресурса, с целью перехвата учетных данных пользователя.

Открытое перенаправление также может применяться для формирования URL, обходящего механизмы контроля доступа приложения, направляя атакующего к привилегированным функциям, к которым в обычном режиме доступ запрещен.

## Цели тестирования

- Идентифицировать точки внедрения, обрабатывающие URL или пути.
- Оценить целевые расположения, на которые система может осуществлять перенаправление.

## Методика тестирования

При выполнении ручной проверки на наличие уязвимости данного типа тестировщики в первую очередь определяют, реализованы ли клиентские перенаправления в коде на стороне браузера. В качестве примера на JavaScript подобные перенаправления могут быть построены с использованием объекта `window.location`. Его можно использовать для направления браузера на другую страницу простым присваиванием строки. Это проиллюстрировано в следующем фрагменте:

```javascript
var redir = location.hash.substring(1);
if (redir) {
    window.location='https://'+decodeURIComponent(redir);
}
```

В данном примере скрипт не выполняет никакой валидации переменной `redir`, содержащей пользовательский ввод из строки запроса. Поскольку к данным не применяется кодирование, этот непроверенный ввод передается напрямую объекту `window.location`, создавая уязвимость перенаправления URL.

Это означает, что злоумышленник может перенаправить жертву на вредоносный ресурс, просто передав следующую строку запроса:

```text
https://www.victim.site/?#www.malicious.site
```

С незначительными изменениями приведенный выше фрагмент кода становится уязвим для внедрения кода JavaScript (JavaScript injection):

```javascript
var redir = location.hash.substring(1);
if (redir) {
    window.location=decodeURIComponent(redir);
}
```

Данную брешь можно проэксплуатировать передачей следующей строки запроса:

```text
https://www.victim.site/?#javascript:alert(document.cookie)
```

При тестировании на эту уязвимость учитывайте, что разные браузеры обрабатывают некоторые символы по-разному. Дополнительную информацию см. в разделе [DOM-based XSS](https://owasp.org/www-community/attacks/DOM_Based_XSS).
