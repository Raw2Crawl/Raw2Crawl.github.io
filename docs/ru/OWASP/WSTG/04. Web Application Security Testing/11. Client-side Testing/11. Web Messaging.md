# Обмен сообщениями в вебе (Web Messaging)

| ID |
| --- |
| WSTG-CLNT-11 |

## Резюме

Механизм веб-сообщений (Web Messaging), также известный как [обмен сообщениями между документами (Cross Document Messaging)](https://html.spec.whatwg.org/multipage/web-messaging.html#web-messaging), позволяет приложениям, функционирующим на разных доменах, взаимодействовать безопасным образом. До внедрения технологии Web Messaging взаимодействие между разными источниками (между фреймами iframe, вкладками и окнами) жестко ограничивалось правилом ограничения домена (Same-Origin Policy, SOP) и контролировалось браузером. Разработчики прибегали к различным обходным путям, большинство из которых были фундаментально небезопасными.

Данное ограничение внутри браузера реализовано для предотвращения чтения вредоносным веб-сайтом конфиденциальных данных из сторонних iframe, вкладок и окон; тем не менее существует ряд легитимных сценариев, в которых два доверенных веб-сайта должны обмениваться данными. Для решения этой задачи механизм Cross Document Messaging был включен в проект спецификации [WHATWG HTML5](https://html.spec.whatwg.org/multipage/) и реализован во всех основных современных браузерах. Он обеспечивает защищенное взаимодействие между несколькими источниками через iframes, вкладки и окна.

API сообщений предоставил [метод `postMessage()`](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage), с помощью которого текстовые сообщения могут передаваться между источниками. Метод принимает два основных параметра: само сообщение и целевой домен (target origin).

Использование маски `*` в качестве целевого домена несет в себе риски безопасности, которые подробно обсуждаются ниже. Для приема сообщений принимающий веб-сайт должен зарегистрировать обработчик событий, обладающий следующими атрибутами:

- `data`: содержимое входящего сообщения;
- `origin`: источник документа-отправителя;
- `source`: объект исходного окна, откуда было отправлено сообщение.

Ниже приведен пример использования API сообщений. Отправка сообщения:

```javascript
iframe1.contentWindow.postMessage("Hello world","https://www.example.com");
```

Прием сообщения:

```javascript
window.addEventListener("message", handler, true);
function handler(event) {
    if(event.origin === 'chat.example.com') {
        /* обработка сообщения (event.data) */
    } else {
        /* игнорирование сообщений от недоверенных доменов */
    }
}
```

### Безопасность источника (Origin)

Источник (origin) формируется из схемы (протокола), имени хоста и порта. Он однозначно идентифицирует домен, отправляющий или принимающий сообщение, и не включает в себя путь или фрагмент URL. Например, `https://example.com` считается источником, отличным от `http://example.com`, поскольку схема первого — `https`, а второго — `http`. Это правило также распространяется на веб-серверы, запущенные в одном домене, но слушающие разные порты.

## Цели тестирования

- Оценить безопасность проверки источника сообщений.
- Проверить использование безопасных методов и обязательную валидацию входящих данных.

## Методика тестирования

### Анализ безопасности источника (Origin)

Тестировщики должны проверить, выполняет ли код приложения фильтрацию и обработку сообщений исключительно от доверенных доменов. В коде домена-отправителя необходимо также убедиться, что принимающий домен указан явно и символ `*` не используется в качестве второго аргумента `postMessage()`. Пренебрежение этим правилом способно повлечь за собой угрозы безопасности: в случае перенаправления или смены источника иными средствами сайт отправит данные на неизвестные хосты, что приведет к утечке конфиденциальной информации на вредоносные серверы.

Если веб-сайт не внедряет механизмы контроля для ограничения доменов или источников, которым разрешено отправлять ему сообщения, это создает прямой риск безопасности. Тестировщикам следует исследовать код на наличие слушателей событий сообщений (`message`) и проанализировать функцию обратного вызова из метода `addEventListener`. Домены отправителей обязаны валидироваться строго до начала каких-либо манипуляций с данными.

### Анализ валидации входных данных

Хотя теоретически веб-сайт принимает сообщения исключительно от доверенных доменов, полученные данные все равно необходимо рассматривать как внешние недоверенные данные и обрабатывать с применением соответствующих мер безопасности. Тестировщикам следует проанализировать исходный код на наличие небезопасных методов — в частности, мест передачи данных в функцию `eval()` или записи в DOM через свойство `innerHTML`, что способно приводить к уязвимостям DOM-based XSS.

### Статический анализ кода

Код на JavaScript необходимо проанализировать, чтобы понять архитектуру реализации Web Messaging. В частности, тестировщиков должно интересовать то, как сайт ограничивает сообщения от недоверенных доменов и как данные обрабатываются даже в случае доверенных источников.

В следующем примере требуется предоставить доступ для всех поддоменов (www, chat, forums, ...) в пределах домена owasp.org. Код пытается принимать сообщения от любого домена, содержащего подстроку `.owasp.org`:

```javascript
window.addEventListener("message", callback, true);

function callback(e) {
    if(e.origin.indexOf(".owasp.org")!=-1) {
        /* обработка сообщения (e.data) */
    }
}
```

Замысел разработчика состоял в том, чтобы разрешить поддомены:

- `www.owasp.org`
- `chat.owasp.org`
- `forums.owasp.org`

К сожалению, такая реализация привносит уязвимость. Атакующий может легко обойти подобный фильтр, поскольку домен вроде `www.owasp.org.attacker.com` успешно пройдет проверку совпадения подстроки.

Ниже приведен пример кода с полным отсутствием проверки источника. Это крайне небезопасно, так как скрипт принимает ввод от абсолютно любого домена:

```javascript
window.addEventListener("message", callback, true);

function callback(e) {
        /* обработка сообщения (e.data) */
}
```

Ниже представлен пример с уязвимостью валидации входных данных, способной привести к XSS-атаке:

```javascript
window.addEventListener("message", callback, true);

function callback(e) {
        if(e.origin === "trusted.domain.com") {
            element.innerHTML= e.data;
        }
}
```

Более безопасным подходом является использование свойства `innerText` вместо `innerHTML`.
