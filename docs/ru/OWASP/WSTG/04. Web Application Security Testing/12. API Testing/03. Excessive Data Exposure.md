# Чрезмерное раскрытие данных

| ID |
| --- |
| WSTG-APIT-03 |

## Резюме

Избыточное раскрытие данных (Excessive Data Exposure) происходит, когда API возвращает в своих ответах больше информации, чем требуется клиенту для отображения или функционирования. Обычно это случается, когда разработчики реализуют эндпоинты API путем прямой сериализации внутренних объектов бэкенда (таких как модели баз данных или внутренние структуры данных) в ответы API, полагаясь на то, что клиентский код самостоятельно отфильтрует чувствительные поля перед отображением пользователю.

Проблема заключается в том, что ответы API напрямую доступны любому, кто может отправлять запросы, независимо от того, что именно пользовательский интерфейс решает отобразить на экране. Атакующий, анализирующий необработанный трафик API, может увидеть все возвращаемые поля, включая те, которые UI намеренно скрывает. Это может привести к раскрытию паролей, токенов аутентификации, внутренних идентификаторов, персональных идентифицируемых данных (Personally Identifiable Information, PII), финансовых данных, сведений об инфраструктуре или внутренней бизнес-логики.

Данная уязвимость сопоставляется с [OWASP API Security Top 10 API3:2023 Broken Object Property Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/) (нарушение авторизации на уровне свойств объектов).

## Цели тестирования

- Выявить ответы API, содержащие больше данных, чем отображает или требует клиентское приложение.
- Обнаружить конфиденциальные поля, возвращаемые в ответах API, такие как хеши паролей, токены аутентификации, внутренние ID объектов, PII или сведения об инфраструктуре.
- Определить, полагается ли API на клиентскую фильтрацию вместо серверной выборки полей для контроля раскрытия данных.

## Методика тестирования

### Сравнение ответов API с отображаемыми данными

Наиболее прямой тест — сравнить то, что отображает пользовательский интерфейс, с тем, что фактически возвращает API.

1. Откройте приложение в браузере и перейдите на страницу, отображающую данные пользователя или объекта (например, страницу профиля, сводку заказа или дашборд).
2. Откройте инструменты разработчика браузера (вкладку Network) или настройте перехватывающий прокси, такой как Burp Suite или ZAP.
3. Определите API-запросы, заполняющие контент страницы.
4. Сравните поля, отображаемые в интерфейсе, с полным набором полей в ответе API.

Например, страница профиля пользователя может отображать только имя и адрес электронной почты, однако ответ нижележащего API может содержать:

```json
{
  "id": 12045,
  "name": "Alice Johnson",
  "email": "alice@example.com",
  "password_hash": "$2b$12$LJ3m4ys5qGn...",
  "role": "admin",
  "internal_account_id": "ACC-2024-88421",
  "ssn": "123-45-6789",
  "api_key": "REDACTED_EXAMPLE_KEY_12345",
  "created_by": "system_migration_v2",
  "last_login_ip": "10.0.3.47"
}
```

В данном случае API возвращает хеши паролей, номера социального страхования, API-ключи, внутренние идентификаторы и внутренние IP-адреса, которые интерфейс никогда не отображает.

### Анализ ответов различных конечных точек API

Не ограничивайте тестирование одним эндпоинтом. Проверяйте ответы различных типов конечных точек:

- **Эндпоинты пользователей и аккаунтов:** `GET /api/users/{id}`, `GET /api/me`, `GET /api/account`
- **Эндпоинты списков и поиска:** `GET /api/users`, `GET /api/orders?status=completed` (эндпоинты списков часто возвращают один и тот же полный объект для каждого элемента в списке, усиливая масштаб утечки)
- **Эндпоинты связанных объектов:** `GET /api/orders/{id}` может внедрять полные объекты пользователей, детали платежей или адреса доставки в ответ на запрос заказа
- **Ответы с ошибками:** неудачные запросы могут возвращать подробные сообщения об ошибках, содержащие трассировки стека (stack traces), внутренние пути к файлам, детали SQL-запросов к БД или параметры конфигурации
- **Административные или внутренние эндпоинты:** проверьте, доступны ли эндпоинты, предназначенные для внутреннего использования, извне, и возвращают ли они данные повышенного уровня доступа

### Тестирование с различными уровнями привилегий пользователей

Один и тот же эндпоинт может возвращать различный объем данных в зависимости от роли запрашивающего пользователя. Проверьте:

- Получает ли низкопривилегированный пользователь те же поля, что и администратор, при запросе того же ресурса.
- Возвращает ли неаутентифицированный запрос данные, требующие аутентификации.
- Возвращает ли запрос данных другого пользователя (IDOR) такой же подробный объект, как и запрос собственных данных.

Например, `GET /api/users/124` может возвращать полный объект, включая конфиденциальные поля, независимо от того, отправлен ли запрос пользователем 124, другим пользователем или неаутентифицированным клиентом.

### Анализ вложенных и встроенных объектов

Современные API часто встраивают связанные объекты в ответы. Один вызов API может возвращать глубоко вложенные структуры, раскрывающие данные из нескольких серверных систем.

Пример: эндпоинт заказа, возвращающий встроенный объект клиента, объект платежа и объект доставки:

```json
{
  "order_id": "ORD-9923",
  "items": [...],
  "customer": {
    "id": 5001,
    "name": "Bob Smith",
    "email": "bob@example.com",
    "phone": "+1-555-0199",
    "date_of_birth": "1985-03-14",
    "loyalty_tier": "gold"
  },
  "payment": {
    "method": "card",
    "card_last_four": "4242",
    "card_brand": "Visa",
    "card_fingerprint": "fp_abc123xyz",
    "billing_address": {...}
  },
  "internal_notes": "Customer flagged for manual review - suspected fraud"
}
```

Каждый вложенный объект необходимо проверять на наличие полей, выходящих за рамки потребностей клиентского приложения.

### Тестирование на массовое присваивание (Mass Assignment)

Для эндпоинтов, принимающих тело запроса в формате JSON или XML, проведите тестирование на уязвимости массового присвоения (mass assignment) путем добавления дополнительных полей в тело запроса помимо тех, что отображаются в интерфейсе приложения. Такие поля, как идентификаторы ролей, флаги привилегий или атрибуты статуса аккаунта, представляют собой первоочередные цели.

### Проверка наличия конфиденциальных данных в ответах GraphQL

API на базе GraphQL представляют специфическую форму данной проблемы. Хотя GraphQL позволяет клиентам выбирать, какие именно поля запрашивать, схема может содержать конфиденциальные поля, которые не запрашиваются стандартными запросами интерфейса, но которые атакующий может добавить в кастомный запрос.

1. Если интроспекция включена, получите схему и проанализируйте доступные поля каждого типа (см. [GraphQL](99.%20GraphQL.md)):

    ```graphql
    {
      __type(name: "User") {
        fields {
          name
          type { name }
        }
      }
    }
    ```

2. Ищите поля, такие как `passwordHash`, `apiKey`, `ssn`, `internalId`, `role` или `isAdmin`, которые доступны для запроса, но не используются фронтендом.
3. Попробуйте запросить эти поля напрямую:

    ```graphql
    {
      user(id: "123") {
        name
        email
        passwordHash
        apiKey
        role
      }
    }
    ```

### Анализ карт кода (Source Maps) JavaScript и клиентских сборок

Фронтенд-бандлы JavaScript и карты исходного кода (source maps) могут непреднамеренно раскрывать ожидаемую структуру ответа API, включая поля, которые интерфейс намеренно скрывает. Если файлы source maps общедоступны (например, по адресу `main.js.map`), они могут раскрывать:

- Полный список полей, которые фронтенд ожидает получить от API
- Внутренние пути к эндпоинтам API
- Логику процессов аутентификации и авторизации
- Захардкоженные API-ключи, токены или параметры конфигурации

Проверьте доступность source maps:

```http
GET /static/js/main.js.map
GET /assets/app.js.map
```

Если карта исходного кода доступна и содержит секцию `sourcesContent`, исходный код может быть восстановлен и проанализирован для выявления ожидаемых структур ответов API и скрытых полей.

### Проверка ответов с ошибками и отладочного вывода

API могут раскрывать конфиденциальную информацию через сообщения об ошибках, особенно при работе в режиме разработки или отладки:

- **Трассировки стека (stack traces)**, раскрывающие внутренние пути к файлам, версии фреймворков и структуру кода
- **Сообщения об ошибках баз данных**, раскрывающие имена таблиц, колонок или синтаксис запросов
- **Подробные ошибки валидации**, перечисляющие все ожидаемые поля, включая недокументированные в публичном API
- **Отладочные заголовки**, такие как `X-Debug-Token`, `X-Powered-By` или кастомные заголовки, содержащие внутреннюю информацию

Инициируйте ответы с ошибками, отправляя некорректно сформированные входные данные, недействительные учетные данные аутентификации или запросы к несуществующим ресурсам, и исследуйте полный ответ, включая заголовки.

## Рекомендации по устранению

- **Внедрите фильтрацию ответов на стороне сервера.** Никогда не возвращайте необработанные объекты базы данных или полные сериализации моделей в ответах API. Явно определяйте схемы ответов, включающие только те поля, которые необходимы клиенту для каждого конкретного эндпоинта и контекста.
- **Используйте объекты передачи данных (Data Transfer Objects, DTO) или разрешающие списки сериализации (serialization allowlists).** Сопоставляйте внутренние объекты с узкоспециализированными объектами ответов, содержащими только разрешенные поля. Большинство веб-фреймворков предоставляют для этого механизмы (например, сериализаторы в Django REST Framework, JsonView в Spring или ActiveModel::Serializers в Rails).
- **Применяйте контроль доступа на уровне полей.** Некоторые поля (такие как адреса электронной почты или номера телефонов) могут быть допустимы для одного потребителя, но запрещены для другого. Реализуйте логику включения или исключения полей на основе роли запрашивающего пользователя и его связи с запрашиваемым ресурсом.
- **Избегайте раскрытия внутренних идентификаторов.** Используйте внешние идентификаторы (такие как UUID или непрозрачные токены) вместо последовательных внутренних ID базы данных, которые раскрывают количество записей и упрощают перебор.
- **Ограничивайте схемы GraphQL.** Полностью удаляйте конфиденциальные поля из схемы GraphQL, а не полагайтесь на проверки на уровне резолверов (resolvers). Если поле должно присутствовать в схеме для внутреннего использования, применяйте директивы авторизации для предотвращения несанкционированного доступа.
- **Отключайте карты исходного кода (source maps) в производственной среде.** Не развертывайте файлы `.map` на проде. Настройте конвейер сборки (build pipeline) так, чтобы исключить файлы `.map` из производственных артефактов.
- **Очищайте ответы об ошибках (Sanitize error responses).** Возвращайте обобщенные сообщения об ошибках в производственной среде. Логируйте подробную информацию об ошибках на стороне сервера, но не включайте трассировки стека, внутренние пути или детали запросов в ответы клиенту.

## Инструменты

- **Burp Suite:** используйте инструмент Comparer для сравнения отображаемого в интерфейсе контента с сырыми ответами API. Инструменты Repeater и Intruder могут использоваться для систематического тестирования эндпоинтов с различными параметрами и контекстами аутентификации.
- **ZAP (Zed Attack Proxy):** перехват и анализ ответов API, использование правил активного сканирования для выявления утечек информации и фаззинг для вызова подробных сообщений об ошибках.
- **Postman:** отправка запросов к API с различными токенами аутентификации и сравнение тел ответов для выявления различий в раскрытии данных в зависимости от роли.
- **Инструменты разработчика браузера:** вкладка Network обеспечивает мгновенную видимость ответов API без необходимости настройки прокси. Полезна для быстрого сопоставления данных, отрисованных в UI, и необработанного содержимого ответов.
- **jq:** консольный процессор JSON для извлечения и сравнения полей в ответах API: команда `curl -s https://api.example.com/users/me | jq 'keys'` выводит список всех возвращаемых полей.
