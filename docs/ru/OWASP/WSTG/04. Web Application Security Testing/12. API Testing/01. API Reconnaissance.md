## Резюме

Разведка (Reconnaissance) — важный этап любого проекта по тестированию на проникновение, включая пентест API. Разведка существенно повышает эффективность процесса тестирования за счет сбора информации об API и формирования глубокого понимания целевой системы. Эта фаза не только увеличивает вероятность обнаружения критических проблем безопасности, но и гарантирует всестороннюю оценку защищенности API.

В данном руководстве есть раздел [Сбор информации](../01.%20Information%20Gathering/index.md), применимый и при аудите API. Однако здесь есть ряд отличий. Как исследователи безопасности, мы часто концентрируемся на конкретных областях, а поиск применимых разделов по всему руководству может отнимать много времени. Чтобы предоставить исследователю единую точку входа для работы с API, данный раздел сосредоточен именно на аспектах, специфичных для API, и содержит ссылки на вспомогательные материалы в других частях руководства.

### Типы API

API могут быть публичными (public) или приватными (private).

#### Публичные API

Публичные API обычно описываются в опубликованных документах Swagger/OpenAPI. Получение доступа к такому документу крайне важно для понимания поверхности атаки (attack surface). Не менее важно найти устаревшие версии этого документа, которые могут указывать на выводящийся из эксплуатации (deprecated), но все еще функционирующий код, содержащий уязвимости безопасности.

Имейте в виду, что эта документация, какими бы благими намерениями ни руководствовались ее авторы, может содержать неточности и не полностью раскрывать функционал API.

Публичные API также могут документироваться в общедоступных библиотеках или каталогах API.

#### Закрытые API

Доступность приватных API зависит от их предполагаемого потребителя. API может быть приватным, но доступным только клиентам по подписке (партнерам — `partners`), либо доступным исключительно внутренним клиентам, таким как другие отделы той же компании. Обнаружение приватных API с использованием методов разведки также является критически важной задачей. Эти API можно выявить с помощью ряда методик, которые мы рассмотрим ниже.

## Цели тестирования

- Найти все эндпоинты API, поддерживаемые кодом бэкенд-сервера, как задокументированные, так и недокументированные.
- Найти все параметры для каждого эндпоинта, поддерживаемого бэкенд-сервером, как задокументированные, так и недокументированные.
- Обнаружить интересные данные, связанные с API, в HTML и JavaScript, передаваемых клиентам.

## Методика тестирования

### Поиск документации

Как в случае публичных, так и в случае приватных API документация полезна настолько, насколько высоки ее качество и точность. Документация публичных API обычно открыта для всех, тогда как документация приватных API предоставляется только целевым клиентам. Однако в обоих случаях поиск документации — случайно утекшей или опубликованной — будет крайне полезен в вашем исследовании.

Вне зависимости от видимости API целенаправленный поиск документации может помочь найти устаревшие, еще не опубликованные или случайно утекшие документы. Эта документация окажет неоценимую помощь в понимании того, какую поверхность атаки открывает API.

В проектах с ограниченными временными рамками запрашивайте у заказчика машиночитаемые артефакты API как можно раньше, чтобы инструменты тестирования могли импортировать или обрабатывать их напрямую. Запрашивайте определения OpenAPI, спецификации устаревшего формата Swagger 2.0 и актуальные коллекции запросов (например, [Postman](https://www.postman.com/) или [Bruno](https://www.usebruno.com/)). Для входящих в область оценки API, отличных от REST (например, GraphQL), запрашивайте схемы или экспортированные схемы, если интроспекция отключена. Также полезны файлы определений повторного воспроизведения запросов (например, [Hurl](https://hurl.dev/)). Если API устарел, в некоторых инфраструктурах могут присутствовать артефакты WSDL или WADL. Это особенно актуально для приватных, внутренних или недавно развернутых API, для которых публичная документация может отсутствовать.

### Файл Robots.txt

`robots.txt` — это текстовый файл, создаваемый владельцами сайтов для указания веб-краулерам (роботам поисковых систем) правил сканирования и индексации их сайта. Он является частью протокола исключения роботов (Robots Exclusion Protocol, REP), регулирующего взаимодействие ботов с сайтами.

Этот файл может дать дополнительные подсказки о структуре путей или эндпоинтах API.

Раздел [Сбор информации](../01.%20Information%20Gathering/index.md) ссылается на `robots.txt` в ряде тестов, включая WSTG-INFO-01, WSTG-INFO-03, WSTG-INFO-05 и WSTG-INFO-08.

### GitDorking

Если в приложении используется GitHub, GitLab или другие публичные репозитории на базе Git, мы также можем искать любые зацепки или конфиденциальный контент (техника `GitDorking`). Эта информация может включать пароли, ключи API, конфигурационные файлы и другие конфиденциальные данные, которые разработчики могут случайно или по невнимательности закоммитить в свои репозитории. Организации могут случайно выложить конфиденциальный код, примеры или тестовый код, раскрывающий детали реализации. Личные аккаунты сотрудников целевой компании на GitHub также могут стать источником случайной утечки полезной информации.

### Навигация и сканирование структуры приложения

Даже при наличии документации API ручное исследование приложения остается хорошей идеей. Документация может быть устаревшей, неточной или неполной.

Исследование приложения с помощью перехватывающего прокси, такого как ZAP или Burp Suite, фиксирует эндпоинты для последующего анализа. Кроме того, встроенный функционал автоматического сканирования (spidering / crawling) перехватывающих прокси помогает сформировать исчерпывающий список эндпоинтов. Среди найденных пауком URL ищите ссылки с очевидными схемами именования API-адресов. К ним относятся:

- `https://example.com/api/v1` (или v2 и т. д.)  
- `https://example.com/graphql`

Либо поддомены, используемые приложениями или от которых они зависят:

- `https://api.example.com/api/v1`

Пентестеру важно попытаться задействовать как можно больший функционал приложения. Это необходимо не только для составления исчерпывающего списка эндпоинтов, но и для предотвращения проблем, связанных с отложенной загрузкой (lazy loading) и разделением кода (code splitting). Кроме того, ваш проект по тестированию должен включать тестовые учетные записи с различными уровнями привилегий, чтобы браузер и веб-паук могли получить доступ и выявить эндпоинты для максимального спектра функций.

После завершения этапа информация об эндпоинтах, полученная в ходе исследования и паучинга приложения, может помочь пентестеру сформировать документацию API и коллекции запросов с использованием таких инструментов, как [Postman](https://www.postman.com/) и [Bruno](https://www.usebruno.com/). Инструменты воспроизведения запросов, такие как [Hurl](https://hurl.dev/), могут использовать эту информацию для автоматизации повторяемых тестовых сценариев. Некоторые клиенты, такие как Postman и Bruno, также поддерживают выполнение скриптов до и после запроса (pre-request и post-request), что помогает воспроизводить реалистичные сценарии при тестировании API с сохранением состояния (stateful).

### Анализ перехваченных запросов

При аудите REST API используйте перехватывающий прокси для сбора полных HTTP-запросов. Сервисы REST используют не только параметры URL, поэтому сбор полного тела запроса и заголовков имеет критическое значение.

Проанализируйте собранные запросы для выявления нестандартных или скрытых параметров:

- Определите HTTP-заголовки, влияющие на поведение приложения или выбор ресурсов.
- Проверьте, содержит ли сегмент URL повторяющийся шаблон в нескольких URL. Шаблоны, содержащие даты, числа или идентификаторы, могут указывать на параметр, встроенный в URL. Например, в URL `https://api.example.com/user/2026-10-03/profile` сегмент даты может представлять собой значение параметра.
- Выявите структурированные значения параметров в формате JSON, XML или других специализированных форматах.
- Исследуйте завершающий элемент URL. Если у него отсутствует расширение файла, он может быть параметром.
- Ищите сегменты URL с высокой вариативностью. Если один сегмент часто меняется на протяжении сотен запросов, он с большей вероятностью представляет собой значение параметра, чем статический компонент пути.
- Проверяйте предполагаемые переменные сегменты URL, устанавливая для них заведомо некорректные значения. Это относится как к промежуточным сегментам, выглядящим динамическими, так и к конечным сегментам без расширений файлов. Ответ `404` на уровне маршрутизации до обработки запроса приложением может указывать на статический сегмент пути. Одних лишь ответов `404`, сгенерированных приложением, недостаточно для проведения такого различия. Если запрос достигает логики приложения и возвращает ошибку «ресурс не найден» или ошибку валидации, сегмент может маршрутизироваться приложением и быть параметризованным. Рассматривайте это как эвристику и сопоставляйте источник ответа с наблюдаемым поведением маршрутизации.

### Google Dorking

Использование методов пассивной разведки, таких как Google Dorking с операторами `site` и `inurl`, позволяет адаптировать поиск под распространенные ключевые слова API, проиндексированные Google. Дополнительную информацию см. в разделе [Проведение разведки через поисковые системы для выявления утечек информации](../01.%20Information%20Gathering/01.%20Conduct%20Search%20Engine%20Reconnaissance%20for%20Information%20Leakage.md).

Вот несколько специализированных примеров для API:

`site:"mytargetsite.com" inurl:"/api"`

`inurl:apikey filetype:env`

К другим ключевым словам могут относиться `"v1"`, `"api"`, `"graphql"`.

Мы можем расширить Google Dorking на поддомены цели.

Словари (wordlists) здесь полезны для получения полного списка распространенных терминов, используемых в API.

### Взгляд в прошлое

В целом API меняются со временем. Однако устаревшие или предыдущие версии могут оставаться рабочими — либо намеренно, либо из-за ошибок конфигурации. Их также необходимо тестировать, так как высока вероятность, что они содержат уязвимости, исправленные в более новых версиях. Кроме того, изменения в API указывают на новые функции, которые могут быть менее надежными и потому представляют собой отличный объект для тестирования.

Для обнаружения старых версий мы можем использовать сервис `Wayback Machine`, помогающий находить прежние эндпоинты. Полезный инструмент [WayBackUrls](https://github.com/tomnomnom/waybackurls) от TomNomNom извлекает все URL-адреса для домена, известные веб-архиву Wayback Machine.

- [WayBackUrls](https://github.com/tomnomnom/waybackurls). Извлечение всех URL, известных Wayback Machine для домена.
- [waymore](https://github.com/xnl-h4ck3r/waymore). Поиск значительно большего объема данных в Wayback Machine, Common Crawl, Alien Vault OTX, URLScan и VirusTotal.
- [gau](https://github.com/lc/gau). Получение известных URL из AlienVault Open Threat Exchange, Wayback Machine и Common Crawl.

### Клиентское приложение

Превосходным источником информации об API и других данных служат HTML и JavaScript, отправляемые сервером клиенту. Иногда клиентское приложение раскрывает конфиденциальную информацию, включая конечные точки API и секреты. Раздел [Анализ содержимого веб-страниц на предмет утечки информации](../01.%20Information%20Gathering/05.%20Review%20Web%20Page%20Content%20for%20Information%20Leakage.md) содержит общую информацию по выявлению утечек в веб-контенте. Здесь мы подробнее остановимся на анализе содержимого JavaScript на предмет секретов, связанных с API.

Существует множество инструментов, помогающих извлекать конфиденциальную информацию из JavaScript, переданного в браузер. Эти инструменты обычно опираются на один из двух подходов: регулярные выражения (Regular Expressions) или абстрактные синтаксические деревья (Abstract Syntax Trees, AST). Кроме того, существуют универсальные инструменты, помогающие упорядочивать файлы JS и управлять ими для последующего анализа средствами AST и регулярных выражений.

Регулярные выражения проще: они ищут известные шаблоны в содержимом JS или HTML. Однако такой подход может пропускать контент, не описанный явно регулярным выражением. С учетом структуры некоторых JS-скриптов этот подход может упустить многое. AST, напротив, представляют собой древовидные структуры, отражающие синтаксис исходного кода. Каждый узел в дереве соответствует определенной части кода. Для JavaScript парсер AST разбивает код на базовые компоненты, позволяя инструментам и компиляторам легко понимать и анализировать структуру кода.

#### Общие инструменты

1. [Uproot](https://github.com/0xDexter0us/uproot-JS). Плагин для Burp Suite, сохраняющий все обнаруженные JS-файлы на диск. Это упрощает извлечение файлов для последующего анализа утилитами командной строки.
2. [OpenAPI Support](https://www.zaproxy.org/docs/desktop/addons/openapi-support/). Это дополнение для ZAP позволяет сканировать и импортировать определения OpenAPI (Swagger) версий 1.2, 2.0 и 3.0.
3. [OpenAPI Parser](https://github.com/aress31/openapi-parser). Плагин для Burp Suite, выполняющий парсинг документов OpenAPI в Burp Suite для автоматизации оценки безопасности API на базе OpenAPI.

#### Инструменты для работы с регулярными выражениями

1. [JSParser](https://github.com/nahamsec/JSParser). Скрипт на Python 2.7, использующий Tornado и JSBeautifier для парсинга относительных URL из файлов JavaScript.
2. [JSMiner](https://github.com/PortSwigger/js-miner). Плагин для Burp Suite, который пытается найти интересные данные внутри статических файлов (преимущественно JavaScript и JSON). Этот инструмент выполняет пассивное сканирование во время обхода приложения.
3. [JSpector](https://github.com/hisxo/JSpector). Плагин для Burp Suite, пассивно анализирующий файлы JavaScript и автоматически создающий уязвимости (issues) с URL, эндпоинтами и опасными методами, найденными в JS-файлах.
4. [Link Finder](https://github.com/GerbenJavado/LinkFinder). Python-скрипт для поиска эндпоинтов в файлах JavaScript.

#### Инструменты анализа AST

1. [JSLuice](https://github.com/BishopFox/jsluice). Консольная утилита, извлекающая URL, пути, секреты и другие интересные данные из исходного кода JavaScript.

### Другие инструменты разведки

1. [Attack Surface Detector](https://github.com/secdec/attack-surface-detector-burp). Плагин для Burp Suite, использующий статический анализ кода для идентификации эндпоинтов веб-приложений путем парсинга маршрутов и выявления параметров.
2. [Param Miner](https://github.com/portswigger/param-miner). Плагин для Burp Suite, выявляющий скрытые, несвязанные параметры.
3. [xnLinkFinder](https://github.com/xnl-h4ck3r/xnLinkFinder). Утилита на Python для обнаружения эндпоинтов, потенциальных параметров и генерации специализированного словаря под конкретную цель.
4. [GAP](https://github.com/xnl-h4ck3r/GAP-Burp-Extension). Расширение для Burp Suite для поиска потенциальных эндпоинтов, параметров и генерации кастомных словарей.

### Исходный код на стороне сервера

При наличии доступа к серверному исходному коду извлеките эндпоинты из него. [OWASP Noir](https://owasp.org/projects/noir) выполняет парсинг кода маршрутизации множества веб-фреймворков и выводит список всех эндпоинтов с их методами и параметрами, включая внутренние или устаревшие API, к которым ни один текущий клиент не обращается. Руководство по работе с этим инструментом см. в разделе [Определение точек входа приложения](../01.%20Information%20Gathering/06.%20Identify%20Application%20Entry%20Points.md#owasp-noir).

Для тестирования API экспортируйте результаты в формате OpenAPI. Следующая команда генерирует документ OpenAPI 3.0 для каждого эндпоинта в исходном коде [OWASP RailsGoat](https://github.com/OWASP/railsgoat):

```bash
noir scan railsgoat -f oas3 -o railsgoat-openapi.json
```

Сгенерированный файл начинается следующим образом:

```json
{
  "openapi": "3.0.3",
  "info": {
    "title": "Generated by Noir",
    "version": "1.0.0"
  },
  "servers": [
    {
      "url": "http://localhost"
    }
  ],
  "paths": {
    "/api/v1/mobile/1": {
      "get": {
        "responses": {
          "200": {
            "description": "Successful response",
            "content": {
              "application/json": {
                "schema": {
                  "type": "object"
                }
              }
            }
          }
        },
        "parameters": [
          {
            "name": "class",
            "in": "query",
            "required": false,
            "schema": {
              "type": "string"
            }
          }
        ],
        "x-noir-unmapped-path-params": [
          "id"
        ]
      }
    },
```

Импортируйте этот документ с помощью дополнения ZAP [OpenAPI Support](https://www.zaproxy.org/docs/desktop/addons/openapi-support/) или расширения Burp Suite OpenAPI Parser (см. [General Tools](#общие-инструменты)). Прокси добавит каждый эндпоинт в структуру сайта (site tree), что позволит запускать тесты из данного раздела против них. Noir заменяет каждый параметр пути тестовым значением, поэтому маршрут с заполнителем `:id` будет представлен как `/api/v1/mobile/1`, а исходные имена сохраняются в поле `x-noir-unmapped-path-params`. Используйте их при тестировании на [нарушение авторизации на уровне объектов в API (API Broken Object Level Authorization)](02.%20API%20Broken%20Object%20Level%20Authorization.md).

### Сканирование портов

Серверы API часто развертываются на нестандартных портах либо совместно с другими доступными сервисами (внутренними панелями администратора, листенерами gRPC или WebSocket, эндпоинтами отладки/метрик), которые можно пропустить при анализе одной лишь документации. [naabu](https://github.com/projectdiscovery/naabu) — это быстрый сканер портов, позволяющий быстро определить открытые порты на выявленных хостах и передать результаты напрямую в Nmap для обнаружения сервисов только на открытых портах:

```bash
naabu -p - -rate 2000 -c 50 -retries 2 -warm-up-time 1 -silent -host api.example.com -nmap-cli 'nmap -sV -oX scan.xml'
```

Предварительный запуск этого сканирования и последующее выполнение более медленного детального сканирования Nmap только по портам, определенным naabu как открытые, значительно сокращает общее время работы по сравнению с прямым полнодиапазонным сканированием Nmap. Дополнительные рекомендации по оптимизации сканирования API-серверов см. в статье [Improving Port Scans Against API Servers](https://danaepp.com/improving-port-scans-against-api-servers), включая объяснение того, почему сканирование CONNECT может работать эффективнее SYN-сканирования в условиях высокой параллельности, и как избежать пропуска сервисов из-за ограничения частоты запросов (rate limiting) или сетевых экранов.

Дополнительную информацию об обнаружении нестандартных портов см. также в разделе [Идентификация поверхности атаки](../01.%20Information%20Gathering/04.%20Attack%20Surface%20Identification.md).

### Активный фаззинг

Активный фаззинг (Active Fuzzing) предполагает использование специализированных инструментов со словарями и фильтрацией результатов запросов для обнаружения эндпоинтов методом перебора.

После выявления эндпоинтов и параметров используйте собранные значения запросов для оптимизации фаззинга на уровне значений:

- Сравнивайте наблюдаемые значения для определения вероятных диапазонов и форматов валидных и невалидных данных.
- Начинайте с пограничных невалидных значений (например, `0` для полей, которые всегда являются положительными целыми числами).
- Ищите числовые или логические последовательности, чтобы иметь возможность протестировать значения за пределами диапазона, выделенного аутентифицированному пользователю.

#### KiteRunner

[KiteRunner](https://github.com/assetnote/kiterunner) — инструмент, выполняющий традиционное обнаружение контента и перебор маршрутов/эндпоинтов в современных приложениях и API.

```console
kr [scan|brute] <input> [flags]
```

Для сканирования цели на наличие API с использованием словаря можно выполнить:

```console
kr scan https://example.com/api -w /usr/share/wordlists/apis/routes-large.kite --fail-status-codes 404,403
```

#### FFUF/DirBuster/GoBuster

Все три инструмента (FFUF, DirBuster и GoBuster) предназначены для обнаружения скрытых путей и файлов на веб-серверах с помощью методов перебора (brute-force). Все они используют настраиваемые словари для генерации запросов к целевому веб-серверу, пытаясь идентифицировать существующие каталоги и файлы. Все три поддерживают многопоточную или высокоэффективную обработку для ускорения процесса перебора.

К популярным словарям для API относятся: [SecLists](https://github.com/danielmiessler/SecLists) в разделе Discovery/Web-Content/API, [GraphQL Wordlist](https://github.com/Escape-Technologies/graphql-wordlist) и [Assetnote](https://wordlists.assetnote.io/).

Пример использования GoBuster:

`gobuster dir -u <target url> -w <wordlist file>`

#### Аутентифицированный фаззинг

При фаззинге аутентифицированных API воспроизводите тот же контекст аутентификации и обработки сессий, которого ожидает целевой сервис. Включайте специализированные токены, нестандартные заголовки авторизации, подписанные метаданные запросов или cookie по мере необходимости, иначе инструменты могут давать ложноотрицательные результаты (false negatives), вообще не достигая логики приложения. Если механизм использует динамические поля (например, временны́е метки, одноразовые числа — nonces или подписи, привязанные к телу запроса), пересчитывайте эти значения для каждого мутированного запроса, обычно с помощью pre-request скриптов или перехватчиков прокси/запросов.
