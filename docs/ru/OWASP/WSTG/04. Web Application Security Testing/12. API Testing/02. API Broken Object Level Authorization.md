# Нарушение авторизации на уровне объектов в API (BOLA)

| ID |
| --- |
| WSTG-APIT-02 |

## Резюме

Нарушение авторизации на уровне объектов (Broken Object Level Authorization, BOLA) возникает, когда API не выполняет должным образом проверки авторизации для каждого объекта, к которому обращается клиент. Злоумышленники могут манипулировать идентификаторами объектов в API-запросах (такими как ID, GUID или токены) для доступа или модификации ресурсов, на взаимодействие с которыми у них нет прав. Эта уязвимость имеет критическое значение в API из-за их прямого доступа к нижележащим объектам и широкой распространенности API в современных приложениях.

Эксплуатация BOLA может привести к несанкционированному доступу к конфиденциальным данным, выдаче себя за другого пользователя (user impersonation), горизонтальной эскалации привилегий (получению доступа к ресурсам других пользователей) и вертикальной эскалации привилегий (получению несанкционированного доступа с правами администратора).

## Цели тестирования

- Цель данного теста — определить, обеспечивает ли API надлежащие проверки **авторизации на уровне объектов (object-level authorization)**, гарантируя, что пользователи могут получать доступ и манипулировать только теми объектами, с которыми им разрешено взаимодействовать.

## Методика тестирования

### Анализ конечных точек API и ссылок на объекты

Изучите документацию API (например, спецификацию OpenAPI), трафик или используйте перехватывающий прокси (например, **Burp Suite**, **ZAP**) для выявления эндпоинтов, принимающих интересующие идентификаторы объектов. Они могут быть представлены в виде **ID**, **UUID** или других ссылок.

Примеры:

- `GET /api/users/{user_id}`
- `GET /api/orders/{order_id}`
- `POST /graphql`\
        `query: {user(id: "123") }`

Опираясь на знания, полученные на предыдущем этапе, изучите и соберите сторонние идентификаторы объектов (например, ID пользователей, ID заказов и т. д.), которые впоследствии могут быть использованы для манипулирования идентификаторами объектов.

Кроме того, сформируйте список потенциальных идентификаторов объектов для перебора (brute-force). Например, если API извлекает заказ на покупку для аутентифицированного пользователя, сгенерируйте различные ID заказов для тестирования.

### Манипуляция идентификаторами объектов в API-запросах

С целью определить, могут ли пользователи получать доступ или изменять объекты, которыми они не владеют, путем изменения идентификаторов объектов в API-запросе, замените идентификатор объекта (например, ID пользователя, ID заказа) в URL или теле запроса.

Пример: измените запрос вида `GET /api/users/123/profile` (где 123 — ID текущего пользователя) на `GET /api/users/124/profile` (где 124 — ID другого пользователя).

В зависимости от контекста приложения используйте две разные учетные записи для проведения тестов. Под учетной записью A создайте ресурсы, принадлежащие исключительно этой учетной записи (например, заказ на покупку), а под учетной записью B попытайтесь получить доступ к ресурсу учетной записи A (например, к этому заказу).

### Тестирование доступа на уровне объектов с различными HTTP-методами

Проверьте различные **HTTP-методы** на наличие уязвимостей BOLA:

- **GET**: попробуйте получить доступ к несанкционированным объектам путем манипулирования ID объекта в запросе.
- **POST/PUT/PATCH**: попытайтесь создать или изменить объекты, принадлежащие другим пользователям.
- **DELETE**: попробуйте удалить объект, принадлежащий другому пользователю.

### Тестирование BOLA в GraphQL API

Для **GraphQL API** отправьте запрос с измененным ID объекта в параметрах запроса (см. [GraphQL](99.%20GraphQL.md)):

Пример: `query { user(id: "124") { name, email } }`.

### Тестирование массового доступа к объектам

Проверьте, разрешает ли API несанкционированный **массовый доступ (bulk access)** к объектам. Это может происходить в эндпоинтах, возвращающих списки объектов.

Пример: `GET /api/users` возвращает данные всех пользователей вместо данных исключительно аутентифицированного пользователя.

## Признаки BOLA

- **Успешная эксплуатация**: если изменение ID объекта в запросе возвращает данные или позволяет выполнять действия над объектами, принадлежащими другим пользователям, API уязвим к BOLA.
- **Ответы с ошибками**: должным образом защищенные API, как правило, возвращают `403 Forbidden` или `401 Unauthorized` при попытке несанкционированного доступа к объекту. Ответ `200 OK` для объекта другого пользователя указывает на наличие BOLA.
- **Несогласованные ответы**: если некоторые эндпоинты применяют контроль авторизации, а другие — нет, это указывает на неполные или несогласованные механизмы безопасности.

## Рекомендации по устранению

- **Проверка владения объектом (Object Ownership Checks)**: убедитесь, что проверки авторизации на уровне объектов выполняются для каждого API-запроса. Всегда проверяйте, что пользователь, отправляющий запрос, авторизован для доступа к запрашиваемому объекту.
- **Управление доступом на основе ролей (Role-Based Access Control, RBAC)**: внедрите политики RBAC, определяющие, какие роли могут получать доступ к конкретным объектам или изменять их.
- **Принцип наименьших привилегий (Least Privilege Principle)**: применяйте принцип наименьших привилегий, чтобы пользователи могли получать доступ только к минимальному набору объектов, необходимому для их роли.
- **Использование UUID или непоследовательных ID**: отдавайте предпочтение непредсказуемым, непоследовательным идентификаторам объектов (например, **UUID** вместо простых целых чисел), чтобы затруднить атаки методом перебора и перечисления.

## Инструменты

- **ZAP**: автоматизированные сканеры или средства ручного проксирования помогают тестировать ссылки на объекты в запросах к API.
- **Burp Suite**: используйте инструменты **Repeater** или **Intruder** для манипулирования ID объектов и отправки множественных запросов для проверки контроля доступа.
- **Postman**: отправляйте запросы с измененными идентификаторами объектов и анализируйте ответы.
- **Инструменты фаззинга**: используйте фаззеры для перебора ID объектов и проверки несанкционированного доступа.
