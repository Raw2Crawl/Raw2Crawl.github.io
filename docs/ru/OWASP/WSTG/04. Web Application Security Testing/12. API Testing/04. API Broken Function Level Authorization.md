# Нарушение авторизации на уровне функций в API (BFLA)

| ID |
| --- |
| WSTG-APIT-04 |

## Резюме

Нарушение авторизации на уровне функций (Broken Function Level Authorization, BFLA) возникает, когда API ненадлежащим образом применяет ограничения к пользователям, обращающимся к определенным функциям или операциям. Эта уязвимость позволяет злоумышленникам вызывать конфиденциальные функции, на выполнение которых у них нет прав, такие как административные функции или другие высокопривилегированные операции.

BFLA часто возникает в ситуациях, когда API предоставляет множество эндпоинтов, обслуживающих различные роли пользователей (например, обычный пользователь против администратора), но не может ограничить доступ к этим функциям на основе уровня полномочий запрашивающего пользователя.

Эксплуатация BFLA может привести к серьезным последствиям, таким как повышение привилегий (privilege escalation), несанкционированный доступ к критическим функциям (например, административным операциям) или раскрытие функционала, который должен быть доступен исключительно определенным ролям пользователей.

## Цели тестирования

- Цель данного теста — определить, применяет ли API **контроль доступа на основе ролей или привилегий (role or privilege-based access control)** для ограничения доступа или выполнения пользователями функций, на использование которых они не авторизованы. Это гарантирует надлежащее соблюдение границ безопасности на уровне функций.

## Методика тестирования

### Определение конечных точек уровня функций

Изучите документацию API (например, спецификацию OpenAPI), трафик или используйте перехватывающий прокси (например, **Burp Suite**, **ZAP**) для выявления различных эндпоинтов функционального уровня. К ним могут относиться:

- **Административные функции** (например, `/api/admin/deleteUser`, `/api/admin/getAllUsers`)
- **Операции на основе ролей** (например, `/api/admin/promoteUser`, `/api/user/createOrder`)
- **Критические функции** для пользователей (например, `/api/user/withdrawFunds`)

Сосредоточьтесь на **различиях в функционале** между различными ролями пользователей (например, обычный пользователь, администратор, партнер, гость) и на эндпоинтах, предоставляющих более чувствительные возможности.

### Манипуляция управлением доступом на основе ролей

Попробуйте получить доступ или выполнить конфиденциальные операции через эндпоинты API, которые должны быть ограничены на основе ролей пользователей.

Войдите в систему под учетной записью с низким уровнем привилегий (например, гость или обычный пользователь) и отправьте запросы к эндпоинтам, выполняющим конфиденциальные действия, предназначенные для ролей с более высоким уровнем привилегий (например, администратора).

Пример: от имени **обычного пользователя** отправьте запрос к следующему административному эндпоинту для удаления произвольного пользователя:

```http
POST /api/admin/deleteUser
Authorization: Bearer <regular_user_token>

{ "userId": "12345" }
```

### Тестирование доступа на уровне функций с различными HTTP-методами

Проверьте различные **HTTP-методы** на наличие уязвимостей BFLA. Протестируйте каждый выявленный ресурс с альтернативными методами HTTP. Отправляйте запросы с использованием методов, отличных от задокументированных (таких как `PUT`, `DELETE` или `PATCH`), к эндпоинтам, которые обычно принимают только `GET` или `POST`. Фиксируйте любые различия в поведении ответов или результатах авторизации.

- **GET**: попытайтесь получить доступ к информации, доступной только высокопривилегированным пользователям, например администраторам.
    - Пример: `GET /api/admin/getAllUsers`
- **POST/PUT/PATCH**: попытайтесь изменить или создать конфиденциальные ресурсы, например изменить роли пользователей или системно важные данные.
    - Пример: `POST /api/admin/promoteUser { "userId": "12345", "newRole": "admin" }`
- **DELETE**: попытайтесь удалить конфиденциальные ресурсы, например учетные записи пользователей или данные.
    - Пример: `DELETE /api/admin/deleteUser/12345`

### Тестирование BFLA в GraphQL API

В **GraphQL API** проверьте, может ли пользователь вызывать функции, доступные только для ролей с более высоким уровнем привилегий, путем модификации GraphQL-запросов (мутаций).

Пример: `mutation { deleteUser(id: "12345") { success } }`.

## Признаки BFLA

- **Успешная эксплуатация**: если низкопривилегированный пользователь (например, обычный пользователь или гость) может выполнять функции высокого уровня привилегий или совершать действия, зарезервированные для других ролей (например, администратора).
- **Ответы с ошибками**: должным образом защищенные API, как правило, возвращают `403 Forbidden` или `401 Unauthorized` при вызове ограниченных функций вместо ответа `200 OK`.
- **Непоследовательное применение (Inconsistent enforcement)**: некоторые эндпоинты применяют ролевые ограничения, в то время как другие этого не делают, что указывает на несогласованность механизмов безопасности.

## Рекомендации по устранению

Для предотвращения уязвимостей BFLA реализуйте следующие меры защиты:

- **Принудительное применение управления доступом на основе ролей (Role-Based Access Control, RBAC)**: убедитесь, что API проверяет роли и разрешения пользователя на **уровне функций** перед предоставлением доступа к определенным операциям. Вызывать конфиденциальные функции должно быть разрешено только авторизованным ролям.
- **Принцип наименьших привилегий (Least Privilege Principle)**: применяйте принцип наименьших привилегий, гарантируя пользователям доступ только к минимальному набору функций, необходимому для их роли.
- **Централизованная логика контроля доступа**: используйте единую централизованную логику управления доступом для обеспечения согласованности на всех эндпоинтах API. Это позволяет избежать пробелов, при которых в отдельных функциях могут отсутствовать надлежащие проверки доступа.

## Инструменты

- **ZAP**: используйте автоматические сканеры и инструменты ручного проксирования для проверки API-запросов и ответов на наличие уязвимостей BFLA.
- **Burp Suite**: используйте **Repeater** или **Intruder** для отправки запросов от имени низкопривилегированных пользователей для проверки соблюдения ограничений на уровне функций.
- **Postman**: вручную отправляйте запросы к API под разными ролями пользователей и анализируйте ответы.
- **Инструменты фаззинга**: используйте фаззеры для тестирования различных параметров функций и методов с целью выявления потенциальных слабых мест авторизации.
