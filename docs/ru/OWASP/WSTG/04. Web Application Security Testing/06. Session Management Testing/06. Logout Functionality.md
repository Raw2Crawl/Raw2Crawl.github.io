# Функциональность выхода из системы

| ID |
| --- |
| WSTG-SESS-06 |

## Резюме

Завершение сессии (Session Termination) является важной частью жизненного цикла сессии. Сведение к минимуму времени жизни токенов сессий снижает вероятность успешной атаки с перехватом сессии (session hijacking). Это можно рассматривать как меру защиты от других атак, таких как межсайтовый скриптинг (Cross-Site Scripting, XSS) и подделка межсайтовых запросов (Cross-Site Request Forgery, CSRF). Известно, что подобные атаки опираются на наличие активной аутентифицированной сессии пользователя. Отсутствие безопасного механизма завершения сессии лишь увеличивает поверхность атаки для каждой из этих угроз.

Безопасное завершение сессии требует наличия как минимум следующих компонентов:

- Наличие элементов пользовательского интерфейса, позволяющих пользователю вручную выйти из системы (logout).
- Автоматическое завершение сессии после периода неактивности или по достижении максимального времени жизни сессии (таймаут бездействия — idle timeout и абсолютный таймаут — absolute timeout), рассматриваемые в разделе [Session Timeout](07.%20Session%20Timeout.md).
- Корректная инвалидация состояния сессии на стороне сервера (server-side session state).

Существует множество проблем, способных препятствовать эффективному завершению сессии. В идеальном безопасном веб-приложении пользователь должен иметь возможность завершить сессию в любое время через пользовательский интерфейс. Непонятные или неоднозначные функции выхода могут вызвать недоверие пользователей к подобной функциональности.

Другая распространенная ошибка при завершении сессии заключается в том, что токену сессии на стороне клиента присваивается новое значение, в то время как состояние на стороне сервера остается активным и может быть повторно использовано путем возврата сессионного cookie к предыдущему значению. Иногда пользователю лишь выводится подтверждающее сообщение без выполнения каких-либо дальнейших действий. Этого следует избегать.

Некоторые фреймворки веб-приложений полагаются исключительно на сессионный cookie для идентификации вошедшего в систему пользователя. Идентификатор пользователя внедряется в (зашифрованное) значение cookie. Сервер приложений не выполняет никакого отслеживания сессии на стороне сервера. При выходе сессионный cookie удаляется из браузера. Однако, поскольку приложение не ведет учет сессий, оно не знает, завершена сессия или нет. Таким образом, повторно используя сессионный cookie, можно получить доступ к аутентифицированной сессии. Известным примером этого является функционал Forms Authentication в ASP.NET.

Использование системы единого входа (Single Sign-On, SSO) вместо схемы аутентификации, специфичной для конкретного приложения, часто приводит к сосуществованию нескольких сессий, которые должны завершаться раздельно. Например, завершение сессии в конкретном приложении не завершает сессию в системе SSO. Возврат на портал SSO дает пользователю возможность снова войти в приложение, из которого он только что вышел. С другой стороны, функция выхода в системе SSO не обязательно приводит к завершению сессий в подключенных приложениях.

## Цели тестирования

- Оценить интерфейс выхода из системы.
- Убедиться, что сессия корректно завершается на стороне сервера после выхода.

## Методика тестирования

### Интерфейс выхода из системы

Проверьте оформление и видимость функционала выхода в пользовательском интерфейсе. Для этого просмотрите каждую страницу с точки зрения пользователя, намеревающегося выйти из веб-приложения.

> Существует ряд признаков качественного интерфейса выхода из системы:
>
> - Кнопка выхода присутствует на всех страницах веб-приложения.
> - Кнопка выхода должна быстро идентифицироваться пользователем, желающим выйти из веб-приложения.
> - После загрузки страницы кнопка выхода должна быть видна без прокрутки.
> - В идеале кнопка выхода располагается в области страницы, зафиксированной в области просмотра (viewport) браузера и не смещающейся при прокрутке содержимого.

### Завершение сессии на стороне сервера

Сначала сохраните значения cookie, используемых для идентификации сессии. Вызовите функцию выхода и понаблюдайте за поведением приложения, особенно в отношении сессионных cookie. Попробуйте перейти на страницу, доступную только в аутентифицированной сессии, например с помощью кнопки «Назад» в браузере. Если отображается кэшированная версия страницы, используйте кнопку перезагрузки для обновления страницы с сервера. Если функция выхода приводит к установке новых значений сессионных cookie, восстановите старое значение cookie и перезагрузите страницу из аутентифицированной области приложения. Если эти тесты не выявили уязвимостей на конкретной странице, проверьте как минимум еще несколько страниц приложения, считающихся критически важными с точки зрения безопасности, чтобы убедиться, что завершение сессии корректно обрабатывается этими компонентами приложения.

> Во время проведения тестов на исследуемых страницах не должны отображаться данные, предназначенные только для аутентифицированных пользователей. В идеале приложение должно перенаправлять пользователя в публичный раздел или на форму входа при попытке доступа к защищенным областям после завершения сессии. Хотя это не является строго обязательным требованием безопасности, присвоение сессионным cookie новых значений после выхода из системы считается общепринятой надежной практикой.

### Завершение сессии в средах единого входа (Single Sign-Off)

Выполните выход из тестируемого приложения. Проверьте, существует ли центральный портал или каталог приложений, позволяющий пользователю повторно войти в приложение без повторной аутентификации. Проверьте, требует ли приложение от пользователя пройти аутентификацию при прямом запросе URL-адреса точки входа в приложение. Находясь в учетной записи тестируемого приложения, выполните выход в системе SSO. Затем попробуйте получить доступ к аутентифицированной области тестируемого приложения.

> Ожидается, что вызов функции выхода в веб-приложении, подключенном к системе SSO, или в самой системе SSO приводит к глобальному завершению всех сессий. После выхода в системе SSO и подключенном приложении для получения доступа к приложению должна требоваться повторная аутентификация пользователя.

### Повторное использование сессий между устройствами и зависимость от одного значения в SSO

> В то время как традиционное тестирование выхода в SSO сосредоточено на процессах повторной аутентификации в рамках одного контекста браузера, тестировщики также должны оценивать возможность повторного использования (replay) артефакта аутентификации (например, cookie, заголовка или bearer-токена) на других устройствах.

В некоторых реализациях единого входа (SSO) аутентификация между несколькими приложениями опирается на один артефакт аутентификации, выдаваемый после успешного входа (например, после проверки пароля и многофакторной аутентификации — Multi-Factor Authentication, MFA).

> Например: даже если cookie установлен с атрибутами Secure и HttpOnly, его безопасность целиком зависит от механизмов валидации и отзыва на стороне сервера. Если экосистема SSO полагается на единственный cookie как на исключительное подтверждение аутентификации, компрометация этого cookie может предоставить мгновенный доступ ко всем приложениям.

Тестировщикам следует оценить:

- Достаточно ли одного артефакта аутентификации для поддержания аутентифицированного состояния.
- Может ли артефакт аутентификации использоваться повторно в различных браузерах или на разных устройствах.
- Приводит ли выход из системы к надлежащей инвалидации артефакта аутентификации на стороне сервера.
- Отклоняют ли данный артефакт все приложения, доверяющие артефакту аутентификации SSO, после выполнения выхода.

Процедура тестирования:

- Шаг 1 — Аутентификация и перехват всех выданных артефактов аутентификации

1. Войдите в систему на Устройстве 1 (Device 1), используя валидные учетные данные, и пройдите MFA.
2. Перехватите ответ аутентификации.
3. Зафиксируйте все артефакты аутентификации (например, cookie, заголовок или bearer-токен), выданные приложением или доменом SSO.

Например: `auth-cookie=XYZ123`, `session_meta=ABC456`, `tracking_id=DEF789`...

- Шаг 2 — Идентификация критически важных для аутентификации артефактов

Цель этого шага — определить, зависит ли реализация SSO от единственного артефакта аутентификации (например, cookie, заголовка или bearer-токена).

1. Отправьте запросы к защищенным эндпоинтам.
2. Удаляйте артефакты аутентификации по очереди и отправляйте запрос повторно.
3. Отслеживайте, какие из них необходимы для получения ответа 200 OK.

Если для поддержания аутентификации требуется только один артефакт (например, `auth-cookie`), это указывает на то, что граница доверия SSO может целиком опираться на это единственное значение.

> Примечание по безопасности:
> Когда единственный артефакт аутентификации олицетворяет собой все состояние аутентификации, он становится высокоценной целью. Злоумышленнику, получившему это единственное значение, могут не потребоваться никакие дополнительные метаданные сессии или контекст устройства для получения доступа.

- Шаг 3 — Внедрение сессии на другом устройстве (Cross-Device Session Injection)

1. Скопируйте значение критического артефакта аутентификации (например, `auth-cookie=XYZ123`).
2. Откройте другой браузер или другое устройство (Устройство 2 / Device 2).
3. Вручную внедрите скопированный одиночный артефакт.
4. Попробуйте получить доступ к защищенным эндпоинтам в:
    - Исходном приложении
    - Других приложениях, участвующих в той же экосистеме SSO

Если Устройство 2 получает аутентифицированный доступ без ввода учетных данных или прохождения MFA, артефакт может использоваться повторно между различными контекстами.

- Шаг 4 — Проверка выхода из системы между устройствами

1. На Устройстве 1 выполните выход из системы (logout).
2. На Устройстве 2 обновите страницу или обратитесь к защищенным ресурсам, используя то же внедренное значение артефакта аутентификации.

Ожидаемый результат:

- Выход из системы должен инвалидировать артефакт аутентификации (например, cookie или bearer-токен) на стороне сервера.
- Все сессии, использующие данный артефакт, должны быть прекращены.
- Доступ не должен оставаться валидным вплоть до истечения срока действия артефакта аутентификации.
- Все приложения, доверяющие артефакту аутентификации SSO, должны отклонить его.

Если реализация SSO:

- Полагается преимущественно на единственный артефакт аутентификации
- Позволяет повторно использовать этот артефакт на разных устройствах
- Не отзывает его на стороне сервера при выходе из системы

то:

- Кража этого единичного артефакта аутентификации может привести к немедленной компрометации активных сессий.
- Механизмы защиты MFA фактически обходятся после первичного входа в систему.
- Выход из системы может не обеспечивать глобальное завершение сессии.
- Доступ может сохраняться в течение всего срока жизни артефакта (например, `auth-cookie=XYZ123; max-age=28800`, 8 часов).

В реализациях следует избегать архитектурных решений, при которых одиночный артефакт аутентификации представляет собой все аутентифицированное состояние без дополнительных механизмов валидации.
