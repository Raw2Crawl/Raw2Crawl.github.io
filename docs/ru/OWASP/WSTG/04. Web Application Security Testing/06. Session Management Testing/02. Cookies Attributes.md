# Атрибуты файлов cookie

| ID |
| --- |
| WSTG-SESS-02 |

## Резюме

Веб-cookie (далее именуемые cookie) часто служат ключевым вектором атак для злоумышленников (обычно нацеленных на других пользователей), поэтому приложение всегда должно проявлять должную осмотрительность для защиты cookie.

Протокол HTTP не сохраняет состояние (stateless), то есть он не хранит никаких связей между запросами, отправляемыми одним и тем же пользователем. Чтобы решить эту проблему, были созданы сессии, данные которых передаются вместе с HTTP-запросами. Браузеры, как описано в разделе [тестирование хранилищ браузера](../11.%20Client-side%20Testing/12.%20Browser%20Storage.md), содержат множество механизмов хранения. В указанном разделе руководства подробно рассматривается каждый из них.

Наиболее часто используемым механизмом хранения сессий в браузерах является хранилище cookie. Cookie могут устанавливаться сервером путем добавления заголовка [`Set-Cookie`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie) в HTTP-ответ или через JavaScript. Cookie могут использоваться для множества целей, таких как:

- управление сессиями (session management)
- персонализация (personalization)
- отслеживание (tracking)

Чтобы защитить данные cookie, индустрия разработала средства, помогающие изолировать эти cookie и ограничить их поверхность атаки. Со временем cookie стали предпочтительным механизмом хранения для веб-приложений, поскольку они обеспечивают высокую гибкость в использовании и защите.

К средствам защиты cookie относятся:

- [Атрибуты cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies#Creating_cookies)
- [Префиксы cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies#Cookie_prefixes)

## Цели тестирования

- Убедиться, что для cookie задана надлежащая конфигурация безопасности.

## Методика тестирования

Ниже приведено описание каждого атрибута и префикса. Тестировщику необходимо проверить правильность их использования приложением. Анализировать cookie можно с помощью [перехватывающего прокси](#перехватывающий-прокси-сервер) или просматривая хранилище cookie браузера (cookie jar).

### Атрибуты cookie

#### Атрибут Secure

Атрибут [`Secure`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#Secure) предписывает браузеру отправлять cookie только в том случае, если запрос передается по защищенному каналу, такому как `HTTPS`. Это помогает защитить cookie от передачи в незашифрованных запросах. Если доступ к приложению возможен как по `HTTP`, так и по `HTTPS`, злоумышленник может перенаправить пользователя так, чтобы его cookie были отправлены в составе незащищенных запросов.

#### Атрибут HttpOnly

Атрибут [`HttpOnly`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#HttpOnly) используется для предотвращения таких атак, как утечка сессии (session leakage), поскольку он блокирует доступ к cookie для клиентских скриптов, таких как JavaScript.

> Это не устраняет полностью поверхность атак межсайтового скриптинга (Cross-Site Scripting, XSS), так как атакующий по-прежнему может отправлять запросы от имени пользователя, однако существенно ограничивает возможности векторов атак XSS.

#### Атрибут Domain

Атрибут [`Domain`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies#Scope_of_cookies) используется для сопоставления домена cookie с доменом сервера, к которому выполняется HTTP-запрос. Если домен совпадает или является поддоменом, следующим будет проверяться атрибут [`path`](#атрибут-path).

Только хосты, принадлежащие указанному домену, могут устанавливать cookie для этого домена. Кроме того, атрибут `domain` не может указывать на домен верхнего уровня (например, `.gov` или `.com`) — это предотвращает установку серверами произвольных cookie для других доменов (например, установку cookie для `owasp.org`). Если атрибут `domain` не задан, в качестве значения по умолчанию используется имя хоста сервера, сгенерировавшего cookie.

Например, если cookie устанавливается приложением на `app.mydomain.com` без указания атрибута domain, то этот cookie будет повторно отправляться для всех последующих запросов к `app.mydomain.com`, но не к его поддоменам (таким как `hacker.app.mydomain.com`) и не к `otherapp.mydomain.com`. (Однако старые версии Edge/IE ведут себя иначе и *отправляют* такие cookie на поддомены.) Если разработчик хочет ослабить это ограничение, он может установить атрибут `domain` в значение `mydomain.com`. В этом случае cookie будет отправляться со всеми запросами к `app.mydomain.com` и к поддоменам `mydomain.com`, таким как `hacker.app.mydomain.com` и даже `bank.mydomain.com`. Если на поддомене имеется уязвимый сервер (например, `otherapp.mydomain.com`), а атрибут `domain` был задан слишком широко (например, `mydomain.com`), уязвимый сервер может использоваться для сбора cookie (таких как сессионные токены) во всей области действия `mydomain.com`.

#### Атрибут Path

Атрибут [`Path`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies#Scope_of_cookies) играет важную роль в определении области действия cookie в сочетании с атрибутом [`domain`](#атрибут-domain). В дополнение к домену можно указать URL-путь, для которого действителен cookie. Если домен и путь совпадают, cookie будет включен в запрос. Как и в случае с атрибутом domain, если атрибут path задан слишком широко, это может сделать приложение уязвимым для атак со стороны других приложений на том же сервере. Например, если атрибут path установлен в корень веб-сервера `/`, cookie приложения будут отправляться каждому приложению в пределах того же домена (если на одном сервере размещено несколько приложений). Несколько примеров путей для приложений на одном сервере:

- `path=/bank`
- `path=/private`
- `path=/docs`
- `path=/docs/admin`

#### Атрибут Expires

Атрибут [`Expires`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies#Permanent_cookies) используется для:

- установки постоянных cookie (persistent cookies)
- ограничения времени жизни, если сессия существует слишком долго
- принудительного удаления cookie путем указания прошедшей даты

В отличие от [сессионных cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies#Session_cookies), постоянные cookie используются браузером до тех пор, пока не истечет их срок действия. Как только срок действия превысит установленное время, браузер удаляет cookie.

#### Атрибут SameSite

Атрибут [`SameSite`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies#SameSite_cookies) может использоваться для определения того, должен ли cookie отправляться вместе с межсайтовыми запросами (cross-site requests). Эта функция позволяет серверу снизить риск межсайтовой утечки информации. В некоторых случаях он также используется как стратегия снижения рисков (или механизм эшелонированной защиты — defense in depth) для предотвращения атак [подделки межсайтовых запросов (Cross-Site Request Forgery, CSRF)](05.%20Cross%20Site%20Request%20Forgery.md). Этот атрибут можно настроить в трех различных режимах:

- `Strict`
- `Lax`
- `None`

`SameSite` сравнивает [сайты (sites)](https://developer.mozilla.org/en-US/docs/Glossary/Site), а не источники (origins). Сайт представляет собой комбинацию схемы и регистрируемого домена, например `https://mydomain.com`, поэтому `https://app.mydomain.com` и `https://otherapp.mydomain.com` относятся к одному и тому же сайту, хотя являются разными источниками. `SameSite` не ограничивает запросы между ними. Если злоумышленник контролирует какой-либо поддомен того же сайта, например через XSS или [захват поддомена (subdomain takeover)](../02.%20Configuration%20and%20Deployment%20Management%20Testing/10.%20Subdomain%20Takeover.md), он может отправлять запросы к приложению, включающие его cookie, даже помеченные как `Strict`. При оценке уровня защиты, обеспечиваемого `SameSite`, следует учитывать каждый поддомен сайта.

##### Значение Strict

Значение `Strict` является наиболее строгим вариантом использования `SameSite`. Браузер отправляет cookie только в запросах, исходящих с того же сайта, который установил cookie, и никогда — в межсайтовых запросах, включая навигацию верхнего уровня (top-level navigation), такую как переход по ссылке с другого сайта. Это значение особенно рекомендуется для действий, выполняемых внутри одного сайта. Однако оно может повлиять на удобство навигации в некоторых системах управления сессиями. Когда авторизованный пользователь переходит по ссылке на приложение с другого сайта (например, из веб-почты), браузер не отправляет cookie в этом первом запросе, в результате чего пользователь выглядит неавторизованным. Cookie отправляется повторно при следующем запросе внутри того же сайта (same-site), например, когда пользователь переходит по внутренней ссылке в приложении.

##### Значение Lax

Значение `Lax` менее строгое, чем `Strict`. Оно разрешает отправку cookie при межсайтовой *навигации верхнего уровня*, в которой используются «безопасные» методы HTTP (на практике — `GET`), например, когда пользователь переходит по ссылке с другого сайта. Оно **не** отправляет cookie при межсайтовых запросах *подэлементов (subresources)*, таких как запросы, инициированные тегами `<img>`, `<script>` или `<iframe>`, вызовами `fetch()` или `XMLHttpRequest`, а также не отправляет cookie при межсайтовых переходах с использованием метода `POST` или других небезопасных методов.

Начиная с 2020 года браузеры на базе Chromium (Chrome, Edge, Opera) обрабатывают любой cookie, установленный **без** явного атрибута `SameSite`, как `SameSite=Lax` по умолчанию. Браузеры Firefox и Safari не применяют это правило по умолчанию. В них cookie без атрибута `SameSite` остается доступным для отправки в межсайтовых запросах с учетом их собственных механизмов предотвращения отслеживания и сторонних cookie (Enhanced Tracking Protection / Total Cookie Protection в Firefox, Intelligent Tracking Prevention в Safari). Обратите внимание, что отсутствие атрибута не эквивалентно установке [`SameSite=None`](#значение-none), которое является явным значением и дополнительно требует наличия атрибута [`Secure`](#атрибут-secure) для принятия браузером. Эти механизмы предотвращения отслеживания служат для обеспечения приватности, а не заменяют явную установку `SameSite`, и их поведение отличается от явного ограничения `SameSite=Lax`. Тестировщикам не следует полагать, что cookie защищен от CSRF только потому, что межсайтовый запрос кажется заблокированным в Firefox или Safari, — проверяйте фактический заголовок `Set-Cookie`, а не делайте выводы о защите на основе наблюдаемого поведения браузера.

Когда браузер на базе Chromium применяет `Lax` по умолчанию, он использует [более разрешительный вариант `Lax`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#samesitesamesite-value): cookie без атрибута `SameSite` по-прежнему отправляется в межсайтовых `POST`-запросах верхнего уровня в течение двух минут после его установки. Cookie с явно заданным атрибутом `SameSite=Lax` такого исключения не получают. Это означает, что межсайтовый `POST`-запрос, отправленный вскоре после входа пользователя в систему, все еще может нести сессионный cookie, у которого отсутствует атрибут `SameSite`.

##### Значение None

Значение `None` указывает на то, что браузер будет отправлять cookie во всех контекстах, включая межсайтовые запросы (стандартное поведение до появления `SameSite`). Cookie с установленным `SameSite=None` обязательно должен иметь также атрибут [`Secure`](#атрибут-secure), например `SameSite=None; Secure`. Браузеры на базе Chromium и Firefox отклоняют cookie со значением `SameSite=None` без `Secure`, поэтому такой cookie вообще не будет сохранен. Safari не применяет это требование (см. [таблицу совместимости браузеров на MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#browser_compatibility)).

### Префиксы cookie

По своей архитектуре cookie не имеют встроенных механизмов для гарантии целостности и конфиденциальности хранящейся в них информации. Эти ограничения не позволяют серверу иметь уверенность в том, как именно были настроены атрибуты данного cookie при его создании. Чтобы предоставить серверам такую возможность с сохранением обратной совместимости, индустрия ввела концепцию [префиксов имен cookie (`Cookie Name Prefixes`)](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis#section-4.1.3), позволяющую передавать эти свойства прямо в имени cookie.

#### Префикс Host

Префикс [`__Host-`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies#Cookie_prefixes) требует, чтобы cookie удовлетворял следующим условиям:

  1. Cookie должен быть установлен с [атрибутом `Secure`](#атрибут-secure).
  2. Cookie должен быть установлен с URI, признанного агентом пользователя (браузером) безопасным.
  3. Отправляться только на хост, установивший cookie, и НЕ ДОЛЖЕН содержать [атрибут `Domain`](#атрибут-domain).
  4. Cookie должен быть установлен с [атрибутом `Path`](#атрибут-path) со значением `/`, чтобы он отправлялся с каждым запросом к данному хосту.

По этой причине cookie `Set-Cookie: __Host-SID=12345; Secure; Path=/` будет принят, в то время как любой из следующих вариантов всегда будет отклонен:
`Set-Cookie: __Host-SID=12345`
`Set-Cookie: __Host-SID=12345; Secure`
`Set-Cookie: __Host-SID=12345; Domain=site.example`
`Set-Cookie: __Host-SID=12345; Domain=site.example; Path=/`
`Set-Cookie: __Host-SID=12345; Secure; Domain=site.example; Path=/`

#### Префикс Secure

Префикс [`__Secure-`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies#Cookie_prefixes) менее строгий и может применяться путем добавления чувствительной к регистру строки `__Secure-` к имени cookie. Любой cookie, имя которого начинается с префикса `__Secure-`, должен удовлетворять следующим условиям:

  1. Cookie должен быть установлен с атрибутом `Secure`.
  2. Cookie должен быть установлен с URI, признанного агентом пользователя безопасным.

### Надежные практики

Атрибуты и префиксы должны применяться в зависимости от потребностей приложения и требуемого режима работы cookie. Чем строже изолирован cookie, тем лучше.

Обобщая все вышесказанное, наиболее безопасную конфигурацию атрибутов cookie можно определить следующим образом: `Set-Cookie: __Host-SID=<session token>; path=/; Secure; HttpOnly; SameSite=Strict`.
