# Раскрытые переменные сессии

| ID |
| --- |
| WSTG-SESS-04 |

## Резюме

Токены сессий (Cookie, SessionID, скрытые поля — Hidden Field) в случае их раскрытия обычно позволяют злоумышленнику выдать себя за жертву и получить неправомерный доступ к приложению. Крайне важно постоянно защищать их от перехвата (eavesdropping), особенно при передаче данных между браузером клиента и серверами приложений.

Приведенная здесь информация относится к тому, как безопасность транспортного уровня применяется к передаче конфиденциальных данных Session ID, а не к данным в целом, и эти правила могут быть строже, чем политики кэширования и транспортировки, применяемые к остальному контенту сайта.

С помощью персонального прокси (personal proxy) можно выяснить следующую информацию о каждом запросе и ответе:

- Используемый протокол (например, HTTP или HTTPS)
- HTTP-заголовки
- Тело сообщения (например, параметры POST-запроса или содержимое страницы)

Каждый раз при передаче данных Session ID между клиентом и сервером необходимо проверять используемый протокол, директивы кэширования и приватности, а также тело сообщения. Под безопасностью транспортного уровня здесь понимается передача Session ID в запросах GET или POST, телах сообщений или иными способами в рамках валидных HTTP-запросов.

## Цели тестирования

- Убедиться в корректной реализации шифрования.
- Проанализировать конфигурацию кэширования.
- Оценить безопасность канала и методов передачи данных.

## Методика тестирования

### Уязвимости шифрования и повторного использования токенов сессии

Защита от прослушивания и перехвата часто обеспечивается шифрованием TLS, но может включать и другие механизмы туннелирования или шифрования. Следует отметить, что шифрование или криптографическое хеширование Session ID следует рассматривать отдельно от шифрования транспортного уровня, поскольку защищается сам Session ID, а не данные, которые он может представлять.

Если Session ID может быть отправлен злоумышленником приложению для получения доступа, он должен быть защищен при передаче для снижения этого риска. Поэтому необходимо гарантировать, что шифрование включено по умолчанию и применяется принудительно для любых запросов и ответов, содержащих Session ID, независимо от используемого механизма (например, скрытого поля формы). Следует выполнять простые проверки, такие как замена `https://` на `http://` в процессе взаимодействия с приложением, а также модификацию отправляемых форм (form posts), чтобы определить, реализовано ли надлежащее разделение между защищенными и незащищенными сегментами сайта.

Обратите внимание: если на сайте есть раздел, где действия пользователя отслеживаются с помощью Session ID, но безопасность не обеспечивается (например, фиксация того, какие публичные документы скачивает зарегистрированный пользователь), критически важно, чтобы использовался другой Session ID. Таким образом, Session ID необходимо отслеживать при переходе клиента от защищенных разделов к незащищенным, чтобы убедиться в использовании другого идентификатора.

> Каждый раз при успешной аутентификации пользователь должен ожидать получение:
>
> - Другого токена сессии
> - Токена, передаваемого по зашифрованному каналу при каждом последующем HTTP-запросе

### Прокси-серверы и уязвимости кэширования

При анализе безопасности приложения также необходимо учитывать прокси-серверы. Во многих случаях клиенты получают доступ к приложению через корпоративные прокси, прокси интернет-провайдеров или другие шлюзы с анализом протоколов (например, сетевые экраны — Firewalls). Протокол HTTP предоставляет директивы для управления поведением нижестоящих прокси (downstream proxies), и корректность реализации этих директив также подлежит оценке.

В целом Session ID никогда не должен передаваться по незашифрованному каналу и никогда не должен кэшироваться. Необходимо исследовать приложение, чтобы убедиться, что зашифрованная связь включена по умолчанию и является обязательной при любой передаче Session ID. Кроме того, при любой передаче Session ID должны действовать директивы, предотвращающие его сохранение в промежуточных и даже локальных кэшах.

Приложение также должно быть настроено на безопасную обработку данных в кэшах как для HTTP/1.0, так и для HTTP/1.1 — в RFC 9111 описаны соответствующие механизмы контроля применительно к HTTP. HTTP/1.1 предоставляет ряд механизмов управления кэшированием. Заголовок `Cache-Control: no-cache` указывает, что прокси-сервер не должен повторно использовать какие-либо данные. Хотя директива `Cache-Control: private` кажется подходящей, она все равно разрешает разделяемым или локальным клиентам кэшировать данные. В случае интернет-кафе или других общедоступных систем это создает явный риск. Даже на однопользовательских рабочих станциях кэшированный Session ID может быть раскрыт в случае компрометации файловой системы или при использовании сетевых хранилищ. Кэши HTTP/1.0 не распознают директиву `Cache-Control: no-cache`.

> Директивы `Expires: 0` и `Cache-Control: max-age=0` должны использоваться для дополнительной гарантии того, что кэши не раскроют эти данные. Каждый запрос и ответ, содержащий данные Session ID, должен быть проверен на предмет использования надлежащих директив кэширования.

### Уязвимости в запросах GET и POST

Как правило, запросы GET не должны использоваться для передачи данных сессии, поскольку Session ID может быть раскрыт в журналах прокси-серверов или сетевых экранов. Ими также гораздо легче манипулировать, чем другими типами передачи данных, хотя следует учитывать, что клиент с помощью соответствующих инструментов может изменить практически любой механизм передачи. Кроме того, атаки межсайтового скриптинга (Cross-Site Scripting, XSS) проще всего эксплуатировать путем отправки специально сформированной ссылки жертве. Это гораздо менее вероятно, если данные отправляются клиентом через запросы POST.

Весь серверный код, принимающий данные из POST-запросов, должен быть протестирован, чтобы убедиться, что он не принимает эти же данные, отправленные через метод GET. В качестве примера рассмотрим следующий POST-запрос (`https://owaspapp.com/login.asp`), сгенерированный страницей входа.

```http
POST /login.asp HTTP/1.1
Host: owaspapp.com
[...]
Cookie: ASPSESSIONIDABCDEFG=ASKLJDLKJRELKHJG
Content-Length: 51

Login=Username&password=Password&SessionID=12345678
```

Если скрипт login.asp реализован некорректно, вход в систему может оказаться возможным по следующему URL: `https://owaspapp.com/login.asp?Login=Username&password=Password&SessionID=12345678`

Потенциально небезопасные серверные скрипты можно выявить, проверяя каждый POST-запрос подобным образом.

### Уязвимости транспортного уровня

Любое взаимодействие между клиентом и приложением должно быть протестировано как минимум по следующим критериям:

- Как передаются Session ID? Например: GET, POST, поле формы (включая скрытые поля)
- Всегда ли Session ID отправляются по зашифрованному каналу по умолчанию?
- Можно ли склонить приложение к отправке Session ID в незашифрованном виде? Например, изменив HTTPS на HTTP?
- Какие директивы управления кэшем применяются к запросам/ответам, передающим Session ID?
- Всегда ли присутствуют эти директивы? Если нет, то в каких случаях делаются исключения?
- Используются ли GET-запросы, содержащие Session ID?
- Если используется POST, можно ли заменить его на GET?
