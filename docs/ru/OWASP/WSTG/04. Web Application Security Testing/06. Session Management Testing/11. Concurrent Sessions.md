# Одновременные сессии

| ID |
| --- |
| WSTG-SESS-11 |

## Резюме

Параллельные сессии (Concurrent Sessions) — распространенный аспект веб-приложений, обеспечивающий возможность одновременного взаимодействия нескольких пользователей или одного пользователя с нескольких устройств. Данный тест направлен на оценку способности приложения обрабатывать несколько активных сессий для одной учетной записи пользователя. Эта функциональность необходима для эффективного управления параллельными пользовательскими сессиями, особенно в чувствительных сегментах, таких как панели администратора, содержащие персональные идентифицируемые данные (Personally Identifiable Information, PII), личные кабинеты пользователей или API, использующие сторонние сервисы для обогащения предоставленных пользователем данных. Основная цель — убедиться, что поведение параллельных сессий соответствует требованиям безопасности приложения.

Понимание требований безопасности приложения является ключевым фактором при оценке того, соответствует ли разрешение параллельных сессий предполагаемому функционалу. Разрешение параллельных сессий само по себе не является вредоносным и намеренно допускается во многих приложениях. Однако крайне важно убедиться, что функционал приложения согласован с мерами безопасности в отношении параллельных сессий. Если параллельные сессии предусмотрены архитектурой, жизненно важно внедрить дополнительные средства контроля безопасности, такие как управление активными сессиями, принудительное завершение сессий и оповещение о потенциально новых входах. И наоборот, если параллельные сессии не предусмотрены или не планируются в приложении, критически важно проверить действующие ограничения на предмет уязвимостей управления сессиями.

Чтобы определить необходимость параллельных сессий, следует учитывать следующие факторы:

- Понимание характера приложения, особенно ситуаций, в которых пользователям может требоваться одновременный доступ из разных мест или с разных устройств.
- Выявление критических операций, таких как финансовые транзакции, требующие строго защищенного доступа.
- Обработка конфиденциальных данных, таких как персональные идентифицируемые данные (PII), указывающая на необходимость защищенного взаимодействия.
- Разграничение между панелью управления администратора и стандартным пользовательским интерфейсом.

## Цели тестирования

- Оценить систему управления сессиями приложения путем проверки обработки нескольких активных сессий для одной учетной записи пользователя.

## Методика тестирования

1. **Создание валидной сессии:**
   - Отправьте валидные учетные данные (имя пользователя и пароль) для создания сессии.
   - Пример HTTP-запроса:

     ```http
     POST /login HTTP/1.1
     Host: www.example.com
     Content-Length: 32

     username=admin&password=admin123
     ```

   - Пример ответа:

     ```http
     HTTP/1.1 200 OK
     Set-Cookie: SESSIONID=0add0d8eyYq3HIUy09hhus; Path=/; Secure
     ```

   - Сохраните сгенерированный аутентификационный cookie. В некоторых случаях созданный cookie аутентификации заменяется токенами, такими как JSON Web Tokens (JWT).

2. **Тест на генерацию активных сессий:**
   - Попробуйте создать множество аутентификационных cookie, отправляя запросы на вход (например, 100 раз).

   Примечание: использование режима инкогнито (private browsing) или контейнеров с разделением учетных записей (multi-account containers) может быть полезным при проведении этих тестов, так как они предоставляют изолированные среды для тестирования управления сессиями без влияния существующих сессий или cookie, сохраненных в браузере.

3. **Тест на валидацию активных сессий:**
   - Попробуйте обратиться к приложению, используя первоначальный токен сессии (например, `SESSIONID=0add0d8eyYq3HIUy09hhus`).
   - Если аутентификация по первому сгенерированному токену проходит успешно, рассматривайте это как потенциальную проблему, указывающую на неполноценное управление сессиями.

Кроме того, существуют дополнительные сценарии, расширяющие охват методологии тестирования на случаи множественных сессий, исходящих с различных IP-адресов и из разных геолокаций. Эти тесты помогают выявить потенциальные уязвимости или аномалии в обработке сессий, связанные с географическими или сетевыми факторами:

- Тестирование множественных сессий с одного и того же IP-адреса.
- Тестирование множественных сессий с разных IP-адресов.
- Тестирование множественных сессий из геолокаций, посещение которых одним и тем же пользователем за короткий промежуток времени маловероятно или невозможно (например, одна сессия создана в определенной стране, а следующая сессия инициирована через пять минут из другой страны).

## Рекомендации по устранению

Приложение должно отслеживать и ограничивать количество активных сессий на одну учетную запись пользователя. При превышении максимально допустимого количества сессий система обязана инвалидировать предыдущие сессии для поддержания безопасности. Внедрение дополнительных решений позволяет еще больше снизить этот риск:

   1. **Оповещение пользователя (User Notification):** уведомляйте пользователей после каждого успешного входа для повышения осведомленности об активных сессиях.
   2. **Страница управления сессиями (Session Management Page):** создайте специализированную страницу для отображения активных сессий и возможности их завершения для лучшего контроля со стороны пользователя.
   3. **Отслеживание IP-адресов (IP Address Tracking):** отслеживайте IP-адреса пользователей, выполняющих вход в учетную запись, и отмечайте любую подозрительную активность, например множественные входы из разных локаций.
   4. **Ограничения по IP-адресам (IP Address Restrictions):** позвольте пользователям указывать доверенные IP-адреса или диапазоны, с которых разрешен доступ к их учетным записям, повышая безопасность за счет ограничения сессий только известными и одобренными локациями.
