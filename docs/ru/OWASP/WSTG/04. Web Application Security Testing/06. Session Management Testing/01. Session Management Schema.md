# Схема управления сессиями

## Резюме

Одним из ключевых компонентов любого веб-приложения является механизм, с помощью которого оно контролирует и поддерживает состояние (state) взаимодействующего с ним пользователя. Чтобы избежать непрерывной аутентификации для каждой отдельной страницы сайта или сервиса, веб-приложения реализуют различные механизмы хранения и валидации учетных данных в течение заранее определенного периода времени. Эти механизмы известны как управление сессиями (Session Management).

В рамках данного теста специалист проверяет, создаются ли cookie и другие токены сессии безопасным и непредсказуемым образом. Злоумышленник, способный спрогнозировать и подделать слабый cookie-файл, может легко перехватить сессии легитимных пользователей (session hijacking).

Cookie используются для реализации управления сессиями и подробно описаны в спецификации RFC 6265. Вкратце: когда пользователь обращается к приложению, которому необходимо отслеживать действия и идентифицировать этого пользователя на протяжении нескольких запросов, сервер генерирует cookie (один или несколько) и отправляет их клиенту. Затем клиент отправляет cookie обратно на сервер во всех последующих соединениях до тех пор, пока срок действия cookie не истечет или они не будут уничтожены. Данные, хранящиеся в cookie, могут предоставлять серверу широкий спектр информации о том, кем является пользователь, какие действия он совершил к текущему моменту, каковы его предпочтения и т. д., тем самым обеспечивая сохранение состояния (state) поверх протокола без сохранения состояния (stateless), такого как HTTP.

Типичным примером является корзина в интернет-магазине. На протяжении всей сессии пользователя приложение должно отслеживать его личность, его профиль, выбранные для покупки товары, их количество, индивидуальные цены, скидки и т. д. Cookie служат эффективным способом хранения и передачи этой информации туда и обратно (другими методами являются параметры URL и скрытые поля формы — hidden fields).

В силу важности хранимых ими данных cookie играют жизненно важную роль в общей безопасности приложения. Возможность манипулирования cookie может привести к перехвату сессий легитимных пользователей, получению повышенных привилегий в активной сессии (эскалация привилегий — privilege escalation) и в целом к несанкционированному влиянию на функционирование приложения.

В данном тесте специалисту необходимо проверить, способны ли выдаваемые клиентам cookie противостоять широкому спектру атак, направленных на вмешательство в сессии легитимных пользователей и в работу самого приложения. Главная цель — проверить возможность подделки cookie, который будет воспринят приложением как валидный и предоставит некий несанкционированный доступ (перехват сессии, эскалация привилегий и т. д.).

Обычно основной шаблон атаки включает следующие шаги:

- **Сбор cookie (cookie collection)**: сбор достаточного количества образцов cookie;
- **Реверс-инжиниринг cookie (cookie reverse engineering)**: анализ алгоритма генерации cookie;
- **Манипуляция cookie (cookie manipulation)**: подделка валидного cookie для проведения атаки. Этот последний шаг может потребовать большого количества попыток в зависимости от того, как сформирован cookie (атака методом перебора cookie — cookie brute-force attack).

Другой шаблон атаки заключается в переполнении cookie (cookie overflow). Строго говоря, данная атака имеет иную природу, поскольку в этом случае тестировщики не пытаются воссоздать идеально валидный cookie. Вместо этого целью является переполнение области памяти, что нарушает корректное поведение приложения и потенциально позволяет внедрить (и удаленно выполнить) вредоносный код.

## Цели тестирования

- Собрать токены сессий как для одного и того же пользователя, так и для разных пользователей, где это возможно.
- Проанализировать и убедиться, что уровень энтропии/случайности достаточен для предотвращения атак с подделкой сессий.
- Модифицировать неподписанные cookie, содержащие данные, которыми можно манипулировать.

## Методика тестирования

### Тестирование методом «черного ящика» и примеры

Все взаимодействия между клиентом и приложением необходимо проверить как минимум по следующим критериям:

- Помечены ли все директивы `Set-Cookie` атрибутом `Secure`?
- Происходят ли какие-либо операции с Cookie по незашифрованному каналу передачи?
- Можно ли принудительно передать Cookie по незашифрованному каналу?
- Если да, то каким образом приложение обеспечивает безопасность?
- Являются ли какие-либо Cookie постоянными (persistent)?
- Какое время истечения (`Expires`) установлено для постоянных cookie и является ли оно обоснованным?
- Сконфигурированы ли cookie, которые должны быть сессионными (transient), соответствующим образом?
- Какие параметры заголовка `Cache-Control` протокола HTTP/1.1 используются для защиты Cookie?
- Какие параметры заголовка `Cache-Control` протокола HTTP/1.0 используются для защиты Cookie?

#### Сбор файлов cookie

Первый шаг, необходимый для манипуляции cookie, состоит в том, чтобы понять, как приложение создает cookie и управляет ими. Для выполнения этой задачи тестировщикам необходимо попытаться ответить на следующие вопросы:

- Сколько cookie использует приложение?

  Исследуйте приложение. Обращайте внимание на то, когда создаются cookie. Составьте список полученных cookie, укажите страницу, которая их устанавливает (с помощью директивы `Set-Cookie`), домен, для которого они действительны, их значение и характеристики.

- Какие компоненты приложения генерируют или модифицируют cookie?

  Работая с приложением, определите, какие cookie остаются неизменными, а какие изменяются. Какие события приводят к изменению cookie?

- Для доступа к каким компонентам приложения и их использования требуется данный cookie?

  Выясните, каким частям приложения необходим cookie. Перейдите на страницу, затем повторите запрос без cookie или с измененным значением. Попробуйте составить карту использования cookie.

Электронная таблица, связывающая каждый cookie с соответствующими компонентами приложения и сопутствующей информацией, может стать ценным результатом этого этапа.

#### Анализ сессий

Токены сессий (Cookie, идентификатор сессии — SessionID или скрытое поле — Hidden Field) должны быть проверены для оценки их качества с точки зрения безопасности. Их необходимо протестировать по таким критериям, как случайность (randomness), уникальность, устойчивость к статистическому и криптографическому анализу, а также утечка информации.

- Структура токена и утечка информации (Token Structure & Information Leakage)

Первый этап — изучение структуры и содержимого идентификатора сессии (Session ID), выдаваемого приложением. Распространенной ошибкой является включение конкретных конфиденциальных данных в сам токен вместо выдачи случайного значения со ссылкой на реальные данные на стороне сервера.

Если Session ID передается в открытом виде (clear-text), структура и важные данные могут быть сразу очевидны, например `192.168.100.1:owaspuser:password:15:58`.

Если часть токена или весь токен закодирован или хеширован, его следует сопоставить с различными методами для выявления явной обфускации. Например, строка `192.168.100.1:owaspuser:password:15:58` представлена в шестнадцатеричном виде (hex), base64 и в виде MD5-хеша:

- Hex: `3139322E3136382E3130302E313A6F77617370757365723A70617373776F72643A31353A3538`
- Base64: `MTkyLjE2OC4xMDAuMTpvd2FzcHVzZXI6cGFzc3dvcmQ6MTU6NTg=`
- MD5: `01c2fc4f0a817afd8366689bd29dd40a`

Определив тип обфускации, можно декодировать токен обратно в исходные данные. В большинстве случаев, однако, это маловероятно. Тем не менее полезно определить используемое кодирование по формату сообщения. Более того, если удается выяснить и формат, и технику обфускации, можно разработать автоматизированные атаки методом перебора (brute-force).

Гибридные токены могут содержать такую информацию, как IP-адрес или идентификатор пользователя (User ID), наряду с закодированной частью, например `owaspuser:192.168.100.1:a7656fafe94dae72b1e1487670148412`.

Проанализировав отдельный токен сессии, следует исследовать репрезентативную выборку. Простой анализ токенов должен сразу выявить любые очевидные закономерности. Например, 32-битный токен может включать 16 бит статических данных и 16 бит переменных данных. Это может указывать на то, что первые 16 бит представляют собой фиксированный атрибут пользователя — например, имя пользователя или IP-адрес. Если второй 16-битный блок инкрементируется с постоянной скоростью, это может свидетельствовать о последовательном или временнóм (time-based) компоненте при генерации токена. См. примеры.

Если в токенах выявлены статические элементы, следует собрать дополнительные выборки, варьируя по одному потенциальному входному параметру за раз. Например, попытки входа в систему под другой учетной записью пользователя или с другого IP-адреса могут вызвать изменения в ранее статической части токена сессии.

При исследовании структуры одиночных и множественных Session ID следует ответить на следующие вопросы:

- Какие части Session ID являются статическими?
- Какая открытая конфиденциальная информация хранится в Session ID? Например, имена пользователей/UID, IP-адреса
- Какая легко декодируемая конфиденциальная информация хранится в нем?
- Какую информацию можно извлечь из структуры Session ID?
- Какие части Session ID остаются неизменными при одинаковых условиях входа?
- Какие очевидные закономерности присутствуют в Session ID в целом или в его отдельных частях?

#### Предсказуемость и случайность идентификаторов сессии

Необходимо провести анализ переменных областей (при их наличии) Session ID для установления наличия каких-либо распознаваемых или предсказуемых закономерностей. Этот анализ может выполняться вручную, а также с помощью специализированных или готовых (OTS) инструментов статистического и криптоанализа для выявления любых паттернов в содержимом Session ID. Ручные проверки должны включать сравнение Session ID, выданных при идентичных условиях аутентификации — например, при одинаковых имени пользователя, пароле и IP-адресе.

Время является важным фактором, который также необходимо контролировать. Следует выполнять большое количество одновременных подключений, чтобы собрать выборки в одном временнóм окне и сохранить эту переменную постоянной. Даже квантование в 50 мс или менее может оказаться слишком грубым, а выборка, полученная таким образом, может выявить временны́е компоненты, которые иначе были бы пропущены.

Переменные элементы следует анализировать во времени, чтобы определить, носят ли они инкрементный характер. Если они инкрементны, необходимо исследовать закономерности, связанные с абсолютным или истекшим временем. Во многих системах время используется в качестве начального значения (seed) для генераторов псевдослучайных чисел. Если закономерности кажутся случайными, в качестве возможного варианта следует рассматривать односторонние хеши от времени или других параметров окружения. Как правило, результатом криптографического хеширования является десятичное или шестнадцатеричное число, поэтому его можно идентифицировать.

При анализе последовательностей Session ID, паттернов или циклов необходимо рассматривать статические элементы и клиентские зависимости как возможные факторы, влияющие на структуру и функционирование приложения.

- Являются ли Session ID действительно случайными по своей природе? Можно ли воспроизвести полученные значения?
- Приводят ли одни и те же входные условия к генерации одинакового ID при последующем запуске?
- Доказана ли устойчивость Session ID к статистическому или криптографическому анализу?
- Какие элементы Session ID привязаны ко времени?
- Какие части Session ID предсказуемы?
- Можно ли вычислить следующий ID, обладая полной информацией об алгоритме генерации и предыдущих ID?

#### Обратная разработка (реверс-инжиниринг) cookie

Теперь, когда тестировщик выявил используемые cookie и получил общее представление об их назначении, пришло время более подробно рассмотреть те cookie, которые представляют интерес. Какие именно cookie интересуют тестировщика? Чтобы обеспечить безопасный метод управления сессиями, cookie должен сочетать в себе несколько характеристик, каждая из которых предназначена для защиты cookie от определенного класса атак.

Эти характеристики приведены ниже:

1. Непредсказуемость (Unpredictability): cookie должен содержать определенный объем трудноугадываемых данных. Чем сложнее подделать валидный cookie, тем труднее проникнуть в сессию легитимного пользователя. Если злоумышленник сможет угадать cookie, используемый в активной сессии легитимного пользователя, он сможет полностью выдать себя за этого пользователя (перехват сессии — session hijacking). Для обеспечения непредсказуемости cookie могут использоваться случайные значения или криптография.
2. Устойчивость к модификации (Tamper resistance): cookie должен противостоять попыткам злонамеренного изменения. Если тестировщик получает cookie вида `IsAdmin=No`, изменить его для получения административных прав тривиально, если только приложение не выполняет двойную проверку (например, добавляя к cookie зашифрованный хеш его значения).
3. Срок действия (Expiration): критически важный cookie должен быть действителен только в течение соответствующего периода времени и должен удаляться с диска или из памяти после этого, чтобы избежать риска повторного воспроизведения (replay attack). Это не относится к cookie, в которых хранятся некритичные данные, сохраняемые между сессиями (например, оформление сайта).
4. Флаг `Secure`: для cookie, значение которого критично для целостности сессии, должен быть включен этот флаг, разрешающий передачу cookie только по зашифрованному каналу для предотвращения перехвата трафика (eavesdropping).

Подход здесь заключается в том, чтобы собрать достаточное количество экземпляров cookie и начать поиск закономерностей в их значениях. Точное значение понятия «достаточное» может варьироваться от нескольких образцов, если метод генерации cookie очень легко взломать, до нескольких тысяч, если тестировщику необходимо провести математический анализ (например, критерий хи-квадрат, аттракторы; подробнее см. ниже).

Важно уделять особое внимание логике работы приложения (workflow), так как состояние сессии может оказывать существенное влияние на собранные cookie. Cookie, полученный до аутентификации, может сильно отличаться от cookie, выданного после нее.

Еще один аспект, который следует учитывать, — это время. Всегда фиксируйте точное время получения cookie, если есть вероятность, что время играет роль в формировании его значения (сервер может использовать временну́ю метку — timestamp как часть значения cookie). Зафиксированное время может быть локальным временем или временнóй меткой сервера, указанной в HTTP-ответе (либо тем и другим).

При анализе собранных значений тестировщик должен попытаться определить все переменные, которые могли повлиять на значение cookie, и попробовать изменять их по одной. Передача на сервер модифицированных версий одного и того же cookie может быть весьма полезной для понимания того, как приложение считывает и обрабатывает cookie.

Примеры проверок, выполняемых на этом этапе, включают:

- Какой набор символов (character set) используется в cookie? Имеет ли cookie числовое значение? Буквенно-цифровое? Шестнадцатеричное? Что произойдет, если тестировщик вставит в cookie символы, не входящие в ожидаемый набор?
- Состоит ли cookie из различных подчастей, несущих разные фрагменты информации? Как разделены эти части? С помощью каких разделителей? Некоторые части cookie могут иметь более высокую дисперсию, другие могут быть постоянными, третьи могут принимать лишь ограниченный набор значений. Разделение cookie на базовые компоненты — первый и фундаментальный шаг.

Примером легко различимого структурированного cookie является следующий:

```text
ID=5a0acfc7ffeb919:CR=1:TM=1120514521:LM=1120514521:S=j3am5KzC4v01ba3q
```

Этот пример демонстрирует 5 различных полей, содержащих разные типы данных:

- ID — шестнадцатеричное значение
- CR — небольшое целое число
- TM и LM — большие целые числа (и любопытно, что они имеют одинаковое значение; стоит проверить, что произойдет при изменении одного из них)
- S — буквенно-цифровое значение

Даже когда разделители не используются, наличие достаточного количества выборок помогает понять структуру.

#### Атаки методом полного перебора

Атаки методом перебора (brute-force) неизбежно вытекают из вопросов, связанных с предсказуемостью и случайностью. Вариативность Session ID должна рассматриваться совместно с продолжительностью сессии приложения и таймаутами. Если разброс значений Session ID относительно невелик, а срок действия Session ID продолжителен, вероятность успешной атаки перебором значительно возрастает.

Длинный Session ID (или, вернее, токен с высокой степенью энтропии/вариативности) и более короткий период валидности существенно затрудняют проведение успешной атаки перебором.

- Сколько времени займет атака методом перебора всех возможных значений Session ID?
- Достаточно ли велико пространство значений Session ID для предотвращения перебора? Например, достаточна ли длина ключа по сравнению со временем жизни сессии?
- Снижают ли задержки между попытками подключения с различными Session ID риск подобной атаки?

### Тестирование методом «серого ящика» и пример

Если тестировщик имеет доступ к реализации схемы управления сессиями, он может проверить следующее:

- Случайный токен сессии (Random Session Token)

  Выдаваемый клиенту Session ID или Cookie не должен легко прогнозироваться (не используйте линейные алгоритмы, основанные на предсказуемых переменных, таких как IP-адрес клиента). Рекомендуется использовать криптографические алгоритмы с длиной ключа 256 бит (например, AES).

- Длина токена (Token length)

  Длина Session ID должна составлять не менее 50 символов.

- Таймаут сессии (Session Time-out)

  Токен сессии должен иметь определенный таймаут (он зависит от критичности данных, обрабатываемых приложением).

- Конфигурация cookie:
    - Непостоянные (non-persistent): хранятся только в оперативной памяти (RAM)
    - Безопасные (secure, передаются только по HTTPS-каналу): `Set-Cookie: cookie=data; path=/; domain=.aaa.it; secure`
    - [HTTPOnly](https://owasp.org/www-community/HttpOnly) (не считываются скриптами): `Set-Cookie: cookie=data; path=/; domain=.aaa.it; HttpOnly`

Дополнительную информацию см. здесь: [cookies attributes](02.%20Cookies%20Attributes.md)
