# Определение отпечатка веб-сервера

| ID |
| --- |

## Резюме

Фингерпринтинг веб-сервера (web server fingerprinting) — это задача идентификации типа и точной версии программного обеспечения веб-сервера, под управлением которого функционирует целевая система. Хотя определение версии сервера зачастую встроено в инструменты автоматизированного сканирования, исследователю важно глубоко понимать фундаментальные механизмы, используемые данными утилитами для идентификации ПО, и практическую ценность получаемых результатов.

Точное определение типа и версии веб-сервера позволяет специалистам по безопасности оценить потенциальную уязвимость приложения к атакам. В частности, серверы под управлением устаревших версий ПО без актуальных обновлений безопасности уязвимы перед известными эксплойтами, специфичными для конкретных релизов.

## Цели тестирования

- Определить тип и точную версию запущенного веб-сервера для последующего поиска известных уязвимостей.

## Методика тестирования

Методики фингерпринтинга веб-серверов включают в себя захват баннера (banner grabbing), анализ ответов на некорректно сформированные запросы (malformed requests) и применение автоматизированных сканеров, комбинирующих различные тактики. Базовый принцип, лежащий в основе всех этих техник, одинаков: инициировать специфический ответ веб-сервера, который затем сравнивается с базой данных известных сигнатур и поведенческих характеристик для точного сопоставления с конкретным типом сервера.

### Захват баннеров (Banner Grabbing)

Захват баннера (banner grab) выполняется путем отправки стандартного HTTP-запроса к веб-серверу с последующим анализом его [заголовков ответа](https://developer.mozilla.org/en-US/docs/Glossary/Response_header) (response headers). Это можно реализовать с помощью команды `curl -I` (отправляющей метод `HEAD` и отображающей только заголовки ответа), утилиты [httpx](https://github.com/projectdiscovery/httpx) для массового зондирования хостов в больших масштабах или команды `openssl s_client` для анализа соединений по протоколам TLS/SSL.

Например, следующая команда запрашивает исключительно заголовки ответа сервера:

```bash
curl -I https://example.org
```

Ниже представлен пример типичного ответа веб-сервера Apache:

```http
HTTP/1.1 200 OK
Date: Thu, 05 Sep 2019 17:42:39 GMT
Server: Apache/2.4.43 (Unix)
Last-Modified: Thu, 05 Sep 2026 17:40:42 GMT
ETag: "75-591d1d21b6167"
Accept-Ranges: bytes
Content-Length: 117
Connection: close
Content-Type: text/html
...
```

А вот пример ответа сервера под управлением Nginx:

```http
HTTP/1.1 200 OK
Server: nginx/1.31.5
Date: Thu, 05 Sep 2026 17:50:24 GMT
Content-Type: text/html
Content-Length: 117
Last-Modified: Thu, 05 Sep 2026 17:40:42 GMT
Connection: close
ETag: "5d71489a-75"
Accept-Ranges: bytes
...
```

А так выглядит ответ сервера lighttpd:

```http
HTTP/1.1 200 OK
Content-Type: text/html
Accept-Ranges: bytes
ETag: "4192788355"
Last-Modified: Thu, 05 Sep 2026 17:40:42 GMT
Content-Length: 117
Connection: close
Date: Thu, 05 Sep 2026 17:57:57 GMT
Server: lighttpd/1.4.85
...
```

В этих примерах тип и версия сервера раскрываются в явном виде. Однако веб-приложения с повышенными требованиями к безопасности могут маскировать сведения о сервере путем модификации заголовков. Ниже приведен фрагмент ответа с модифицированным заголовком `Server`:

```http
HTTP/1.1 200 OK
Server: Website.com
Date: Thu, 05 Sep 2019 17:57:06 GMT
Content-Type: text/html; charset=utf-8
Status: 200 OK
...
```

В ситуациях, когда заголовок `Server` скрыт или подменен, специалисты могут определить тип сервера по характерному порядку следования полей заголовков HTTP. Обратите внимание, что в приведенном выше примере Apache поля расположены в следующем порядке:

- Date
- Server
- Last-Modified
- ETag
- Accept-Ranges
- Content-Length
- Connection
- Content-Type

В то же время в ответах Nginx и сервера с замаскированным заголовком общие поля следуют в ином порядке:

- Server
- Date
- Content-Type

Тестировщик может использовать эту закономерность для выдвижения гипотезы о том, что под маской скрывается Nginx. Тем не менее, учитывая, что различные веб-серверы могут использовать аналогичный порядок полей, а промежуточные прокси способны изменять или удалять заголовки, этот метод не дает стопроцентной гарантии.

### Отправка некорректных запросов

Веб-серверы можно идентифицировать по структуре диагностических сообщений об ошибках, а в случаях отсутствия кастомизации — по стандартным шаблонам страниц ошибок по умолчанию. Один из способов спровоцировать сервер на выдачу стандартной ошибки — отправка заведомо некорректного или синтаксически нарушенного запроса.

Например, ниже представлен ответ сервера Apache на запрос с несуществующей версией протокола HTTP `SANTA CLAUS`:

```http
GET / SANTA CLAUS/1.1


HTTP/1.1 400 Bad Request
Date: Fri, 06 Sep 2019 19:21:01 GMT
Server: Apache/2.4.41 (Unix)
Content-Length: 226
Connection: close
Content-Type: text/html; charset=iso-8859-1

<!DOCTYPE HTML PUBLIC "-//IETF//DTD HTML 2.0//EN">
<html><head>
<title>400 Bad Request</title>
</head><body>
<h1>Bad Request</h1>
<p>Your browser sent a request that this server could not understand.<br />
</p>
</body></html>
```

А вот ответ сервера Nginx на аналогичный некорректный запрос:

```http
GET / SANTA CLAUS/1.1


<html>
<head><title>404 Not Found</title></head>
<body>
<center><h1>404 Not Found</h1></center>
<hr><center>nginx/1.17.3</center>
</body>
</html>
```

Ответ сервера lighttpd на тот же запрос:

```http
GET / SANTA CLAUS/1.1


HTTP/1.0 400 Bad Request
Content-Type: text/html
Content-Length: 345
Connection: close
Date: Sun, 08 Sep 2019 21:56:17 GMT
Server: lighttpd/1.4.54

<?xml version="1.0" encoding="iso-8859-1"?>
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Transitional//EN"
         "https://www.w3.org/TR/xhtml1/DTD/xhtml1-transitional.dtd">
<html xmlns="https://www.w3.org/1999/xhtml/" xml:lang="en" lang="en">
 <head>
  <title>400 Bad Request</title>
 </head>
 <body>
  <h1>400 Bad Request</h1>
 </body>
</html>
```

Поскольку стандартные страницы ошибок содержат множество характерных отличительных признаков конкретных реализаций веб-серверов, их анализ служит эффективным методом фингерпринтинга даже при скрытых полях заголовков `Server`.  
Кроме того, специализированный [справочник](https://0xdf.gitlab.io/cheatsheets/404) может оказаться весьма полезным, особенно при анализе дефолтных страниц ошибок, не содержащих прямого указания названия веб-сервера.

### Использование автоматизированных сканеров

Как отмечалось выше, функция фингерпринтинга веб-серверов обычно входит в состав автоматизированных средств сканирования. Эти инструменты способны не только отправлять запросы, аналогичные продемонстрированным выше, но и производить зондирование специфичными для конкретных платформ тестами. Автоматизированные утилиты сопоставляют ответы серверов значительно быстрее ручного тестирования и задействуют обширные сигнатурные базы данных известных ответов. По этим причинам применение автоматизированных сканеров обычно обеспечивает высокую точность распознавания.

Распространенные инструменты сканирования с функциями фингерпринтинга веб-серверов:

- [Netcraft Site Report](https://sitereport.netcraft.com/) — онлайн-сервис комплексного анализа инфраструктуры сайтов, включая детальные сведения о веб-серверах.
- [Nikto](https://github.com/sullo/nikto) — консольный сканер безопасности веб-серверов с открытым исходным кодом.
- [Nmap](https://nmap.org/) — открытая утилита сетевого сканирования с графическим интерфейсом [Zenmap](https://nmap.org/zenmap/).
- [WhatWeb](https://github.com/urbanadventurer/WhatWeb) и [httpx](https://github.com/projectdiscovery/httpx) (с флагом `-tech-detect`) — распознают ПО веб-серверов параллельно с другими веб-технологиями (см. сценарии [Fingerprint Web Application Framework](08.%20Fingerprint%20Web%20Application%20Framework.md) и [Fingerprint Web Application](09.%20Fingerprint%20Web%20Application.md) для более широкого анализа технологического стека).

## Рекомендации по устранению

Хотя открытые сведения о типе и версии веб-сервера сами по себе не являются уязвимостью, они существенно облегчают злоумышленникам эксплуатацию других дефектов системы. Раскрытие версии позволяет атакующим быстро подобрать эксплойты под конкретный релиз необновленного сервера. В связи с этим рекомендуется соблюдать меры предосторожности:

- Скрывать или маскировать сведения о веб-сервере в заголовках ответов, например, с помощью модуля Apache [mod_headers](https://httpd.apache.org/docs/current/mod/mod_headers.html).
- Использовать защищенный [обратный прокси-сервер (reverse proxy)](https://en.wikipedia.org/wiki/Proxy_server#Reverse_proxies) для создания дополнительного эшелона безопасности между веб-сервером и публичной сетью интернет.
- Обеспечивать регулярное и своевременное обновление веб-серверов актуальными патчами безопасности.
