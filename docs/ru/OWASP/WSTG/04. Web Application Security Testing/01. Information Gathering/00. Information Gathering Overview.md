# Обзор этапа сбора информации

Протестировать можно лишь то, что удалось обнаружить. Прежде чем специалист сможет оценить механизмы аутентификации, авторизации, бизнес-логику или любую другую область приложения, он обязан определить реальные границы доступного охвата: приложения, хосты, конечные точки (endpoints) и технологии, формирующие поверхность атаки (attack surface). Активы, которые не были обнаружены, никогда не будут протестированы — независимо от того, насколько скрупулезно выполнена остальная часть аудита.

Таким образом, сбор информации и разведка являются фундаментом любой оценки безопасности веб-приложений. Этот этап сочетает пассивную разведку (не взаимодействующую напрямую с целевой системой) с активным перечислением (напрямую отправляющим запросы цели), формируя максимально полную картину того, какие компоненты доступны извне, каким образом они опубликованы и какие технологии задействованы в стеке.

Современные аудиты обычно объединяют пассивное перечисление поддоменов (`subfinder`, пассивный режим Amass), зондирование активных хостов (`httpx`), анализ журналов прозрачности сертификатов (Certificate Transparency), сбор архивных URL (`gau`, `waybackurls`, `waymore`), статический анализ JavaScript (`jsluice`, LinkFinder) и прицельное обнаружение скрытого контента (`ffuf`, `feroxbuster`, Kiterunner). Наглядные примеры приведены в отдельных сценариях категории INFO и в главе [API Reconnaissance](../12.%20API%20Testing/01.%20API%20Reconnaissance.md).

Всегда строго соблюдайте установленные границы охвата (scope) проекта.
