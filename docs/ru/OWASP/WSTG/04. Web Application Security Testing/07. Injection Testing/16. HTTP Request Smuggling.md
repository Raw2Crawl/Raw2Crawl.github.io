# Контрабанда HTTP-запросов (HTTP Request Smuggling)

| ID |
| --- |
| WSTG-INJT-16 |

## Резюме

Контрабанда HTTP-запросов (HTTP Request Smuggling, HRS) — это класс уязвимостей, возникающих вследствие несогласованности разбора (парсинга) HTTP-запросов компонентами фронтенда и бэкенда. Когда промежуточные сетевые узлы, такие как обратные прокси-серверы (reverse proxies), балансировщики нагрузки или шлюзы API, интерпретируют границы запросов иначе, чем серверы бэкенда, злоумышленник получает возможность внедрить («протащить») скрытый запрос, который обрабатывается вне установленной очереди.

Современные сетевые инфраструктуры существенно расширяют поверхность атаки за счет внедрения протокола HTTP/2, понижения версии протокола (protocol downgrade: HTTP/2 → HTTP/1.1) и открытых обновлений сессий (cleartext upgrade, H2C), при которых логика нормализации и трансляции запросов часто расходится с требованиями спецификаций RFC.

Атаки типа Request Smuggling становятся возможными, когда два или более HTTP-парсера расходятся во мнении относительно того, где начинается или заканчивается запрос. Исторически наиболее распространенным сценарием было противоречие в интерпретации заголовков `Content-Length` (CL) и `Transfer-Encoding` (TE).

В современных архитектурах дополнительные векторы десинхронизации возникают вследствие:

- Трансляции запросов на границе HTTP/2 и HTTP/1.1
- Механизмов обновления соединения через открытый HTTP/2 (H2C)
- Несоответствий в алгоритмах нормализации заголовков
- Повторного появления запрещенных промежуточных заголовков при понижении версии протокола
- Повторного использования TCP-соединений (connection reuse) между разными протоколами

Подобное поведение может приводить к устойчивой десинхронизации сессий, отравлению кэша (Web Cache Poisoning), перехвату учетных данных (Credential Hijacking) и обходу механизмов контроля доступа (Access Control Bypass).

## Цели тестирования

- Идентифицировать несогласованность границ запросов между компонентами фронтенда и бэкенда.
- Выявить классические уязвимости десинхронизации CL/TE.
- Оценить логику трансляции протоколов (HTTP/2 → HTTP/1.1).
- Проверить безопасность обработки обновлений H2C и механизмов понижения протокола.
- Подтвердить возможность отравления очереди запросов (request queue poisoning) на стороне бэкенда.

## Методика тестирования

### Тестирование методом «черного ящика»

#### Рассинхронизация CL.TE

В сценарии CL.TE фронтенд определяет размер тела запроса на основе заголовка `Content-Length`, тогда как сервер бэкенда ориентируется на заголовок `Transfer-Encoding`.

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 35
Transfer-Encoding: chunked

0

GET /404 HTTP/1.1
Foo: x
```

Ожидаемый результат:

- Бэкенд прекращает обработку тела запроса на чанке нулевой длины `0`
- Внедренный запрос остается в буфере соединения
- Последующий легитимный запрос пользователя повреждается или возвращает непредусмотренный ответ (например, 404 Not Found)

#### Рассинхронизация TE.CL

В сценарии TE.CL фронтенд корректно обрабатывает чанковое кодирование (chunked encoding), тогда как бэкенд полагается на значение `Content-Length`.

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 4
Transfer-Encoding: chunked

5c
GET /admin HTTP/1.1
Content-Length: 0

0
```

Ожидаемый результат:

- Бэкенд преждевременно завершает чтение первого запроса
- Оставшаяся в потоке полезная нагрузка интерпретируется как начало нового самостоятельного запроса
- Возникает несанкционированный доступ к защищенному эндпоинту или отравление очереди запросов

#### TE.TE (обфусцированный заголовок Transfer-Encoding)

Если оба сервера поддерживают `Transfer-Encoding`, обфускация заголовка может вынудить один из парсеров проигнорировать его, переключившись на `Content-Length`.

Распространенные техники включают:

- Манипуляции с пробельными символами и табуляцией
- Дублирование заголовков
- Использование нестандартных разделителей

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 44
Transfer-Encoding:\tchunked
Transfer-Encoding: identity

0

GET /404 HTTP/1.1
Foo: bar
```

### Современные векторы атак

#### Десинхронизация при переходе с HTTP/2 на HTTP/1.1

Во многих инфраструктурах клиенты взаимодействуют с граничными прокси (edge servers) по протоколу HTTP/2, тогда как внутренние сервисы бэкенда продолжают работать по протоколу HTTP/1.1. В процессе трансляции протокола промежуточный узел должен преобразовать бинарные фреймы HTTP/2 в текстовый формат HTTP/1.1.

Типовые точки отказа включают:

- Некорректный перерасчет заголовка `Content-Length`
- Повторное внедрение промежуточных заголовков перехода (hop-by-hop headers)
- Слияние нескольких логических запросов в один запрос к бэкенду

> Примечание: само по себе понижение версии протокола HTTP/2 не является уязвимостью.  
> Эксплуатация становится возможной, когда в процессе трансляции реконструируется запрос HTTP/1.1, нарушающий предположения парсера бэкенда, что приводит к десинхронизации границ запросов.

Подход к тестированию:

- Отправка нескольких фреймов HTTP/2 DATA с противоречивой семантикой длины
- Анализ поведения бэкенда по временным задержкам или разделению ответов
- Мониторинг признаков отравления очереди запросов

##### Пример: контрабанда запросов при понижении версии HTTP/2 через реконструкцию запроса

В данном сценарии клиент отправляет запросы на фронтенд по протоколу HTTP/2, тогда как бэкенд поддерживает только HTTP/1.1. Промежуточный прокси реконструирует запрос HTTP/1.1 из нескольких фреймов HTTP/2 DATA.

**HTTP/2 (концептуальное представление):**

- DATA frame 1:

```http
0\r\n\r\n
```

- DATA frame 2:

```http
GET /admin HTTP/1.1
Host: internal
```

**Реконструированный запрос HTTP/1.1 (восприятие бэкенда):**

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 0

GET /admin HTTP/1.1
Host: internal
```

Если фронтенд считает запрос полностью переданным, а бэкенд продолжает парсить данные из входящего буфера, второй запрос выполнится вне очереди, приводя к успешной контрабанде запроса.

> Неявное понижение протокола (Implicit Downgrades):  
> Даже в отсутствие явного механизма `Upgrade: h2c` многие CDN и обратные прокси скрытно понижают клиентские соединения HTTP/2 до HTTP/1.1 при проксировании на внутренние бэкенды.  
> Такие неявные понижения расширяют поверхность атак request smuggling, особенно в комбинации с повторным использованием соединений и недостаточной нормализацией запросов.

#### Контрабанда запросов H2C (обновление до открытого HTTP/2)

H2C позволяет переключить незашифрованное соединение HTTP/1.1 на протокол HTTP/2 с помощью механизма `Upgrade: h2c`.  
В отличие от трансляции протоколов, H2C-контрабанда возникает при динамическом переходе на другой протокол внутри одного соединения: компоненты фронтенда и бэкенда могут временно разойтись в оценке активного состояния парсера, оставляя остаточные байты в буфере бэкенда.

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Connection: Upgrade, HTTP2-Settings
Upgrade: h2c
HTTP2-Settings: AAMAAABkAARAAAAAAAIAAAAA

0

GET /admin HTTP/1.1
Host: internal
```

Факторы риска:

- Неполное согласование перехода на протокол
- Продолжение парсинга бэкендом в режиме HTTP/1.1
- Обработка контрабандного запроса после завершения процедуры Upgrade

#### Отравление очереди запросов (Request Queue Poisoning) через понижение версии протокола

Некоторые прокси понижают запросы HTTP/2 до HTTP/1.1, но не выполняют должную санитизацию:

- Значений `Content-Length`
- Дублирующихся заголовков
- Некорректного порядка псевдозаголовков (pseudo-headers)

Атакующие могут использовать это для отравления постоянных пулов соединений к бэкенду, что затронет сессии множества независимых пользователей.

### Признаки уязвимости

- Различные ответы на серию идентичных запросов
- Неожиданные коды ответов 404 Not Found или 400 Bad Request
- Задержки ответов или смещение их очередности
- Утечка ответов других пользователей в чужие сессии

## Рекомендации по устранению

- Обеспечить строгое соблюдение спецификаций RFC при разборе HTTP-запросов
- Унифицировать правила нормализации запросов на всех промежуточных прокси
- Отключить поддержку незашифрованного H2C там, где она не требуется
- Исключить понижение версии протокола для недоверенных соединений
- Принудительно разрывать и повторно валидировать соединения к бэкенду при любых ошибках парсинга
