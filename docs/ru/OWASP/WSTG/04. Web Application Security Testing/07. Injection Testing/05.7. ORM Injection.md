# Инъекция ORM

## Резюме

[Внедрение через объектно-реляционное отображение (Object Relational Mapping (ORM) Injection)](https://capec.mitre.org/data/definitions/109.html) представляет собой атаку класса SQL Injection, направленную против объектной модели доступа к данным, созданной ORM. С точки зрения тестировщика эта атака практически идентична классической SQL-инъекции. Однако уязвимость внедрения локализуется в коде, генерируемом уровнем ORM.

Преимущества использования ORM-инструментов включают быструю генерацию объектного слоя для взаимодействия с реляционной базой данных, стандартизацию шаблонов кода для этих объектов, а также то, что они обычно предоставляют набор безопасных функций для защиты от атак SQL Injection. Объекты, сгенерированные ORM, могут использовать SQL (или в некоторых случаях диалекты SQL) для выполнения CRUD-операций (Create, Read, Update, Delete) в базе данных. Тем не менее веб-приложение, использующее созданные ORM объекты, может быть уязвимо к атакам SQL Injection, если методы принимают неочищенные входные параметры.

## Методика тестирования

Уровни ORM могут быть подвержены уязвимостям, поскольку они расширяют поверхность атаки. Вместо прямой отправки SQL-запросов к приложению тестирование фокусируется на эксплуатации недостатков уровня ORM для передачи вредоносных SQL-запросов.

### Определение уровня ORM

Для эффективного тестирования и понимания того, что происходит между вашими запросами и бэкенд-запросами к БД, как и при любом качественном тестировании, важно определить используемую технологию. Следуя инструкциям главы [Сбор информации](../01.%20Information%20Gathering/index.md), вы должны установить технологический стек приложения. Ознакомьтесь с этим [списком соответствия языков программирования и их ORM](https://en.wikipedia.org/wiki/List_of_object-relational_mapping_software).

### Злоупотребление уровнем ORM

Определив потенциально используемую ORM, необходимо понять принцип работы ее парсера и изучить методы его эксплуатации либо, если приложение использует устаревшую версию, найти CVE, относящиеся к данной библиотеке. Иногда уровни ORM реализованы некорректно, что позволяет тестировщику проводить стандартную [SQL-инъекцию](05.%20SQL%20Injection.md), не заботясь о наличии ORM.

#### Слабая реализация ORM

Сценарий уязвимости при некорректной реализации уровня ORM, взятый из материалов [SANS](https://web.archive.org/web/20191122124952/https://software-security.sans.org/developer-how-to/fix-sql-injection-in-java-hibernate):

```java
List results = session.createQuery("from Orders as orders where orders.id = " + currentOrder.getId()).list();
List results = session.createSQLQuery("Select * from Books where author = " + book.getAuthor()).list();
```

В приведенном коде не были реализованы позиционные параметры, позволяющие разработчику заменить входные данные знаком `?`. Пример безопасной реализации:

```java
Query hqlQuery = session.createQuery("from Orders as orders where orders.id = ?");
List results = hqlQuery.setString(0, "123-ADB-567-QTWYTFDL").list(); // 0 is the first position, where it is dynamically replaced by the string set
```

Такая реализация возлагает валидацию и санитизацию на сам уровень ORM, и единственным способом ее обхода становится выявление уязвимостей в самом слое ORM.

#### Уязвимый уровень ORM

Уровни ORM представляют собой программный код — чаще всего сторонние библиотеки. Они могут содержать уязвимости точно так же, как и любой другой код. Одним из примеров является [npm-библиотека Sequelize ORM](https://snyk.io/blog/sequelize-orm-npm-library-found-vulnerable-to-sql-injection-attacks/), в которой уязвимость была найдена в 2019 году. В другом исследовании компании [RIPS Tech](https://www.ripstech.com/) были обнаружены способы обхода в [библиотеке Hibernate ORM для Java](https://hibernate.org/orm/).

На основе их [статьи в блоге](https://www.sonarsource.com/blog/exploiting-hibernate-injections/) шпаргалку для выявления подобных проблем можно представить следующим образом:

| DBMS       | SQL Injection                                                         |
|------------|-----------------------------------------------------------------------|
| MySQL      | `abc\' INTO OUTFILE --`                                               |
<!-- markdownlint-disable-next-line MD055 MD056 -->
| PostgreSQL | `$$='$$=chr(61) || chr(0x27) and 1=pg_sleep(2) || version()'`         |
| Oracle     | `NVL(TO_CHAR(DBMS_XMLGEN.getxml('select 1 where 1337>1')),'1')!='1'`  |
| MS SQL     | `1<LEN(%C2%A0(select%C2%A0top%C2%A01%C2%A0name%C2%A0from%C2%A0users)` |

Другим примером является компонент [Laravel Query Builder](https://laravel.com/docs/queries), в котором уязвимость была обнаружена [в 2019 году](https://freek.dev/1317-an-important-security-release-for-laravel-query-builder).
