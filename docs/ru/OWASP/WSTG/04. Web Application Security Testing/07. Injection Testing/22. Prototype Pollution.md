# Загрязнение прототипа (Prototype Pollution)

| ID |
| --- |
| WSTG-INJT-22 |

## Резюме

JavaScript является языком с прототипным наследованием. Практически каждый объект наследует свойства от `Object.prototype`, и любое свойство, не найденное непосредственно в самом объекте, ищется вверх по цепочке прототипов (prototype chain). Загрязнение прототипа (Prototype Pollution) возникает в тех случаях, когда приложение использует контролируемый пользователем ввод для установки *ключей* объекта во время рекурсивного слияния (merge), клонирования или присваивания по динамическому пути, позволяя атакующему добраться до `Object.prototype` через специальные служебные ключи, такие как `__proto__`, `constructor` или `prototype`. Поскольку базовый прототип разделяется всеми объектами в среде выполнения, внедренное свойство скрытно становится видимым для всех несвязанных компонентов приложения.

> Примечание: данная уязвимость не имеет отношения к [загрязнению параметров HTTP (HTTP Parameter Pollution)](04.%20HTTP%20Parameter%20Pollution.md); несмотря на схожесть названий, это принципиально разные классы дефектов.

Само по себе загрязнение прототипа редко наносит прямой ущерб. Его влияние зависит от наличия *гаджета* (gadget) — существующего участка кода приложения, который впоследствии считывает внедренное свойство и использует его в критической операции. Первопричина уязвимости одинакова, но проявляется в двух различных контекстах:

- **На стороне сервера (Node.js)**: в зависимости от доступных гаджетов последствия варьируются от отказа в обслуживании (Denial of Service, DoS) и обхода проверок безопасности до удаленного выполнения кода (Remote Code Execution, RCE). Известным примером RCE является уязвимость в Kibana ([CVE-2019-7609](https://nvd.nist.gov/vuln/detail/CVE-2019-7609)).
- **На стороне клиента (в браузере)**: в сочетании с подходящим гаджетом уязвимость обычно приводит к межсайтовому скриптингу на основе DOM ([DOM-based Cross-Site Scripting, DOM XSS](01.%20Reflected%20Cross%20Site%20Scripting.md)) и позволяет обходить клиентские механизмы защиты.

## Цели тестирования

- Идентифицировать функции и библиотеки, выполняющие рекурсивное слияние, клонирование или присваивание контролируемых пользователем свойств.
- Определить, способен ли пользовательский ввод достигать и модифицировать `Object.prototype`.
- Найти гаджеты, позволяющие превратить загрязнение прототипа в конкретный вектор атаки.

## Методика тестирования

Следующий пример иллюстрирует первопричину уязвимости. Простая рекурсивная функция слияния копирует все ключи переданного пользователем объекта в целевой объект:

```javascript
function merge(target, source) {
    for (const key in source) {
        if (typeof source[key] === "object" && typeof target[key] === "object") {
            merge(target[key], source[key]);
        } else {
            target[key] = source[key];
        }
    }
    return target;
}
```

Если источник десериализуется из пользовательского ввода вида `{"__proto__": {"polluted": "yes"}}`, операция присваивания переходит по ссылке `__proto__` и осуществляет запись в `Object.prototype`. После этого каждый вновь создаваемый объект в среде выполнения наследует внедренное свойство:

```javascript
merge({}, JSON.parse('{"__proto__": {"polluted": "yes"}}'));
({}).polluted;   // "yes"  -> Object.prototype был загрязнен
```

### Тестирование методом «черного ящика»

#### Определение источников

Загрязнение прототипа достижимо через любые входные точки, чьи ключи используются в качестве имен свойств объектов. Проверьте приложение на наличие следующих источников:

- Параметры строки запроса URL и фрагмент URL (хэш), использующие нотацию квадратных скобок или точек, например `?__proto__[key]=value` или `?__proto__.key=value`.
- Тела JSON-запросов, которые десериализуются, а затем объединяются или клонируются (часто встречаются в эндпоинтах настроек, профилей или конфигураций).
- Другие структурированные входные данные, парсируемые во вложенные объекты, такие как данные форм или cookie.

#### Загрязнение прототипа на стороне клиента

Отправьте тестовую нагрузку, пытающуюся установить уникальное свойство в прототипе через проверяемый источник. Приведенные ниже два формата отражают одну и ту же цель:

```text
https://example.com/#__proto__[testpolluted]=reflected
https://example.com/#constructor[prototype][testpolluted]=reflected
```

Затем в консоли разработчика браузера проверьте, попало ли свойство в глобальный прототип, попытавшись прочитать его из нового пустого объекта:

```javascript
({}).testpolluted;
// "reflected" -> Object.prototype загрязнен через этот источник
// undefined   -> прототип не загрязнен
```

Если значение возвращается, источник уязвим. Следующим шагом является поиск гаджета, превращающего загрязненное свойство в DOM XSS (например, свойства, которое библиотека считывает при формировании HTML-разметки или настройке логики скриптов). Использование специализированных расширений для поиска источников и гаджетов (таких как DOM Invader) значительно ускоряет данный процесс.

#### Серверное загрязнение прототипа (Server-Side Prototype Pollution)

При тестировании бэкенда тестировщик не может напрямую прочитать свойства прототипа через консоль, поэтому обнаружение строится косвенным путем: загрязняется определенное свойство и отслеживаются изменения во внешнем поведении сервера. Отправьте тело JSON-запроса, в котором специальный ключ вложен в обычный объект, ориентируясь на эндпоинты, выполняющие слияние или клонирование данных:

```http
POST /api/update HTTP/1.1
Host: example.com
Content-Type: application/json

{"name":"test","__proto__":{"json spaces":10}}
```

Надежным и неразрушающим индикатором для приложений на базе Express является загрязнение свойства `json spaces`: если последующий ответ приложения в формате JSON возвращается с форматированием (отступами), хотя ранее отдавался в одну строку, значит сервер прочитал настройку форматирования из загрязненного прототипа, подтверждая наличие уязвимости. Другие поведенческие маркеры:

- Появление в последующих JSON-ответах свойства, которое клиент никогда не передавал.
- Изменение HTTP-кода состояния, заголовков или механизма согласования контента после загрязнения свойства, считываемого фреймворком.
- Характерные сообщения об ошибках или сбои парсинга входных данных, ранее принимавшихся сервером.

#### Оценка последствий

Поскольку последствия зависят от наличия подходящих гаджетов, оцените реальный ущерб для каждого подтвержденного факта загрязнения. На стороне клиента это чаще всего DOM XSS или обход механизмов защиты. На стороне сервера известные цепочки гаджетов приводили к отказу в обслуживании, обходу аутентификации или авторизации и удаленному выполнению команд. Любой подтвержденный факт Prototype Pollution следует считать дефектом высокой критичности до тех пор, пока анализ гаджетов полностью не исключит возможность эксплуатации.

### Тестирование методом «серого ящика»

При наличии доступа к исходному коду эффективнее искать уязвимые шаблоны напрямую, а не через слепой перебор.

Ищите функции рекурсивного слияния, клонирования, расширения (`extend`) или глубокого присваивания, как самописные, так и входящие в состав сторонних библиотек. Функции, выполняющие обход вложенных путей ключей с присваиванием в объект, выступают основными приемниками (sinks). Стандартный поиск нацелен на вспомогательные функции `merge` и `assign`, утилиты глубокого клонирования (`deep-clone`) и динамический доступ к свойствам по пользовательскому пути.

Для каждого потенциального приемника убедитесь, валидируются ли ключи перед операцией присваивания. Безопасный код отклоняет или пропускает ключи `__proto__`, `constructor` и `prototype`, либо оперирует объектами без прототипа:

```javascript
// Vulnerable: слепое присваивание по вложенному пути ключей
target[key] = source[key];

// Safer: отклонение опасных системных ключей
if (key === "__proto__" || key === "constructor" || key === "prototype") {
    continue;
}
```

Также проверьте версии сторонних зависимостей на предмет известных бюллетеней безопасности, так как многие популярные утилиты со временем выпустили патчи от Prototype Pollution. При наличии исходного кода легко проследить путь пользовательских данных от парсера запроса до уязвимых приемников, подтвердить достижимость точек входа и обнаружить рабочие гаджеты.

## Рекомендации по устранению

- Выполняйте санитизацию ключей свойств перед присваиванием, явно блокируя `__proto__`, `constructor` и `prototype`.
- Используйте объекты без прототипа для ассоциативных массивов (словарей), например создавая их через `Object.create(null)`, либо применяйте встроенную коллекцию `Map` вместо обычных объектов.
- Замораживайте базовый прототип с помощью `Object.freeze(Object.prototype)`, если это не нарушает логику работы сторонних библиотек.
- Валидируйте входящие структурированные данные по строгой схеме (например, JSON Schema), отбрасывая любые непредусмотренные ключи.
- Используйте актуальные и поддерживаемые библиотеки для слияния и клонирования объектов, своевременно обновляя все зависимости.
- В среде Node.js запуск с флагом `--disable-proto=delete` отключает аксессор `__proto__` в рамках эшелонированной защиты.
