# Загрузка вредоносных файлов

| ID |
| --- |
| WSTG-BUSL-09 |

## Резюме

Бизнес-процессы многих приложений позволяют пользователям загружать файлы данных. Хотя принципы валидации текстовых полей ввода широко известны, ее реализация для загружаемых файлов значительно сложнее. Многие ресурсы внедряют простейшие ограничения, основанные на списке разрешенных (или заблокированных) расширений файлов, однако этого недостаточно для предотвращения загрузки легитимных типов файлов, содержащих вредоносный контент.

Уязвимости, связанные с загрузкой вредоносных файлов, специфичны тем, что подобные «вредоносные» файлы можно легко отклонить при наличии в бизнес-логике механизма антивирусного сканирования файлов непосредственно в процессе загрузки. Кроме того, это отличается от загрузки непредусмотренных файлов тем, что тип файла может быть разрешенным, но сам файл несет прямую угрозу безопасности системы.

Наконец, понятие «вредоносный» различается в зависимости от архитектуры: например, файлы, эксплуатирующие уязвимости Microsoft SQL Server, могут быть абсолютно безопасными в инфраструктуре, использующей хранилище данных NoSQL.

Приложение может допускать загрузку файлов, содержащих эксплойты или шеллкоды, без их проверки на вредоносность. Вредоносные файлы могут детектироваться и блокироваться на различных эшелонах архитектуры: системами обнаружения и предотвращения вторжений (Intrusion Detection/Prevention System, IDS/IPS), антивирусным ПО на сервере приложений или встроенным сканированием файлов при загрузке (например, с делегированием проверок по протоколу SCAP).

### Пример

Типичным примером этой уязвимости являются блоги или форумы, позволяющие пользователям загружать изображения и другие мультимедиа-файлы. Хотя эти форматы считаются безопасными, возможность загрузки исполняемого кода (например, PHP-скрипта) позволит злоумышленнику выполнять команды операционной системы, читать и изменять файлы на сервере, получать доступ к базе данных и полностью скомпрометировать сервер.

## Цели тестирования

- Определить наличие функциональности загрузки файлов.
- Изучить проектную документацию, чтобы выяснить, какие типы файлов считаются допустимыми, а какие — опасными или вредоносными.
    - При отсутствии документации определить допустимые форматы исходя из бизнес-назначения приложения.
- Определить механизм обработки загруженных файлов.
- Получить или сгенерировать набор тестовых вредоносных файлов.
- Попытаться загрузить вредоносные файлы в приложение и проверить, принимаются ли они и выполняются ли системой.

## Методика тестирования

### Вредоносные типы файлов

Самая базовая проверка, которую выполняет приложение, заключается в контроле того, что загружаются файлы только доверенных типов.

#### Веб-шеллы (Web Shells)

Если сервер сконфигурирован на выполнение серверного кода, получение удаленного выполнения команд на сервере возможно путем загрузки файла веб-шелла (web shell), позволяющего исполнять произвольный код или команды операционной системы. Для успешной атаки файл должен быть загружен в корень веб-директории (webroot), а сервер должен быть настроен на выполнение скриптов данного типа.

Размещение подобного веб-шелла на сервере, доступном из Интернета, крайне опасно, поскольку любой, кто знает (или подберет) путь к шеллу, сможет выполнять команды на сервере. Для защиты веб-шелла от несанкционированного доступа используются следующие приемы:

- Загрузка шелла со случайно сгенерированным именем.
- Защита веб-шелла паролем.
- Ограничение доступа к шеллу по IP-адресу.

**Обязательно удаляйте веб-шеллы по завершении тестирования.**

Ниже приведен пример простого шелла на PHP, выполняющего команды операционной системы из GET-параметра и доступного только с определенного IP-адреса:

```php
<?php
    if ($_SERVER['REMOTE_HOST'] === "FIXME") { // Укажите ваш IP-адрес здесь
        if(isset($_REQUEST['cmd'])){
            $cmd = ($_REQUEST['cmd']);
            echo "<pre>\n";
            system($cmd);
            echo "</pre>";
        }
    }
?>
```

После загрузки шелла (под случайным именем) вы можете выполнять команды операционной системы, передавая их в GET-параметре `cmd`:

`https://example.org/7sna8uuorvcx3x4fx.php?cmd=cat+/etc/passwd`

#### Обход фильтров

Первый шаг — определить, какие файлы фильтры пропускают или блокируют, и где именно они реализованы. Если ограничения наложены на стороне клиента средствами JavaScript, их можно тривиально обойти с помощью перехватывающего прокси-сервера.

Если фильтрация осуществляется на стороне сервера, для ее обхода (filter evasion) можно применить различные техники:

- Изменить значение заголовка `Content-Type` на `image/jpeg` в HTTP-запросе.
- Заменить расширение на менее распространенное исполняемое: `file.php5`, `file.shtml`, `file.asa`, `file.jsp`, `file.jspx`, `file.aspx`, `file.asp`, `file.phtml`, `file.cshtml`.
- Использовать двойные расширения, такие как `file.jpg.php` или `file.png.php`. Для успеха атаки необходимо понимать, как веб-сервер обрабатывает файлы с составными расширениями. В некоторых случаях сервер проверяет лишь вхождение `.jpg` или `.png` в строку имени файла, что позволяет обойти фильтрацию расширений.
- Изменить сигнатуру файла ([file signature](https://en.wikipedia.org/wiki/List_of_file_signatures)) или начальные сигнатурные байты (magic bytes) загружаемого файла.
- Использовать различный регистр символов в расширении: `file.PhP` или `file.AspX`.
- Если запрос содержит несколько имен файлов, задать им разные значения.
- Использовать спецсимволы в конце имени: пробелы, точки или null-байты (`file.asp...`, `file.php;jpg`, `file.asp%00.jpg`, `1.jpg%00.php`).
- В некорректно настроенных версиях Nginx загрузка файла вида `test.jpg/x.php` может привести к его выполнению как `x.php`.
- Загрузить файл `.htaccess` со следующим содержимым: `AddType application/x-httpd-php .png`. Это заставит Apache интерпретировать изображения `.png` как исполняемые PHP-скрипты.
- На серверах IIS загрузить файл `web.config`. Размещение `web.config` в директории может изменить правила обработки файлов сервером, например добавить маппинг обработчика, выполняющий разрешенное расширение как серверный код.
- На PHP-серверах с CGI или FastCGI (например, PHP-FPM) загрузить файл `.user.ini`, содержащий директиву `auto_prepend_file=image.png`. Если каталог содержит любой скрипт PHP, загруженное изображение будет подключено и выполнено до старта этого скрипта.
- Внедрить код в метаданные файла, чтобы он успешно проходил валидацию содержимого. Например, команда `exiftool -Comment='<?php phpinfo(); ?>' image.jpg` добавляет безопасный PHP-пейлоад в валидное изображение JPEG. Код выполнится, если сервер в дальнейшем обработает файл как код (например, через изменение конфигурации или уязвимость [внедрения файлов (File Inclusion)](../07.%20Injection%20Testing/11.1.%20File%20Inclusion.md)).

В ряде ситуаций для успешного обхода серверных фильтров может потребоваться комбинирование нескольких перечисленных техник.

### Вредоносное содержимое файлов

После проверки типа файла критически важно убедиться в безопасности его содержимого. Сделать это значительно сложнее, поскольку необходимые меры зависят от конкретного формата разрешенных файлов.

#### Вредоносное ПО

Приложения должны проверять загружаемые файлы с помощью антивирусного программного обеспечения. Простейший способ проверки эффективности сканирования — использование тестового файла [EICAR](https://www.eicar.org/download-anti-malware-testfile/), представляющего собой безопасный файл, на который реагируют все антивирусные сканеры.

В зависимости от профиля приложения может потребоваться тестирование других опасных форматов, например документов Microsoft Office, содержащих вредоносные макросы. Такие инструменты, как [Metasploit Framework](https://github.com/rapid7/metasploit-framework) и [Social Engineer Toolkit (SET)](https://github.com/trustedsec/social-engineer-toolkit), позволяют генерировать вредоносные файлы различных форматов.

При загрузке тестового вредоносного файла он должен быть обнаружен и помещен в карантин либо удален приложением. В зависимости от внутренней архитектуры обработки файлов реакция приложения может быть незаметна внешнему пользователю.

#### Обход каталогов при распаковке архивов

Если приложение производит распаковку архивов (например, ZIP), существует риск записи файлов в непредусмотренные каталоги через обход каталога (directory traversal). Это эксплуатируется путем загрузки специально сформированного архива ZIP, содержащего пути с последовательностями вида `..\..\..\..\shell.php`. Данная техника детально описана в [исследовании Snyk о Zip Slip](https://security.snyk.io/research/zip-slip-vulnerability).

Тестирование на уязвимость выхода за пределы каталога при распаковке архива (Archive Directory Traversal) состоит из двух частей:

1. Подготовка вредоносного архива, файлы которого при распаковке выходят за пределы целевой директории. Вредоносный архив должен содержать два файла: базовый файл (`base`), распаковываемый в целевую директорию, и файл выхода (`traversed`), пытающийся подняться вверх по дереву каталогов до корневого раздела, создавая файл в каталоге `/tmp`. Вредоносный путь содержит множество уровней `../` (например, `../../../../../../../../tmp/traversed`), гарантирующих достижение корня файловой системы. При успехе атаки тестировщик обнаружит файл `/tmp/traversed`, созданный на веб-сервере в результате атаки ZIP Slip.
2. Логика распаковки сжатых файлов, реализованная собственным кодом или сторонней библиотекой. Уязвимости распаковки архивов возникают тогда, когда функция декомпрессии не валидирует пути к файлам внутри архива. Ниже показан пример уязвимой реализации на Java:

```java
Enumeration<ZipEntry> entries =​ ​zip​.g​etEntries();

while(entries​.h​asMoreElements()){
    ZipEntry e ​= ​entries.nextElement();
    File f = new File(destinationDir, e.getName());
    InputStream input = zip​.g​etInputStream(e);
    IOUtils​.c​opy(input, write(f));
}
```

Следуйте инструкциям ниже для создания ZIP-файла, способного проэксплуатировать уязвимый код выше при загрузке на веб-сервер:

```bash
# Откройте новый терминал и создайте древовидную структуру
# (в зависимости от целевой системы может потребоваться больше уровней вложенности)
mkdir -p a/b/c
# Создайте базовый файл
echo 'base' > a/b/c/base
# Создайте файл с выходом из каталога
echo 'traversed' > traversed
# На этом этапе можно проверить структуру каталогов с помощью утилиты `tree`
# Перейдите в каталог a/b/c
cd a/b/c
# Запакуйте файлы в архив
zip test.zip base ../../../traversed
# Проверьте содержимое архива
unzip -l test.zip
```

#### Атаки с использованием символических ссылок в архивах

Если приложение распаковывает архивные файлы (такие как ZIP или TAR), важно проверить порядок обработки символических ссылок (symlinks), находящихся внутри архива. В отличие от атак Archive Directory Traversal (ZIP Slip), данная техника не требует использования последовательностей обхода путей `../`.

Злоумышленник может сформировать архив, содержащий символическую ссылку, указывающую на конфиденциальный файл операционной системы сервера (например, `/etc/passwd`). Если процесс распаковки сохраняет символические ссылки без валидации, а приложение в дальнейшем обрабатывает или предоставляет доступ к распакованным файлам, это может привести к несанкционированному доступу к критическим файлам системы.

Например, вредоносный архив может содержать запись: `link.txt -> /etc/passwd`.

Если бэкенд распаковывает архив без валидации или отклонения символических ссылок, а приложение читает `link.txt`, оно непреднамеренно раскроет содержимое файла `/etc/passwd`.

##### Методика тестирования

1. Создайте символическую ссылку: `ln -s /etc/passwd link.txt`
1. Создайте архив: `tar -czf malicious.tar.gz link.txt`
1. Загрузите архив в приложение.
1. Проверьте:
   - Распакована ли символическая ссылка?
   - Переходит ли приложение по ссылке?
   - Доступно ли содержимое конфиденциального файла?

##### Последствия

- Чтение произвольных файлов (Arbitrary file read).
- Раскрытие конфиденциальной информации.

#### ZIP-бомбы

[ZIP-бомба](https://en.wikipedia.org/wiki/zip_bomb) (в более широком смысле — декомпрессионная бомба) — это архивный файл, содержащий огромный объем несжатых данных при компактном исходном размере. Она предназначена для вызова отказа в обслуживании (Denial of Service, DoS) за счет исчерпания дискового пространства или оперативной памяти целевой системы при попытке распаковать архив. Хотя формат ZIP является наиболее частым примером, уязвимы и другие форматы сжатия, включая gzip (часто используемый для сжатия сетевого трафика).

В простейшем варианте ZIP-бомбу можно создать путем сжатия большого файла, состоящего из одного повторяющегося символа. Следующий пример демонстрирует создание файла размером 1 МБ, который при распаковке разворачивается в 1 ГБ:

```bash
dd if=/dev/zero bs=1M count=1024 | zip -9 > bomb.zip
```

Существует ряд методов для достижения гораздо более высоких коэффициентов сжатия, включая многоуровневое сжатие, [эксплуатацию особенностей спецификации формата ZIP](https://www.bamsoftware.com/hacks/zipbomb/) и архивы-квайны ([quines](https://research.swtch.com/zip)) — архивы, содержащие копию самих себя и порождающие бесконечную рекурсию.

Успешная атака с применением ZIP-бомбы приведет к отказу в обслуживании системы, а также к существенному росту финансовых затрат при использовании облачных платформ с автоматическим масштабированием. **Никогда не проводите подобные атаки без предварительного анализа рисков и наличия официального письменного разрешения заказчика.**

#### XML-файлы

Файлы XML подвержены ряду потенциальных уязвимостей, таких как внедрение внешних сущностей XML (XML External Entity, XXE) и атаки типа «отказ в обслуживании», например атака [«миллиард смешков» (billion laughs attack)](https://en.wikipedia.org/wiki/Billion_laughs_attack).

Эти вопросы подробно рассмотрены в руководстве [XML Injection](../07.%20Injection%20Testing/07.%20XML%20Injection.md).

#### Другие форматы файлов

Многие другие форматы файлов также имеют специфические риски безопасности, которые необходимо учитывать:

- Графические файлы должны проверяться на максимально допустимое разрешение в пикселях и размер кадра.
- Изображения SVG представляют собой XML-документы и могут содержать исполняемый код JavaScript. Скрипты не выполняются, если SVG отображается через HTML-тег `<img>` или в качестве фона CSS, однако они выполняются при прямом открытии файла в браузере или при встраивании документа через `<object>`, `<embed>` или `<iframe>`. Если приложение отдает загруженные SVG-файлы со своего собственного домена (origin) с заголовком `Content-Type: image/svg+xml`, откройте прямой URL загруженного файла для проверки на хранимый XSS (Stored XSS). Кроме того, SVG-файлы могут использоваться для проведения XXE-атак, если сервер выполняет их XML-парсинг.
- Файлы HTML и XHTML аналогичным образом могут приводить к хранимому XSS, если они отдаются напрямую с домена приложения. См. раздел [Upload of Unexpected File Types](08.%20Upload%20of%20Unexpected%20File%20Types.md).
- Полиглот-файлы (Polyglot files) валидны сразу в нескольких различных форматах, например изображение формата GIF, одновременно являющееся валидным кодом JavaScript. Браузеры отклоняют выполнение скрипта, если он передан с графическим MIME-типом (например, `image/gif`), поэтому атака срабатывает только в случае, если сервер возвращает загруженный файл с типом, допустимым для скриптов (при наличии заголовка `X-Content-Type-Options: nosniff` — с MIME-типом JavaScript), и в приложении существует отдельная точка инъекции, позволяющая подключить файл через тег `<script>`. При соблюдении обоих условий полиглот способен обойти политику защиты контента (Content Security Policy, CSP), разрешающую исполнение скриптов с собственного домена приложения.
- Файлы формата CSV могут допускать проведение атак внедрения формул ([CSV injection](https://owasp.org/www-community/attacks/CSV_Injection)).
- Документы Office могут содержать вредоносные макросы или код PowerShell.
- Документы PDF могут содержать вредоносный JavaScript.

Разрешенные форматы файлов должны быть тщательно проанализированы на наличие потенциально опасной функциональности, а в процессе тестирования необходимо предпринимать попытки ее практической эксплуатации.

### Анализ исходного кода

При аудите исходного кода приложений с функциональностью загрузки файлов часто встречаются следующие методы и функции API:

- Java: `new file`, `import`, `upload`, `getFileName`, `Download`, `getOutputString`
- C/C++: `open`, `fopen`
- PHP: `move_uploaded_file()`, `Readfile`, `file_put_contents()`, `file()`, `parse_ini_file()`, `copy()`, `fopen()`, `include()`, `require()`

## Рекомендации по устранению

Обеспечение комплексной защиты от загрузки вредоносных файлов — нетривиальная инженерная задача. Необходимые защитные меры зависят от форматов загружаемых файлов, а также от способов их обработки и парсинга на сервере. Детальные рекомендации представлены в [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).
