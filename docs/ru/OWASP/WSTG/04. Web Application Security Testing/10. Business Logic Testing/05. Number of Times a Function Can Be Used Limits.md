# Ограничения на количество использований функции

| ID |
| --- |
| WSTG-BUSL-05 |

## Резюме

Многие задачи, решаемые приложениями, требуют ограничений на количество вызовов функции или выполнения действия. Приложения должны быть достаточно защищены, чтобы не позволять пользователю превышать лимит использования этих функций, поскольку во многих случаях каждый вызов приносит пользователю определенную выгоду, которая должна быть учтена для защиты интересов владельца сервиса. Например: интернет-магазин может разрешать применять скидку только один раз за транзакцию, а сервис с подписочной моделью — скачивать не более трех полных документов в месяц.

Уязвимости, связанные с тестированием лимитов использования функций, специфичны для каждого конкретного приложения. Сценарии неправомерного использования (misuse cases) должны быть направлены на многократный вызов компонентов, функций или действий приложения сверх допустимого лимита.

Злоумышленники могут обойти бизнес-логику и выполнить функцию большее количество раз, чем разрешено («allowable»), извлекая личную выгоду в ущерб приложению.

### Пример

Предположим, интернет-магазин позволяет пользователям воспользоваться одной из нескольких доступных скидок на общую сумму покупки, после чего перейти к оформлению и оплате. Что произойдет, если злоумышленник вернется на страницу скидок после выбора и применения одной «разрешенной» скидки? Сможет ли он применить еще одну скидку? Сможет ли он активировать ту же самую скидку повторно?

## Цели тестирования

- Определить функции, требующие жесткого ограничения на количество вызовов.
- Оценить, установлены ли логические ограничения на функции и валидируются ли они надлежащим образом.

## Методика тестирования

- Изучите проектную документацию и проведите исследовательское тестирование для поиска функций или возможностей приложения/системы, которые не должны выполняться более одного раза или более заданного числа раз в рамках рабочего процесса бизнес-логики.
- Для каждой найденной функции или возможности, рассчитанной на однократное или строго ограниченное число выполнений, разработайте сценарии злоупотребления/нецелевого использования (abuse/misuse cases), позволяющие превысить допустимый лимит. Например, может ли пользователь переходить назад и вперед по страницам, повторно инициируя функцию, которая должна срабатывать лишь однажды? Или может ли пользователь наполнять и очищать корзину покупок для начисления дополнительных скидок?

## Рекомендации по устранению

В приложении должны быть реализованы строгие механизмы контроля для предотвращения злоупотребления лимитами. Это может быть достигнуто путем деактивации купона на уровне базы данных, установки счетчика ограничений на пользователя на уровне бэкенда или базы данных (поскольку все пользователи должны однозначно идентифицироваться через сессию) — в зависимости от требований конкретного бизнеса.
