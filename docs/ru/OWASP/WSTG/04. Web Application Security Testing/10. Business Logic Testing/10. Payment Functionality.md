# Платежная функциональность

| ID |
| --- |
| WSTG-BUSL-10 |

## Резюме

Многие приложения реализуют платежную функциональность (payment functionality), включая платформы электронной коммерции, сервисы подписки, благотворительные фонды, сайты сбора пожертвований и валютные обменники. Безопасность этой функциональности имеет решающее значение, поскольку уязвимости могут позволить злоумышленникам похищать средства организации, совершать мошеннические покупки или даже красть данные платежных карт других пользователей. Подобные инциденты чреваты не только репутационным ущербом для организации, но и колоссальными финансовыми потерями — как от прямых убытков, так и в виде штрафов со стороны отраслевых регуляторов.

## Цели тестирования

- Определить, насколько надежна бизнес-логика функциональности электронной коммерции.
- Понять архитектуру и логику работы платежной системы.
- Проверить безопасность реализации платежной функциональности.

## Методика тестирования

### Методы интеграции платежных шлюзов

Приложения могут интегрировать платежную функциональность несколькими различными способами, и подход к тестированию варьируется в зависимости от выбранного метода. Наиболее распространенные методы интеграции:

- Перенаправление пользователя на сторонний платежный шлюз (redirect).
- Загрузка стороннего платежного шлюза внутри фрейма IFRAME на странице приложения.
- Использование HTML-формы, отправляющей междоменный (cross-domain) POST-запрос на сторонний платежный шлюз.
- Прием данных банковской карты напрямую приложением с последующей отправкой POST-запроса из бэкенда приложения к API платежного шлюза.

### PCI DSS

Стандарт безопасности данных индустрии платежных карт (Payment Card Industry Data Security Standard, PCI DSS) — это отраслевой регламент, которому обязаны соответствовать организации для обработки платежей по дебетовым и кредитным картам (важно отметить, что формально он не является законом). Полный разбор стандарта выходит за рамки данного руководства (и большинства типовых пентестов), однако тестировщикам полезно понимать несколько ключевых положений.

Наиболее частое заблуждение относительно PCI DSS состоит в том, что он распространяется исключительно на системы, хранящие данные владельцев карт (Cardholder Data, CHD — реквизиты дебетовых или кредитных карт). Это неверно: он применяется к любой системе, которая «хранит, обрабатывает или передает» эту информацию. Конкретный перечень подлежащих выполнению требований зависит от того, какой именно метод интеграции платежного шлюза используется. Руководство [Visa Processing E-Commerce Payments](https://web.archive.org/web/2023/https://www.visa.co.uk/dam/VCOM/regional/ve/unitedkingdom/PDF/risk/processing-e-commerce-payments-guide-73-17337.pdf) подробно описывает эти аспекты, краткая сводка представлена ниже:

| Integration Method | Self Assessment Questionnaire (SAQ) |
|--------------------|-------------------------------------|
| Redirect | SAQ A |
| IFRAME | SAQ A |
| Cross-domain POST | SAQ A-EP |
| Backend API | SAQ D |

Актуальные версии опросников самооценки (SAQ) доступны в [библиотеке документов PCI SSC](https://www.pcisecuritystandards.org/document_library/?category=saqs).

Помимо различий в векторе атаки и профиле риска каждого подхода, существует значительная разница в количестве требований между SAQ A и SAQ D, которым должна соответствовать организация. Соответственно, стоит обращать особое внимание на приложения, не использующие перенаправление (redirect) или IFRAME, поскольку они несут в себе повышенные технические риски и сложности комплаенса.

### Подмена количества

Большинство интернет-магазинов позволяют пользователям добавлять товары в корзину перед переходом к оформлению заказа. В корзине фиксируются выбранные товары и количество каждой позиции. Количество обычно должно представлять собой положительное целое число, но если сайт не валидирует его должным образом, может оказаться возможным указать дробное количество (например, `0.1`) или отрицательное число (например, `-1`). В зависимости от логики обработки на бэкенде добавление отрицательного количества товара может привести к вычислению отрицательной стоимости, уменьшая общую сумму корзины.

Обычно существует несколько способов изменения содержимого корзины, которые необходимо протестировать:

- Добавление отрицательного количества товара.
- Последовательное удаление позиций до тех пор, пока количество не станет отрицательным.
- Прямое обновление количества на отрицательное значение.

Некоторые ресурсы предлагают выпадающий список допустимых количеств (например, для товаров, продающихся упаковками по 10 штук). Тестировщик должен проверить возможность модификации запросов для добавления произвольного числа позиций.

Если детальные данные корзины передаются платежному шлюзу целиком (а не только итоговая сумма), подмена значений может быть возможна и на этом этапе.

Наконец, если приложение уязвимо к [загрязнению параметров HTTP (HTTP Parameter Pollution)](../07.%20Injection%20Testing/04.%20HTTP%20Parameter%20Pollution.md), можно попытаться вызвать непредусмотренное поведение за счет многократной передачи одного и того же параметра:

```http
POST /api/basket/add
Host: example.org

item_id=1&quantity=5&quantity=4
```

### Подмена цены

#### На стороне приложения

При добавлении товара в корзину запрос приложения должен содержать только идентификатор товара и количество, как показано в примере ниже:

```http
POST /api/basket/add HTTP/1.1
Host: example.org

item_id=1&quantity=5
```

Однако в некоторых случаях приложение также передает цену, что открывает возможность для манипуляции:

```http
POST /api/basket/add HTTP/1.1
Host: example.org

item_id=1&quantity=5&price=2.00
```

Различные типы товаров могут обрабатываться разными правилами валидации, поэтому каждый тип требует отдельной проверки. Некоторые приложения также позволяют пользователям добавлять добровольное благотворительное пожертвование к покупке, и сумма пожертвования обычно задается произвольно. Если эта сумма не валидируется, можно передать отрицательное значение пожертвования, уменьшив общую стоимость заказа.

#### На стороне платежного шлюза

Если процесс оплаты происходит на стороннем платежном шлюзе, существует вероятность модификации цен на этапе взаимодействия между приложением и шлюзом.

Передача данных на шлюз может осуществляться посредством кросс-доменного POST-запроса, как показано в примере HTML-кода ниже.

> Примечание: Данные карты не передаются в этом запросе — шлюз запросит их у пользователя на собственной защищенной странице:

```html
<form action="https://example.org/process_payment" method="POST">
    <input type="hidden" id="merchant_id" value="123" />
    <input type="hidden" id="basket_id" value="456" />
    <input type="hidden" id="item_id" value="1" />
    <input type="hidden" id="item_quantity" value="5" />
    <input type="hidden" id="item_total" value="20.00" />
    <input type="hidden" id="shipping_total" value="2.00" />
    <input type="hidden" id="basket_total" value="22.00" />
    <input type="hidden" id="currency" value="GBP" />
    <input type="submit" id="submit" value="submit" />
</form>
```

Путем модификации HTML-формы или перехвата POST-запроса можно изменить цены товаров и приобрести их значительно дешевле. Учитывайте, что многие платежные шлюзы отклоняют транзакции с нулевой стоимостью, поэтому сумма в 0.01 имеет больше шансов на успешную обработку. Однако некоторые шлюзы принимают отрицательные значения (используемые для оформления возвратов). При наличии нескольких параметров (цены товаров, стоимость доставки и общая сумма заказа) необходимо протестировать каждый из них.

Если платежный шлюз загружается в IFRAME, аналогичную атаку можно провести за счет манипулирования URL внутри фрейма:

```html
<iframe src="https://example.org/payment_iframe?merchant_id=123&basket_total=22.00" />
```

> Примечание: Платежные шлюзы обычно управляются сторонними организациями и могут не входить в область действия (scope) тестирования. Это означает, что проверка подмены цен допустима, однако другие виды атак (например, внедрение SQL-кода) категорически запрещены без явного письменного разрешения заказчика.

#### Зашифрованные детали транзакции

Чтобы исключить подмену параметров транзакции, некоторые платежные шлюзы шифруют данные отправляемого к ним запроса. Например, [PayPal](https://developer.paypal.com/api/nvp-soap/paypal-payments-standard/integration-guide/encryptedwebpayments/#link-usingewptoprotectmanuallycreatedpaymentbuttons) использует для этого асимметричную криптографию на базе открытых ключей.

В первую очередь попробуйте отправить незашифрованный запрос: некоторые платежные шлюзы принимают незащищенные транзакции, если в их настройках явно не активирован запрет на подобные операции.

Если это не сработало, необходимо найти открытый ключ, используемый для шифрования транзакций: он может обнаружиться в забытых резервных копиях приложения или при эксплуатации уязвимости обхода каталога.

Кроме того, возможно, что приложение использует одну и ту же пару открытого/закрытого ключей как для взаимодействия с платежным шлюзом, так и для своего цифрового сертификата SSL/TLS. Извлечь открытый ключ сервера можно следующей командой:

```bash
echo -e '\0' | openssl s_client -connect example.org:443 2>/dev/null | openssl x509 -pubkey -noout
```

Получив ключ, попытайтесь сформировать зашифрованный запрос (в соответствии с документацией шлюза) и отправить его на шлюз для проверки обработки.

#### Надежные хеш-функции

Другие платежные шлюзы используют безопасный хеш (или HMAC) от параметров транзакции для предотвращения подмены. Конкретная реализация зависит от провайдера (например, [Adyen](https://docs.adyen.com/online-payments/classic-integrations/hosted-payment-pages/hmac-signature-calculation) использует HMAC-SHA256), но обычно хеш формируется на основе параметров транзакции и секретного ключа. Например:

```php
$secure_hash = md5($merchant_id . $transaction_id . $items . $total_value . $secret)
```

Полученное значение добавляется к POST-запросу, направляемому платежному шлюзу, и верифицируется им для подтверждения неизменности транзакции.

Сначала попробуйте просто удалить защитный хеш из запроса: некоторые шлюзы пропускают транзакции без хеша, если соответствующая проверка не включена принудительно в панели управления.

POST-запрос обычно содержит все компоненты, необходимые для расчета хеша, кроме секретного ключа. Это значит, что если вам известен алгоритм расчета хеша (описанный в открытой документации платежного шлюза), можно попытаться подобрать секрет полным перебором (brute-force). Если на сайте используется коробочное решение, дефолтный секрет может присутствовать в стандартных файлах конфигурации или исходном коде. Наконец, секретный ключ можно обнаружить в резервных копиях или при чтении файлов конфигурации через LFI.

Завладев секретным ключом, вы сможете произвольно модифицировать детали транзакции и самостоятельно рассчитывать валидный защитный хеш, который будет успешно принят платежным шлюзом.

#### Манипулирование валютой

Если прямая подмена цен заблокирована, может оказаться возможным изменить валюту платежа, особенно в приложениях с поддержкой мультивалютности. Например, если приложение валидирует только числовое значение цены (10), смена валюты с 10 GBP на 10 USD позволит приобрести товар со значительной скидкой.

#### Запросы с временной задержкой

Если стоимость позиций на сайте динамически изменяется во времени (например, на биржевых сервисах или в валютных обменниках), можно попытаться совершить покупку или продажу по старой цене, перехватывая запросы через локальный прокси и задерживая их отправку. Для успешной эксплуатации цена должна либо передаваться в самом запросе, либо быть привязана к сущности внутри запроса (например, идентификатору сессии или транзакции). Ниже показан пример эксплуатации в сервисе покупки/продажи золота:

- Проверьте текущую стоимость золота на сайте.
- Инициируйте покупку 1 унции золота.
- Перехватите и приостановите отправку запроса в прокси-сервере.
- Подождите одну минуту и снова проверьте курс золота:
    - Если курс вырос, пропустите запрос и приобретите золото по цене ниже текущей рыночной.
    - Если курс упал, сбросьте (drop) запрос.

Если ресурс принимает оплату в криптовалютах (отличающихся повышенной волатильностью), атаку можно реализовать путем фиксации цены в криптовалюте с последующим ожиданием колебаний курса относительно базовой валюты сайта.

### Промокоды и коды скидок

Если приложение поддерживает скидочные промокоды, необходимо выполнить следующие проверки:

- Являются ли коды легко угадываемыми (`TEST`, `TEST10`, `SORRY`, `SORRY10`, название компании и т. д.)?
    - Если код содержит цифру, можно ли найти новые коды путем ее инкремента?
- Реализована ли защита от перебора (brute-force)?
- Можно ли применить несколько промокодов одновременно?
- Можно ли применить один промокод несколько раз?
- Можно ли [внедрить спецсимволы подстановки (wildcard)](../07.%20Injection%20Testing/05.%20SQL%20Injection.md#инъекция-подстановочных-символов-sql-sql-wildcard-injection), такие как `%` или `*`?
- Присутствуют ли промокоды в исходном коде HTML или скрытых полях `<input>` на страницах приложения?

Помимо этого, поля ввода промокодов необходимо протестировать на стандартные инъекции, такие как SQL-инъекции.

### Нарушение платежных сценариев

Если процесс оформления заказа или оплаты состоит из нескольких последовательных этапов (добавление позиций в корзину, ввод скидочного купона, ввод адреса доставки и указание платежных реквизитов), можно попытаться вызвать нештатное поведение системы путем нарушения заданной последовательности шагов. Например:

- Изменение адреса доставки после ввода платежных данных с целью занижения стоимости доставки.
- Удаление позиций из корзины после указания адреса доставки для обхода требования к минимальной сумме заказа.
- Изменение содержимого корзины после применения скидочного промокода.
- Модификация содержимого корзины после завершения процесса оплаты.

Также может существовать возможность полностью обойти этап оплаты. Например, если сайт выполняет перенаправление на сторонний платежный шлюз, процесс выглядит следующим образом:

- Пользователь заполняет данные на сайте магазина.
- Пользователь перенаправляется на сторонний платежный шлюз.
- Пользователь вводит реквизиты карты.
    - При успешной оплате происходит редирект на страницу `success.php` на сайте магазина.
    - При ошибке оплаты происходит редирект на страницу `failure.php`.
- Приложение обновляет базу заказов и начинает выполнение заказа в случае успешного статуса.

В зависимости от того, проверяет ли приложение реальный статус платежа на стороне шлюза, может быть достаточно принудительно перейти (force-browse) на страницу `success.php` (возможно, передав параметр `transaction_id`), в результате чего сайт обработает заказ как успешно оплаченный. Кроме того, повторные запросы к странице `success.php` могут спровоцировать многократную отгрузку одного и того же заказа.

### Эксплуатация комиссий за обработку транзакций

Продавцы обычно платят комиссию за каждую обработанную транзакцию, состоящую из небольшой фиксированной суммы и процента от общего чека. Это означает, что получение микроплатежей (например, в размере $0.01) может принести продавцу прямые убытки, так как межбанковская комиссия за эквайринг превысит сумму самого платежа.

Эта проблема редко встречается в классической электронной коммерции, так как стоимость самых дешевых товаров покрывает комиссию. Однако если ресурс позволяет переводить произвольные суммы (например, пожертвования), убедитесь, что система накладывает ограничение на минимально допустимую сумму платежа.

### Тестовые платежные карты

Большинство платежных шлюзов предоставляют набор тестовых номеров банковских карт для разработчиков. Они должны работать исключительно в тестовых средах (sandbox), однако из-за ошибок конфигурации могут ошибочно приниматься на боевых (production) серверах.

Примеры страниц с тестовыми данными различных платежных шлюзов:

- [Adyen - Test Card Numbers](https://docs.adyen.com/development-resources/test-cards-and-credentials/test-card-numbers)
- [Globalpay - Test Cards](https://developer.globalpayments.com/resources/test-cards)
- [Stripe - Basic Test Card Numbers](https://docs.stripe.com/testing#cards)

### Организационные вопросы

Тестирование платежной функциональности сопряжено с организационными сложностями, особенно при работе на боевых стендах. Факторы, которые необходимо предусмотреть:

- Получение тестовых реквизитов карт для приложения.
    - При их отсутствии рассмотрите использование предоплаченных виртуальных карт (pre-paid).
- Ведение строгого учета всех оформленных заказов для их своевременной отмены и возврата средств.
- Исключение создания заказов, которые невозможно отменить, или операций, вызывающих реальные необратимые действия (например, мгновенная физическая отгрузка товаров со склада логистической службой).

#### Совпадение источника и назначения (Source Equals Destination)

Если источник перевода совпадает с получателем, это может привести к простому зачислению баланса на счет без фактического списания. Данный сценарий необходимо протестировать, чтобы убедиться, что приложение блокирует подобные самопереводы.

#### Двухэтапные платежи или переводы

Для платежей или переводов, требующих двух этапов (инициация и подтверждение), убедитесь, что проверки выполняются на обеих стадиях. Например:

- Инициируйте два отдельных платежа.
- Подтвердите их по отдельности.

Убедитесь, что обязательные проверки, такие как дневные лимиты или сверка остатка на счете, повторно выполняются на этапе подтверждения. Отсутствие валидации может привести к образованию отрицательного баланса или обходу лимитов.

#### Добавление товаров после инициации оплаты

Протестируйте сценарий, при котором платеж инициируется на определенную сумму, а затем в корзину добавляются новые товары. Подтверждение платежа может пометить вновь добавленные позиции как оплаченные, вызвав логическую рассинхронизацию в процессе покупки.

#### Состояния гонки

Состояние гонки (race condition) возникает, когда поведение приложения зависит от времени выполнения или порядка событий, которые не контролируются должным образом. В платежных операциях это обычно проявляется, когда несколько параллельных конкурентных запросов обращаются к общему разделяемому состоянию (баланс счета, остаток товара на складе или одноразовый купон) без надлежащей синхронизации, позволяя злоумышленнику использовать временной интервал между проверкой условия и последующим действием. Это явление широко известно как дефект «время проверки к времени использования» (Time-of-Check to Time-of-Use, TOCTOU).

Состояния гонки несут критические риски в следующих операциях:

- Финансовые транзакции (переводы, платежи, снятие средств).
- Одноразовые токены или промокоды (купоны, подарочные карты, реферальные бонусы).
- Распределение ограниченных ресурсов (товары на складе, бронирование мест, регистрация).
- Переходы между состояниями, которые должны происходить строго единожды (активация учетной записи, согласование заявок).

При тестировании сосредоточьтесь на эндпоинтах, где значение проверяется, а затем изменяется, либо где действие должно завершиться успешно только один раз. Отправьте серию идентичных одновременных запросов и проанализируйте, обработает ли приложение более одного запроса там, где должен был пройти лишь один.

Отправка 20 быстрых параллельных запросов с помощью curl к эндпоинту, меняющему состояние:

```bash
# Отправка 20 параллельных запросов на активацию одноразового купона
for i in $(seq 1 20); do
  curl -s -X POST https://example.com/api/redeem-coupon \
    -H "Cookie: session=USER_SESSION" \
    -H "Content-Type: application/json" \
    -d '{"code":"SINGLE-USE-CODE"}' &
done
wait
```

Для прецизионной синхронизации во времени используйте расширение [Burp Suite Turbo Intruder](https://github.com/PortSwigger/turbo-intruder) с механизмом шлюза (gate), удерживающим все запросы и освобождающим их одновременно:

```python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=20,
                           requestsPerConnection=1,
                           pipeline=False)
    for i in range(20):
        engine.queue(target.req, gate='race')
    engine.openGate('race')

def handleResponse(req, interesting):
    table.add(req)
```

Типовые сценарии тестирования включают:

- Параллельное подтверждение платежей:
  Одновременная отправка нескольких запросов на подтверждение (например, `POST /confirm-payment`) для одного и того же заказа. Это может привести к повторной обработке и дублированию заказа.

- Повтор или флуд колбэков (Callback Replay):
  Перехват запроса обратного вызова от платежного шлюза (например, на `success.php` или `/payment/callback`) и его быстрое параллельное воспроизведение. При отсутствии идемпотентности на бэкенде это способно:
    - Вызвать множественные события отгрузки товаров или начисления услуг.
    - Многократно отметить один и тот же заказ как «оплаченный».
    - Привести к накрутке баланса или искажению складского учета.

- Операции с балансом:
  Если на аккаунте есть 100 бонусов/кредитов, отправьте несколько одновременных запросов, каждый из которых списывает весь баланс целиком. Если итоговая сумма списания превысит исходный остаток (например, баланс уйдет в -100), приложение уязвимо.

- Одноразовые токены:
  Для промокодов, ссылок-приглашений или токенов сброса пароля отправьте параллельные запросы на их использование. Если успешно завершится более одного запроса, приложение не обеспечивает атомарную инвалидацию токена.

Индикаторы уязвимости: множественные успешные ответы на одноразовое действие, отрицательный баланс после параллельных списаний, бронирование ресурсов сверх доступного лимита или дублирующиеся побочные эффекты (несколько писем подтверждения, двойные списания).

Для устранения состояний гонки оборачивайте операции проверки и изменения в транзакции базы данных с блокировкой на уровне строк (`SELECT ... FOR UPDATE`), применяйте оптимистические блокировки с версионированием записей, требуйте ключи идемпотентности (idempotency keys) для запросов изменения состояния и производите инвалидацию токенов атомарно через операции вида `DELETE FROM tokens WHERE token = ? RETURNING *`.

См. также [CWE-362: Concurrent Execution using Shared Resource with Improper Synchronization](https://cwe.mitre.org/data/definitions/362.html).

#### Системы с множественным вводом (массовые платежи)

В системах пакетных платежей протестируйте сценарии, когда общая итоговая сумма остается положительной, однако отдельные составные поля содержат отрицательные числа. Например:

```plaintext
account_id_1 = $5
account_id_2 = -$4
Total = $1 paid, but $5 credited
```

Убедитесь, что приложение корректно валидирует каждое поле и исключает возможность подобных манипуляций.

## Рекомендации по устранению

- По возможности полностью избегайте хранения, обработки или передачи карточных данных в собственной инфраструктуре.
    - Используйте перенаправление (redirect) или фрейм IFRAME на платежный шлюз.
- Изучите документацию платежного шлюза и задействуйте все доступные механизмы безопасности (такие как шифрование и защитные хеши).
- Обрабатывайте всю информацию, связанную с расчетом цен, исключительно на стороне сервера:
    - Запросы от клиента должны содержать только идентификаторы позиций и их количество.
- Внедрите строгую валидацию входных данных и бизнес-ограничения (например, проверку на недопустимость отрицательных чисел и цен).
- Гарантируйте целостность платежного процесса и невозможность нарушения последовательности этапов оформления заказа.
