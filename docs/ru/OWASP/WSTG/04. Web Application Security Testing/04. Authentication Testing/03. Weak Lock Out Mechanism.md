# Слабый механизм блокировки

| ID |
| --- |
| WSTG-ATHN-03 |

## Резюме

Механизмы блокировки учетных записей (account lockout mechanisms) применяются для противодействия атакам методом перебора (brute-force attacks). Среди атак, которые могут быть нейтрализованы с помощью механизма блокировки:

- Подбор паролей или атаки методом прямого перебора (brute force).
- Подбор секретных/контрольных вопросов.
- Подбор OTP-кодов (One-Time Password) при двухфакторной аутентификации (Two-Factor Authentication, 2FA / Multi-Factor Authentication, MFA).

Механизмы блокировки учетных записей требуют баланса между защитой аккаунтов от несанкционированного доступа и предотвращением отказа в доступе легитимным пользователям (denial of authorized access). Обычно учетные записи блокируются после 3–5 неудачных попыток ввода пароля и могут быть разблокированы только по истечении заданного периода времени, с помощью механизма самообслуживания или при вмешательстве администратора.

Несмотря на простоту проведения атак методом перебора, последствия успешной атаки крайне опасны, поскольку злоумышленник получает полный доступ к учетной записи пользователя, а вместе с ней — ко всем доступным функциям и сервисам.

## Цели тестирования

- Оценить способность механизма блокировки учетных записей противодействовать атакам методом подбора паролей.
- Оценить устойчивость механизма разблокировки к несанкционированному восстановлению доступа к учетной записи.

## Методика тестирования

### Подстановка учетных данных (Credential Stuffing) и распределенный перебор

Подстановка учетных данных (credential stuffing) использует ранее скомпрометированные пары логинов и паролей из утечек баз данных для получения несанкционированного доступа к аккаунтам. Распределенный перебор (distributed brute force) и распыление паролей (password spraying) отправляют множество попыток аутентификации с различных IP-адресов. Обе эти техники позволяют обходить механизмы блокировки, которые подсчитывают количество неудачных попыток исключительно в привязке к IP-адресу.

Многие приложения блокируют учетные записи только при повторяющихся попытках входа с одного и того же IP-адреса. Злоумышленники обходят этот контроль, распределяя запросы через ботнеты или ротируемые прокси-серверы.

Проверьте, использует ли приложение защиту на уровне учетных записей (account-based protections), а не только ограничения на основе IP-адресов при обработке подобных атак.

1. Получите контролируемый набор тестовых учетных записей и учетных данных, на использование которых у вас есть полномочия. Для проверки подстановки учетных данных (credential stuffing) используйте известные пары логинов и паролей. Для распределенного перебора или распыления паролей (password spraying) используйте словарь паролей против одного или нескольких тестовых имен пользователей.
2. Отправьте запросы на аутентификацию с указанными учетными данными.
3. Распределите попытки между несколькими IP-адресами, используя прокси-серверы или VPN-эндпоинты.
4. Проследите, применяет ли приложение механизмы защиты на уровне учетных записей или ограничивается лишь проверками по IP.
5. Отслеживайте ответы на предмет блокировки учетной записи, появления проверок CAPTCHA или ограничения частоты запросов (rate limiting).

Пример запроса аутентификации:

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=user1@example.com&password=Password123
```

Пример использования ffuf для фаззинга паролей к одной тестовой учетной записи (распределенный перебор или распыление паролей в сочетании с ротацией IP):

```bash
ffuf -w passwords.txt -X POST -d "username=test&password=FUZZ" -u https://example.com/login
```

Для проверки credential stuffing отправляйте известные пары логинов и паролей с помощью Burp Intruder, ZAP Fuzzer, Hydra или кастомного скрипта, который отправляет каждую пару и осуществляет ротацию исходных IP-адресов.

### Механизм блокировки учетной записи

Чтобы протестировать надежность механизмов блокировки, вам потребуется доступ к учетной записи, которую вы готовы или можете позволить себе заблокировать. Если у вас есть только одна учетная запись для входа в веб-приложение, выполняйте этот тест в самом конце вашего плана тестирования, чтобы избежать потери времени из-за блокировки.

Для оценки способности механизма блокировки противодействовать подбору паролей совершите попытку входа с неверным паролем заданное количество раз, после чего проверьте блокировку аккаунта с помощью корректного пароля. Пример сценария тестирования может выглядеть следующим образом:

1. Попробуйте войти с неверным паролем 3 раза.
2. Успешно выполните вход с правильным паролем, подтвердив, что механизм блокировки не срабатывает после 3 неудачных попыток аутентификации.
3. Попробуйте войти с неверным паролем 4 раза.
4. Успешно выполните вход с правильным паролем, подтвердив, что механизм блокировки не срабатывает после 4 неудачных попыток аутентификации.
5. Попробуйте войти с неверным паролем 5 раз.
6. Попробуйте войти с правильным паролем. Приложение возвращает сообщение: "Your account is locked out.", тем самым подтверждая, что учетная запись блокируется после 5 неверных попыток аутентификации.
7. Попробуйте войти с правильным паролем через 5 минут. Приложение возвращает: "Your account is locked out.", подтверждая, что механизм блокировки не разблокирует аккаунт автоматически через 5 минут.
8. Попробуйте войти с правильным паролем через 10 минут. Приложение возвращает: "Your account is locked out.", подтверждая, что механизм блокировки не разблокирует аккаунт автоматически через 10 минут.
9. Успешно войдите с правильным паролем через 15 минут, подтвердив, что механизм блокировки автоматически снимается в интервале от 10 до 15 минут.

#### Уникальные механизмы блокировки

Существуют более специфические реализации механизмов блокировки, которые также признаются допустимыми. Одной из них является сервис AWS [Cognito](https://docs.aws.amazon.com/cognito/latest/developerguide/authentication.html#authentication-flow-lockout-behavior). В нем используется простой масштабируемый алгоритм, который предотвращает атаки методом перебора, не создавая при этом условий для долговременного отказа в обслуживании (Denial-of-Service, DoS) атакуемого пользователя. После 5 неудачных попыток входа с паролем учетная запись блокируется на одну секунду. Продолжительность блокировки удваивается с каждой последующей неудачной попыткой вплоть до максимума в 15 минут. Попытки входа, предпринятые в период блокировки, вызывают исключения `Password attempts exceeded`, которые в большинстве реализаций не отображаются пользователю, инициировавшему вход. Если они скрыты от пользователя, тестировщик может ошибочно предположить, что механизм блокировки отсутствует, поскольку 200 быстрых попыток входа сгенерируют множество таких исключений и лишь единичные легитимно зарегистрированные неудачные попытки входа.

Математическая формула механизма имеет вид: `2^(n-5)`, где `n` — число неудачных попыток входа. Результирующее значение представляет собой количество секунд, на которое блокируется пользователь. Чтобы сбросить счетчик блокировки до нуля, пользователь должен успешно авторизоваться или подождать 15 минут.

Для проверки данного поведения с помощью инструмента фаззинга, такого как Burp Suite Intruder, перейдите в раздел "Resource Pool". Установите максимальное количество параллельных запросов равным 1, а задержку между запросами — 2 секунды. Выполните 200 попыток неверной аутентификации, затем сразу после завершения работы фаззера выполните 3 попытки входа с валидными учетными данными. Подождите 2 минуты и попробуйте войти снова. Если вход окажется успешным, возможно, используется Cognito. Дальнейшее тестирование для подтверждения применения Cognito может включать попытки увеличения времени блокировки, однако зачастую проще уточнить эту информацию у клиента.

CAPTCHA может затруднить атаки методом перебора, однако она сопряжена с собственным набором уязвимостей и не должна полностью заменять механизм блокировки. При некорректной реализации механизм CAPTCHA может быть обойден. К распространенным недостаткам CAPTCHA относятся:

1. Легко решаемая задача (простая арифметика или ограниченный набор вопросов).
2. Проверка CAPTCHA ориентируется на HTTP-код ответа вместо признака успешного решения.
3. Серверная логика проверки CAPTCHA по умолчанию считает проверку пройденной.
4. Результат проверки CAPTCHA вообще не валидируется на стороне сервера.
5. Поле ввода или параметр CAPTCHA обрабатывается вручную и валидируется или экранируется ненадлежащим образом.
6. Однократно решенная CAPTCHA может использоваться повторно несколько раз.

Для оценки эффективности CAPTCHA:

1. Проанализируйте задачи CAPTCHA и попытайтесь автоматизировать их решение в зависимости от сложности.
2. Попробуйте отправить запрос без прохождения CAPTCHA через стандартные элементы интерфейса пользователя (UI).
3. Попробуйте отправить запрос с заведомо неверным решением CAPTCHA.
4. Попробуйте отправить запрос без решения CAPTCHA (исходя из предположения, что клиентский код может передавать значения по умолчанию и т. д.), используя перехватывающий прокси-сервер (прямая отправка запроса на сервер).
5. Попробуйте фаззить точки ввода данных CAPTCHA (при их наличии) стандартными пейлоадами инъекций или последовательностями специальных символов.
6. Проверьте, не является ли решением CAPTCHA значение alt-текста изображения, имя файла или значение ассоциированного скрытого поля.
7. Попробуйте повторно отправить ранее полученные заведомо валидные ответы.
8. Проверьте, приводит ли очистка cookie к обходу CAPTCHA (например, если CAPTCHA отображается только после определенного количества неудач).
9. Если CAPTCHA является частью многошагового процесса, попытайтесь напрямую обратиться к следующему шагу или завершить его в обход CAPTCHA (например, если ввод CAPTCHA является первым шагом при входе, попробуйте напрямую отправить второй шаг с логином и паролем).
10. Проверьте наличие альтернативных методов, в которых проверка CAPTCHA может быть не принудительной, таких как эндпоинты API для мобильных приложений.

Повторите данный процесс для каждого функционала, в котором требуется механизм блокировки.

### Механизм разблокировки

Для оценки устойчивости механизма разблокировки к несанкционированному снятию блокировки инициируйте процедуру разблокировки и проанализируйте ее на наличие слабых мест. Типичные механизмы разблокировки включают использование секретных вопросов или отправку ссылки для разблокировки по электронной почте. Ссылка для разблокировки должна быть уникальной и одноразовой, чтобы злоумышленник не мог угадать ее, повторить (replay) или осуществлять перебор партиями.

Помните, что механизм разблокировки должен служить исключительно для разблокировки учетных записей. Это не то же самое, что механизм восстановления пароля, хотя он может строиться по тем же принципам безопасности.

## Рекомендации по устранению

Внедряйте механизмы разблокировки учетных записей в зависимости от уровня риска. В порядке возрастания уровня надежности:

1. Блокировка и разблокировка на основе тайм-аута (time-based).
2. Разблокировка по принципу самообслуживания (self-service: отправка ссылки на зарегистрированный адрес электронной почты).
3. Ручная разблокировка администратором.
4. Ручная разблокировка администратором с однозначной идентификацией пользователя.

Факторы, которые следует учитывать при проектировании механизма блокировки учетных записей:

1. Каков риск атак методом подбора паролей против приложения?
2. Достаточно ли внедрения CAPTCHA для снижения данного риска?
3. Используется ли блокировка на стороне клиента (например, средствами JavaScript)? (Если да, отключите выполнение клиентского кода для проверки.)
4. Количество неудачных попыток входа до срабатывания блокировки. При слишком низком пороге легитимные пользователи будут блокироваться слишком часто. При слишком высоком пороге у злоумышленника будет больше попыток для перебора до момента блокировки. В зависимости от назначения приложения типовой порог блокировки обычно составляет от 5 до 10 неудачных попыток.
5. Каким образом будут разблокироваться учетные записи?
    1. Вручную администратором: это наиболее безопасный способ, однако он может создавать неудобства для пользователей и отнимать ценное рабочее время администратора.
        1. У администратора также должен быть предусмотрен метод восстановления доступа на случай блокировки его собственной учетной записи.
        2. Данный механизм разблокировки может стать вектором атаки типа «отказ в обслуживании» (DoS), если целью злоумышленника является намеренная блокировка учетных записей всех пользователей веб-приложения.
    2. По истечении периода времени: какова длительность блокировки? Достаточна ли она для защищаемого приложения? Например, период блокировки от 5 до 30 минут может служить разумным компромиссом между защитой от перебора и удобством легитимных пользователей.
    3. Через механизм самообслуживания: как отмечалось ранее, процедура самообслуживания должна быть достаточно защищенной, чтобы исключить возможность самостоятельной разблокировки чужих аккаунтов атакующим.
