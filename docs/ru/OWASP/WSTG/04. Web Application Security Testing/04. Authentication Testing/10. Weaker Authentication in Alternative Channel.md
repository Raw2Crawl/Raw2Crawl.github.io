# Более слабая аутентификация в альтернативном канале

| ID |
| --- |
| WSTG-ATHN-10 |

## Резюме

Даже если основные механизмы аутентификации не содержат уязвимостей, бреши в безопасности могут присутствовать в альтернативных легитимных каналах взаимодействия пользователей с теми же самыми учетными записями. Необходимо провести тестирование для выявления таких альтернативных каналов и, с учетом согласованных рамок тестирования, поиска в них уязвимостей.

Альтернативные каналы взаимодействия с пользователем могут использоваться для обхода основного канала либо для извлечения информации, которая затем может способствовать атаке на основной канал. Некоторые из этих каналов могут сами по себе представлять собой отдельные веб-приложения, использующие другие имена хостов или пути. Например:

- Основной веб-сайт
- Веб-сайт, оптимизированный для мобильных или специализированных устройств
- Веб-сайт, оптимизированный для людей с ограниченными возможностями (accessibility)
- Региональные и языковые версии веб-сайта
- Параллельные веб-сайты, использующие те же учетные записи пользователей (например, другой сайт той же организации с иным функционалом, партнерский сайт с общими учетными записями)
- Версии основного веб-сайта для разработки, тестирования, приемочного тестирования (UAT) и предпроизводственные стенды (staging)

Кроме того, это могут быть иные типы приложений или бизнес-процессов:

- Приложения для мобильных устройств
- Десктопные приложения
- Операторы контакт-центра (колл-центра)
- Системы интерактивного голосового ответа (Interactive Voice Response, IVR) или голосовые меню

Следует помнить, что фокусом данного теста являются альтернативные каналы; некоторые варианты аутентификации могут предоставляться в рамках разного контента одного и того же веб-сайта и практически наверняка входят в рамки тестирования. Они не рассматриваются здесь подробно и должны были быть идентифицированы в ходе сбора информации и тестирования основного канала аутентификации. Например:

- Прогрессивное улучшение (progressive enrichment) и изящная деградация (graceful degradation), изменяющие функционал приложения
- Использование сайта без поддержки cookie
- Использование сайта с отключенным JavaScript

Даже если рамки тестирования не позволяют провести активную проверку альтернативных каналов, факт их существования необходимо задокументировать. Их наличие может снижать общий уровень доверия к механизмам аутентификации и служить поводом для проведения дополнительных проверок.

## Пример

Основной веб-сайт — `https://www.example.com`, и функции аутентификации всегда выполняются на страницах с использованием TLS: `https://www.example.com/myaccount/`.

Однако существует отдельный мобильный сайт, который вообще не использует TLS и содержит более слабый механизм восстановления пароля: `https://m.example.com/myaccount/`.

## Цели тестирования

- Выявить альтернативные каналы аутентификации.
- Оценить применяемые меры безопасности и проверить наличие возможностей обхода через альтернативные каналы.

## Методика тестирования

### Изучение основного механизма

Полностью протестируйте основные функции аутентификации веб-сайта. Это позволит определить, как создаются, выдаются и изменяются учетные записи, а также как восстанавливаются, сбрасываются или изменяются пароли. Кроме того, необходимо получить представление о любых процедурах аутентификации с повышенными привилегиями и реализованных мерах защиты. Эти предварительные сведения необходимы для сопоставления с альтернативными каналами.

### Определение других каналов

Другие каналы можно обнаружить следующими методами:

- Изучение содержимого сайта, особенно главной страницы, страниц контактов, справочных разделов, базы знаний и FAQ, условий обслуживания (Terms & Conditions), политик конфиденциальности, файлов robots.txt и любых карт сайта sitemap.xml.
- Поиск по журналам HTTP-прокси, записанным на этапах сбора информации и предварительного тестирования, по ключевым словам, таким как "mobile", "Android", "blackberry", "ipad", "iphone", "mobile app", "e-reader", "wireless", "auth", "sso", "single sign on" в путях URL и теле ответов.
- Использование поисковых систем для обнаружения других сайтов той же организации или на том же домене, имеющих схожее оформление или собственные механизмы аутентификации.

Для каждого потенциального канала проверьте, используются ли общие учетные записи пользователей или предоставляется ли доступ к аналогичному функционалу.

### Перечисление функций аутентификации

Для каждого альтернативного канала с общими учетными записями или функционалом определите, доступны ли в нем все функции аутентификации основного канала и имеются ли дополнительные возможности. Полезно составить матрицу соответствия, подобную приведенной ниже:

  | Primary | Mobile  |  Call Center | Partner Website |
  |---------|---------|--------------|-----------------|
  | Register| Yes     |     -        |       -         |
  | Log in  | Yes     |    Yes       |    Yes(SSO)     |
  | Log out |   -     |     -        |       -         |
  | Password reset |   Yes  |   Yes   |       -         |
  | -       | Change password |   -  |       -         |

В данном примере в мобильной версии присутствует дополнительная функция «change password», однако отсутствует «log out». Определенный набор действий также можно выполнить, позвонив в колл-центр. Колл-центры представляют особый интерес, поскольку их процедуры подтверждения личности могут быть значительно слабее проверок веб-сайта, что позволяет использовать этот канал для реализации атак на учетную запись пользователя.

В процессе перечисления функций обратите внимание на реализацию управления сессиями (session management) на случай пересечений между каналами (например, файлы cookie с областью действия на весь родительский домен, допустимость параллельных сессий между разными каналами при запрете параллельных сессий в одном канале).

### Анализ и тестирование

Альтернативные каналы должны быть отражены в отчете по тестированию, даже если они помечены как «только для информации» (information only) или «вне рамок тестирования» (out of scope). В некоторых случаях альтернативный канал может входить в границы проекта (например, являясь просто отдельным путем на целевом хосте) или быть включен в скоуп после согласования с владельцами систем. Если тестирование разрешено и авторизовано, необходимо провести все остальные тесты аутентификации из данного руководства и сопоставить полученные результаты с основным каналом.

## Связанные тест-кейсы

Следует использовать тест-кейсы всех остальных проверок аутентификации.

## Рекомендации по устранению

Обеспечьте применение единой и согласованной политики аутентификации во всех каналах, гарантируя их равнозначный уровень защищенности.
