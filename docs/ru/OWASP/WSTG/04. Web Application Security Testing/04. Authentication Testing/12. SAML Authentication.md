# Аутентификация SAML

| ID |
| --- |
| WSTG-ATHN-12 |

## Резюме

Security Assertion Markup Language (SAML) 2.0 представляет собой основанный на XML стандарт для обеспечения единого входа (Single Sign-On, SSO). Пользователь проходит процедуру аутентификации у поставщика удостоверений (Identity Provider, IdP), который передает подписанное утверждение о пользователе (assertion) в приложение, выступающее поставщиком услуг (Service Provider, SP). SP доверяет этому утверждению и создает сессию для пользователя.

Широко распространены два сценария (flows):

- **SP-initiated:** пользователь обращается к SP, который отправляет запрос на аутентификацию (`AuthnRequest`) к IdP и получает взамен ответ `SAMLResponse`.
- **IdP-initiated:** пользователь начинает процедуру на стороне IdP, который отправляет `SAMLResponse` в адрес SP без предварительного запроса со стороны последнего.

При стандартной привязке HTTP POST (HTTP POST binding) браузер передает `SAMLResponse` на эндпоинт службы приема утверждений (Assertion Consumer Service, ACS) поставщика услуг в виде base64-кодированного поля формы. Поскольку браузер (а следовательно, пользователь или злоумышленник) участвует в передаче сообщения, SP обязан валидировать абсолютно все данные, на которые он опирается. Наиболее распространенные ошибки возникают при проверке подписи и при чтении XML поставщиком услуг после проверки.

В этом разделе рассматриваются специфичные для SAML аспекты. Уязвимости парсинга XML, такие как внешние сущности XML, описаны в разделе [XML Injection](../07.%20Injection%20Testing/07.%20XML%20Injection.md). Вопросы управления сессиями после входа описаны в разделе [Session Management](../06.%20Session%20Management%20Testing/index.md).

## Цели тестирования

- Определить используемый сценарий SAML и задействованные эндпоинты.
- Определить, проверяет ли SP цифровую подпись и распространяется ли подпись на все данные, используемые SP.
- Определить, проверяет ли SP условия в утверждении (audience, период действия, recipient и привязку к исходному запросу).
- Оценить, возможно ли повторное использование утверждений (replay) или их принятие из недоверенных источников.

## Методика тестирования

### Определение потока SAML

Используйте перехватывающий прокси-сервер для отслеживания процесса входа. Обратите внимание на:

- Перенаправление (redirect) на IdP с параметром `SAMLRequest` (в сценарии SP-initiated).
- POST-запрос к эндпоинту, такому как `/saml/acs`, `/saml2/consume` или `/Shibboleth.sso/SAML2/POST`, содержащий `SAMLResponse` и иногда `RelayState`.
- Метаданные SP и IdP, часто публикуемые по путям вроде `/saml/metadata`, которые содержат entity ID, эндпоинты и сертификаты.

Декодируйте значение `SAMLResponse`: выполните URL-декодирование и base64-декодирование для получения XML. Параметр `SAMLRequest` или сообщение выхода (logout), отправленное через HTTP Redirect binding, дополнительно сжимаются алгоритмом deflate. Расширения для браузера, такие как SAML-tracer, и расширение SAML Raider для [Burp Suite](https://portswigger.net/burp), делают декодирование, модификацию и повторную отправку сообщений и их цифровых подписей простыми и удобными.

В структуре XML обратите внимание на элементы `Issuer`, `Subject`/`NameID`, `Conditions` (`NotBefore`, `NotOnOrAfter`, `AudienceRestriction`), `SubjectConfirmationData` (`Recipient`, `InResponseTo`, `NotOnOrAfter`), атрибуты и элементы, содержащие тег `Signature`. Элементы `Response` и `Assertion` могут подписываться независимо друг от друга.

### Проверка валидации подписи

Повторно отправьте запрос на вход с модифицированным `SAMLResponse`, используя учетную запись, на тестирование которой у вас есть разрешение. Поставщик услуг (SP) должен отклонять каждый из следующих вариантов:

- Элементы `Signature` удалены.
- Подписанные значения изменены (например, `NameID` или атрибут), тогда как исходная подпись оставлена без изменений.
- Сообщение повторно подписано другим ключом, например самоподписанным сертификатом. SAML Raider умеет клонировать сертификаты для этих целей.
- Подпись валидна, но покрывает только элемент `Response`, в то время как SP считывает данные из неподписанного элемента `Assertion`, или наоборот.
- Передано открытое утверждение `Assertion` вместо `EncryptedAssertion`, если SP настроен на прием зашифрованных утверждений. Некоторые SP расшифровывают сообщения при обнаружении зашифрованного утверждения, но одновременно принимают и незашифрованные.
- Элемент `Transform` внутри подписи использует XSLT. Некоторые библиотеки XML-подписей выполняют преобразования transforms до проверки подписи, поэтому XSLT-трансформация, выполняющая сетевой запрос к контролируемому вами серверу, подтвердит обработку XML со стороны SP, даже если подпись впоследствии будет отклонена.

Если модифицированный ответ принимается, значит, SP не проверяет подписи либо не проверяет их соответствие открытому ключу IdP.

### Тестирование на подмену XML-подписи (XML Signature Wrapping)

При атаке оборачивания XML-подписи (XML Signature Wrapping, XSW) злоумышленник сохраняет корректно подписанный элемент, но перемещает его в структуре документа так, чтобы проверка подписи оставалась успешной, и добавляет второй, неподписанный элемент, который считывается бизнес-логикой SP вместо подписанного.

- Скопируйте подписанный элемент `Assertion` в другое место документа (например, внутрь элемента `Extensions` или после исходного assertion) и поместите модифицированный элемент assertion на то место, где SP обычно ожидает его найти.
- Проверьте, считывает ли SP идентификатор пользователя из того же элемента, цифровую подпись которого он только что проверил.

Поскольку проверка подписи проходит успешно, уязвимый SP принимает такой ответ. Успешность атаки часто зависит от используемой XML-библиотеки и способа выборки элементов поставщиком услуг (по положению в дереве или по ссылке на `ID`), поэтому протестируйте различные варианты размещения.

Смежной уязвимостью является расхождение парсеров (parser differential), когда SP использует один XML-парсер для проверки подписи и другой — для чтения утверждения. Разметка, которую эти два парсера интерпретируют по-разному (например, нестандартные объявления пространств имен, комментарии, сущности или дублирующиеся элементы), может привести к тому, что верификатор и модуль чтения увидят совершенно разные документы. В 2025 году это привело к обходу аутентификации в библиотеке `ruby-saml`. Если используемый SP технологический стек известен, проверьте, подвергалась ли данная SAML-библиотека подобным проблемам и пропатчена ли установленная версия.

### Тестирование обработки NameID и атрибутов

- **Внедрение комментариев (Comment injection):** некоторые парсеры возвращают только текстовый узел перед комментарием. Значение `NameID` вида `user@example.com<!---->.attacker.com` может быть прочитано как `user@example.com`, при этом цифровая подпись останется валидной, поскольку эксклюзивная канонизация (exclusive canonicalization) отбрасывает комментарии, и подписанное значение не изменяется. Протестируйте это со значением подконтрольного аккаунта и проверьте, какую учетную запись идентифицирует SP.
- Проверьте, как SP сопоставляет `NameID` или атрибуты с локальными учетными записями. Если сопоставление выполняется только по адресу электронной почты или имени пользователя, атакующий, контролирующий учетную запись у IdP (или у другого IdP, которому доверяет SP), может попытаться захватить учетную запись другого пользователя.
- Проверьте, принимаются ли атрибуты, определяющие роли или группы, из утверждения без каких-либо ограничений.

### Проверка условий утверждений (Assertions)

Измените или повторно отправьте (replay) утверждение, используя ситуации, которые SP обязан отклонять:

- **Audience:** принимается утверждение, выпущенное для другого SP (с другим значением `Audience`).
- **Срок действия (Validity period):** принимается утверждение, использованное после `NotOnOrAfter` или до `NotBefore`. Учитывайте небольшое допустимое расхождение часов (clock skew).
- **Recipient:** значение `Recipient` в `SubjectConfirmationData` не сверяется с ACS URL.
- **Повторное воспроизведение (Replay):** одно и то же утверждение (`ID`) принимается повторно более одного раза, в том числе после выхода из системы (logout).
- **InResponseTo:** в сценарии SP-initiated принимается ответ, который не относится к запросу, сформированному данным SP.
- **Issuer:** принимается ответ от издателя, отличного от настроенного IdP.

### Тестирование обработки потоков IdP-Initiated и параметра RelayState

- Если SP принимает незапрошенные ответы (IdP-initiated SSO), зафиксируйте это. Это допустимый сценарий, однако он отключает проверку `InResponseTo` и облегчает атаки подделки межсайтовых запросов при входе (login CSRF). См. [Cross Site Request Forgery](../06.%20Session%20Management%20Testing/05.%20Cross%20Site%20Request%20Forgery.md).
- Параметр `RelayState` часто используется для перенаправления пользователя на нужную страницу после входа. Проверьте его на наличие открытых перенаправлений (open redirect), изменив значение на внешний URL. См. [Client-side URL Redirect](../11.%20Client-side%20Testing/04.%20Client-side%20URL%20Redirect.md).

### Тестирование выхода из системы

Если реализован единый выход (Single Logout, SLO), проверьте, завершает ли выход на стороне SP локальную сессию SP, а также подписывается и верифицируется ли запрос `LogoutRequest`. Убедитесь, что старая сессия не может быть использована после выхода.

## Рекомендации по устранению

- Проверяйте цифровую подпись каждого сообщения и утверждения, используемого SP, на соответствие настроенному сертификату IdP, и используйте только те данные, которые покрываются подписью.
- Используйте поддерживаемую библиотеку SAML, своевременно обновляйте ее и настраивайте на обязательное отклонение неподписанных утверждений.
- Обеспечьте строгую валидацию параметров `Audience`, `Recipient`, `Issuer`, `NotBefore` и `NotOnOrAfter`, а для сценариев SP-initiated проверяйте `InResponseTo`.
- Сохраняйте идентификаторы утверждений (assertion ID) до истечения их срока действия и отклоняйте повторные запросы.
- Отключите обработку DTD и внешних сущностей в парсере XML.
- Считывайте утверждение из того же распарсенного документа, который использовался для проверки подписи, и отклоняйте подписи, использующие преобразования XSLT.
- Сопоставляйте пользователей с использованием стабильного уникального идентификатора и не позволяйте внешним атрибутам неконтролируемо назначать привилегии, которыми должно управлять само приложение.
- Разрешайте только ожидаемые значения для параметра `RelayState`.
