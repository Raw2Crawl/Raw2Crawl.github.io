# Конфигурация платформы приложений

| ID |
| --- |
| WSTG-CONF-02 |

## Резюме

Корректная конфигурация отдельных компонентов архитектуры приложения играет ключевую роль в предотвращении ошибок, способных поставить под угрозу безопасность всей инфраструктуры в целом.

Анализ и тестирование конфигураций являются критически важными задачами при проектировании и эксплуатации архитектуры. Это обусловлено тем, что различные системы поставляются с типовыми настройками по умолчанию, которые зачастую не согласуются с требованиями безопасности конкретных веб-ресурсов, на которых они развертываются.

Стандартная установка веб-сервера и сервера приложений обычно содержит избыточную функциональность (демонстрационные приложения, документацию, тестовые страницы). Все компоненты, не являющиеся строго обязательными для работы системы, должны быть удалены перед развертыванием во избежание их последующей эксплуатации злоумышленниками.

## Цели тестирования

- Убедиться, что стандартные, демонстрационные и общеизвестные файлы удалены из развернутой платформы, контейнерного образа или бессерверного (serverless) пакета.
- Проверить, что отладочный код, эндпоинты отладки, режимы отладки (debug modes) и неиспользуемые модули/зависимости отключены в рабочей среде (production).
- Проанализировать механизмы журналирования (logging), настроенные для приложения, включая перечень потенциально регистрируемых конфиденциальных данных, а также права доступа и сроки хранения журналов.
- Подтвердить применение специфичных для фреймворков, контейнеров и serverless-сред настроек усиления безопасности (hardening), исключающих использование небезопасных параметров по умолчанию.

## Методика тестирования

### Тестирование методом «черного ящика»

#### Типовые и известные файлы и каталоги

При установке с настройками по умолчанию многие веб-серверы, серверы приложений и фреймворки развертывают демонстрационные примеры, типовые каркасы проектов (scaffolding) и тестовые страницы для удобства разработчиков, позволяя им оперативно проверить работоспособность сервера сразу после установки или выполнения команды `init`. Исторически данный класс проблем иллюстрируют такие уязвимости, как CVE-1999-0449 (отказ в обслуживании в IIS при установленном демонстрационном сайте Exair), CAN-2002-1744 (уязвимость обхода каталога `[Directory Traversal]` в скрипте CodeBrws.asp в Microsoft IIS 5.0) или CAN-2003-1172 (обход каталога в демонстрационном компоненте view-source в Apache Cocoon). Сама суть проблемы (попадание неудаленных демонстрационных материалов и шаблонов в рабочую среду) остается актуальной и сегодня, изменились лишь целевые объекты:

- Неудаленный каркас (scaffolding) фреймворка: стандартные страницы приветствия Django, Rails, Laravel, страницы ошибок по умолчанию в Spring Boot (whitelabel error pages), стартовые шаблоны create-react-app, Next.js, Vite или немодифицированный файл `index.html` из начального шаблона. Каждый из них раскрывает используемый фреймворк и его точную версию, а иногда и забытые маршруты-заготовки.
- Автоматически генерируемая документация API и консоли тестирования, оставленные доступными в рабочей среде: Swagger UI / OpenAPI (`/swagger-ui`, `/swagger.json`, `/v2/api-docs`), GraphQL Playground / GraphiQL или рефлексия gRPC (gRPC reflection). Зачастую они полностью раскрывают схему API, включая недокументированные или сугубо административные операции, а некоторые позволяют выполнять прямые запросы («try it out») без дополнительной проверки авторизации.
- Классические демонстрационные файлы прошлых лет: `phpinfo.php`, `test.php`, `info.php`, а также стандартные скрипты установки CMS (например, `wp-admin/install.php`, директория `installation/` в Joomla), оставленные доступными после запуска ресурса.

Специализированные сканеры CGI и веб-уязвимостей с базой данных известных типовых файлов и каталогов позволяют оперативно выявлять подобные ресурсы. После автоматизированного сканирования необходимо провести ручной анализ веб-сайта для обнаружения специфичных артефактов используемого фреймворка, которые универсальные сканеры могут пропустить.

#### Отладочные конечные точки и режимы отладки

Большинство современных фреймворков предоставляют режим отладки/разработки (debug/development mode), который категорически небезопасен для промышленной среды. Он спроектирован так, чтобы предоставить разработчику максимальную видимость процессов (полные трассировки стека `[stack traces]`, консоль выполнения кода в браузере, дампы переменных окружения). Если оставить его включенным, вся эта информация становится доступной злоумышленнику:

- Django: при `DEBUG=True` на любое необработанное исключение выводится полная трассировка стека, значения локальных переменных, а также список установленных приложений и настроек конфигурации. Спровоцируйте ошибку (например, запросив несуществующий путь или передав некорректные входные данные) и убедитесь, что ответ содержит стандартную страницу 404/500, а не страницу отладки Django.
- Flask / Werkzeug: при включении отладчика Werkzeug (`app.run(debug=True)` или переменная `FLASK_DEBUG=1`) при возникновении необработанного исключения в окне браузера активируется интерактивная консоль Python. Хотя номинально она защищена PIN-кодом, в старых версиях Werkzeug этот PIN нередко можно вычислить по информации со страницы ошибки и предсказуемым значениям параметров хоста. Любой доступный в production отладчик Werkzeug следует расценивать как уязвимость критического уровня (удаленное выполнение кода [Remote Code Execution, RCE]), а не просто утечку данных.
- Spring Boot Actuator: такие эндпоинты, как `/actuator/env`, `/actuator/heapdump`, `/actuator/httptrace` и `/actuator/mappings`, способны раскрыть переменные окружения и секреты, полный дамп кучи JVM (который может содержать учетные данные и данные сессий пользователей), а также внутреннюю схему маршрутизации. Проверьте, доступны ли эндпоинты Actuator в рабочей среде, и если да, ограничена ли директива `management.endpoints.web.exposure.include` минимально необходимым набором метрик.
- Ruby on Rails: директива `config.consider_all_requests_local = true` (активная по умолчанию в среде разработки) формирует детализированные страницы ошибок с фрагментами исходного кода, параметрами запроса и данными сессий. Убедитесь, что в конфигурации production-окружения выставлено значение `false`.
- Express / Node.js: стандартные обработчики ошибок, возвращающие свойство `err.stack` клиенту, либо встроенные в dev-сборку промежуточные обработчики (middleware) сборщиков (например, dev-серверы бандлеров), оставшиеся подключенными в продакшене.
- Next.js / React и другие инструменты сборки SPA: рабочие сборки, продолжающие отдавать файлы карт исходного кода (source maps с расширением `.map`) или оставляющие доступным сервер разработки, что позволяет полностью восстановить оригинальный исходный код из минифицированных бандлов.
- Интроспекция GraphQL (GraphQL introspection): даже при отсутствии интерфейса GraphQL Playground включенная в рабочей среде интроспекция (запрос вида `{ __schema { types { name } } }`) позволяет полностью извлечь всю схему данных, включая типы, поля и мутации, не анонсированные в публичном API.

Общая методика тестирования: намеренно вызовите ошибку приложения (некорректный ввод, отсутствующий обязательный параметр, форсированное исключение) для каждого задействованного компонента и фреймворка, после чего убедитесь, что сервер возвращает общую унифицированную страницу ошибки без раскрытия отладочной информации.

#### Анализ комментариев

При разработке масштабных веб-приложений программисты регулярно оставляют комментарии в коде. Однако комментарии, размещенные непосредственно в разметке HTML, могут раскрывать внутреннюю информацию об архитектуре, которая не должна попадать к злоумышленникам. Нередко фрагменты кода комментируются при отключении функциональности, однако непреднамеренно остаются в HTML-разметке, отдаваемой конечным пользователям.

Анализ комментариев проводится для выявления непреднамеренных утечек данных. Полноценная проверка требует исследования статического и динамического содержимого веб-сервера, а также контекстного поиска по исходным файлам страниц. Рекомендуется обойти ресурс в автоматическом или полуавтоматическом режиме, сохранить все полученные страницы и провести поиск по HTML-комментариям в собранном массиве данных.

Для комплексной оценки соответствия целевых систем базовым стандартам и эталонам конфигурации безопасности (benchmarks) специалисты могут использовать специализированные инструменты, чек-листы и руководства. К ним относятся:

- [CIS-CAT Lite](https://learn.cisecurity.org/cis-cat-lite)
- [Microsoft Attack Surface Analyzer](https://github.com/microsoft/AttackSurfaceAnalyzer)

### Тестирование методом «серого ящика»

#### Анализ конфигурации

Конфигурация веб-сервера или сервера приложений имеет первостепенное значение для защиты содержимого ресурса и требует тщательного анализа с целью выявления типичных конфигурационных ошибок. Очевидно, что рекомендуемые параметры варьируются в зависимости от политик безопасности организации и функционала, возложенного на серверное ПО. Тем не менее, во всех случаях аудит должен опираться на признанные руководства по безопасной настройке (как от разработчиков ПО, так и от независимых экспертных организаций).

Невозможно сформулировать единый универсальный шаблон конфигурации для всех типов серверов, однако следует придерживаться ключевых правил:

- Включайте только те серверные модули (в случае IIS — расширения ISAPI), которые строго необходимы для работы приложения. Это сокращает поверхность атаки за счет уменьшения кодовой базы и снижения сложности системы. Кроме того, это нивелирует риски от потенциальных уязвимостей в ПО вендора, если они затрагивают отключенные модули. Тот же принцип распространяется на современные стеки промежуточного ПО: проверяйте модули веб-серверов (Apache/Nginx, IIS), связующее ПО (middleware) фреймворков и списки установленных пакетов/зависимостей (`npm ls`, `pip list` и др.) на предмет наличия компонентов, включенных шаблонными сборщиками, но не используемых в проекте — любая неиспользуемая зависимость остается частью поверхности атаки и требует регулярного патчинга.
- Обрабатывайте серверные ошибки (коды 40x и 50x) с помощью специально созданных страниц вместо стандартных страниц веб-сервера. Убедитесь, что ошибки приложения не возвращаются конечному пользователю и не содержат фрагментов программного кода или трассировок стека. Разработчики нередко забывают переопределить стандартные страницы, поскольку в тестовых средах им необходим доступ к детальной информации об ошибках.
- Убедитесь, что программное обеспечение сервера запускается с минимально возможными привилегиями в операционной системе. Это препятствует мгновенной компрометации всей ОС в случае ошибки в коде сервера, хотя злоумышленник может попытаться повысить привилегии после получения возможности выполнения команд в контексте сервисной учетной записи.
- Убедитесь, что серверное ПО корректно регистрирует как легитимные запросы, так и события ошибок.
- Настройте сервер на устойчивую обработку пиковых нагрузок для предотвращения атак типа «отказ в обслуживании» (Denial of Service). Убедитесь, что параметры производительности сервера оптимизированы надлежащим образом.
- Никогда не предоставляйте неадминистративным учетным записям (за исключением системной службы `NT SERVICE\WMSvc`) доступ на чтение или запись к файлам `applicationHost.config`, `redirection.config` и `administration.config`.
- Запретите общий сетевой доступ (file sharing) к файлам `applicationHost.config`, `redirection.config` и `administration.config`.
- Не храните конфиденциальные сведения в общедоступных для чтения конфигурационных файлах.
- При необходимости шифруйте конфиденциальные конфигурационные данные.
- Ограничивайте доступ к общим конфигурационным ресурсам и обеспечивайте их адекватную защиту.

#### Журналирование

Журналирование (logging) является неотъемлемой частью безопасности приложений, обеспечивая процессы мониторинга, реагирования на инциденты и проведение расследований. Необходимо проанализировать ведение журналов как на уровне платформы, так и на уровне самого приложения, чтобы убедиться, что события безопасности фиксируются в полном объеме, записи информативны, а сам процесс логирования не порождает дополнительных угроз.

В ходе анализа необходимо проверить следующие параметры:

- Фиксация событий безопасности: аутентификация, отказы в авторизации, действия администраторов, сбои валидации входных данных.
- Информативность: записи журнала должны содержать достаточный контекст для проведения расследования инцидентов.
- Отсутствие конфиденциальных данных в журналах: убедитесь, что в логи не попадают пароли, токены и ключи API, идентификаторы сессий, полные номера банковских карт или персональные данные. Распространенной причиной таких утечек является избыточно подробное журналирование (verbose/debug-уровень), оставленное включенным в рабочей среде (например, сохранение полного тела запросов и ответов фреймворком или логирование объектов исключений, содержащих учетные данные, переданные в качестве аргументов функций), а также интеграции с внешними системами отслеживания ошибок (APM / error-tracking), которые по умолчанию пересылают сырые данные HTTP-запросов (заголовки, payload).
- Безопасная обработка данных журнала перед сохранением и выводом: записи журнала не должны отображаться без экранирования в интерфейсах веб-просмотрщиков логов, что предотвращает возникновение хранимого межсайтового скриптинга (Stored XSS) через инъекции в логи (log injection).
- Разграничение доступа к журналам: доступ должен быть строго ограничен авторизованным персоналом и службами. Проверяйте как права доступа к локальным файлам журналов и потокам (см. раздел [Права доступа к файлам (File Permissions)](09.%20File%20Permissions.md)), так и политики централизованных платформ сбора логов (SIEM, облачные службы журналов) на предмет избыточных прав на чтение или отсутствия изоляции между арендаторами в мультиарендных (multi-tenant) средах.
- Сроки хранения: подтвердите наличие и соблюдение четкого регламента хранения данных. Опасны обе крайности: как слишком короткий срок хранения, не позволяющий расследовать инцидент, так и неограниченное хранение, превращающее архив логов в массивное хранилище конфиденциальных сведений.
- Защита от модификации: журналы должны быть защищены от несанкционированного изменения (режим добавления без перезаписи [append-only / write-once] или аналогичные механизмы контроля целостности).
- Отказоустойчивость: сбои подсистемы журналирования не должны приводить к выводу отладочной информации конечному пользователю (при невозможности записать лог система не должна отображать сырую ошибку в теле ответа).
- Централизация и корреляция: в распределенных средах (контейнеры, serverless-функции, кластеры за балансировщиками нагрузки) требуется унифицированный механизм сквозной корреляции запросов (наличие идентификатора трассировки / сквозного `Request ID` / `Trace ID` вместо изолированных записей компонентов без общего идентификатора).

Тестирование должно подтвердить, что журналы пригодны для анализа, согласованы и эффективно поддерживают процессы обнаружения и реагирования на инциденты, не становясь при этом источником утечки конфиденциальной информации.

#### Образы контейнеров

Если приложение развертывается в виде контейнерного образа, к его содержимому применяется тот же базовый принцип минимизации («удаляйте все лишнее»), что и при классическом усилении защиты серверов. Большинство этих проверок требует анализа самого образа методом «серого ящика» (gray-box); исключения оговорены отдельно. Специфика параметров контекста безопасности времени выполнения (`securityContext`: директивы `runAsNonRoot`, `readOnlyRootFilesystem`, capabilities, `seccompProfile`, пространства имен хоста) детально рассмотрена в чек-листе раздела [Права доступа к файлам (File Permissions)](09.%20File%20Permissions.md#чек-лист-по-настройке-securitycontext-и-усилению-защиты-контейнеров).

- Проверьте `Dockerfile` и процесс сборки образа на наличие неудаленных файлов по умолчанию/примеров, секретов сборки (ключей API или паролей, переданных в build arguments и сохранившихся в промежуточных слоях, даже если они были удалены в финальном слое) и лишних сборочных инструментов (компиляторов, кэша пакетных менеджеров, командных оболочек), которые должны отсекаться с помощью многоэтапной сборки (multi-stage build). При тестировании методом «серого ящика»: выполните `docker history --no-trunc <image>` либо используйте специализированные инструменты анализа слоев (например, `dive`) для проверки реального образа; уязвимость подтверждается наличием секрета или инструментов в сохраненном слое, а не просто предположением на основе чтения `Dockerfile`.
- Отдавайте предпочтение минималистичным базовым образам (версии slim, distroless или scratch) для финального слоя времени выполнения. При gray-box анализе: сопоставьте базовый образ финального этапа в `Dockerfile` со списком реально установленных в образе пакетов (команда `docker run --rm <image> sh -c "..."` при наличии оболочки или утилиты анализа слоев при ее отсутствии).
- Убедитесь, что переменные окружения режима отладки/разработки не заданы в качестве значений по умолчанию внутри образа (например, `ENV FLASK_DEBUG=1`, `ENV NODE_ENV=development`). Метод «черного ящика»: спровоцируйте ошибку приложения в работающем контейнере и проверьте, возвращается ли страница отладки или трассировка стека (по аналогии с подразделом [Debug Endpoints and Debug Modes](#отладочные-конечные-точки-и-режимы-отладки)) — это доказывает, что значение по умолчанию действительно действует во время выполнения, поскольку переопределение на уровне оркестратора могло скорректировать небезопасный параметр образа. Метод «серого ящика»: проверьте с помощью команды `docker inspect --format '{{.Config.Env}}' <image>`, что базовые параметры самого образа безопасны независимо от внешних переопределений.
- Убедитесь, что контейнер не запускается от имени пользователя `root` по умолчанию, и что в образ не встроены каталоги `.git`, файлы `.env` или иные конфиденциальные данные, скопированные широкой директивой `COPY . .` без соответствующего файла `.dockerignore`. При gray-box анализе: выполните `docker inspect --format '{{.Config.User}}' <image>` (пустое значение или `0` означает запуск от `root`) и проинспектируйте файловую систему слоев на наличие нежелательных файлов.

Пример уязвимости: выполнение команды `docker history --no-trunc` для опубликованного образа показывает сборочный слой с командой `RUN echo $DB_PASSWORD > /tmp/debug.log`, раскрывающий пароль к рабочей базе данных любому пользователю, имеющему доступ к выгрузке (pull) образа, даже несмотря на то, что в итоговом слое этот файл был удален. Доказательством уязвимости служит значение, видимое в истории слоев образа, а не сам факт использования аргумента сборки в `Dockerfile`.

#### Среды выполнения Serverless

Бессерверные функции (AWS Lambda, Azure Functions, Google Cloud Functions / Cloud Run functions) меняют точки возникновения конфигурационных ошибок, однако базовые категории уязвимостей остаются теми же. Интерфейсы консолей и CLI провайдеров различаются (AWS, Azure и GCP имеют собственную специфику); адаптируйте конкретные команды и пути под целевого облачного провайдера.

- Демонстрационный код и заготовки: убедитесь, что сгенерированный шаблонами код (`sam init`, `serverless create` и др.), включая демонстрационные обработчики (handlers) и примеры событий, удален и не развернут вместе с боевой функцией. Метод «черного ящика»: обратитесь к обнаруженным демонстрационным маршрутам и убедитесь, что они возвращают реальные данные приложения или ошибку, а не стандартный ответ шаблона.
- Отладочное логирование и детальные ответы об ошибках: многие бессерверные фреймворки по умолчанию логируют весь payload события или возвращают трассировку стека в ответе HTTP в локальном/отладочном режиме. Метод «черного ящика»: вызовите ошибку приложения через публичную точку входа функции и проверьте HTTP-ответ на наличие трассировки стека. Метод «серого ящика»: проанализируйте журналы функции (например, CloudWatch Logs) на предмет логирования полных тел запросов и ответов согласно рекомендациям по защите конфиденциальных данных в логах.
- Избыточные полномочия ролей выполнения (IAM / Execution Roles): роль выполнения функции должна быть ограничена только теми ресурсами и действиями, которые ей необходимы. В большинстве случаев анализируется в режиме «серого ящика»: просмотрите прикрепленную к роли политику (например, с помощью команды `aws iam get-role-policy`) и сопоставьте разрешенные действия и ресурсы с тем, к чему фактически обращается код функции. Если в коде функции дополнительно выявлена уязвимость выполнения команд или внедрения, подтверждение методом «черного ящика» (успешное чтение или запись ресурса, не входящего в целевой скоуп) переводит это наблюдение из ранга конфигурационных недочетов в статус критической уязвимости.
- Переменные окружения для секретов: убедитесь, что секреты извлекаются во время выполнения из специализированных хранилищ (Secrets Manager / Parameter Store), а не хранятся в открытом виде в переменных окружения функции. Метод «серого ящика»: проверьте настроенные переменные окружения через консоль или CLI провайдера и определите, содержат ли они открытые значения секретов либо ссылки (ARN / идентификаторы ресурсов) на защищенное хранилище.
- Консоли тестирования и прямого вызова: убедитесь, что встроенная в консоль функция тестового вызова («test invoke») защищена теми же механизмами разграничения доступа, что и сам аккаунт/консоль, и что вспомогательный HTTP-эндпоинт для тестирования не оставлен общедоступным. Метод «черного ящика»: попытайтесь напрямую обратиться к обнаруженным тестовым HTTP-эндпоинтам.

Пример уязвимости: роли выполнения функции предоставлены полные права `s3:*` ко всем корзинам вместо точечного действия `s3:GetObject` к одной конкретной корзине (подтверждено методом «серого ящика» через IAM-политику), а независимая уязвимость обхода каталога (path traversal) в коде функции (подтвержденная методом «черного ящика») используется для чтения и записи данных в постороннюю корзину. Это демонстрирует, как локальная брешь переросла в компрометацию всех S3-хранилищ в рамках аккаунта из-за избыточных прав роли.

#### Усиление защиты конкретных фреймворков в продакшене

Убедитесь, что для каждого используемого фреймворка применены официальные параметры усиления безопасности для рабочей среды, а не оставлены значения по умолчанию. В таблице ниже приведены характерные контрольные параметры для каждого фреймворка в качестве отправной точки для анализа. Это не исчерпывающий перечень настроек безопасности и не финальный чек-лист — названия параметров, их значения по умолчанию и даже само их наличие меняются от версии к версии, и система может оставаться уязвимой даже при корректной настройке перечисленных директив, если были упущены другие рекомендации вендора.

| Фреймворк | Контрольный параметр для проверки |
|-----------|-----------------------------------|
| Django | `DEBUG = False`, директива `ALLOWED_HOSTS` ограничена реальными доменными именами |
| Flask | `FLASK_DEBUG=0` / `debug=False`, `app.config['ENV'] = 'production'` |
| Ruby on Rails | `RAILS_ENV=production`, `config.consider_all_requests_local = false` |
| Spring Boot | Директива `management.endpoints.web.exposure.include` ограничена необходимым минимумом; `server.error.include-stacktrace=never` |
| Express / Node.js | `NODE_ENV=production` (поведение многих библиотек промежуточной обработки, включая детализацию ошибок, зависит от этой переменной) |
| Next.js / другие SPA-фреймворки | Сервер отдает рабочую сборку (production build, а не dev-сервер), карты исходного кода (source maps) исключены или доступ к ним ограничен |

Для каждого исследуемого фреймворка:

- Воспринимайте пункты таблицы как ориентировочные проверки для первичной оценки, а не как доказательство полной защищенности системы; сверяйтесь с официальными актуальными руководствами по развертыванию в production (ссылки приведены в разделе References).
- Проверяйте фактическую конфигурацию времени выполнения (runtime configuration), а не только статичные конфигурационные файлы: переменные окружения, флаги командной строки или переопределения на уровне оркестрации (переменные контейнера, Kubernetes ConfigMap/Secret, настройки панели PaaS) могут изменять действующие значения в рантайме, даже если файл в репозитории настроен верно. По возможности подтверждайте параметры через поведенческие тесты работающего приложения (например: отдает ли приложение страницу отладки при ошибке? доступен ли отладочный эндпоинт?), а не только статическим анализом файлов.
- Не делайте вывод, что наличие одной правильной настройки гарантирует безопасность фреймворка в целом: прочие критические параметры из того же руководства могут быть не настроены.
