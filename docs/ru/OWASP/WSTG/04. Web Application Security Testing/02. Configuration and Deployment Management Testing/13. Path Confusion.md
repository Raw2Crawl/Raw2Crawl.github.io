# Путаница путей (Path Confusion)

| ID |
| --- |
| WSTG-CONF-13 |

## Резюме

Путаница путей (Path Confusion) возникает в тех случаях, когда различные компоненты на пути обработки запроса (маршрутизаторы, обратные прокси, кэширующие серверы, WAF, само веб-приложение) по-разному интерпретируют один и тот же URL-путь из-за различий в алгоритмах нормализации путей, обработке завершающих слешей (trailing slashes), чувствительности к регистру или правил декодирования символов. Подобное несогласование позволяет атакующему добиться того, чтобы один компонент трактовал путь одним образом, а другой — принципиально иначе, обходя средства защиты, опирающиеся на сопоставление путей (например, правила контроля доступа, маршрутизаторы или ключи кэширования).

Например, если маршруты в приложении настроены некорректно, а целевой ресурс использует CDN, злоумышленник может сыграть на расхождениях между тем, что отдает сервер-источник, и тем, по какому ключу кэширует ответ CDN, для реализации атаки обмана веб-кэша (Web Cache Deception, WCD).

Примечание по скоупу: данное тестирование направлено именно на проверку несогласованности идентификации строкового пути между компонентами, которые должны интерпретировать его одинаково. Оно не касается передачи последовательностей `../` или закодированных спецсимволов для выхода за пределы каталога (это классический обход каталога `[Path Traversal]`, рассматриваемый в рамках тестирования валидации входных данных и инъекций, например WSTG-ATHZ-01). Путаница путей охватывает ситуации, когда путь синтаксически корректен и не пытается покинуть целевой каталог, но обрабатывается различными уровнями архитектуры не согласованно.

В связи с этим специалисту по безопасности необходимо оценить устойчивость данной конфигурации для предотвращения сопутствующих атак.

## Цели тестирования

- Убедиться, что пути приложения настраиваются и нормализуются единообразно во всех компонентах архитектуры (приложение, прокси, кэш, CDN, WAF), принимающих решения на основе анализа URL-пути.
- Выявить сценарии, при которых завершающие слеши, регистр символов или особенности кодирования приводят к обходу механизмов безопасности (правил аутентификации/авторизации, маршрутизации, генерации ключей кэша) или к их некорректной работе.

## Методика тестирования

### Тестирование методом «черного ящика»

В сценарии тестирования методом «черного ящика» аудитор подменяет существующие легитимные пути несуществующими вариантами, после чего анализирует реакцию системы и возвращаемые коды состояния.

Например, в приложении существует путь панели управления, отображающий баланс учетной записи пользователя (денежные средства, игровые очки и т. д.).

Предположим, базовый путь имеет вид `https://example.com/user/dashboard`. Тестировщик должен проверить различные варианты обработки, которые разработчик мог предусмотреть для данного адреса. Для поиска уязвимостей класса Web Cache Deception следует запросить путь вида `https://example.com/user/dashboard/non.js`: если конфиденциальные данные панели управления продолжают отображаться, а ресурс подключен к CDN (или иному веб-кэшу), то атака Web Cache Deception с высокой вероятностью применима.

Для каждого защищенного или маршрутизируемого пути протестируйте следующие вариации и сравните полученный код статуса, тело ответа и примененный эшелон безопасности с эталонным поведением базового пути:

- Завершающий слеш: сравните `/user/dashboard` и `/user/dashboard/` — проверьте, применяется ли правило контроля доступа, маршрутизатор или ключ кэша только к одному из этих вариантов.
- Чувствительность к регистру (Case sensitivity): сравните `/user/dashboard` и `/User/Dashboard` — проверьте, одинаково ли нормализуют регистр сервер-источник, прокси, кэш и WAF.
- Нормализация пути / относительные сегменты без выхода из контекста: проверьте пути `/user/dashboard/./` или повторные слеши `/user//dashboard` — это не выход за пределы директории, а альтернативное представление того же ресурса.
- Процентное кодирование (Percent-encoding) разделителей путей или зарезервированных символов: `/user%2Fdashboard`, `/user/dashboard%2F..%2F` (где результат декодирования остается в рамках разрешенного контекста) — выясните, выполняет ли компонент фильтрации декодирование до сопоставления с правилом или после него.
- Комбинации кодирования и смены регистра: проверьте, не сопоставляет ли WAF или шлюз авторизации сырую строку запроса, в то время как приложение обрабатывает уже декодированную и нормализованную строку (или наоборот).

Уязвимость фиксируется, если любая из вариаций приводит к иному результату (обходит проверку прав, попадает в другой обработчик маршрута, кэшируется или отдается в обход политики), чем канонический путь, именно по причине разночтений в идентификации пути между компонентами, а не из-за выхода за пределы каталога.

### Тестирование методом «белого ящика»

Проанализируйте конфигурацию маршрутизации приложения. В большинстве случаев разработчики используют регулярные выражения для сопоставления URL-путей.

В приведенном ниже фрагменте файла `urls.py` фреймворка Django продемонстрирован пример уязвимости Path Confusion. Разработчик применил некорректное регулярное выражение, порождающее брешь в безопасности:

```python
    from django.urls import re_path
    from . import views

    urlpatterns = [

        re_path(r'.*^dashboard', views.path_confusion ,name = 'index'),

    ]
```

Если пользователь откроет в браузере URL вида `https://example.com/dashboard/none.js`, приложение все равно отобразит данные личного кабинета пользователя, и при наличии промежуточного CDN или кэш-сервера злоумышленник сможет реализовать атаку Web Cache Deception.

## Рекомендации по устранению

- Откажитесь от принятия решений о кэшировании исключительно на основе расширения файла или пути запроса (опирайтесь на заголовок `Content-Type`).
- Убедитесь, что промежуточные механизмы кэширования строго соблюдают заголовки `Cache-Control`, передаваемые приложением.
- Реализуйте обработку несуществующих ресурсов (File Not Found) и перенаправления в строгом соответствии со стандартами RFC.
- Обеспечьте согласованную нормализацию путей (регистр, завершающие слеши, кодирование, повторяющиеся разделители) к единой канонической форме во всех компонентах архитектуры, принимающих решения на основе URL (приложение, обратный прокси, кэш, CDN, WAF).
- Выполняйте сопоставление путей для контроля доступа и маршрутизации только после полной нормализации и декодирования строки, а не по сырой строке HTTP-запроса.
