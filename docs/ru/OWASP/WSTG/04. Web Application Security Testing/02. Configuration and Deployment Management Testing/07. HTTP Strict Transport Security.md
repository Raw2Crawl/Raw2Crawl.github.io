# HTTP Strict Transport Security (HSTS)

| ID |
| --- |
| WSTG-CONF-07 |

## Резюме

Механизм строгой транспортной безопасности HTTP (HTTP Strict Transport Security, HSTS) позволяет веб-серверу уведомлять браузер пользователя с помощью специального HTTP-заголовка ответа о том, что клиент никогда не должен устанавливать незашифрованные соединения по протоколу HTTP с серверами указанного домена. Вместо этого браузер обязан автоматически направлять все последующие запросы к сайту исключительно по защищенному протоколу HTTPS. Данный механизм также блокирует возможность игнорирования пользователями предупреждений об ошибках цифровых сертификатов.

Отсутствие заголовка HSTS или его некорректная конфигурация приводят к серьезным угрозам безопасности:

- Перехват и несанкционированный доступ к конфиденциальным данным, передаваемым по открытому сетевому каналу.
- Проведение атак типа «человек посередине» (Manipulator-in-the-Middle, MITM) за счет согласия пользователей с предупреждениями о недействительных сертификатах либо путем принудительного понижения версии протокола и удаления перенаправлений на HTTPS (SSL stripping).
- Ошибочный ввод адреса пользователем в адресной строке браузера с указанием `http://` вместо `https://` либо переход по ссылкам внутри веб-приложения, ошибочно сформированным по протоколу HTTP.

## Цели тестирования

- Проверить наличие заголовка HSTS, его директивы и их числовые значения на соответствие актуальным рекомендациям безопасности.
- Убедиться, что ресурс защищен от риска первого небезопасного соединения (trust gap) с помощью включения в список предзагрузки (preload list) или защищенной схемы перенаправления с HTTP на HTTPS.
- Проверить согласованное применение HSTS для основного домена и всех его поддоменов, а также отсутствие маскировки проблем со смешанным содержимым (mixed content).

## Методика тестирования

- Убедитесь в наличии заголовка HSTS в ответах по протоколу HTTPS, исследовав заголовки ответа сервера через перехватывающий прокси-сервер.
- Используйте утилиту `curl` следующим образом:

```bash
$ curl -s -D- https://owasp.org | grep -i strict-transport-security:
Strict-Transport-Security: max-age=31536000
```

- Оцените значения параметров директивы. Пример заголовка, пригодного для включения в список предзагрузки: `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`:
    - Параметр `max-age` (время в секундах, на протяжении которого браузер обязан принудительно использовать только HTTPS для данного хоста) должен составлять не менее `31536000` (1 год) или `63072000` (2 года), если домен подается или уже включен в список HSTS preload. Существенно меньшие значения или значение `max-age=0` являются поводом для фиксации уязвимости (за исключением контролируемого отката политики HSTS).
    - Проверьте наличие директивы `includeSubDomains` (распространяет действие политики на все поддомены домена). При ее наличии проверьте выборку поддоменов целевой организации — включая сервисы за рамками основного приложения (почтовые службы, внутренние утилиты, тестовые стенды staging и др.) — на предмет поддержки корректного HTTPS. Поддомен, не поддерживающий HTTPS, станет полностью недоступным для браузеров пользователей, закэшировавших данную политику.
    - Проверьте наличие директивы `preload`. При ее указании убедитесь, что домен действительно внесен в [список Chromium HSTS preload list](https://hstspreload.org/), используемый браузерами Chrome, Firefox, Safari и Edge (сама по себе директива `preload` в заголовке не активирует встроенную защиту в браузерах — значение имеет лишь фактическое присутствие домена в глобальном списке):

```bash
curl -s "https://hstspreload.org/api/v2/status?domain=example.com"
```

  Если директива `preload` присутствует в заголовке, но домен отсутствует в списке (или был удален из него), убедитесь, что процедура включения находится в процессе обработки, а директива не является забытым неработающим параметром.

- Проверьте путь первого запроса и редиректа: HSTS защищает только те запросы, которые отправляются после того, как браузер хотя бы один раз получил данный заголовок от сервера (модель доверия при первом использовании — Trust On First Use, TOFU). Соответственно, самый первый визит пользователя — или любой сеанс после истечения времени жизни закэшированной политики — осуществляется по открытому протоколу HTTP, если только домен не включен в глобальный список предзагрузки preload. Этот начальный запрос или редирект может быть перехвачен или модифицирован злоумышленником до того, как браузер узнает о существовании HSTS. Проверьте этот вектор напрямую:

```bash
curl -s -D- http://example.com | head -n 5
```

  Убедитесь, что сервер возвращает перенаправление (`301 Moved Permanently` или `308 Permanent Redirect`) на защищенную версию HTTPS, и что последующий ответ HTTPS содержит заголовок HSTS (согласно спецификации, браузеры игнорируют заголовок HSTS, если он получен по незашифрованному протоколу HTTP, поэтому он обязательно должен передаваться на стороне HTTPS после редиректа). Включение в глобальный список `preload` является единственным надежным способом полностью закрыть данную брешь безопасности, поскольку в этом случае правила защиты уже вшиты в исходный код браузера.

- Оцените взаимодействие механизма со смешанным содержимым (mixed content): HSTS принудительно переводит на HTTPS навигацию верхнего уровня и загрузку подресурсов с того же хоста, однако не переписывает явные абсолютные кросс-доменные ссылки `http://` в HTML-разметке страницы. Проверьте исходный код страницы и вкладку Network инструментов разработчика на предмет абсолютных ссылок вида `http://otherhost/...` — они по-прежнему подвержены стандартной браузерной блокировке смешанного содержимого независимо от HSTS (см. раздел [Совместное использование ресурсов между разными источниками (Cross Origin Resource Sharing)](../11.%20Client-side%20Testing/07.%20Cross%20Origin%20Resource%20Sharing.md)). Отдельно убедитесь, что ссылки вида `http://` на ресурсы собственного домена изначально переведены на HTTPS, а не просто «работают» за счет невидимого автоматического апгрейда HSTS в браузере (подобное поведение маскирует некорректные ссылки, требующие исправления в коде).

- Для приложений, размещенных за CDN, балансировщиками нагрузки или обратными прокси-серверами, убедитесь, что заголовок добавляется (или корректно проксируется) на граничном узле, терминирующем сессии TLS для конечных пользователей, а не только на внутреннем сервере-источнике (origin).

### Отправка в список предзагрузки (Preload List)

Включение домена в список HSTS preload ([hstspreload.org](https://hstspreload.org/)) представляет собой ручную организационную процедуру, которая не активируется исключительно указанием директивы в заголовке ответа. Перед выдачей рекомендации на включение убедитесь в соблюдении обязательных условий:

- На основном домене должен быть установлен валидный SSL/TLS-сертификат, а все HTTP-запросы должны безусловно перенаправляться на HTTPS.
- Поддомен `www` (при наличии соответствующей DNS-записи) также должен обслуживаться по HTTPS с валидным сертификатом.
- Заголовок `Strict-Transport-Security` в ответах HTTPS основного домена должен содержать параметр `max-age` не менее `31536000` (1 год, хотя сервис рекомендует `63072000` — 2 года), а также обязательные директивы `includeSubDomains` и `preload`.
- Все без исключения поддомены, включая почтовые службы, корпоративные порталы и тестовые стенды, должны корректно поддерживать HTTPS, поскольку директива `includeSubDomains` сделает протокол HTTPS обязательным для всех субдоменов организации.

Поскольку изменения списка preload включаются непосредственно в релизы браузеров и процесс исключения домена из этого списка крайне сложен и длителен (удаление может занимать месяцы, пока обновления не дойдут до всех пользователей), решение о подаче заявки должно приниматься централизованно на уровне руководства организации. Тестировщикам категорически запрещено самостоятельно отправлять заявки на добавление доменов клиентов в ходе проведения аудита.

## Рекомендации по устранению

- Отправляйте заголовок `Strict-Transport-Security` во всех ответах по протоколу HTTPS со значением `max-age` не менее одного года.
- Настройте обязательное перенаправление всего HTTP-трафика на HTTPS и убедитесь, что целевой ресурс перенаправления возвращает заголовок HSTS.
- Добавляйте директиву `includeSubDomains` после подтверждения того, что абсолютно все поддомены организации поддерживают протокол HTTPS.
- Рассмотрите возможность использования параметра `preload` и подачи заявки на включение в глобальный список предзагрузки HSTS для доменов, требующих максимального уровня защиты с самого первого подключения, предварительно согласовав это решение с руководством.
- Не полагайтесь на автоматический апгрейд соединений механизмом HSTS вместо исправления жестко заданных ссылок `http://` в верстке и скриптах приложения.
