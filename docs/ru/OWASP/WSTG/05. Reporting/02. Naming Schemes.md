# Схемы именования уязвимостей

В условиях непрерывного роста числа администрируемых ИТ-активов специалистам по безопасности требуются все более мощные инструменты для проведения масштабного автоматизированного анализа. Благодаря программным средствам эксперты могут сосредоточить внимание на более сложных и творческих интеллектуальных задачах. К сожалению, организация взаимодействия между сканерами уязвимостей, антивирусным ПО и системами обнаружения вторжений (Intrusion Detection Systems, IDS) представляет собой нетривиальную проблему. Это приводит к техническим сложностям и требует стандартизированного способа идентификации каждого программного дефекта, уязвимости или ошибки конфигурации. Отсутствие необходимой интероперабельности влечет за собой расхождения в оценках защищенности, противоречивость отчетов и необходимость дополнительных усилий по корреляции данных, что вызывает существенные непроизводительные затраты времени и ресурсов.

Схема именования уязвимостей (naming scheme) представляет собой систематизированную методологию идентификации каждой уязвимости для обеспечения однозначной идентификации и эффективного обмена информацией. Эта цель достигается путем определения уникального, структурированного и удобного для машинной обработки имени каждой уязвимости. Существует несколько схем именования, наиболее распространенными из которых являются:

- Common Platform Enumeration (`CPE`) — общий перечень платформ
- Software Identification Tag (`SWID`) — тег идентификации программного обеспечения
- Package URL (`PURL`) — универсальный локатор пакета

## Тег идентификации программного обеспечения (SWID)

Тег идентификации программного обеспечения (Software Identification Tag, `SWID`) — это международный стандарт Международной организации по стандартизации (ISO), определенный в ISO/IEC 19770-2:2015. Теги `SWID` применяются для однозначной идентификации каждого программного продукта в рамках комплексных жизненных циклов управления программными активами (Software Asset Management, SAM). Национальный институт стандартов и технологий США (NIST) рекомендует использовать эту схему в качестве основного идентификатора для любого разрабатываемого или устанавливаемого ПО. На основе `SWID` возможно автоматически генерировать другие форматы идентификации, такие как схема `CPE`, используемая в Национальной базе уязвимостей США (National Vulnerability Database, NVD), тогда как обратное преобразование невозможно.

Каждый тег `SWID` оформляется в стандартизированном формате XML. Структура тега `SWID` состоит из трех групп элементов. Первый блок содержит 7 обязательных предопределенных элементов, необходимых для признания тега валидным. Далее следует опциональный блок, предоставляющий набор из 30 возможных предопределенных параметров, которые создатель тега может использовать для передачи достоверной и детализированной информации. Наконец, группа элементов `Extended` дает возможность разработчику тега задавать любые нестандартные параметры, необходимые для точного описания продукта. Высокая гранулярность `SWID` позволяет описывать не только сам продукт, но и его конкретный статус на текущем этапе жизненного цикла программного обеспечения.

### Примеры

- Патч _ACME Roadrunner Service Pack 1_, выпущенный корпорацией ACME для уже установленного продукта с идентификатором `@tagId`: _com.acme.rms-ce-v4-1-5-0_:

```xml
<SoftwareIdentity
                  xmlns="https://standards.iso.org/iso/19770/-2/2015/schema.xsd"
                  name="ACME Roadrunner Service Pack 1"
                  tagId="com.acme.rms-ce-sp1-v1-0-0"
                  patch="true"
                  version="1.0.0">
  <Entity
          name="The ACME Corporation"
          regid="acme.com"
          role="tagCreator softwareCreator"/>
  <Link
        rel="patches"
        href="swid:com.acme.rms-ce-v4-1-5-0">
    ...
</SoftwareIdentity>
```

- Дистрибутив Red Hat Enterprise Linux версии 8 для архитектуры x86-64:

```xml
<SoftwareIdentity
                  xmlns="https://standards.iso.org/iso/19770/-2/2015/schema.xsd"
                  xmlns:xsi="https://www.w3.org/2001/XMLSchema-instance"
                  xsi:schemaLocation="https://standards.iso.org/iso/19770/-2/2015/schema.xsd"
                  xml:lang="en-US"
                  name="Red Hat Enterprise Linux"
                  tagId="com.redhat.RHEL-8-x86_64"
                  tagVersion="1"
                  version="8"
                  versionScheme="multipartnumeric"
                  media="(OS:linux)">
```

## Универсальное перечисление платформ (CPE)

Схема Common Platform Enumeration (`CPE`) — это структурированная схема именования систем информационных технологий, программного обеспечения и пакетов, поддерживаемая базой данных `NVD`. Как правило, она используется в связке с кодами Common Vulnerabilities and Exposures (например, `CVE-2017-0147`). Несмотря на то что `CPE` официально считается устаревающей схемой, вытесняемой `SWID`, она по-прежнему широко применяется во множестве систем безопасности.

Схема реализована в виде словаря зарегистрированных значений, предоставляемого `NVD`. Каждый код `CPE` может быть представлен в виде отформатированного имени (Well-Formed Name, WFN) или в виде URL-идентификатора. Каждое значение ОБЯЗАНО следовать следующей грамматике:

- _cpe-name_ = "cpe:" component-list
- _component-list_ = part ":" vendor ":" product ":" version ":" update ":" edition ":" lang
- _component-list_ = part ":" vendor ":" product ":" version ":" update ":" edition
- _component-list_ = part ":" vendor ":" product ":" version ":" update
- _component-list_ = part ":" vendor ":" product ":" version
- _component-list_ = part ":" vendor ":" product
- _component-list_ = part ":" vendor
- _component-list_ = part
- _component-list_ = empty
- _part_ = "h" / "o" / "a" = string
- _vendor_ = string
- _product_ = string
- _version_ = string
- _update_ = string
- _edition_ = string
- _lang_ LANGTAG / empty
- _string_ = *( unreserved / pct-encoded )
- _empty_ = ""
- _unreserved_ = ALPHA / DIGIT / "-" / "." / "_" / " ̃"
- _pct-encoded_ = "%" HEXDIG HEXDIG
- _ALPHA_ = %x41-5a / %x61-7a ; A-Z or a-z
- _DIGIT_ = %x30-39 ; 0-9
- _HEXDIG_ = DIGIT / "a" / "b" / "c" / "d" / "e" / "f"
- _LANGTAG_ = cf. `[RFC5646]`

### Примеры

- Microsoft Internet Explorer 8.0.6001 Beta (любая редакция): `wfn:[part="a",vendor="microsoft",product="internet_explorer", version="8\.0\.6001",update="beta",edition=ANY]`, который преобразуется в URL: `cpe:/a:microsoft:internet_explorer:8.0.6001:beta`.
- Foo\Bar Big$Money Manager 2010 Special Edition для iPod Touch 80GB: `wfn:[part="a",vendor="foo\\bar",product="big\$money_manager_2010", sw_edition="special",target_sw="ipod_touch",target_hw="80gb"]`, который преобразуется в URL: `cpe:/a:foo%5cbar:big%24money_manager_2010:::~~special~ipod_touch~80gb~`.

## URL пакета (Package URL)

Стандарт Package URL унифицирует представление метаданных программных пакетов, позволяя однозначно идентифицировать и находить пакеты независимо от конкретного поставщика, проекта или экосистемы разработки.

PURL представляет собой валидный URL в кодировке ASCII согласно стандарту `RFC3986`, состоящий из семи элементов, разделенных специальными символами для удобства автоматизированного парсинга:

`scheme:type/namespace/name@version?qualifiers#subpath`

Назначение каждого компонента:

- _scheme_: константный префикс схемы URL `"pkg"`. (**Обязательный**).
- _type_: тип пакета или протокол пакетного менеджера, например `maven`, `npm`, `nuget`, `gem`, `pypi` и т. д. (**Обязательный**).
- _namespace_: специфичный для типа пакета префикс, такой как имя владельца, groupid и т. д. (Опциональный).
- _name_: имя пакета. (**Обязательный**).
- _version_: версия пакета. (Опциональный).
- _qualifiers_: дополнительные уточняющие квалификаторы пакета, такие как операционная система, архитектура, дистрибутив и т. д. (Опциональный).
- _subpath_: дополнительный относительный путь внутри пакета относительно его корня. (Опциональный).

### Примеры

- Утилита Curl, собранная в виде пакета `.deb` для Debian Jessie под архитектуру i386: `pkg:deb/debian/curl@7.50.3-1?arch=i386&distro=jessie`
- Docker-образ Apache Cassandra с подписью по хешу SHA256 244fd47e07d1004f0aed9c: `pkg:docker/cassandra@sha256:244fd47e07d1004f0aed9c`

## Рекомендации по использованию

| USE  | RECOMMENDATION  |
|---|---|
| Client or Server Application | CPE or SWID |
| Container | PURL or SWID |
| Firmware | CPE or SWID* |
| Library or Framework (package) | PURL |
| Library or Framework (non-package) | SWID |
| Operating System | CPE or SWID |
| Operating System Package | PURL or SWID |

> Примечание: Ввиду устаревания стандарта `CPE`, в индустрии принято рекомендовать новым проектам внедрять `SWID` при выборе между этими двумя методами. Несмотря на это, `CPE` сохраняет широкое практическое применение в существующих решениях и проектах.
