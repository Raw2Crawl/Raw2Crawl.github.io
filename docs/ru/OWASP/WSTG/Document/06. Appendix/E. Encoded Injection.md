# E. Кодированные инъекции {#encoded-injection}

## Предпосылки

Кодирование символов (character encoding) — это процесс сопоставления символов, чисел и других знаков со стандартным форматом представления. Как правило, это выполняется для подготовки сообщения к передаче между отправителем и получателем. Простыми словами, это преобразование символов (принадлежащих к различным языкам, таким как английский, китайский, греческий или любой другой) в байты. Примером широко распространенной схемы кодирования является американский стандартный код для обмена информацией (American Standard Code for Information Interchange, ASCII), в котором изначально использовались 7-битные коды. Более современными примерами схем кодирования выступают отраслевые стандарты Юникода `UTF-8` и `UTF-16`.

В сфере информационной безопасности приложений из-за колоссального разнообразия доступных схем кодирования возникла распространенная практика их нецелевого использования: кодирование вредоносных строк инъекций с целью их обфускации (obfuscation). Это позволяет обходить фильтры валидации входных данных или эксплуатировать особенности отрисовки закодированного текста веб-браузерами.

## Кодирование ввода и обход фильтров

Веб-приложения обычно применяют различные механизмы фильтрации входных данных, чтобы ограничить значения, которые могут быть отправлены пользователем. Если эти входные фильтры реализованы недостаточно надежно, злоумышленник может пропустить через них опасные символы. Например, прямой слэш `/` в стандарте ASCII в шестнадцатеричном представлении кодируется как `2F` (hex), тогда как в кодировке Юникод тот же символ (`/`) может быть закодирован двухбайтовой последовательностью `C0` `AF`. Соответственно, механизмы фильтрации обязаны учитывать используемую кодировку. Если фильтр выявляет инъекции исключительно в кодировке `UTF-8`, для его обхода атакующий может применить иную схему кодирования.

## Кодирование вывода: согласованность сервера и браузера

Веб-браузеры должны однозначно понимать используемую схему кодирования для корректного отображения страницы. В идеале эта информация передается браузеру через поле HTTP-заголовка `Content-Type`, как показано ниже:

```http
Content-Type: text/html; charset=UTF-8
```

либо через HTML-тег `META` (`META HTTP-EQUIV`):

```html
<META http-equiv="Content-Type" content="text/html; charset=ISO-8859-1">
```

Именно на основе этих объявлений кодировки браузер определяет набор символов для декодирования байтов в отображаемые символы. Учитывайте, что тип содержимого, указанный в HTTP-заголовке, имеет приоритет перед объявлением в META-теге.

Организация CERT описывает данную проблему следующим образом:

Многие веб-страницы оставляют кодировку символов (параметр `charset` в протоколе HTTP) неопределенной. В ранних версиях HTML и HTTP предполагалось, что при отсутствии явного указания кодировка должна по умолчанию принимать значение `ISO-8859-1`. Однако на практике во многих браузерах дефолтное значение отличалось, поэтому полагаться на стандартную `ISO-8859-1` было невозможно. Спецификация HTML 4 легитимизировала данную ситуацию: если кодировка не задана явно, может применяться любая кодировка символов.

Если веб-сервер не указывает используемую кодировку, он не может определить, какие именно символы являются специальными. Страницы без явно заданной кодировки открываются корректно в большинстве случаев, поскольку подавляющее большинство наборов символов присваивают одинаковые символы байтовым значениям меньше 128. Однако какие значения выше 128 являются специальными? Некоторые 16-битные схемы кодирования содержат альтернативные многобайтовые представления для специальных символов, таких как `<`. Отдельные браузеры распознают эту альтернативную кодировку и обрабатывают ее. Такое поведение формально «корректно», но оно чрезвычайно затрудняет предотвращение атак с применением вредоносных скриптов. Сервер попросту не знает, какие байтовые последовательности соответствуют спецсимволам.

Таким образом, не получив информацию о кодировке от сервера, браузер либо пытается угадать схему кодирования, либо переключается на схему по умолчанию. В некоторых случаях пользователь самостоятельно настраивает дефолтную кодировку в браузере. Любое подобное несоответствие между кодировкой сервера и браузера может привести к тому, что браузер интерпретирует веб-страницу непредусмотренным или потенциально опасным образом.

### Кодированные инъекции

Все приведенные ниже сценарии представляют собой лишь небольшую выборку методов обфускации, используемых для обхода фильтров входных данных. Кроме того, успешность атак через кодированные инъекции во многом зависит от используемого браузера. Например, инъекции в кодировке `US-ASCII` ранее срабатывали только в браузере Internet Explorer, но блокировались в Firefox. Следовательно, эффективность атак с кодированными инъекциями в значительной степени определяется браузером жертвы.

### Базовое кодирование

Рассмотрим базовый фильтр валидации входных данных, блокирующий внедрение одинарной кавычки. В этом случае фильтр можно легко обойти следующей инъекцией:

```html
<script>alert(String.fromCharCode(88,83,83))</script>
```

Функция JavaScript `String.fromCharCode` принимает заданные числовые коды Юникода и преобразует их в соответствующую строку. Это одна из базовых форм кодированных инъекций. Другой вектор обхода фильтра:

```html
<IMG src="" onerror=javascript:alert(&quot;XSS&quot;)>
```

Либо с использованием соответствующих HTML-мнемоник ([HTML character codes](https://www.rapidtables.com/code/text/unicode-characters.html)):

```html
<IMG src="" onerror="javascript:alert(&#34;XSS&#34;)">
```

В приведенном примере для формирования строки инъекции используются HTML-сущности (HTML Entities). Кодирование HTML-сущностями применяется для отображения знаков, имеющих специальное служебное значение в разметке HTML. Например, символ `>` служит закрывающей скобкой тега. Чтобы отобразить этот символ как текст на странице, в исходный код внедряются соответствующие символьные мнемоники HTML. Указанные инъекции представляют собой лишь один из вариантов кодирования; существует множество других способов обфускации строк для обхода описанного фильтра.

### Шестнадцатеричное кодирование

Шестнадцатеричная система счисления (Hex) имеет основание 16 и использует 16 различных символов (от `0` до `9` и от `A` до `F`) для представления значений. Шестнадцатеричное кодирование — еще одна форма обфускации, применяемая для обхода фильтров валидации. Например, шестнадцатеричная версия строки `<IMG SRC=javascript:alert('XSS')>` имеет вид:

```html
<IMG SRC=%6A%61%76%61%73%63%72%69%70%74%3A%61%6C%65%72%74%28%27%58%53%53%27%29>
```

Вариация приведенной строки представлена ниже; она применима в ситуациях, когда символ `%` фильтруется системой:

```html
<IMG SRC=&#x6A&#x61&#x76&#x61&#x73&#x63&#x72&#x69&#x70&#x74&#x3A&#x61&#x6C&#x65&#x72&#x74&#x28&#x27&#x58&#x53&#x53&#x27&#x29>
```

Существуют и другие схемы кодирования, такие как Base64 и восьмеричная система (Octal), которые также могут применяться для обфускации. Хотя универсального способа обхода не существует, сочетание практических экспериментов и грамотного манипулирования входными данными позволяет обнаружить бреши в слабо спроектированных фильтрах валидации.

### Кодировка UTF-7

Кодирование UTF-7 для конструкции:

```html
<SCRIPT>
    alert('XSS');
</SCRIPT>
```

выглядит следующим образом:

`+ADw-SCRIPT+AD4-alert('XSS');+ADw-/SCRIPT+AD4-`

Для исполнения приведенного скрипта браузер должен интерпретировать веб-страницу в кодировке `UTF-7`.

### Многобайтовое кодирование

Кодирование с переменной шириной символа (variable-width encoding) — это схема кодирования, использующая байтовые последовательности различной длины для представления символов. Многобайтовое кодирование (Multi-Byte Encoding) относится к этой категории и использует различное число байтов для представления одного знака. Многобайтовое кодирование применяется преимущественно для языков с объемным набором иероглифов и символов (китайский, японский, корейский).

Многобайтовое кодирование исторически активно применялось для обхода стандартных функций валидации данных и проведения атак межсайтового скриптинга и SQL-инъекций.
