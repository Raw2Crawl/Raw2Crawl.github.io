# Перехват сессии (Session Hijacking)

| ID |
| --- |
| WSTG-SESS-09 |

## Резюме

Злоумышленник, получивший доступ к сессионным cookie пользователя, может выдать себя за него, предъявив эти cookie. Такая атака известна как перехват сессии (Session Hijacking). При рассмотрении сетевых злоумышленников (network attackers), то есть атакующих, контролирующих используемую жертвой сеть, сессионные cookie могут быть неправомерно раскрыты атакующему по незашифрованному протоколу HTTP. Чтобы предотвратить это, сессионные cookie должны быть помечены атрибутом `Secure`, гарантирующим их передачу исключительно по протоколу HTTPS.

Атрибут `Secure` следует использовать даже в том случае, когда веб-приложение полностью развернуто поверх HTTPS, иначе становится возможной следующая атака с кражей cookie. Предположим, что сайт `example.com` полностью функционирует по HTTPS, но не помечает свои сессионные cookie как `Secure`. В этом случае возможна следующая последовательность шагов атаки:

1. Жертва отправляет запрос на `https://another-site.com`.
2. Атакующий искажает соответствующий ответ так, чтобы он инициировал запрос к `https://example.com`.
3. Браузер теперь пытается получить доступ к `https://example.com`.
4. Несмотря на то что запрос завершается сбоем, сессионные cookie передаются в открытом виде по HTTP.

В качестве альтернативы перехват сессии можно предотвратить путем запрета использования протокола HTTP с помощью [HSTS](https://en.wikipedia.org/wiki/HTTP_Strict_Transport_Security) (HTTP Strict Transport Security). Обратите внимание на тонкость, связанную с областью действия cookie (cookie scoping). В частности, полное внедрение HSTS требуется в тех случаях, когда сессионные cookie выдаются с установленным атрибутом `Domain`.

Полное внедрение HSTS описано в исследовательской работе *Testing for Integrity Flaws in Web Sessions* авторов Stefano Calzavara, Alvise Rabitti, Alessio Ragazzo и Michele Bugliesi. Полное внедрение HSTS происходит, когда хост активирует HSTS для себя и всех своих поддоменов. Частичное внедрение HSTS имеет место, когда хост активирует HSTS только для самого себя.

При установленном атрибуте `Domain` сессионные cookie могут разделяться между поддоменами. Использования HTTP на поддоменах следует избегать во избежание раскрытия незашифрованных cookie, отправляемых по HTTP. Чтобы проиллюстрировать этот недостаток безопасности, предположим, что сайт `example.com` активирует HSTS без директивы `includeSubDomains`. При этом сайт выдает сессионные cookie с атрибутом `Domain`, установленным в `example.com`. В таком случае возможна следующая атака:

1. Жертва отправляет запрос к `https://another-site.com`.
2. Атакующий искажает соответствующий ответ так, чтобы он инициировал запрос к `https://fake.example.com`.
3. Браузер теперь пытается обратиться к `https://fake.example.com`, что разрешено конфигурацией HSTS.
4. Поскольку запрос отправляется к поддомену `example.com` с установленным атрибутом `Domain`, он включает сессионные cookie, которые утекают в открытом виде по HTTP.

Для предотвращения этой атаки на корневом домене (apex domain) должен быть активирован полный механизм HSTS.

## Цели тестирования

- Выявить уязвимые сессионные cookie.
- Перехватить уязвимые cookie и оценить уровень риска.

## Методика тестирования

Данная стратегия тестирования ориентирована на сетевых злоумышленников, поэтому ее необходимо применять только к сайтам без полного внедрения HSTS (сайты с полным внедрением HSTS защищены, поскольку их cookie не передаются по протоколу HTTP). Предполагается наличие двух тестовых учетных записей на исследуемом сайте: одна выступает в роли жертвы, а другая — в роли атакующего. Мы моделируем сценарий, при котором злоумышленник похищает все cookie, не защищенные от раскрытия по HTTP, и отправляет их сайту для доступа к учетной записи жертвы. Если этих cookie достаточно для выполнения действий от имени жертвы, перехват сессии возможен.

Ниже приведены шаги для выполнения данного теста:

1. Войти на сайт под учетной записью жертвы и перейти на любую страницу, предоставляющую защищенную функцию, требующую аутентификации.
2. Удалить из хранилища cookie (cookie jar) все cookie, удовлетворяющие любому из следующих условий:
    - в случае отсутствия внедрения HSTS: установлен атрибут `Secure`.
    - в случае частичного внедрения HSTS: установлен атрибут `Secure` или не установлен атрибут `Domain`.
3. Сохранить снимок cookie jar.
4. Вызвать защищенную функцию, определенную на шаге 1.
5. Проверить, была ли операция из шага 4 выполнена успешно. Если да, атака завершилась успехом.
6. Очистить cookie jar, войти под учетной записью атакующего и перейти на страницу из шага 1.
7. Записать в cookie jar по одному все cookie, сохраненные на шаге 3.
8. Снова вызвать защищенную функцию, определенную на шаге 1.
9. Очистить cookie jar и снова войти под учетной записью жертвы.
10. Проверить, была ли операция из шага 8 успешно выполнена в учетной записи жертвы. Если да, атака завершилась успехом; в противном случае сайт защищен от перехвата сессии.

Мы рекомендуем использовать две разные машины или браузера для жертвы и атакующего. Это позволяет снизить количество ложных срабатываний, если веб-приложение использует снятие цифровых отпечатков (fingerprinting) для проверки доступа, предоставляемого по данному cookie. Более короткий, но менее точный вариант стратегии тестирования требует только одной тестовой учетной записи. Он следует той же схеме, но останавливается на шаге 5 (обратите внимание, что это делает шаг 3 ненужным).
