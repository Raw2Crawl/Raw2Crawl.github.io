# Фиксация сессии (Session Fixation)

| ID |
| --- |
| WSTG-SESS-03 |

## Резюме

Фиксация сессии (Session Fixation) становится возможной из-за небезопасной практики сохранения одного и того же значения сессионных cookie до и после аутентификации. Обычно это происходит, когда сессионные cookie используются для хранения информации о состоянии еще до входа в систему, например для добавления товаров в корзину покупок перед прохождением аутентификации для оплаты.

При типичной эксплуатации уязвимостей фиксации сессии злоумышленник может получить набор сессионных cookie с целевого сайта без предварительной аутентификации. Затем злоумышленник может навязать эти cookie браузеру жертвы с помощью различных техник. Если жертва позже пройдет аутентификацию на целевом сайте, а cookie не будут обновлены при входе, жертва будет идентифицироваться сессионными cookie, выбранными злоумышленником. После этого злоумышленник сможет выдать себя за жертву с помощью этих известных ему cookie.

Эту проблему можно устранить путем обновления сессионных cookie после процесса аутентификации. В качестве альтернативы атаку можно предотвратить, обеспечив целостность сессионных cookie. При противодействии сетевым злоумышленникам (network attackers), то есть атакующим, контролирующим используемую жертвой сеть, применяйте полное внедрение [HSTS](https://en.wikipedia.org/wiki/HTTP_Strict_Transport_Security) (HTTP Strict Transport Security) или добавляйте префикс `__Host-` / `__Secure-` к имени cookie.

Полное внедрение HSTS происходит тогда, когда хост активирует HSTS для себя и всех своих поддоменов. Это описано в исследовательской работе *Testing for Integrity Flaws in Web Sessions* авторов Stefano Calzavara, Alvise Rabitti, Alessio Ragazzo и Michele Bugliesi.

## Цели тестирования

- Проанализировать механизм аутентификации и процесс его работы (flow).
- Навязать cookie и оценить последствия (impact).

## Методика тестирования

В этом разделе приводится описание стратегии тестирования, которая будет продемонстрирована далее.

Первый шаг — отправить запрос к тестируемому сайту (*например* `www.example.com`). Если тестировщик запрашивает следующее:

```http
GET / HTTP/1.1
Host: www.example.com
```

Он получит следующий ответ:

```http
HTTP/1.1 200 OK
Date: Wed, 14 Aug 2008 08:45:11 GMT
Server: IBM_HTTP_Server
Set-Cookie: JSESSIONID=0000d8eyYq3L0z2fgq10m4v-rt4:-1; Path=/; secure
Cache-Control: no-cache="set-cookie,set-cookie2"
Expires: Thu, 01 Dec 1994 16:00:00 GMT
Keep-Alive: timeout=5, max=100
Connection: Keep-Alive
Content-Type: text/html;charset=Cp1254
Content-Language: en-US
```

Приложение устанавливает для клиента новый идентификатор сессии: `JSESSIONID=0000d8eyYq3L0z2fgq10m4v-rt4:-1`.

Далее, если тестировщик успешно аутентифицируется в приложении с помощью следующего POST-запроса к `https://www.example.com/authentication.php`:

```http
POST /authentication.php HTTP/1.1
Host: www.example.com
[...]
Referer: https://www.example.com
Cookie: JSESSIONID=0000d8eyYq3L0z2fgq10m4v-rt4:-1
Content-Type: application/x-www-form-urlencoded
Content-length: 57

Name=Meucci&wpPassword=secret!&wpLoginattempt=Log+in
```

Тестировщик наблюдает следующий ответ от сервера:

```http
HTTP/1.1 200 OK
Date: Thu, 14 Aug 2008 14:52:58 GMT
Server: Apache/2.2.2 (Fedora)
X-Powered-By: PHP/5.1.6
Content-language: en
Cache-Control: private, must-revalidate, max-age=0
X-Content-Encoding: gzip
Content-length: 4090
Connection: close
Content-Type: text/html; charset=UTF-8
...
HTML data
...
```

Поскольку после успешной аутентификации новый cookie выдан не был, тестировщик понимает, что перехват сессии (session hijacking) возможен, если только не обеспечена целостность сессионного cookie.

Тестировщик может передать валидный идентификатор сессии пользователю (возможно, применив прием социальной инженерии), дождаться прохождения им аутентификации и впоследствии убедиться, что этому cookie были присвоены привилегии.

### Тестирование с принудительной передачей cookie

Эта стратегия тестирования ориентирована на сетевых злоумышленников, поэтому ее необходимо применять только к сайтам без полного внедрения HSTS (сайты с полным внедрением HSTS защищены, поскольку все их cookie обладают целостностью). Предполагается наличие двух тестовых учетных записей на исследуемом сайте: одна выступает в роли жертвы, а другая — в роли атакующего. Мы моделируем сценарий, в котором атакующий навязывает браузеру жертвы все cookie, которые не генерируются заново после входа в систему и не обладают целостностью. После входа жертвы в систему атакующий отправляет навязанные cookie сайту для доступа к учетной записи жертвы: если их достаточно для выполнения действий от имени жертвы, фиксация сессии возможна.

Ниже приведены шаги для выполнения данного теста:

1. Открыть страницу входа на сайт.
2. Сохранить снимок хранилища cookie (cookie jar) до входа в систему, исключив cookie, содержащие префикс `__Host-` или `__Secure-` в своем имени.
3. Войти на сайт под учетной записью жертвы и перейти на любую страницу, предоставляющую защищенную функцию, требующую аутентификации.
4. Восстановить в cookie jar состояние по снимку, сделанному на шаге 2.
5. Вызвать защищенную функцию, определенную на шаге 3.
6. Проверить, была ли операция из шага 5 выполнена успешно. Если да, то атака прошла успешно.
7. Очистить cookie jar, войти под учетной записью атакующего и перейти на страницу из шага 3.
8. Записать в cookie jar по одному все cookie, сохраненные на шаге 2.
9. Снова вызвать защищенную функцию, определенную на шаге 3.
10. Очистить cookie jar и снова войти под учетной записью жертвы.
11. Проверить, была ли операция из шага 9 успешно выполнена в учетной записи жертвы. Если да, атака завершилась успехом; в противном случае сайт защищен от фиксации сессии.

Мы рекомендуем использовать две разные машины или браузера для жертвы и атакующего. Это позволяет снизить количество ложных срабатываний (false positives), если веб-приложение применяет снятие цифровых отпечатков (fingerprinting) для проверки доступа, предоставляемого по данному cookie. Более короткий, но менее точный вариант стратегии тестирования требует только одной тестовой учетной записи. Он повторяет те же шаги, но останавливается на шаге 6.

## Рекомендации по устранению

Реализуйте обновление токена сессии после успешной аутентификации пользователя.

Приложение всегда должно сначала инвалидировать существующий Session ID перед аутентификацией пользователя и, в случае успешной аутентификации, предоставить другой Session ID.
