# Проверки целостности

| ID |
| --- |
| WSTG-BUSL-03 |

## Резюме

Многие приложения спроектированы таким образом, чтобы отображать различные поля в зависимости от прав пользователя или контекста ситуации, оставляя часть полей ввода скрытыми. Однако во многих случаях отправка значений скрытых полей на сервер легко реализуется с помощью прокси-сервера. В таких сценариях механизмы контроля на стороне сервера должны быть достаточно развиты, чтобы выполнять реляционные проверки или серверную валидацию, гарантируя обработку только тех данных, которые допустимы на основании бизнес-логики приложения и роли конкретного пользователя.

Кроме того, приложение не должно полагаться на нередактируемые элементы управления (non-editable controls), выпадающие списки или скрытые поля при обработке бизнес-логики, поскольку эти элементы остаются неизменяемыми исключительно в контексте веб-браузера. Пользователи могут изменять их значения с помощью инструментов редактирования прокси-трафика и предпринимать попытки манипулирования бизнес-логикой. Если приложение выставляет критичные для бизнес-правил значения (например, количество и т. д.) в виде нередактируемых полей, оно обязано хранить эталонную копию на стороне сервера и использовать именно ее для выполнения бизнес-логики. Наконец, помимо данных самого приложения или системы, системы журналирования (logs) также должны быть защищены от несанкционированного чтения, записи и модификации.

Уязвимости проверок целостности бизнес-логики уникальны тем, что сценарии их неправомерного использования (misuse cases) специфичны для конкретного приложения: если пользователям разрешено вносить изменения, они должны иметь возможность создавать, обновлять или редактировать строго определенные артефакты и только в разрешенные логикой бизнес-процесса моменты времени.

Приложение должно корректно осуществлять реляционный контроль и не позволять пользователям напрямую отправлять на сервер недопустимые данные, считая их доверенными лишь на том основании, что они получены из нередактируемых элементов управления, либо данные, на отправку которых через фронтенд у пользователя нет полномочий. Кроме того, системные артефакты, такие как файлы журналов (logs), должны быть надежно защищены от несанкционированного чтения, модификации и удаления.

### Пример 1

Представьте веб-приложение на базе ASP.NET, интерфейс которого позволяет только пользователю с ролью администратора менять пароли других учетных записей в системе. Администратор видит поля для ввода имени пользователя и пароля, тогда как обычные пользователи эти поля не видят. Однако если пользователь без прав администратора отправит значения полей имени пользователя и пароля через перехватывающий прокси, он может «обмануть» сервер, заставив его поверить, что запрос поступил от администратора, и изменить пароли других учетных записей.

### Пример 2

Большинство веб-приложений содержат выпадающие списки, позволяющие пользователю быстро выбрать штат, месяц рождения и т. д. Предположим, система управления проектами (Project Management) позволяет пользователям входить в систему и в зависимости от их прав отображает выпадающий список проектов, к которым у них есть доступ. Что произойдет, если злоумышленник узнает название другого проекта, к которому у него не должно быть доступа, и передаст это значение через прокси-сервер? Предоставит ли приложение доступ к проекту? Доступ не должен предоставляться, даже если злоумышленник обошел проверку авторизации на уровне бизнес-логики интерфейса.

### Пример 3

Предположим, в государственной автотранспортной инспекции регламент изначально требовал, чтобы сотрудник лично проверял документы и сведения каждого гражданина при выдаче удостоверения личности или водительских прав. В этом случае бизнес-процесс обеспечивал высокий уровень целостности данных, так как подлинность передаваемых сведений подтверждалась сотрудниками. Теперь предположим, что систему перенесли в веб: сотрудники могут входить для полнофункционального обслуживания, а граждане — через упрощенный личный кабинет самообслуживания для обновления отдельных сведений. В этот момент злоумышленник может использовать перехватывающий прокси-сервер для добавления или изменения данных, к которым у него не должно быть доступа, нарушая целостность базы: например, указав статус «не женат», но передав данные с именем супруги. Подобная вставка или обновление непроверенных данных разрушает целостность информации, чего можно было бы избежать при строгом соблюдении логики бизнес-процесса.

### Пример 4

Многие системы ведут журналы аудита (audit logging) для целей мониторинга и устранения неполадок. Однако насколько достоверны и валидны содержащиеся в них записи? Могут ли злоумышленники преднамеренно или случайно модифицировать их, разрушая целостность данных журнала?

## Цели тестирования

- Изучить проектную документацию на предмет компонентов системы, перемещающих, хранящих или обрабатывающих данные.
- Определить, какие типы данных логически допустимы для каждого компонента, а от каких система должна быть защищена.
- Определить, кто имеет право на чтение или модификацию этих данных в каждом компоненте.
- Попытаться вставить, обновить или удалить значения данных, используемые каждым компонентом, операции с которыми недопустимы в рамках рабочего процесса бизнес-логики.

## Методика тестирования

### Конкретный метод тестирования 1

- С помощью прокси-сервера перехватите HTTP-трафик и найдите скрытые поля.
- При обнаружении скрытого поля сопоставьте его с графическим интерфейсом приложения и начните исследование этого значения через прокси: отправляйте различные данные, пытаясь обойти бизнес-процесс и изменить значения параметров, к которым у вас не должно быть доступа.

### Конкретный метод тестирования 2

- С помощью прокси-сервера перехватите HTTP-трафик и найдите возможность передачи информации в те области приложения, которые заявлены как нередактируемые.
- При обнаружении сопоставьте эти поля с графическим интерфейсом и начните исследование значений через прокси: передавайте различные данные, пытаясь обойти бизнес-процесс и модифицировать значения, доступ к которым не предусматривался.

### Конкретный метод тестирования 3

- Составьте перечень компонентов приложения или системы, на которые может быть оказано воздействие, например журналы аудита или базы данных.
- Для каждого выявленного компонента попытайтесь прочитать, отредактировать или удалить хранящуюся в нем информацию. Например, при обнаружении файлов журналов тестировщики должны попытаться фальсифицировать или исказить собираемые системой сведения.

## Рекомендации по устранению

В приложении должны применяться строгие механизмы разграничения доступа, определяющие порядок чтения и изменения данных и системных артефактов, а также использующие доверенные каналы передачи данных, гарантирующие их целостность. Должно быть внедрено корректное журналирование событий для мониторинга и контроля отсутствия несанкционированного доступа или модификации.
