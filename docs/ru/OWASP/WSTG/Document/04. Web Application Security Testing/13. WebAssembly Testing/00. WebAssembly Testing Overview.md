# Обзор тестирования WebAssembly

## Введение в WebAssembly

WebAssembly (сокращенно *Wasm*) — это бинарный формат инструкций для стек-ориентированной виртуальной машины (stack-based virtual machine). Wasm спроектирован как переносимая цель компиляции для различных языков программирования, обеспечивающая развертывание клиентских и серверных веб-приложений. Он предоставляет возможность исполнять код, написанный на таких языках, как C, C++, Rust и Go, в веб-среде со скоростью, близкой к нативной.

Внедрение WebAssembly обусловлено потребностью в высокой производительности веб-приложений (например, в системах видеомонтажа, игровых движках, криптографических библиотеках), а также стремлением портировать классические десктопные приложения в веб без необходимости их полного переписывания на JavaScript.

Как и любая новая архитектура, WebAssembly несет в себе специфические дефекты и уязвимости. Хотя виртуальная машина Wasm изолирована (sandboxed) от хост-окружения, код, исполняемый *внутри* Wasm-модуля, сохраняет уязвимости безопасности памяти (memory safety), присущие исходному языку программирования. Кроме того, граница взаимодействия между хостом и модулем Wasm при недостаточной защите может стать прямым вектором полной компрометации приложения.

Данная глава призвана помочь исследователю безопасности освоить концепции, необходимые для тестирования приложений на базе WebAssembly, исследуя его ключевые технологии, среды выполнения и парадигмы уязвимостей.

## История

Благодаря высокой производительности WebAssembly стремительно эволюционировал из чисто браузерной технологии в универсальную платформу, функционирующую на серверах, граничных сетях (edge networks) и встраиваемых устройствах.

WebAssembly был впервые анонсирован в 2015 году как совместная инициатива инженеров Mozilla, Google, Microsoft и Apple. К 2017 году был выпущен минимально жизнеспособный продукт (Minimum Viable Product, MVP), поддержанный всеми основными браузерными движками, что закрепило за Wasm статус четвертого языка, нативно исполняемого в браузерах (наряду с HTML, CSS и JavaScript).

В декабре 2019 года Консорциум Всемирной паутины (W3C) опубликовал WebAssembly Core Specification в качестве официального веб-стандарта. Примерно в это же время был представлен системный интерфейс WebAssembly (WebAssembly System Interface, WASI). WASI стандартизировал взаимодействие модулей WebAssembly с операционной системой, выведя Wasm за пределы браузера в сферу бэкенд-сервисов, микросервисов и бессерверных платформ граничных вычислений (таких как Cloudflare Workers и Fastly Compute).

## Какая среда выполнения WebAssembly используется?

Перед тем как формировать предположения о поверхности атаки, необходимо четко понимать, в какой именно среде функционирует модуль WebAssembly. Исследователь безопасности может столкнуться со следующими вариантами:

- **Client-Side (Browser) Wasm:** Файл `.wasm` загружается и исполняется в браузере пользователя. Для взаимодействия с DOM и Web API он опирается на промежуточный связующий JavaScript-код («glue code»).
- **Server-Side:** Wasm-модуль исполняется на бэкенде, обрабатывая запросы к API или выполняя ресурсоемкие вычисления. Уязвимости в таком окружении могут напрямую приводить к компрометации сервера.
- **Serverless / Edge Computing:** Экземпляры Wasm инициализируются на граничных узлах (edge nodes) для перехвата и обработки HTTP-запросов. Эти среды часто повторно используют одни и те же области памяти для минимизации задержек, что создает риски межпользовательской утечки состояния (cross-tenant state leakage).
- **Standalone WASI:** Модуль нативно исполняется в операционной системе через среды выполнения (runtimes), такие как Wasmtime или Wasmer, под управлением модели безопасности на основе привилегий (capability-based security model).

## Основные компоненты WebAssembly

Архитектура WebAssembly базируется на нескольких фундаментальных концепциях. Их понимание критически важно для анализа механизмов проявления уязвимостей.

### Модули

Модуль WebAssembly представляет собой скомпилированный бинарный файл с расширением `.wasm`. Он не сохраняет состояние (stateless) и содержит скомпилированный байт-код, сигнатуры типов и сегменты данных. В текстовом представлении он отображается в формате WebAssembly Text Format (WAT).

### Линейная память

В отличие от нативных приложений, использующих управляемые операционной системой кучу (heap) и стек (stack), экземпляр WebAssembly хранит данные времени выполнения внутри единого непрерывного массива байтов, называемого **линейной памятью (Linear Memory)**. Эта память предоставляется хосту как объект `ArrayBuffer`. Стек, куча, строковые литералы и глобальные переменные Wasm-модуля делят между собой это неразмеченное плоское адресное пространство.

### Таблицы

Таблица (Table) представляет собой массив непрозрачных значений, обычно ссылок на функции. Поскольку WebAssembly обеспечивает целостность потока управления (Control-Flow Integrity, CFI) и запрещает прямое исполнение кода из линейной памяти, указатели на функции уровня исходного кода (в C, C++ или Rust) и целевые адреса динамических вызовов компилируются в целочисленные индексы, указывающие на конкретные слоты в таблице. Косвенные вызовы (`call_indirect`) впоследствии выполняются с использованием этих индексов.

### Импорты и экспорты

WebAssembly не может взаимодействовать с внешним миром автономно.

- **Imports (Импорты):** Функции или переменные, предоставляемые хостом (например, функция JS `console.log`), которые может вызывать модуль Wasm.
- **Exports (Экспорты):** Функции или экземпляры памяти внутри модуля Wasm, к которым открыт доступ хосту.

## Парадигма безопасности

WebAssembly по умолчанию изолирован в «песочнице» (sandboxed); модуль не может выйти за пределы своей виртуальной машины для чтения произвольных файлов или сетевых сокетов, если хост явно не импортировал соответствующие возможности.

Однако **внутренняя безопасность памяти (internal memory safety) не гарантируется.** При компиляции унаследованного C/C++ кода в WebAssembly многие базовые механизмы защиты нативного кода меняются:

- **Отсутствие ASLR внутри модуля:** Смещения внутри линейной памяти детерминированы, даже если хост-процесс использует рандомизацию размещения адресного пространства (ASLR).
- **Защита стека зависит от параметров сборки:** «Канарейки» стека (stack canaries) могут отсутствовать, если они не были явно активированы в цепочке сборки (toolchain).
- **Линейная память не исполняема, но лишена защиты целостности:** Повреждение памяти способно модифицировать данные, влияющие на поток управления (например, индексы функций, используемые в `call_indirect`), и логику приложения.

Как следствие, классические уязвимости повреждения памяти (переполнение буфера `[Buffer Overflow]`, использование после освобождения `[Use-After-Free]`, ошибки форматных строк `[Format String]`) сохраняются после компиляции. Злоумышленник может перезаписать соседние данные в линейной памяти, чтобы манипулировать логикой приложения, подменить индексы в таблице косвенных вызовов (техника ret2win) или повредить выходные буферы, обрабатываемые хостом, что превращает уязвимость Wasm в межсайтовый скриптинг на основе DOM (DOM-Based XSS) или удаленное выполнение кода на стороне сервера (Server-Side Remote Code Execution, RCE).
