# Повышение привилегий

| ID |
| --- |
| WSTG-ATHZ-03 |

## Резюме

В данном разделе описывается проблема повышения привилегий (Privilege Escalation) от одного уровня к другому. На данном этапе тестировщик должен убедиться, что пользователь не может модифицировать свои права или роли внутри приложения способами, открывающими возможность проведения атак с целью эскалации привилегий.

Повышение привилегий происходит в том случае, когда пользователь получает доступ к большему объему ресурсов или функциональности, чем ему положено в штатном режиме, причем такое повышение или изменения должны были блокироваться приложением. Обычно это вызвано дефектом в логике приложения. В результате приложение выполняет действия с более высоким уровнем привилегий, чем предполагалось разработчиком или системным администратором.

Степень повышения привилегий зависит от того, какими правами злоумышленник обладал изначально и какие привилегии могут быть получены в результате успешной эксплуатации уязвимости. Например, ошибка программирования, позволяющая пользователю получить дополнительные привилегии после успешной аутентификации, ограничивает масштаб эскалации, поскольку пользователь уже авторизован в системе с определенными правами. И наоборот, получение удаленным злоумышленником привилегий суперпользователя без какой-либо аутентификации представляет собой гораздо более высокую степень опасности.

Обычно под *вертикальным повышением привилегий* (vertical escalation) понимают получение доступа к ресурсам, назначенным более привилегированным учетным записям (например, получение прав администратора приложения), а под *горизонтальным повышением привилегий* (horizontal escalation) — получение доступа к ресурсам учетной записи с аналогичным уровнем прав (например, в системе интернет-банкинга — доступ к информации другого клиента).

## Цели тестирования

- Выявить точки внедрения, связанные с манипуляцией привилегиями.
- Провести фаззинг (fuzzing) или иным образом попытаться обойти механизмы защиты.

## Методика тестирования

### Манипулирование ролями и привилегиями

В каждой части приложения, где пользователь может создавать данные в базе данных (например, проводить платеж, добавлять контакт или отправлять сообщение), получать информацию (выписка по счету, детали заказа и т. д.) или удалять данные (удаление пользователей, сообщений и т. д.), необходимо зафиксировать эту функциональность. Тестировщику следует попытаться обратиться к таким функциям от лица другого пользователя, чтобы проверить возможность вызова функций, недопустимых для роли/привилегий текущего пользователя (но потенциально разрешенных другой учетной записи).

#### Манипуляция группой пользователя

Например:
Следующий HTTP POST-запрос позволяет пользователю, принадлежащему к группе `grp001`, просматривать заказ #0001:

```http
POST /user/viewOrder.jsp HTTP/1.1
Host: www.example.com
...

groupID=grp001&orderID=0001
```

Проверьте, может ли пользователь, не входящий в группу `grp001`, изменить значения параметров `groupID` и `orderID`, чтобы получить доступ к этим конфиденциальным данным.

#### Манипуляция профилем пользователя

Например:
В следующем ответе сервера содержится скрытое поле HTML-формы, возвращаемое пользователю после успешной аутентификации:

```html
HTTP/1.1 200 OK
Server: Netscape-Enterprise/6.0
Date: Wed, 1 Apr 2006 13:51:20 GMT
Set-Cookie: USER=aW78ryrGrTWs4MnOd32Fs51yDqp; path=/; domain=www.example.com
Set-Cookie: SESSION=k+KmKeHXTgDi1J5fT7Zz; path=/; domain= www.example.com
Cache-Control: no-cache
Pragma: No-cache
Content-length: 247
Content-Type: text/html
Expires: Thu, 01 Jan 1970 00:00:00 GMT
Connection: close

<form  name="autoriz" method="POST" action = "visual.jsp">
<input type="hidden" name="profile" value="SysGuest">\

<body onload="document.forms.autoriz.submit()">
</td>
</tr>
```

Что произойдет, если тестировщик изменит значение переменной `profile` на `SysAdmin`? Удастся ли получить статус **администратора**?

#### Манипуляция значением условия

Например:
В конфигурации, где сервер отправляет сообщение об ошибке, содержащееся в качестве значения определенного параметра в структуре кодов ответов, как показано ниже:

```text
@0`1`3`3``0`UC`1`Status`OK`SEC`5`1`0`ResultSet`0`PVValid`-1`0`0` Notifications`0`0`3`Command  Manager`0`0`0` StateToolsBar`0`0`0`
StateExecToolBar`0`0`0`FlagsToolBar`0
```

Сервер проявляет безоговорочное доверие к пользователю, предполагая, что клиент вернет данное сообщение и завершит сессию.

В таких условиях убедитесь, что модификация значений параметров не позволяет повысить привилегии. В данном конкретном примере, изменив значение `PVValid` с `-1` на `0` (отсутствие условий ошибки), может оказаться возможным аутентифицироваться на сервере с правами администратора.

#### Манипуляция IP-адресом

Некоторые веб-сайты ограничивают доступ или подсчитывают количество неудачных попыток входа на основе IP-адреса клиента.

Например:

```http
X-Forwarded-For: 8.1.1.1
```

В данном случае, если сайт использует значение `X-Forwarded-For` в качестве IP-адреса клиента, тестировщик может изменить IP-адрес в заголовке `X-Forwarded-For` для обхода механизмов идентификации источника по IP.

### Вертикальный обход авторизации

Вертикальный обход авторизации относится к ситуации, когда злоумышленник получает доступ к роли, превышающей его собственные полномочия. Тестирование данного обхода сосредоточено на проверке реализации схемы вертикальной авторизации для каждой роли. Для каждой функции, страницы, определенной роли или запроса, выполняемого приложением, необходимо проверить возможность:

- Доступа к ресурсам, которые должны быть доступны только пользователю с более высокой ролью.
- Выполнения операций над ресурсами, которые разрешено выполнять только пользователю с более высокой или специфической ролью.

Для каждой роли:

1. Зарегистрируйте пользователя.
2. Установите и поддерживайте две разные сессии для двух разных ролей.
3. Для каждого запроса замените сессионный идентификатор на идентификатор сессии другой роли и оцените ответы для каждого из них.
4. Приложение считается уязвимым, если сессия с более низким уровнем привилегий возвращает те же данные или указывает на успешное выполнение функций, требующих повышенных привилегий.

#### Сценарий ролей для банковского сайта

В следующей таблице проиллюстрированы системные роли на сайте интернет-банкинга. Каждая роль связана с определенными разрешениями для функциональности меню событий:

|      ROLE     |     PERMISSION    | ADDITIONAL PERMISSION |
|---------------|-------------------|-----------------------|
| Administrator | Full Control      | Delete                |
| Manager       | Modify, Add, Read | Add                   |
| Staff         | Read, Modify      | Modify                |
| Customer      | Read Only         |                       |

Приложение будет считаться уязвимым, если:

1. Пользователь Customer может выполнять функции администратора (Administrator), менеджера (Manager) или сотрудника (Staff);
2. Пользователь Staff может выполнять функции менеджера или администратора;
3. Менеджер может выполнять функции администратора.

Предположим, что функция `deleteEvent` входит в меню учетной записи администратора и доступна по URL: `https://www.example.com/account/deleteEvent`. При вызове функции `deleteEvent` генерируется следующий HTTP-запрос:

```http
POST /account/deleteEvent HTTP/1.1
Host: www.example.com
[other HTTP headers]
Cookie: SessionID=ADMINISTRATOR_USER_SESSION

EventID=1000001
```

Корректный ответ сервера:

```http
HTTP/1.1 200 OK
[other HTTP headers]

{"message": "Event was deleted"}
```

Злоумышленник может попытаться выполнить аналогичный запрос:

```http
POST /account/deleteEvent HTTP/1.1
Host: www.example.com
[other HTTP headers]
Cookie: SessionID=CUSTOMER_USER_SESSION

EventID=1000002
```

Если в ответе на запрос злоумышленника возвращаются те же данные `{"message": "Event was deleted"}`, приложение уязвимо.

#### Доступ к странице администратора

Предположим, что панель администратора входит в состав учетной записи администратора.

Приложение будет считаться уязвимым, если любая роль, кроме администратора, сможет получить доступ к меню администратора. Зачастую разработчики проверяют права авторизации исключительно на уровне графического интерфейса (GUI), оставляя сами функции бэкенда без надлежащей проверки авторизации, что приводит к возникновению уязвимости.

### Обход путей через URL (URL Traversal)

Попробуйте выполнить обход путей сайта и проверьте, не пропущены ли проверки авторизации на некоторых страницах.

Например:

```text
/../.././userInfo.html
```

### Тестирование методом «белого ящика»

Если проверка авторизации по URL выполняется исключительно путем частичного совпадения строки URL, велика вероятность, что тестировщики или злоумышленники смогут обойти проверку авторизации с помощью методов кодирования URL.

Например:

```text
startswith(), endswith(), contains(), indexOf()
```
