# Перечисление административных интерфейсов инфраструктуры и приложения

| ID |
| --- |
| WSTG-CONF-05 |

## Резюме

Административные интерфейсы могут присутствовать непосредственно в самом приложении или на сервере приложений, позволяя привилегированным пользователям выполнять критические операции по управлению сайтом. В рамках тестирования необходимо выяснить, возможен ли доступ к этой привилегированной функциональности со стороны неавторизованного или рядового пользователя, и какими путями он может быть получен.

Административный интерфейс требуется веб-приложению для того, чтобы предоставить привилегированному пользователю возможность управления ключевыми функциями ресурса. К таким операциям относятся:

- Создание и управление учетными записями пользователей (user provisioning).
- Изменение дизайна и структуры сайта.
- Модификация и манипуляция данными.
- Внесение изменений в конфигурацию системы.

Во многих случаях такие интерфейсы не имеют достаточных механизмов защиты от несанкционированного доступа. Тестирование направлено на обнаружение скрытых административных интерфейсов и получение несанкционированного доступа к функциональности, предназначенной исключительно для привилегированных пользователей.

## Цели тестирования

- Обнаружить скрытые интерфейсы и функции администрирования, включая панели управления облачной инфраструктурой, оркестраторами контейнеров, шлюзами API (API gateways) и системами CI/CD.
- Проверить каждый выявленный интерфейс на наличие стандартных (default), слабых или повторно используемых учетных данных, а также на предмет непреднамеренной доступности из недоверенных сегментов сети или неавторизованным кругом лиц.

## Методика тестирования

### Тестирование методом «черного ящика»

В данном разделе описаны векторы, используемые для выявления административных интерфейсов. Эти методики также применяются для тестирования сопутствующих уязвимостей, включая повышение привилегий (privilege escalation), которые более подробно рассматриваются в соответствующих разделах руководства (например, [Обход схемы авторизации (Bypassing Authorization Schema)](../05.%20Authorization%20Testing/02.%20Bypassing%20Authorization%20Schema.md) и [Небезопасные прямые ссылки на объекты (Insecure Direct Object References)](../05.%20Authorization%20Testing/04.%20Insecure%20Direct%20Object%20References.md)).

- Перебор каталогов и файлов: административный интерфейс может присутствовать на сервере, но не иметь явных ссылок на страницах сайта. Путь к интерфейсу администрирования можно подобрать с помощью простых запросов вроде `/admin` или `/administrator`. В ряде случаев такие пути выявляются за считанные секунды с помощью техник расширенного поиска Google — так называемых «дорков» ([Google dorks](https://www.exploit-db.com/google-hacking-database)). Существует множество утилит для выполнения брутфорса содержимого сервера (подробнее см. раздел «Tools»). Тестировщику также может потребоваться определить имя конкретного файла страницы управления. Прямой переход по выявленному адресу (forced browsing) может предоставить доступ к интерфейсу.
- Комментарии и ссылки в исходном коде: многие веб-сайты используют общие библиотеки и скрипты, загружаемые для всех пользователей без исключения. Изучение всего клиентского кода (HTML, JS), отдаваемого браузеру, может раскрыть скрытые ссылки на административные панели, которые необходимо детально исследовать.
- Анализ документации к серверу и приложению: если сервер приложений или само приложение развернуты с конфигурацией по умолчанию, доступ к административной панели можно получить, следуя стандартной сопроводительной документации или руководствам по установке. При обнаружении запроса аутентификации в найденном интерфейсе следует обратиться к базам стандартных паролей по умолчанию (default passwords).
- Общедоступная информация: многие популярные CMS (например, WordPress) имеют стандартные административные адреса, активные по умолчанию.
- Нестандартные сетевые порты: интерфейсы администрирования могут функционировать на отдельных портах хоста, отличных от основного веб-приложения. Например, панель администрирования Apache Tomcat часто размещается на порту `8080`.
- Манипуляция параметрами (Parameter tampering): для активации функций администратора может требоваться передача определенного параметра в запросах GET/POST либо установка значения cookie. Подсказкой может служить наличие скрытых полей форм, таких как:

```html
<input type="hidden" name="admin" value="no">
```

или специального параметра в заголовке Cookie:

`Cookie: session_cookie; useradmin=0`

После обнаружения административного интерфейса для попытки обхода аутентификации используется комбинация описанных выше методов. Если обойти проверку не удается, тестировщик может прибегнуть к атаке методом перебора паролей (brute force). В этом случае следует помнить о возможном наличии механизма блокировки учетных записей (account lockout) при превышении лимита неудачных попыток входа.

### Тестирование методом «серого ящика»

Необходимо провести углубленный аудит компонентов сервера и приложения на предмет усиления защиты (hardening) — в частности, убедиться, что административные страницы изолированы от публичного доступа с помощью фильтрации по IP-адресам или аналогичных мер, а также проверить, что ни в одном компоненте не используются учетные данные или настройки по умолчанию.
Необходимо проанализировать исходный код, чтобы убедиться, что архитектура аутентификации и авторизации гарантирует строгое разделение обязанностей (separation of duties) между рядовыми пользователями и администраторами. Функции пользовательского интерфейса, общие для обычных и привилегированных пользователей, должны быть проверены на предмет четкого разграничения рендеринга компонентов и исключения утечки закрытых данных через разделяемую логику.

Каждый веб-фреймворк и платформа имеет собственные типовые административные пути, как показано в следующих примерах:

PHP:

```html
/phpinfo
/phpmyadmin/
/phpMyAdmin/
/mysqladmin/
/MySQLadmin
/MySQLAdmin
/login.php
/logon.php
/xmlrpc.php
/dbadmin
```

WordPress:

```html
wp-admin/
wp-admin/about.php
wp-admin/admin-ajax.php
wp-admin/admin-db.php
wp-admin/admin-footer.php
wp-admin/admin-functions.php
wp-admin/admin-header.php
```

Joomla:

```html
/administrator/index.php
/administrator/index.php?option=com_login
/administrator/index.php?option=com_content
/administrator/index.php?option=com_users
/administrator/index.php?option=com_menus
/administrator/index.php?option=com_installer
/administrator/index.php?option=com_config
```

Tomcat:

```html

```

Apache:

```html

```

Nginx:

```html

/nginx_status
/index.php
/nginx.conf
/html/error
```

### Современные интерфейсы администрирования, управления API, контейнерами и CI/CD

Помимо классических путей веб-приложений и CMS, современные архитектуры часто содержат дополнительные привилегированные интерфейсы, которые аудиторы должны целенаправленно искать и проверять на предмет использования паролей по умолчанию и непреднамеренного сетевого открытия:

#### Консоли облачных провайдеров

- Веб-консоли самих облачных провайдеров (AWS, Azure, GCP) недоступны напрямую через поверхность атаки приложения, однако утечки или некорректно настроенный доступ нередко выявляются через веб-уровень: проверяйте клиентский код JavaScript, файлы конфигураций и сообщения об ошибках на предмет раскрытия облачных учетных данных (API keys, секретов), и убедитесь, что они не предоставляют избыточных прав на доступ к консоли или API провайдера за рамками задач приложения.
- Развернутые внутри инфраструктуры панели управления вспомогательными облачными службами часто оказываются выставленными наружу: браузеры объектных хранилищ, консоли администрирования баз данных (например, прокси RDS/Cloud SQL с открытым веб-интерфейсом) и панели мониторинга IaaS. Любой подобный сервис следует рассматривать как полноправный административный интерфейс и подвергать проверкам на стойкость учетных данных и сетевую изоляцию.

#### Панели управления Kubernetes и оркестраторами контейнеров

- Kubernetes Dashboard: исторически неоднократно развертывался без обязательной аутентификации либо со входом через избыточно привилегированный токен сервисной учетной записи (`service-account-token`), что предоставляло полный контроль над кластером. Проверяйте пути вида `/api/v1/namespaces/kubernetes-dashboard/...` или выделенные Ingress/NodePort панели, убеждаясь в наличии обязательной аутентификации и использовании сервисного аккаунта с минимальными правами вместо роли `cluster-admin` (команда `kubectl auth can-i --list --as=system:serviceaccount:<ns>:<sa>`, см. также [Права доступа к файлам (File Permissions)](09.%20File%20Permissions.md#монтирование-томов-и-securitycontext-в-kubernetes)).
- Read-only API демона `kubelet` (порт `10255`, устарел) и аутентифицированный API kubelet (порт `10250`): убедитесь, что ни один из них не доступен из внешней сети за пределами кластера и что анонимный доступ отключен.
- etcd (порты `2379`/`2380`): при сетевой доступности неаутентифицированный доступ раскрывает полное состояние кластера, включая секреты (Secrets).
- Интерфейсы управления контейнерными платформами (Portainer, Rancher или управляемые прокси-консоли Kubernetes облачных провайдеров): проверяйте наличие учетных данных администратора по умолчанию и доступность эндпоинтов первичной настройки/регистрации после завершения развертывания (ряд платформ позволяет любому внешнему пользователю перехватить первую учетную запись администратора, если процедура инициализации не была завершена).

#### Конечные точки управления приложением и Actuator

- Spring Boot Actuator: эндпоинты `/actuator`, `/actuator/env`, `/actuator/heapdump`, `/actuator/httptrace` и `/actuator/mappings` представляют собой полноценные интерфейсы управления, а не просто отладочный вывод. Путь `/actuator/env` может раскрывать учетные данные, а некоторые версии и конфигурации Actuator поддерживают модификацию параметров (например, эндпоинт `/actuator/loggers` позволяет налету менять уровень журналирования), а не только чтение данных. Полный список эндпоинтов приведен в подразделе [Debug Endpoints and Debug Modes](02.%20Application%20Platform%20Configuration.md#отладочные-конечные-точки-и-режимы-отладки); обнаружение любого доступного неаутентифицированного эндпоинта Actuator следует классифицировать как раскрытие административного интерфейса, а не просто информационную утечку.
- Аналогичные эндпоинты управления других фреймворков: компоненты middleware проверки работоспособности и диагностики ASP.NET Core, панель управления Django (`/admin/` в сочетании с `DEBUG=True` или слабым стандартным суперпользователем), а также подобные встроенные модули администрирования, поставляемые включенными по умолчанию.

#### Консоли управления API

- Панели управления и администрирования шлюзов API (например, Kong Admin API, Apigee, доступ к консоли AWS API Gateway через скомпрометированные ключи, Tyk Dashboard) зачастую прослушивают отдельный сетевой порт или путь, отличный от публичного API, и по умолчанию могут функционировать без аутентификации (например, Kong Admin API исторически поставлялся с неаутентифицированным доступом на порту `8001`).
- Проверяйте доступность интерактивной документации API и порталов разработчиков, которые помимо чтения спецификаций предоставляют административные функции (генерацию ключей, изменение квот и лимитов); убедитесь, что эти операции защищены аутентификацией, соответствующей уровню критичности выполняемых действий.

#### Веб-интерфейсы управления CI/CD

- Распространенные локально развертываемые (self-hosted) консоли CI/CD, подлежащие выявлению: Jenkins (`/login`, консоль `/script`, `/asynchPeople/`), панель администратора GitLab CI/CD, TeamCity, Argo CD, а также интерфейсы управления собственными раннерами (runners) GitHub/GitLab Actions.
- Открытие доступа к этим интерфейсам влечет максимальный ущерб, поскольку системы CI/CD содержат учетные данные для развертывания на боевых серверах, доступ к исходному коду и возможность выполнения произвольных сборочных команд. Проверяйте:
    - Стандартные или описанные в документации учетные данные по умолчанию, которые не были изменены (например, доступные на чтение файлы начального пароля администратора в Jenkins или незавершенные мастера первичной настройки).
    - Включенный анонимный/гостевой доступ (исторически Jenkins позволял включать режим «anonymous read/build»).
    - Доступность скриптовых консолей (script consoles) или функций создания произвольных пайплайнов/задач без полной аутентификации, что эквивалентно удаленному выполнению произвольного кода на сервере.

#### Проверка учетных данных по умолчанию и раскрытия информации

Для любого интерфейса административного типа, выявленного в ходе тестирования (классического или современного), выполните базовый комплекс проверок:

- Проверьте документированные пароли по умолчанию для конкретного продукта и версии (сверяясь с документацией поставщика и базами данных, такими как [Cirt: Default Password list](https://cirt.net/passwords) или [SecLists](https://github.com/danielmiessler/SecLists/tree/master/Passwords/Default-Credentials)). Не проводите масштабный перебор паролей за рамками небольшого списка стандартных учетных данных без прямого согласования с заказчиком.
- Убедитесь, что интерфейс недоступен из публичного интернета, если он предназначен исключительно для внутреннего использования или операторов инфраструктуры (проверяйте как сканированием доменных имен, так и прямым обращением по IP-адресу и порту, поскольку ресурс может открываться по IP, даже не будучи привязанным к DNS-имени).
- Убедитесь в обязательном применении TLS и отсутствии возможности передачи учетных данных открытым текстом по протоколу HTTP.
- Если интерфейс содержит мастер первоначальной настройки (first-run wizard), убедитесь, что его невозможно перезапустить или открыть повторно после развертывания системы для захвата учетной записи администратора.

## Инструменты

Для обнаружения скрытых административных интерфейсов и функционала применяется специализированный инструментарий:

- [ZAP - Forced Browse](https://www.zaproxy.org/docs/desktop/addons/forced-browse/) — поддерживаемое и актуальное развитие функционала классического проекта OWASP DirBuster.
- [THC-HYDRA](https://github.com/vanhauser-thc/thc-hydra) — утилита для быстрого перебора учетных данных во множестве протоколов и интерфейсов, включая формы HTTP-аутентификации.
- Инструменты перебора работают значительно эффективнее при использовании качественных словарей, таких как словарь [Netsparker](https://www.invicti.com/blog/web-security/svn-digger-better-lists-for-forced-browsing).
- [nuclei](https://github.com/projectdiscovery/nuclei) с наборами шаблонов `exposed-panels` и `default-logins` позволяет массово идентифицировать современные интерфейсы администрирования, оркестрации и CI/CD.
- [kube-hunter](https://github.com/aquasecurity/kube-hunter) — инструмент выявления открытых эндпоинтов Kubernetes API server, kubelet и dashboard.
- [SecLists - Default Credentials](https://github.com/danielmiessler/SecLists/tree/master/Passwords/Default-Credentials) — база стандартных учетных записей.
