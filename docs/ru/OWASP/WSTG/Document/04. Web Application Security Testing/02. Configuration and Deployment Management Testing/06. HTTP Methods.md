# HTTP-методы

| ID |
| --- |
| WSTG-CONF-06 |

## Резюме

Протокол HTTP предоставляет ряд методов (или глаголов — verbs), используемых для выполнения действий на веб-сервере. Хотя методы GET и POST являются наиболее распространенными для получения и передачи информации, веб-серверы могут поддерживать и другие методы, которые при определенных условиях могут эксплуатироваться злоумышленниками.

Стандарт [RFC 9110](https://datatracker.ietf.org/doc/html/rfc9110#section-9.3) определяет базовые методы HTTP-запросов, а дополнительные методы регламентируются отдельными документами, такими как [RFC 5789](https://datatracker.ietf.org/doc/html/rfc5789) и [RFC 10008](https://datatracker.ietf.org/doc/html/rfc10008). Ряд этих глаголов получил новое назначение в архитектуре [RESTful](https://en.wikipedia.org/wiki/Representational_state_transfer)-приложений, как показано в таблице ниже.

| Метод | Исходное назначение | Назначение в RESTful |
|-------|---------------------|----------------------|
| [`GET`](https://datatracker.ietf.org/doc/html/rfc9110#section-9.3.1) | Запрос файла. | Запрос объекта. |
| [`HEAD`](https://datatracker.ietf.org/doc/html/rfc9110#section-9.3.2) | Запрос файла с возвратом исключительно HTTP-заголовков. | |
| [`POST`](https://datatracker.ietf.org/doc/html/rfc9110#section-9.3.3) | Отправка данных на сервер. | |
| [`PUT`](https://datatracker.ietf.org/doc/html/rfc9110#section-9.3.4) | Загрузка файла на сервер. | Создание объекта. |
| [`DELETE`](https://datatracker.ietf.org/doc/html/rfc9110#section-9.3.5) | Удаление файла. | Удаление объекта. |
| [`CONNECT`](https://datatracker.ietf.org/doc/html/rfc9110#section-9.3.6) | Установление туннельного соединения с другим узлом. | |
| [`OPTIONS`](https://datatracker.ietf.org/doc/html/rfc9110#section-9.3.7) | Запрос списка поддерживаемых методов HTTP. | Выполнение предварительного запроса [CORS Preflight](https://developer.mozilla.org/en-US/docs/Glossary/Preflight_request). |
| [`TRACE`](https://datatracker.ietf.org/doc/html/rfc9110#section-9.3.8) | Эхо-возврат HTTP-запроса для целей отладки. | |
| [`PATCH`](https://datatracker.ietf.org/doc/html/rfc5789#section-2) | | Частичная модификация объекта. |
| [`QUERY`](https://datatracker.ietf.org/doc/html/rfc10008#section-2) | Безопасное получение данных с телом запроса. | Запрос объектов или ресурсов со сложными фильтрами. |

## Цели тестирования

- Перечислить поддерживаемые веб-сервером методы HTTP.
- Проверить возможность обхода механизмов контроля доступа с помощью альтернативных методов.
- Протестировать техники переопределения методов HTTP (HTTP method overriding).

## Методика тестирования

### Определение поддерживаемых методов

Для проведения теста необходимо определить, какие методы HTTP поддерживаются целевым веб-сервером. Простейший способ — отправить серверу запрос `OPTIONS`:

```http
OPTIONS / HTTP/1.1
Host: example.org
```

Сервер должен вернуть ответ со списком поддерживаемых методов:

```http
HTTP/1.1 200 OK
Allow: OPTIONS, GET, HEAD, POST
```

Однако не все серверы отвечают на запросы `OPTIONS`, а некоторые могут возвращать неточную информацию. Кроме того, сервер может поддерживать разные наборы методов для различных путей. Это означает, что отсутствие поддержки метода для корневого каталога `/` не гарантирует его отключения в других разделах сайта.

Более надежным методом тестирования является прямая отправка запроса с проверяемым типом метода и последующий анализ ответа сервера. Если метод запрещен, сервер должен вернуть статус `405 Method Not Allowed`.

Следует иметь в виду, что некоторые серверы интерпретируют любые неизвестные методы как эквивалент `GET` и отвечают на произвольные глаголы, как в примере ниже. Это иногда позволяет обойти фильтрацию межсетевых экранов веб-приложений (Web Application Firewall, WAF), блокирующих стандартные методы:

```http
FOO / HTTP/1.1
Host: example.org
```

Запросы с произвольными методами можно отправлять с помощью утилиты `curl` с параметром `-X`:

```bash
curl -X FOO https://example.org
```

Существуют автоматизированные инструменты для определения поддерживаемых методов, например скрипт Nmap [`http-methods`](https://nmap.org/nsedoc/scripts/http-methods.html). Однако подобные сканеры могут пропускать опасные методы (способные модифицировать состояние сервера, такие как `PUT` или `DELETE`) либо непреднамеренно изменить данные веб-сервера, если эти методы окажутся активными. По этой причине их следует применять с осторожностью.

#### Тестирование через прокси-серверы и сети CDN

Если приложение размещено за обратным прокси-сервером, балансировщиком нагрузки, CDN или WAF, обработка методов на граничном узле (edge) может отличаться от логики сервера-источника (origin), поэтому результаты необходимо сопоставлять:

- Многие CDN по умолчанию кэшируют и пересылают только ограниченный набор методов (обычно `GET`/`HEAD`, иногда `OPTIONS`), отклоняя или отсекая остальные (`TRACE`, `CONNECT`, иногда `PUT`/`DELETE`) до того, как они достигнут источника. Таким образом, заголовок `Allow` или ответ `OPTIONS`, зафиксированный на граничном узле, не всегда отражает реальные возможности сервера-источника.
- По мере возможности (например, в рамках gray-box аудита с прямым доступом к origin либо через манипуляции с заголовком `Host` и прямое обращение по IP-адресу) тестируйте как граничный узел, так и сервер-источник напрямую. Метод, заблокированный на периметре, но активный на источнике, может быть эксплуатирован при прямом сетевом доступе к origin (ошибки конфигурации файрвола, SSRF, смежные виртуальные хосты на том же сервере).
- Некоторые прокси-серверы и WAF нормализуют или приводят к единому регистру названия методов перед сверкой с черным списком; отправка методов в смешанном регистре (`DeLeTe`) или с нестандартными пробельными символами позволяет выявить расхождения в правилах фильтрации между прокси и бэкендом.

### Методы PUT и DELETE

Методы `PUT` и `DELETE` могут приводить к совершенно разным последствиям в зависимости от того, обрабатываются ли они самим веб-сервером или работающим на нем веб-приложением.

#### Устаревшие веб-серверы

В устаревших веб-серверах метод `PUT` мог использоваться для прямой загрузки файлов на сервер. Если на сервере включена подобная конфигурация, следующий запрос создаст в веб-директории файл `test.html` с содержимым `<script>alert(1)</script>`:

```http
PUT /test.html HTTP/1.1
Host: example.org
Content-Length: 25

<script>alert(1)</script>
```

Аналогичный запрос можно отправить с помощью `curl`:

```bash
curl https://example.org --upload-file test.html
```

Это позволяет злоумышленнику загружать произвольные файлы на веб-сервер, что способно повлечь полную компрометацию системы, если разрешена загрузка исполняемых файлов (например, скриптов PHP). Впрочем, подобная конфигурация в современных системах встречается крайне редко.

Аналогично, метод `DELETE` может использоваться для удаления файлов с сервера. Обратите внимание, что это **деструктивное действие**, требующее максимальной осторожности при тестировании:

```http
DELETE /test.html HTTP/1.1
Host: example.org
```

Либо с помощью `curl`:

```bash
curl https://example.org/test.html -X DELETE
```

#### RESTful API

В современных приложениях с архитектурой REST методы `PUT` и `DELETE` штатно применяются для создания и удаления сущностей (объектов). Например, следующий API-запрос может использоваться для создания пользователя `foo` с ролью `user`:

```http
PUT /api/users/foo HTTP/1.1
Host: example.org
Content-Length: 34

{
    "role": "user"
}
```

Аналогичный запрос с методом DELETE применяется для удаления объекта:

```http
DELETE /api/users/foo HTTP/1.1
Host: example.org
```

Хотя автоматические сканеры безопасности часто регистрируют наличие этих методов, их присутствие в RESTful API **само по себе не является уязвимостью**. Тем не менее, данная функциональность может содержать иные дефекты безопасности (например, недостаточный контроль доступа) и требует тщательного тестирования.

### Метод TRACE

Метод `TRACE` (а также его аналог `TRACK` в серверах Microsoft) предписывает серверу вернуть обратно клиенту точную копию полученного запроса. В [2003 году](https://www.cgisecurity.com/whitehat-mirror/WH-WhitePaper_XST_ebook.pdf) была описана атака межсайтового трейсинга (Cross-Site Tracing, XST), с помощью которой злоумышленники могли обходить флаг `HttpOnly` и считывать конфиденциальные cookie. На сегодняшний день метод `TRACE` заблокирован во всех современных браузерах и плагинах, поэтому данная атака более не эксплуатируема. Однако сканеры по-прежнему сообщают о наличии этого метода, а включенный `TRACE` указывает на то, что веб-сервер не был надлежащим образом усилен (hardened).

### CONNECT

Метод `CONNECT` заставляет веб-сервер открыть прямое TCP-соединение с другим хостом и проксировать трафик между клиентом и этим узлом. Это может позволить злоумышленнику использовать сервер в качестве прокси для сокрытия своего IP-адреса, а также для получения доступа к внутренним сетевым сегментам или службам, привязанным к интерфейсу `localhost`. Пример запроса `CONNECT`:

```http
CONNECT 192.168.0.1:443 HTTP/1.1
Host: example.org
```

### PATCH

Метод `PATCH` описан в стандарте [RFC 5789](https://datatracker.ietf.org/doc/html/rfc5789) и предназначен для частичного изменения ресурсов на основе переданных инструкций. Сам стандарт RFC не фиксирует формат этих инструкций, однако существуют общепринятые спецификации, такие как [RFC 6902 — JavaScript Object Notation (JSON) Patch](https://datatracker.ietf.org/doc/html/rfc6902).

Например, для пользователя `foo` с характеристиками:

```json
{
    "role": "user",
    "email": "foo@example.org"
}
```

Следующий запрос JSON PATCH позволяет изменить роль пользователя на `admin` без модификации адреса электронной почты:

```http
PATCH /api/users/foo HTTP/1.1
Host: example.org

{ "op": "replace", "path": "/role", "value": "admin" }
```

Несмотря на требование RFC о передаче инструкций по модификации, разработчики часто используют метод `PATCH` для прямой передачи измененных полей:

```http
PATCH /api/users/foo HTTP/1.1
Host: example.org

{
    "role": "admin"
}
```

Как и в случае с `PUT`, такая логика может содержать ошибки разграничения доступа. Кроме того, разработчики нередко пренебрегают валидацией входных данных при модификации сущностей по сравнению с этапом их создания. Это способно привести к внедрению вредоносных значений (например, к атакам хранимого межсайтового скриптинга `[Stored XSS]`) либо к нарушению целостности данных и сбоям в бизнес-логике.

### Методы WebDAV

Если на сервере активирован протокол WebDAV (например, компонент WebDAV Publishing в IIS или модуль `mod_dav` в Apache), сервер может обрабатывать дополнительные методы: `PROPFIND`, `PROPPATCH`, `MKCOL`, `COPY`, `MOVE`, `LOCK` и `UNLOCK`. Поддержка WebDAV относится к устаревшим технологиям и крайне редко требуется современным веб-приложениям, поэтому само ее наличие на сервере заслуживает фиксации независимо от наличия прямых уязвимостей.

Метод `PROPFIND` позволяет извлекать листинг каталогов и метаданные ресурсов, даже если стандартный просмотр директорий отключен:

```http
PROPFIND /uploads/ HTTP/1.1
Host: example.org
Depth: 1
```

Методы `MKCOL`, `COPY` и `MOVE` могут применяться для создания каталогов или перемещения/копирования файлов. В сочетании с небезопасным методом `PUT` это исторически использовалось для обхода ограничений загрузки файлов (например, злоумышленник загружал файл с разрешенным расширением, после чего переименовывал его в исполняемый с помощью `MOVE` или `COPY`). Проверьте, применяются ли ограничения на расширения файлов одинаково для методов `PUT`, `MOVE` и `COPY`.

Если WebDAV не требуется для функционирования сервиса, рекомендуется полностью отключить его; если он необходим, ограничьте его применение только строго определенными каталогами, исключив доступ на путях основного веб-приложения.

### QUERY

Метод `QUERY` — современный метод HTTP, стандартизированный в [RFC 10008](https://datatracker.ietf.org/doc/html/rfc10008) и предназначенный для безопасного извлечения данных с передачей параметров в теле запроса. Подобно `POST`, он принимает структурированные данные в теле, однако, в отличие от `POST`, является безопасным (safe) и идемпотентным (idempotent): он не модифицирует состояние сервера и допускает кэширование ответов. По смыслу он аналогичен методу `GET`, но позволяет передавать сложные структуры параметров и фильтров, которые было бы неудобно или невозможно разместить в строке URL.

Например, метод `QUERY` может использоваться для выполнения сложного поискового запроса со множеством параметров фильтрации:

```http
QUERY /api/users/search HTTP/1.1
Host: example.org
Content-Type: application/json

{
    "filters": {
        "role": "admin",
        "status": "active",
        "lastLogin": {"after": "2024-01-01"}
    }
}
```

Метод `QUERY` спроектирован как кэшируемый и доступный только для чтения, что принципиально отличает его от `POST`. Он не должен использоваться для операций, изменяющих данные на сервере. В ходе тестирования необходимо убедиться:

- Сервер корректно трактует `QUERY` как безопасную операцию и не изменяет состояние данных.
- Механизмы контроля доступа и авторизации полноценно применяются к запросам с методом `QUERY`.
- Метод не используется злоумышленниками для обхода средств защиты, фильтрующих другие глаголы HTTP.
- При кэшировании ответов `QUERY` (приложением или промежуточными прокси) ключ кэша (cache key) включает тело запроса, исключая возврат ответа одного поискового запроса для совершенно другого запроса ([RFC 10008, раздел 2.7](https://datatracker.ietf.org/doc/html/rfc10008#section-2.7)).

### Обход контроля доступа

Если защищенная страница приложения перенаправляет неавторизованного пользователя на страницу входа с кодом `302 Found` при стандартном запросе `GET`, это ограничение иногда можно обойти, отправив запрос с альтернативным методом — `HEAD`, `POST` или даже фиктивным глаголом вроде `FOO`. Если приложение в ответ возвращает статус `HTTP/1.1 200 OK` вместо ожидаемого редиректа, возникает потенциальная возможность обхода механизмов аутентификации или авторизации. В примере ниже показано, как запрос `HEAD` приводит к выдаче административной сессионной cookie вместо перенаправления:

```http
HEAD /admin/ HTTP/1.1
Host: example.org
```

```http
HTTP/1.1 200 OK
[...]
Set-Cookie: adminSessionCookie=[...];
```

В других случаях удается отправлять прямые запросы к страницам, выполняющим действия в системе:

```http
HEAD /admin/createUser.php?username=foo&password=bar&role=admin HTTP/1.1
Host: example.org
```

Или:

```http
FOO /admin/createUser.php
Host: example.org
Content-Length: 36

username=foo&password=bar&role=admin
```

### Переопределение HTTP-методов

Ряд веб-фреймворков поддерживает механизм переопределения фактического метода HTTP в запросе. Это достигается за счет эмуляции недостающих методов через специальные пользовательские заголовки. Основная цель подобного механизма — передача запросов через промежуточные прокси-серверы или WAF, блокирующие определенные глаголы HTTP. Для переопределения могут применяться следующие заголовки:

- `X-HTTP-Method`
- `X-HTTP-Method-Override`
- `X-Method-Override`

Для проверки сценария, когда обращение с методами `PUT` или `DELETE` блокируется статусом `405 Method Not Allowed`, повторите исходный запрос методом `GET` или `POST`, добавив один из заголовков переопределения, и проанализируйте реакцию системы. При наличии поддержки переопределения приложение вернет другой статус (например, `200 OK`).

Многие фреймворки поддерживают переопределение методов не только через заголовки, но и через специальные параметры запроса (обычно параметр `_method` в строке URL или теле формы, например `POST /resource.html?_method=DELETE`). Проверяйте параметры наряду с заголовками, поскольку фильтры WAF, инспектирующие только HTTP-заголовки, могут пропускать параметры запроса.

Поскольку переопределение методов предназначено для обхода сетевых шлюзов, всегда сопоставляйте поведение граничного узла (прокси, CDN, WAF) и сервера-источника: если метод заблокирован на периметре, но успешно исполняется бэкендом через заголовок переопределения, это указывает на то, что origin слепо доверяет пользовательским заголовкам, не согласованным с правилами безопасности шлюза.

В следующем примере веб-сервер блокирует метод `DELETE`:

```http
DELETE /resource.html HTTP/1.1
Host: example.org
```

```http
HTTP/1.1 405 Method Not Allowed
[...]
```

После добавления заголовка `X-HTTP-Method` сервер успешно обрабатывает запрос и возвращает код 200:

```http
GET /resource.html HTTP/1.1
Host: example.org
X-HTTP-Method: DELETE
```

```http
HTTP/1.1 200 OK
[...]
```

## Рекомендации по устранению

- Разрешайте только строго необходимые методы HTTP и контролируйте их корректную конфигурацию.
- Исключите механизмы и обходные пути, позволяющие нивелировать средства защиты, реализованные браузерами, фреймворками или серверами.
- Отключите функционал WebDAV (`mod_dav`, IIS WebDAV Publishing), если он не является строго обязательным; при необходимости его использования ограничьте область действия минимально необходимыми каталогами.
- Обеспечьте согласованность политик фильтрации методов между граничными прокси/CDN/WAF и сервером-источником. Убедитесь, что сервер-источник не принимает пользовательские заголовки или параметры переопределения методов (`X-HTTP-Method-Override`, `_method`), если граничные шлюзы явно не используют их в своей логике.
