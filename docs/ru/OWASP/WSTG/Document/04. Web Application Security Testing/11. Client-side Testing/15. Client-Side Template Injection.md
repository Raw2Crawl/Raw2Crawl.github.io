# Внедрение шаблонов на стороне клиента

| ID |
| --- |
| WSTG-CLNT-15 |

## Резюме

Внедрение шаблонов на стороне клиента (Client-Side Template Injection, CSTI), также известное как внедрение шаблонов на основе DOM (DOM-based Template Injection), возникает, когда приложения, использующие клиентские фреймворки (такие как Angular, Vue.js или Alpine.js), динамически встраивают пользовательский ввод в DOM веб-страницы. Если эти данные попадают в шаблонное выражение или интерпретируются движком шаблонов фреймворка, злоумышленник может внедрить вредоносные директивы.

В отличие от [внедрения шаблонов на стороне сервера (Server-Side Template Injection, SSTI)](../07.%20Injection%20Testing/18.%20Server-side%20Template%20Injection.md), где рендеринг шаблона осуществляется на сервере, CSTI происходит исключительно внутри браузера пользователя. Когда фреймворк сканирует DOM на наличие динамического контента, он может исполнить внедренные шаблонные выражения. Часто это приводит к межсайтовому скриптингу (Cross-Site Scripting, XSS), однако механизм инъекции и эксплуатации отличается от стандартного XSS, поскольку полезная нагрузка должна подчиняться синтаксису конкретного движка шаблонов (например, {% raw %}`{{ 7*7 }}`{% endraw %}).

Данная уязвимость особенно распространена в одностраничных приложениях (Single Page Applications, SPA), где разработчики могут полагаться на клиентский рендеринг без строгого разделения контекстов.

## Цели тестирования

- Идентифицировать используемый приложением клиентский фреймворк и его версию.
- Обнаружить точки внедрения, где пользовательский ввод отражается в DOM и обрабатывается движком шаблонов.
- Оценить, позволяет ли инъекция выполнить произвольный код JavaScript (XSS) с помощью синтаксиса шаблонов.

## Методика тестирования

### Тестирование методом «черного ящика»

#### Идентификация фреймворка

Первым шагом является определение факта использования клиентского фреймворка. Тестировщикам следует искать специфические атрибуты в исходном коде HTML или определенные HTTP-заголовки ответов.

- **Angular:** Обратите внимание на такие атрибуты, как `ng-app`, `ng-model` или `ng-bind`.
- **Vue.js:** Ищите атрибуты, начинающиеся с `v-` (например, `v-if`, `v-for`), или присутствие глобального объекта Vue в консоли.
- **Alpine.js:** Ищите атрибуты `x-data`, `x-html`.

#### Обнаружение инъекций

Для обнаружения CSTI тестировщикам следует внедрять символы, имеющие синтаксическое значение для движка шаблонов. Наиболее распространенным синтаксисом интерполяции во многих фреймворках являются двойные фигурные скобки {% raw %}`{{ }}`{% endraw %}.

Стандартным зондом является простая арифметическая операция. Если приложение вычисляет математическое выражение, оно уязвимо.

**Базовый зонд (Generic Probe):**

{% raw %}

```text
Inject the string: {{ 7*7 }}
```

{% endraw %}

- Если приложение отображает `49`, уязвимость CSTI присутствует.
- Если приложение выводит {% raw %}`{{ 7*7 }}`{% endraw %}, оно, скорее всего, не уязвимо либо применяется строгое контекстное экранирование.

#### Angular

Angular оперирует непосредственно с DOM. Если атакующий может внедрить в DOM строку, содержащую выражения Angular, до того, как Angular инициализирует (bootstraps) или скомпилирует этот фрагмент, выражение будет выполнено.

**Полезные нагрузки для детекта:**

{% raw %}

- `{{ 7*7 }}`
- `{{ constructor.constructor('alert(1)')() }}`

{% endraw %}

В ранних версиях Angular (1.x) движок шаблонов функционировал внутри «песочницы» (sandbox). Эксплуатация требовала побега из этой песочницы (sandbox escape). Сложность полезной нагрузки напрямую зависит от конкретной версии.

**Пример пейлоада (обход песочницы Angular 1.5.x):**

{% raw %}

```javascript
{{x={'y':''.constructor.prototype};x['y'].charAt=[].join;$eval('x=alert(1)');}}
```

{% endraw %}

#### Vue.js

Vue.js также подвержен уязвимости, если разработчики используют директиву `v-html` с пользовательским вводом или если они монтируют экземпляр Vue на DOM-элемент, уже содержащий контролируемый пользователем HTML.

**Полезные нагрузки для детекта:**

{% raw %}

- `{{ 7*7 }}`

{% endraw %}

**Пример пейлоада (Vue.js 2.x):**

{% raw %}

```javascript
{{_v.constructor('alert(1)')()}}
```

{% endraw %}

#### Alpine.js

Alpine.js активно опирается на атрибуты DOM. Если атакующий способен контролировать имя атрибута или внедрять данные в директиву, он может выполнить код.

**Пример пейлоада:**

```html
<div x-data="" x-html="'<img src=x onerror=alert(1)>'"></div>
```

### Тестирование методом «серого ящика»

#### Анализ исходного кода

В сценарии «серого ящика» тестировщики проверяют, как пользовательский ввод обрабатывается в коде фронтенда. Главная задача — выявить места, где приёмники («sinks»), интерпретирующие HTML или синтаксис шаблонов, получают данные из «загрязненных» источников (tainted sources / пользовательский ввод).

**Приёмники Angular:**
Выполните поиск вызовов `$compile` или директивы `ng-bind-html`.
Если используется `ng-bind-html`, проверьте, корректно ли настроен сервис `$sce` (Strict Contextual Escaping) и не вызывается ли метод `$sce.trustAsHtml()` для обработки недоверенных данных.

```javascript
// Vulnerable example in Angular
$scope.htmlSnippet = $sce.trustAsHtml(userInput);
```

**Приёмники Vue.js:**
Выполните поиск директивы `v-html`. Использование `v-html` с содержимым, предоставленным пользователем, является основной причиной возникновения CSTI/XSS во Vue.

```html
<div v-html="userProvidedComment"></div>
```

**Приёмники React:**
Хотя React в целом более защищен от внедрения шаблонов, поскольку он не сканирует DOM в поисках шаблонов (JSX предварительно компилируется), некорректное применение свойства `dangerouslySetInnerHTML` приводит к DOM-based XSS, что эквивалентно рассматриваемому профилю риска.

{% raw %}

```javascript
// Vulnerable example in React
<div dangerouslySetInnerHTML={{__html: userContent}} />
```

{% endraw %}

#### Анализ конфигурации

Обратите особое внимание на заголовки политики защиты контента (Content Security Policy, CSP). Строгая политика CSP может нивелировать последствия CSTI путем ограничения источников загрузки скриптов или блокировки выполнения встроенных (inline) сценариев (включая скрипты, генерируемые движками шаблонов).

Проверьте наличие директивы `unsafe-eval` в CSP. Многим движкам шаблонов (особенно устаревшим) требуется `unsafe-eval` для динамической компиляции шаблонов. Если флаг `unsafe-eval` присутствует, эксплуатация атак CSTI существенно упрощается.

## Рекомендации по устранению

- **Избегайте рендеринга пользовательского ввода в виде HTML:** Везде, где возможно, применяйте безопасные директивы, обрабатывающие ввод исключительно как текст.
    - Angular: используйте `ng-bind` вместо `ng-bind-html`.
    - Vue: используйте `v-text` или фигурные скобки {% raw %}`{{ }}`{% endraw %} (которые автоматически экранируют HTML) вместо `v-html`.
    - React: избегайте использования `dangerouslySetInnerHTML`.
- **Очистка данных (Sanitization):** Если рендеринг HTML необходим, используйте специализированную библиотеку санитизации (такую как DOMPurify) для вырезания опасных тегов и атрибутов перед передачей данных во фреймворк.
- **Политика защиты контента (CSP):** Внедрите строгую политику CSP с отключением `unsafe-eval` и ограничением доверенных источников скриптов.
- **Используйте автономную компиляцию (Offline Compilation):** Для таких фреймворков, как Vue или React, отдавайте предпочтение сборщикам (webpack, vite), компилирующим шаблоны предварительно на этапе сборки (ahead-of-time), вместо применения рантайм-компилятора, разбирающего содержимое DOM на лету.

### Инструменты

- [DOMPurify](https://github.com/cure53/DOMPurify): Высокопроизводительный санитизатор XSS для DOM, обрабатывающий HTML, MathML и SVG.
