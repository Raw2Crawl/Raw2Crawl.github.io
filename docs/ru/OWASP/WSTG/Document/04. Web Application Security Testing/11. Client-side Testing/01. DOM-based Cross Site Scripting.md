# Межсайтовый скриптинг на основе DOM (DOM-based XSS)

| ID |
| --- |
| WSTG-CLNT-01 |

## Резюме

[Межсайтовый скриптинг на основе DOM (DOM-based Cross-Site Scripting, DOM XSS)](https://owasp.org/www-community/attacks/DOM_Based_XSS) — это де-факто общепринятое название уязвимостей [межсайтового скриптинга (Cross-Site Scripting, XSS)](https://owasp.org/www-community/attacks/xss/), возникающих в результате работы активного клиентского содержимого страницы (как правило, JavaScript), которое получает пользовательский ввод через [источник (source)](https://github.com/wisec/domxsswiki/wiki/sources) и передает его в [приёмник (sink)](https://github.com/wisec/domxsswiki/wiki/Sinks), что приводит к выполнению внедренного кода. В данном документе рассматриваются исключительно ошибки в коде JavaScript, приводящие к XSS.

DOM, или [объектная модель документа (Document Object Model)](https://en.wikipedia.org/wiki/Document_Object_Model), представляет собой структурный формат, используемый для представления документов в браузере. DOM позволяет динамическим сценариям, таким как JavaScript, обращаться к компонентам документа — например, к полям форм или сессионным cookie. DOM также применяется браузером для обеспечения безопасности — например, для ограничения возможности скриптов из других доменов получать сессионные cookie чужих доменов. Уязвимость DOM-based XSS может возникнуть, когда активное содержимое, такое как функция JavaScript, модифицируется с помощью специально сформированного запроса таким образом, что элементом DOM начинает управлять злоумышленник.

Не все ошибки XSS требуют от атакующего контроля над содержимым, возвращаемым сервером; вместо этого для достижения того же результата могут эксплуатироваться небезопасные практики написания кода на JavaScript. Последствия аналогичны типичным дефектам XSS, отличается лишь механизм доставки полезной нагрузки.

В отличие от других типов межсайтового скриптинга ([отражённого и хранимого](https://owasp.org/www-community/attacks/xss/), где неотфильтрованный параметр передается сервером, возвращается пользователю и исполняется в контексте его браузера), уязвимость DOM-based XSS управляет ходом выполнения кода с помощью элементов объектной модели документа (DOM) совместно со сформированным атакующим кодом, изменяющим этот поток управления.

В силу своей специфики уязвимости DOM-based XSS во многих случаях могут срабатывать без возможности сервера зафиксировать, что именно выполняется на клиенте. Из-за этого многие стандартные методы фильтрации и обнаружения XSS оказываются неэффективными против подобных атак.

В данном гипотетическом примере используется следующий клиентский код:

```html
<script>
document.write("Site is at: " + document.location.href + ".");
</script>
```

Злоумышленник может добавить `#<script>alert('xss')</script>` к URL уязвимой страницы, что при выполнении приведет к отображению всплывающего окна alert. В данном случае добавленный код не будет отправлен на сервер, поскольку все символы после знака `#` обрабатываются браузером не как часть запроса, а как фрагмент (fragment). В этом примере код выполняется незамедлительно, и страница выводит предупреждение «xss». В отличие от более распространенных типов межсайтового скриптинга ([отражённого и хранимого](https://owasp.org/www-community/attacks/xss/), при которых код передается на сервер и затем возвращается обратно в браузер), здесь код выполняется напрямую в браузере пользователя без обращения к серверу.

[Последствия](https://owasp.org/www-community/attacks/xss/) дефектов DOM-based XSS столь же обширны, как и при более известных формах XSS, включая извлечение cookie, дальнейшее внедрение вредоносных сценариев и т. д., и поэтому к ним следует относиться с тем же уровнем критичности.

## Цели тестирования

- Идентифицировать приёмники (DOM sinks).
- Сконструировать полезные нагрузки (payloads), применимые к каждому типу приёмника.

## Методика тестирования

Приложения на JavaScript существенно отличаются от приложений других типов, поскольку они часто динамически генерируются сервером. Чтобы понять, какой именно код выполняется, тестируемый веб-сайт необходимо просканировать (crawl) для выявления всех мест исполнения JavaScript и точек приема пользовательского ввода. Многие веб-сайты опираются на объемные библиотеки функций, размер которых нередко достигает сотен тысяч строк кода, разработанных сторонними авторами. В таких случаях нисходящее тестирование (top-down testing) часто становится единственным жизнеспособным вариантом, поскольку множество низкоуровневых функций никогда не вызываются напрямую, а их построчный анализ для поиска приёмников отнимет больше времени, чем доступно тестировщику. То же самое справедливо и для нисходящего тестирования, если входные данные или их отсутствие не были идентифицированы с самого начала.

Пользовательский ввод поступает в двух основных формах:

- Ввод, записываемый на страницу сервером таким образом, который исключает прямое возникновение XSS, и
- Ввод, получаемый из клиентских объектов JavaScript.

Ниже приведены два примера того, как сервер может внедрять данные в JavaScript:

```javascript
var data = "<escaped data from the server>";
var result = someFunction("<escaped data from the server>");
```

Ниже представлены два примера получения ввода из клиентских объектов JavaScript:

```javascript
var data = window.location;
var result = someFunction(window.referrer);
```

Хотя с точки зрения кода JavaScript способ их извлечения практически не отличается, важно учитывать: когда ввод поступает через сервер, он может применить к данным любые преобразования по своему усмотрению. С другой стороны, преобразования, выполняемые объектами JavaScript, достаточно хорошо изучены и документированы. Если бы функция `someFunction` в приведенном выше примере являлась приёмником (sink), то возможность эксплуатации в первом случае зависела бы от фильтрации, реализованной на стороне сервера, тогда как во втором случае — от кодирования, выполняемого браузером над объектом `window.referrer`. Стефано Ди Паоло (Stefano Di Paulo) написал превосходную статью о том, какие значения возвращают браузеры при обращении к различным элементам [URL с использованием атрибутов document и location](https://github.com/wisec/domxsswiki/wiki/location,-documentURI-and-URL-sources).

Кроме того, JavaScript нередко исполняется вне блоков `<script>`, о чем свидетельствуют многочисленные векторы атак, ранее приводившие к обходу фильтров XSS. При исследовании приложения важно обращать внимание на использование скриптов в таких местах, как обработчики событий (event handlers) и блоки CSS с атрибутами выражений (`expression`). Также следует учитывать, что любые внешние CSS- или script-объекты со сторонних ресурсов потребуется оценить, чтобы определить исполняемый ими код.

Автоматизированное тестирование обладает весьма ограниченной эффективностью при идентификации и валидации DOM-based XSS, поскольку стандартные сканеры обычно выявляют XSS путем отправки специфического пейлоада и попытки обнаружить его в ответе сервера. Это может сработать для простого примера, приведенного ниже, где параметр message отражается обратно пользователю:

```html
<script>
var pos=document.URL.indexOf("message=")+5;
document.write(document.URL.substring(pos,document.URL.length));
</script>
```

Однако уязвимость может остаться незамеченной в следующем искусственном сценарии:

```html
<script>
var navAgt = navigator.userAgent;

if (navAgt.indexOf("MSIE")!=-1) {
        document.write("You are using IE as a browser and visiting site: " + document.location.href + ".");
}
else
{
    document.write("You are using an unknown browser.");
}
</script>
```

По этой причине автоматизированное тестирование не способно обнаружить участки, потенциально подверженные DOM-based XSS, если только инструмент тестирования не выполняет дополнительный анализ клиентского кода.

В связи с этим необходимо проводить ручное тестирование путем анализа тех областей кода, где происходит обращение к параметрам, представляющим интерес для злоумышленника. Примерами таких участков являются места динамической записи кода на страницу, другие точки модификации DOM или даже фрагменты прямого исполнения скриптов.
