# Анализ содержимого веб-страниц на утечку информации

| ID |
| --- |
| WSTG-INFO-05 |

## Резюме

Для программистов вполне естественно и даже рекомендуется оставлять подробные комментарии и метаданные в исходном коде. Однако комментарии и метаданные, включенные в HTML-код, могут раскрывать внутреннюю информацию, которая не должна быть доступна потенциальным злоумышленникам. Анализ комментариев и метаданных должен проводиться для выявления утечки информации (information leakage). Кроме того, некоторые приложения могут допускать утечку данных в теле ответов с перенаправлением (redirect responses).

В современных веб-приложениях все шире применяется клиентский JavaScript на фронтенде. Популярные технологии построения фронтенда используют такие JavaScript-фреймворки, как React, Angular или Vue. Подобно комментариям и метаданным в HTML-коде, многие разработчики также жестко прописывают (hardcode) конфиденциальные данные в переменных JavaScript на стороне клиента. Чувствительная информация может включать (но не ограничивается этим): закрытые API-ключи (*например*, неограниченный Google Maps API Key), внутренние IP-адреса, конфиденциальные маршруты (*например*, путь к скрытым страницам администрирования или функционалу) или даже учетные данные. Эти конфиденциальные сведения могут утекать из клиентского кода JavaScript. Необходимо провести проверку, чтобы определить наличие утечек конфиденциальной информации, которые могут быть использованы злоумышленниками.

Для крупных веб-приложений вопросы производительности представляют первостепенную важность. Разработчики применяют различные методы для оптимизации производительности фронтенда, включая Syntactically Awesome Style Sheets (Sass), Sassy CSS (SCSS), webpack и др. При использовании этих технологий исходный код фронтенда порой становится трудным для восприятия и отладки, поэтому разработчики часто развертывают файлы карт исходного кода (source map files) для целей отладки. «Source map» — это специальный файл, связывающий минифицированную/обфусцированную (minified/uglified) версию ресурса (CSS или JavaScript) с исходной версией кода, написанной разработчиком. Программисты до сих пор спорят о том, допустимо ли размещать файлы карт исходного кода в продуктивной среде (production). Однако неоспоримо то, что файлы source map или отладочные файлы, опубликованные в продакшене, делают исходный код легко читаемым для человека. Это облегчает злоумышленникам поиск уязвимостей на стороне фронтенда или сбор конфиденциальной информации. Следует проводить аудит кода JavaScript для выявления доступных отладочных файлов на клиенте. В зависимости от контекста и уровня критичности проекта специалист по безопасности должен определить, допустимо ли наличие этих файлов в продуктивной среде.

## Цели тестирования

- Проверить комментарии веб-страниц, метаданные и тела ответов с перенаправлениями на предмет утечки информации.
- Собрать JavaScript-файлы и проанализировать код JS для лучшего понимания логики приложения и поиска утечек данных.
- Выяснить, присутствуют ли на сервере файлы карт исходного кода (source maps) или другие файлы отладки фронтенда.

## Методика тестирования

### Анализ комментариев и метаданных веб-страниц

HTML-комментарии часто используются разработчиками для добавления отладочной информации о приложении. Иногда они забывают об этих комментариях и оставляют их в продуктивных окружениях. Тестировщикам следует искать HTML-комментарии, начинающиеся с `<!--`.

Проверьте исходный код HTML на наличие комментариев, содержащих конфиденциальную информацию, которая может помочь злоумышленнику глубже понять устройство приложения. Это может быть SQL-код, имена пользователей и пароли, внутренние IP-адреса или отладочные сообщения:

```html
...
<div class="table2">
  <div class="col1">1</div><div class="col2">Mary</div>
  <div class="col1">2</div><div class="col2">Peter</div>
  <div class="col1">3</div><div class="col2">Joe</div>

<!-- Query: SELECT id, name FROM app.users WHERE active='1' -->

</div>
...
```

Тестировщик может обнаружить даже нечто подобное:

```html
<!-- Use the DB administrator password for testing:  f@keP@a$$w0rD -->
```

Проверьте информацию о версии HTML на наличие корректных номеров версий и URL-адресов определения типа документа (Data Type Definition, DTD):

```html
<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN" "https://www.w3.org/TR/html4/strict.dtd">
```

- `strict.dtd` — строгий DTD по умолчанию
- `loose.dtd` — переходный (loose) DTD
- `frameset.dtd` — DTD для документов с фреймами

Некоторые теги `META` не создают прямых векторов атак, однако позволяют злоумышленнику профилировать приложение:

```html
<META name="Author" content="Andrew Muller">
```

Распространенным (хотя и не соответствующим стандартам [WCAG](https://www.w3.org/WAI/standards-guidelines/wcag/)) тегом `META` является [Refresh](https://en.wikipedia.org/wiki/Meta_refresh):

```html
<META http-equiv="Refresh" content="15;URL=https://www.owasp.org/index.html">
```

Обычное назначение тега `META` — указание ключевых слов, которые поисковая система может использовать для повышения релевантности результатов поиска:

```html
<META name="keywords" lang="en-us" content="OWASP, security, sunshine, lollipops">
```

Хотя большинство веб-серверов управляют индексацией поисковыми системами через файл `robots.txt`, этой логикой можно управлять и с помощью тегов `META`. Приведенный ниже тег предписывает роботам не индексировать страницу и не переходить по ссылкам на HTML-странице, содержащей данный тег:

```html
<META name="robots" content="none">
```

Платформа [Platform for Internet Content Selection (PICS)](https://www.w3.org/PICS/) и протокол [Protocol for Web Description Resources (POWDER)](https://www.w3.org/2007/powder/) предоставляют инфраструктуру для связывания метаданных с интернет-контентом.

### Выявление кода JavaScript и сбор JS-файлов

Программисты часто жестко задают чувствительные данные в переменных JavaScript на фронтенде. Тестировщикам следует проверять исходный HTML-код и искать код JavaScript между тегами `<script>` и `</script>`. Также необходимо выявлять внешние JavaScript-файлы для анализа их кода (файлы JavaScript имеют расширение `.js`, а имя файла обычно указывается в атрибуте `src` тега `<script>`).

Проверьте код JavaScript на предмет утечек конфиденциальной информации, которые могут быть использованы атакующими для дальнейшей компрометации или манипулирования системой. Обращайте внимание на такие значения, как: API-ключи, внутренние IP-адреса, конфиденциальные маршруты или учетные данные. Например:

```javascript
const myS3Credentials = {
  accessKeyId: config('AWSS3AccessKeyID'),
  secretAccessKey: config('AWSS3SecretAccessKey'),
};
```

Тестировщик может встретить даже такие строки:

```javascript
var conString = "tcp://postgres:1234@localhost/postgres";
```

При обнаружении API-ключа тестировщики могут проверить, настроены ли ограничения ключа для конкретного сервиса, по IP-адресу, HTTP Referer, приложению, SDK и т. д.

Например, при обнаружении ключа Google Maps API тестировщики могут проверить, ограничен ли этот ключ по IP или только рамками Google Maps API. Если API-ключ Google ограничен только интерфейсами Google Maps API, атакующие все равно могут использовать его для запросов к неограниченным API Google Maps, а оплачивать эти запросы придется владельцу приложения.

```html
<script type="application/json">
...
{"GOOGLE_MAP_API_KEY":"AIzaSyDUEBnKgwiqMNpDplT6ozE4Z0XxuAbqDi4", "RECAPTCHA_KEY":"6LcPscEUiAAAAHOwwM3fGvIx9rsPYUq62uRhGjJ0"}
...
</script>
```

В ряде случаев в коде JavaScript можно обнаружить конфиденциальные маршруты, такие как ссылки на внутренние или скрытые страницы администрирования:

```html
<script type="application/json">
...
"runtimeConfig":{"BASE_URL_VOUCHER_API":"https://staging-voucher.victim.net/api", "BASE_BACKOFFICE_API":"https://10.10.10.2/api", "ADMIN_PAGE":"/hidden_administrator"}
...
</script>
```

#### Анализ JavaScript и клиентского исходного кода

Современные одностраничные приложения (Single-Page Applications, SPA) и объемный клиентский код часто содержат эндпоинты API, флаги функций (feature flags), а иногда и секреты. Собрав файлы JavaScript (вручную, через прокси или с помощью таких инструментов, как Uproot), тестировщики могут извлечь представляющие интерес данные:

```bash
# Example with jsluice
jsluice urls bundle.js
jsluice secrets bundle.js

# Example with LinkFinder
python linkfinder.py -i bundle.js -o cli
```

Сопоставьте извлеченные эндпоинты и параметры с результатами сбора архивных URL (gau / waybackurls / waymore), а также с методами, описанными в разделе [Identify Application Entry Points](06.%20Identify%20Application%20Entry%20Points.md) и главе [API Reconnaissance](../12.%20API%20Testing/01.%20API%20Reconnaissance.md).

### Выявление файлов Source Map

Файлы карт исходного кода (source map) обычно загружаются при открытии инструментов разработчика (DevTools). Тестировщики также могут найти их, добавив расширение `.map` после расширения каждого внешнего JavaScript-файла. Например, если тестировщик видит файл `/static/js/main.chunk.js`, он может проверить наличие его карты исходников, обратившись по адресу `/static/js/main.chunk.js.map`.

Проверьте файлы source map на наличие конфиденциальной информации, которая поможет злоумышленнику получить более детальное представление о приложении. Например:

```json
{
  "version": 3,
  "file": "static/js/main.chunk.js",
  "sources": [
    "/home/sysadmin/cashsystem/src/actions/index.js",
    "/home/sysadmin/cashsystem/src/actions/reportAction.js",
    "/home/sysadmin/cashsystem/src/actions/cashoutAction.js",
    "/home/sysadmin/cashsystem/src/actions/userAction.js",
    "..."
  ],
  "..."
}
```

Когда сайт загружает файлы source map, исходный код фронтенда становится читаемым и значительно более удобным для анализа и отладки.

### Выявление ответов перенаправления с утечкой информации

Хотя от ответов с перенаправлением (redirect responses) обычно не ожидается наличия какого-либо существенного веб-контента, нет никакой гарантии, что они не содержат данных. Таким образом, хотя ответы серии 300 (редиректы) часто содержат текст типа «redirecting to `https://example.com/`», они также могут допускать утечку контента.

Рассмотрим ситуацию, когда ответ с перенаправлением является результатом проверки аутентификации или авторизации. Если эта проверка завершается неудачно, сервер может отправить ответ, перенаправляющий пользователя на «безопасную» или «стандартную» страницу, однако сам ответ редиректа может по-прежнему содержать полезную нагрузку, которая не отображается в браузере, но фактически передается клиенту. Это можно наблюдать либо с помощью инструментов разработчика браузера, либо через локальный перехватывающий прокси (такой как ZAP, Burp, Fiddler или Charles).

### Проверка сгенерированных файлов на утечку метаданных

Веб-приложения могут генерировать файлы для скачивания, такие как документы PDF, электронные таблицы, счета или отчеты. Эти файлы могут содержать встроенные метаданные с описанием программного обеспечения или библиотек, использованных для их создания.

Поля метаданных, такие как *Producer*, *Creator*, *Application* или *Library Version*, могут раскрывать технологии бэкенда и конкретные номера версий. Эта информация помогает атакующим профилировать приложение и находить общеизвестные уязвимости (CVE).

Например, сгенерированный PDF-документ может раскрывать библиотеку, примененную для его создания:

`Producer: iText 2.1.7`

Злоумышленник может затем выполнить поиск известных уязвимостей, затрагивающих эту версию.

#### Методика тестирования

Скачайте сгенерированные файлы из приложения и проверьте их метаданные.

Для файлов PDF:

```bash
exiftool file.pdf
pdfinfo file.pdf
strings file.pdf | grep -i producer
```

Пример вывода:

`Producer: iText 2.1.7`

Для офисных документов (DOCX, XLSX):

```bash
exiftool file.docx
```

Проверьте такие поля метаданных, как:

- Producer
- Creator
- Application
- Creation Tool
- Library Version
