# Инъекция в заголовок Host

| ID |
| --- |
| WSTG-INJT-17 |

## Резюме

Веб-сервер зачастую размещает несколько веб-приложений на одном IP-адресе, разделяя доступ к каждому приложению через механизм виртуальных хостов (virtual hosts). При получении входящего HTTP-запроса веб-сервер обычно перенаправляет его целевому виртуальному хосту на основе значения, переданного в заголовке `Host`. При отсутствии надлежащей валидации значения этого заголовка атакующий может передать некорректные данные, что приведет к:

- Маршрутизации запросов на первый виртуальный хост в списке сервера (default vhost).
- Выполнению редиректа на подконтрольный атакующему домен.
- Отравлению веб-кэша (Web Cache Poisoning).
- Компрометации функционала сброса паролей (Password Reset Poisoning).
- Получению несанкционированного доступа к закрытым виртуальным хостам, не предназначенным для внешнего использования.

## Цели тестирования

- Определить, обрабатывается ли заголовок `Host` динамически в логике приложения.
- Обойти механизмы безопасности, полагающиеся на значение заголовка `Host`.

## Методика тестирования

Первичное тестирование заключается в подстановке стороннего домена (например, `attacker.com`) в поле заголовка `Host`. Степень опасности и последствия атаки целиком зависят от того, как веб-сервер и приложение обрабатывают значение этого заголовка. Атака считается состоятельной, если веб-сервер обрабатывает ввод таким образом, что перенаправляет запрос на подконтрольный атакующему сервер, расположенный в переданном домене, а не на локальный виртуальный хост веб-сервера.

```http
GET / HTTP/1.1
Host: www.attacker.com
[...]
```

В простейшем случае это может вызвать перенаправление 302 Found на указанный домен:

```http
HTTP/1.1 302 Found
[...]
Location: https://www.attacker.com/login.php

```

Либо веб-сервер может передать запрос на обслуживание первому виртуальному хосту в конфигурационном списке.

### Обход с помощью заголовка X-Forwarded-Host

Если внедрение заголовка `Host` блокируется проверкой входящих данных, можно попробовать передать целевой домен через вспомогательный заголовок `X-Forwarded-Host`.

```http
GET / HTTP/1.1
Host: www.example.com
X-Forwarded-Host: www.attacker.com
[...]
```

Это может привести к генерации клиентского HTML-кода следующего вида:

```html
[...]
<link src="https://www.attacker.com/link" />
[...]
```

Возможность такой манипуляции напрямую зависит от логики обработки заголовков веб-сервером и фреймворком.

### Отравление веб-кэша (Web Cache Poisoning)

Используя эту технику, атакующий может модифицировать содержимое веб-кэша таким образом, чтобы отдавать вредоносный контент всем последующим пользователям, запрашивающим страницу. Атака опирается на возможность отравления кэширующего прокси-сервера самого приложения, сетей доставки контента (CDN) или промежуточных провайдеров. В результате жертва не имеет возможности предотвратить получение вредоносного контента при обращении к уязвимому приложению.

```http
GET / HTTP/1.1
Host: www.attacker.com
[...]
```

При переходе жертвы в уязвимое приложение из отравленного веб-кэша будет возвращен следующий фрагмент:

```html
[...]
<link src="https://www.attacker.com/link" />
[...]
```

### Отравление сброса пароля

Механизмы восстановления доступа и сброса паролей часто используют значение заголовка `Host` для генерации ссылок со сгенерированным секретным токеном подтверждения. Если приложение подставляет подконтрольный атакующему домен при формировании ссылки для сброса пароля, жертва, перейдя по ссылке из полученного электронного письма, передаст секретный токен на сервер атакующего, что позволит злоумышленнику сбросить пароль пользователя и захватить его учетную запись.

В приведенном ниже примере показана генерация ссылки на сброс пароля в PHP с использованием значения переменной `$_SERVER['HTTP_HOST']`, формируемой на основе входящего HTTP-заголовка `Host`:

```php
$reset_url = "https://" . $_SERVER['HTTP_HOST'] . "/reset.php?token=" .$token;
send_reset_email($email,$rset_url);
```

Отправив HTTP-запрос к странице сброса пароля с модифицированным заголовком `Host`, можно изменить целевой домен в ссылке:

```http
POST /request_password_reset.php HTTP/1.1
Host: www.attacker.com
[...]

email=user@example.org
```

Указанный домен (`www.attacker.com`) будет включен в ссылку для сброса пароля, отправляемую пользователю на email. При переходе пользователя по ссылке атакующий перехватывает токен и компрометирует его аккаунт.

```text
... Email snippet ...

Click on the following link to reset your password:

https://www.attacker.com/reset.php?token=12345

... Email snippet ...
```

### Доступ к закрытым виртуальным хостам

В ряде случаев на сервере настроены виртуальные хосты, не предназначенные для доступа из публичной сети. Чаще всего это встречается в конфигурациях DNS с разделением горизонта ([split-horizon DNS](https://en.wikipedia.org/wiki/Split-horizon_DNS)), где внутренние и внешние DNS-серверы возвращают разные записи для одной доменной зоны.

Например, в локальной сети организации может быть развернут один веб-сервер, обслуживающий как публичный веб-сайт (`www.example.org`), так и внутренний интранет-портал (`intranet.example.org`, запись о котором присутствует только на внутреннем DNS-сервере). Хотя прямое обращение к `intranet.example.org` из внешней сети невозможно из-за отсутствия публичной DNS-записи, получить доступ к интранету можно путем отправки внешнего запроса к IP-адресу публичного сервера со следующим заголовком `Host`:

```http
Host: intranet.example.org
```

Аналогичного результата можно добиться добавлением записи для `intranet.example.org` с публичным IP-адресом `www.example.org` в локальный файл `hosts`, либо переопределением правил разрешения DNS в используемом инструменте тестирования.
