# Инъекция LDAP

| ID |
| --- |
| WSTG-INJT-06 |

## Резюме

Протокол облегченного доступа к каталогам (Lightweight Directory Access Protocol, LDAP) используется для хранения информации о пользователях, узлах сети и множестве других объектов. [Внедрение LDAP-кода (LDAP Injection)](https://community.owasp.org/attacks/LDAP_Injection) представляет собой атаку на стороне сервера, которая может позволить раскрыть, изменить или добавить конфиденциальную информацию о пользователях и хостах, представленных в структуре LDAP. Это достигается путем манипулирования входными параметрами, которые впоследствии передаются во внутренние функции поиска, добавления и изменения каталога.

Веб-приложение может использовать LDAP для аутентификации пользователей или поиска информации о сотрудниках внутри корпоративной структуры. Цель атак LDAP Injection — внедрение метасимволов поисковых фильтров LDAP в запрос, выполняемый приложением.

Спецификация [RFC 2254](https://www.ietf.org/rfc/rfc2254.txt) определяет грамматику построения поисковых фильтров в LDAPv3 и расширяет [RFC 1960](https://www.ietf.org/rfc/rfc1960.txt) (LDAPv2).

Поисковый фильтр LDAP строится в польской нотации, также известной как [префиксная польская нотация (Polish notation)](https://en.wikipedia.org/wiki/Polish_notation).

Это означает, что псевдокодовое условие поискового фильтра вида:

`find("cn=John & userPassword=mypass")`

будет представлено в виде:

`find("(&(cn=John)(userPassword=mypass))")`

Булевы условия и групповые агрегации в поисковом фильтре LDAP применяются с помощью следующих метасимволов:

| Metachar |  Meaning              |
|----------|-----------------------|
| &        |  Boolean AND          |
| \|       |  Boolean OR           |
| !        |  Boolean NOT          |
| =        |  Equals               |
| ~=       |  Approx               |
| >=       |  Greater than         |
| <=       |  Less than            |
| *        |  Any character        |
| ()       |  Grouping parenthesis |

Более полные примеры построения поисковых фильтров приведены в соответствующем RFC.

Успешная эксплуатация уязвимости LDAP-инъекции может позволить тестировщику:

- Получить доступ к неавторизованному контенту
- Обойти ограничения приложения
- Собрать несанкционированную информацию
- Добавить или модифицировать объекты в древовидной структуре LDAP

## Цели тестирования

- Идентифицировать точки внедрения LDAP-кода.
- Оценить степень критичности инъекции.

## Методика тестирования

### Пример 1: фильтры поиска

Предположим, что веб-приложение использует следующий поисковый фильтр:

`searchfilter="(cn="+user+")"`

который инициализируется через следующий HTTP-запрос:

`https://www.example.com/ldapsearch?user=John`

Если значение `John` заменить на символ `*`, отправив запрос:

`https://www.example.com/ldapsearch?user=*`

фильтр примет вид:

`searchfilter="(cn=*)"`

который соответствует любому объекту, у которого атрибут 'cn' имеет любое значение.

Если приложение уязвимо к LDAP-инъекции, оно отобразит часть или все атрибуты пользователей в зависимости от логики выполнения приложения и прав пользователя, подключенного к LDAP.

Тестировщик может использовать метод проб и ошибок, подставляя в параметр символы `(`, `|`, `&`, `*` и другие знаки для проверки приложения на наличие сообщений об ошибках.

### Пример 2: вход в систему

Если веб-приложение использует LDAP для проверки учетных данных при входе в систему и уязвимо к LDAP-инъекции, аутентификацию можно обойти, внедрив заведомо истинный LDAP-запрос (по аналогии с инъекциями SQL и XPath).

Предположим, что веб-приложение использует фильтр для сопоставления пары имя пользователя/пароль в LDAP:

`searchlogin= "(&(uid="+user+")(userPassword={MD5}"+base64(pack("H*",md5(pass)))+"))";`

Передав следующие значения:

```txt
user=*)(uid=*))(|(uid=*
pass=password
```

поисковый фильтр примет вид:

`searchlogin="(&(uid=*)(uid=*))(|(uid=*)(userPassword={MD5}X03MO1qnZdYdgyfeuILPmQ==))";`

который синтаксически корректен и всегда возвращает истинное значение (true). В результате тестировщик войдет в систему с правами первого пользователя в дереве каталога LDAP.
