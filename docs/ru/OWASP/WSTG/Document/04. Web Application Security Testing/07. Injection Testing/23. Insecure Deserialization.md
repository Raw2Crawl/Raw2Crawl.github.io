# Небезопасная десериализация

| ID |
| --- |
| WSTG-INJT-23 |

## Резюме

Сериализация данных (Data Serialization) — это процесс преобразования объекта в формат, пригодный для сохранения (например, в файле или базе данных) либо для передачи по сети с возможностью последующего восстановления. Десериализация (Deserialization) — обратный процесс: преобразование структурированных данных из промежуточного формата обратно в программный объект в памяти.

Небезопасная десериализация (Insecure Deserialization) возникает в тех случаях, когда приложение выполняет десериализацию недоверенных входных данных без надлежащей предварительной проверки подлинности и валидации результирующего объекта. Атакующие могут использовать эту особенность для манипулирования сериализованными объектами с целью изменения логики работы приложения или вызова деструктивных побочных эффектов в процессе восстановления состояния объекта.

Наиболее критическим последствием небезопасной десериализации является удаленное выполнение кода (Remote Code Execution, RCE). Однако уязвимость также может приводить к отказу в обслуживании (Denial of Service, DoS), обходу механизмов аутентификации (Authentication Bypass), нарушению контроля доступа или злоупотреблению бизнес-логикой приложения.

Данные JSON, объединяемые с объектами в средах выполнения JavaScript, также могут приводить к [загрязнению прототипа (prototype pollution)](22.%20Prototype%20Pollution.md). Этот вектор следует рассматривать как родственный тест-кейс, а не как отдельный формат десериализации.

## Цели тестирования

- Идентифицировать точки входа, где приложение принимает сериализованные объекты из недоверенных источников (например, HTTP-заголовки, параметры запросов или cookie).
- Определить формат сериализации, используемый приложением.
- Оценить, валидируются ли и ограничиваются ли сериализованные входные данные до этапа десериализации.
- Проверить, приводит ли модификация сериализованных данных к небезопасному поведению системы или компрометации безопасности.

## Методика тестирования

### Тестирование методом «черного ящика»

#### Выявление сериализованных данных

Определите участки приложения, обрабатывающие сериализованные данные. Исследуйте значения cookie-файлов, скрытые поля форм, тела запросов к API, заголовки и механизмы загрузки файлов на предмет узнаваемых сигнатур, форматов кодирования или специфических структурных паттернов.

##### Сериализация в Java

Сериализованные объекты Java обычно начинаются с шестнадцатеричных байтов `AC ED 00 05`. В представлении Base64 эта последовательность чаще всего начинается с префикса `rO0`.

```http
Cookie: rememberMe=rO0ABXNyABpY...
```

##### Сериализация в PHP

Сериализованные данные PHP человекочитаемы и используют специальные односимвольные идентификаторы типов данных (например, `O` для объекта, `a` для массива, `s` для строки).

```http
Cookie: user_data=O:4:"User":2:{s:8:"username";s:5:"admin";s:8:"isAdmin";b:1;}
```

##### Python Pickle

Модуль `pickle` в Python использует бинарный формат, который сложнее идентифицировать визуально. Пейлоады протокола 0 (Protocol 0) более читаемы и часто заканчиваются точкой (`.`). Пейлоады более старших версий протоколов выглядят как непрозрачные бинарные массивы или строки Base64 в cookie, токенах или параметрах очередей фоновых задач.

После идентификации кандидата отправьте контролируемый внеполосный (Out-of-Band, OOB) зонд или безопасный тестовый пейлоад (например, полезную нагрузку, инициирующую обратный DNS- или HTTP-запрос на подконтрольный сервер). Убедитесь, что приложение десериализует переданное значение, зафиксировав обратное соединение, характерное сообщение об ошибке или аварийное завершение процесса. Никогда не начинайте тестирование с деструктивных RCE-пейлоадов.

##### Node.js (node-serialize)

В приложениях на базе Node.js, использующих библиотеку `node-serialize`, сериализованные данные часто представлены в виде JSON-подобной строки. Ключевым маркером риска является префикс самовызывающегося функционального выражения (Immediately Invoked Function Expression, IIFE), начинающийся с сигнатуры `_$$ND_FUNC$$_`.

```javascript
{"rce":"_$$ND_FUNC$$_function (){require('child_process').exec('id')}()"}
```

При обнаружении данного маркера в трафике приложения замените тело функции на безопасный внеполосный вызов (OOB callback) и повторите отправку для подтверждения выполнения кода.

##### Сериализация в .NET

Устаревшие приложения, все еще использующие форматы `BinaryFormatter` или `NetDataContractSerializer`, часто кодируют выходные данные в Base64. Характерная сигнатура сериализованных данных .NET начинается с шестнадцатеричной последовательности байтов `00 01 00 00 00 FF FF FF FF` или строки Base64 `AAEAAAD/////`. Рассматривайте `BinaryFormatter` исключительно как легаси-компонент: он признан небезопасным и полностью удален из современных версий .NET.

```http
Cookie: SessionData=AAEAAAD/////AQAAAAAAAAAMAgAAAF...
```

##### Десериализация JSON с метаданными типов

Некоторые библиотеки парсинга JSON поддерживают полиморфную типизацию (polymorphic typing). Если приложение принимает контролируемые злоумышленником метаданные типов, десериализация может привести к инстанцированию непредусмотренных произвольных классов.

Библиотека Jackson при включенной настройке типизации по умолчанию (default typing) часто включает идентификатор типа `@class`:

```json
{"@class":"com.example.Exploit","cmd":"id"}
```

Библиотека Fastjson обычно использует ключ `@type`:

```json
{"@type":"com.example.Exploit","cmd":"id"}
```

Контролируемые пользователем ключи `@class`, `@type` или аналогичные спецификаторы типов следует расценивать как критическую уязвимость высокой степени опасности, требующую подтверждения безопасным внеполосным гаджетом для соответствующей библиотеки.

#### Манипуляция сериализованными объектами

После выявления точки входа модифицируйте сериализованные данные и проанализируйте реакцию приложения.

Распространенные приемы манипуляции:

- Изменение атрибутов объектов или логических флагов.
- Внедрение дополнительных полей.
- Подмена типов данных.
- Повторная отправка (replay) модифицированных сериализованных пейлоадов.

Пример (PHP):

Сериализованный объект, отражающий состояние пользователя:

```php
O:4:"User":2:{s:8:"username";s:3:"bob";s:8:"isAdmin";b:0;}
```

Если приложение опирается на данный объект при принятии решений об авторизации, измените `b:0;` на `b:1;` и повторите запрос. Повышение привилегий подтвердит небезопасное доверие к десериализованному объекту. При редактировании длины строк или массивов следите за корректностью числовых префиксов длины в формате сериализации PHP, иначе парсер отклонит пейлоад с синтаксической ошибкой.

#### Опасные побочные эффекты

Проверьте, не вызывает ли процесс десериализации непредусмотренных побочных эффектов, таких как:

- Выполнение системных команд ОС.
- Несанкционированный вызов внутренних методов приложения.
- Чрезмерное потребление ресурсов (памяти, процессора).
- Аварийное завершение приложения или неконтролируемое изменение его состояния.

Ищите доказательства через:

- Поведенческие изменения в ответах сервера.
- Диагностические сообщения об ошибках или трассировки стека (stack traces).
- Временные аномалии или деградацию производительности сервиса.
- Внеполосные сетевые DNS- или HTTP-обращения от безопасных тестовых нагрузок.

#### Злоупотребление цепочками гаджетов

Во многих средах исполнение уязвимости десериализации требует построения цепочки гаджетов (gadget chain) — последовательности существующих фрагментов кода (гаджетов) внутри приложения или его сторонних библиотек, которые при десериализации и вызове магических методов или деструкторов приводят к вредоносному результату.

Придерживайтесь следующей последовательности тестирования:

1. Определите используемые сторонние библиотеки (например, Commons Collections, Spring или Jackson) по HTTP-заголовкам, ошибкам, файлам зависимостей или сигнатурным сканерам.
2. Сгенерируйте неразрушающий подтверждающий пейлоад с помощью специализированной утилиты.
3. Отправьте пейлоад в уязвимый приемник сериализованных данных и отследите внеполосное обращение (OOB callback). Эксплуатация RCE часто не возвращает прямого вывода в теле ответа, поэтому обратные запросы DNS или HTTP служат наиболее надежным сигналом.

Пример (Java, использование гаджета `URLDNS` из утилиты ysoserial исключительно для подтверждения уязвимости):

```bash
java -jar ysoserial.jar URLDNS http://<collaborator-host>/
```

Закодируйте полученный бинарный вывод в Base64 (если приложение ожидает Base64), передайте его в проверяемый параметр или cookie и отправьте запрос. Зафиксированный DNS-запрос к домену `<collaborator-host>` подтвердит факт десериализации объекта приложением. Гаджеты для выполнения произвольного кода (RCE) следует использовать только после подтверждения уязвимости и исключительно в авторизованных тестовых средах.

Для PHP используйте утилиту PHPGGC для генерации аналогичных подтверждающих OOB-пейлоадов или пейлоадов записи файлов для известных цепочек гаджетов, присутствующих в проекте.

### Тестирование методом «белого ящика»

#### Анализ кода и приемники данных (Sink Functions)

При наличии доступа к исходному коду не ограничивайтесь простым поиском опасных функций. Отследите путь недоверенных входных данных до каждой функции-приемника (sink) и проверьте реализованные механизмы защиты.

Распространенные функции-приемники:

- Java: `java.io.ObjectInputStream.readObject()`, `readUnshared()`
- PHP: `unserialize()`
- Python: `pickle.loads()`, `marshal.loads()`, `shelve.open()`
- Node.js: `node-serialize.unserialize()`
- .NET: `BinaryFormatter.Deserialize()`, `NetDataContractSerializer.Deserialize()`

Для каждого приемника:

1. Проверьте, могут ли параметры запросов, cookie, заголовки, файлы или сообщения из брокеров очередей достигать вызова функции десериализации.
2. Проверьте наличие списков разрешенных классов (allow-lists), проверок целостности (например, HMAC) или платформенных фильтров, таких как `ObjectInputFilter` в Java.
3. Зафиксируйте отсутствие проверок, чрезмерно широкие списки разрешений или механизмы подписи, которые клиент может обойти.

Примером реализации белых списков в Java является класс `ValidatingObjectInputStream` библиотеки Apache Commons IO; при аудите фиксируйте любой фильтр, реально используемый в кодовой базе, включая системные конфигурации JDK `ObjectInputFilter`.

## Рекомендации по устранению

По возможности полностью откажитесь от десериализации недоверенных данных.

Если десериализация архитектурно необходима:

- Ограничьте принимаемые форматы сериализации и типы объектов с помощью строгого списка разрешений (allow-list).
- Внедрите механизмы контроля целостности для выявления фактов модификации данных.
- Выполняйте валидацию данных строго до начала процесса десериализации.
- Отдавайте предпочтение форматам, содержащим исключительно чистые данные (таким как JSON или XML), разбираемым без поддержки полиморфной типизации и пользовательских метаданных типов.
- В Java используйте `ObjectInputFilter` или списки разрешений (например, `ValidatingObjectInputStream` из Commons IO) до этапа инстанцирования классов в памяти.
- Если сериализованные объекты передаются клиенту, подписывайте их криптографической подписью (например, HMAC), чтобы сервер мог отклонить любые модифицированные пейлоады.
- Категорически откажитесь от использования устаревшего .NET-класса `BinaryFormatter` при обработке внешних данных.

Подробные рекомендации по нейтрализации десериализации приведены в [OWASP Deserialization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html).
