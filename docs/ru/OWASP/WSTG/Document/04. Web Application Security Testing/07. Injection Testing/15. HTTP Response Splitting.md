# Разделение HTTP-ответов (HTTP Response Splitting)

| ID |
| --- |
| WSTG-INJT-15 |

## Резюме

Разделение HTTP-ответов (HTTP Response Splitting) — это уязвимость, возникающая в ситуациях, когда приложение включает несанитизированные пользовательские данные в заголовки HTTP-ответа, позволяя злоумышленнику внедрять символы возврата каретки (Carriage Return, CR, `\r`) и перевода строки (Line Feed, LF, `\n`). В результате единый HTTP-ответ может быть интерпретирован клиентским приложением или промежуточными сетевыми узлами как два и более независимых ответа.

Успешная эксплуатация HTTP Response Splitting может приводить к разнообразным последствиям, включая отравление веб-кэша (Web Cache Poisoning), межсайтовый скриптинг (Cross-Site Scripting, XSS), спуфинг контента (Content Spoofing), фиксацию сессии (Session Fixation) и иные атаки на стороне клиента, в зависимости от логики обработки внедренного ответа.

Данный раздел посвящен исключительно идентификации и тестированию уязвимостей разделения HTTP-ответов на прикладном уровне. Контрабанда HTTP-запросов (HTTP Request Smuggling), основанная на несогласованности парсинга запросов между несколькими сетевыми агентами, рассматривается в отдельной главе.

## Цели тестирования

- Идентифицировать контролируемый пользователем ввод, отражаемый в заголовках HTTP-ответов.
- Оценить возможность внедрения символов CR (`\r`) и LF (`\n`) в заголовки ответа.
- Определить потенциальное воздействие успешной атаки HTTP Response Splitting, такое как отравление кэша или клиентская эксплуатация.

## Методика тестирования

### Тестирование методом «черного ящика»

В некоторых веб-приложениях данные, предоставленные пользователем, задействуются для динамического формирования значений определенных заголовков ответа. Распространенный сценарий — логика перенаправления (редиректа), где целевой URL извлекается из параметров входящего запроса.

Например, предположим, что пользователю предлагается выбрать между стандартным и расширенным интерфейсом. Выбранная опция передается в виде параметра и отражается в заголовке ответа перенаправления.

Если параметр `interface` имеет значение `advanced`, приложение может вернуть следующий ответ:

```http
HTTP/1.1 302 Moved Temporarily
Date: Sun, 03 Dec 2005 16:22:19 GMT
Location: https://victim.com/main.jsp?interface=advanced
```

Получив этот ответ, браузер переходит по URL-адресу, указанному в заголовке `Location`. Однако если приложение не проводит валидацию или санитизацию входящих данных, атакующий может внедрить последовательность `%0d%0a`, представляющую символы CRLF, служащие разделителями строк в заголовках HTTP.

Внедряя последовательности CRLF, тестировщик может добиться того, что downstream-клиенты или промежуточные звенья (например, кэширующие прокси-серверы) интерпретируют один ответ как два независимых HTTP-ответа. Это поведение может быть проэксплуатировано для отравления кэша или доставки вредоносного контента пользователям.

Например, тестировщик передает следующее значение параметра `interface`:

`advanced%0d%0aContent-Length:%200%0d%0a%0d%0aHTTP/1.1%20200%20OK%0d%0aContent-Type:%20text/html%0d%0aContent-Length:%2035%0d%0a%0d%0a<html>Sorry,%20System%20Down</html>`

Результирующий ответ уязвимого приложения примет следующий вид:

```http
HTTP/1.1 302 Moved Temporarily
Date: Sun, 03 Dec 2005 16:22:19 GMT
Location: https://victim.com/main.jsp?interface=advanced
Content-Length: 0

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 35

<html>Sorry,%20System%20Down</html>
```

Кэширующий прокси-сервер, обрабатывающий данный ответ, может расценить его как два раздельных ответа. Если атакующий сразу же отправляет следующий запрос к `/index.html`, кэш может сопоставить его со вторым (внедренным) ответом и сохранить его. В результате все последующие пользователи, запрашивающие `victim.com/index.html` через данный кэш, будут получать контент, сформированный атакующим.

В качестве альтернативы злоумышленник может внедрить JavaScript-пейлоад для реализации атаки XSS против пользователей, получающих контент из отравленного кэша. Хотя уязвимость локализована в серверном приложении, прямой мишенью атаки становятся конечные пользователи.

Для обнаружения данной проблемы тестировщикам следует найти все точки пользовательского ввода, влияющие на заголовки HTTP-ответов, и проверить возможность внедрения последовательностей CRLF.

Заголовки ответа, наиболее часто подверженные уязвимости HTTP Response Splitting:

- `Location`
- `Set-Cookie`

Для успешной эксплуатации в реальных условиях может потребоваться учет дополнительных факторов:

- Тестировщику может понадобиться сформировать заголовки, стимулирующие кэширование (например, заголовок `Last-Modified` с будущей датой), а также предварительно инвалидировать текущие записи кэша с помощью заголовков вида `Pragma: no-cache`.
- Приложения могут фильтровать прямые символы CRLF, но пропускать альтернативные формы кодирования или представления символов, которые иногда позволяют обойти механизмы валидации.
- Некоторые платформы автоматически URL-кодируют путь в заголовке `Location`, оставляя строку запроса (query string) без изменений, что открывает возможность инъекции через отдельные компоненты URL.

### Тестирование методом «серого ящика»

В сценарии тестирования методом «серого ящика» знание внутренней архитектуры приложения и особенностей поведения серверов существенно повышает надежность эксплуатации.

Различные серверы и промежуточные узлы могут определять границы сообщений по-разному (например, используя буферы фиксированного размера), что требует подбора точных смещений или заполнения (padding). Если уязвимые параметры передаются методом GET, ограничения длины URL могут привести к обрезанию пейлоада. Тестировщику следует искать альтернативные точки внедрения или использовать HTTP-методы, такие как POST, для получения большего контроля над размером и позиционированием полезной нагрузки.

## Рекомендации по устранению

Обеспечьте гарантию того, что пользовательские данные никогда не попадут в HTTP-заголовки без строгой валидации и санитизации.

- **Валидация ввода:** Отклоняйте или вырезайте любые входные данные, содержащие символы возврата каретки (`\r`, `%0d`) или перевода строки (`\n`, `%0a`), до их передачи в заголовки HTTP.
- **URL-кодирование:** Если входные данные являются частью URL (например, в заголовке `Location`), убедитесь, что они надлежащим образом URL-закодированы, что исключит интерпретацию управляющих символов в качестве разделителей протокола.
- **Использование безопасных фреймворков:** Используйте встроенные платформенные функции для установки заголовков (например, `setHeader()`, `addHeader()`), избегая ручной конкатенации сырых HTTP-строк. Современные веб-платформы и серверы приложений по умолчанию блокируют внедрение символов переноса строки в заголовки.
