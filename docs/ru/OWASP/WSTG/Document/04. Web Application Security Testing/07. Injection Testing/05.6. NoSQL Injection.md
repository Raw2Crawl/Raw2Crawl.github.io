# Инъекция NoSQL

## Резюме

Базы данных NoSQL предъявляют менее жесткие требования к согласованности данных, чем традиционные реляционные SQL-базы данных. Требуя меньше реляционных ограничений и проверок целостности, NoSQL-базы зачастую обеспечивают повышенную производительность и преимущества в масштабировании. Тем не менее эти базы данных по-прежнему потенциально уязвимы к инъекционным атакам, даже если в них не используется традиционный SQL-синтаксис. Поскольку подобные атаки внедрения NoSQL-кода (NoSQL Injection) могут выполняться в контексте [процедурного языка](https://en.wikipedia.org/wiki/Procedural_programming), а не [декларативного языка SQL](https://en.wikipedia.org/wiki/Declarative_programming), их потенциальные последствия могут быть более разрушительными, чем при классической SQL-инъекции.

Вызовы к базам данных NoSQL пишутся на языке программирования приложения, представляют собой кастомные API-вызовы или форматируются в соответствии с общепринятыми соглашениями (такими как `XML`, `JSON`, `LINQ` и т. д.). Вредоносный ввод, направленный против таких спецификаций, может не вызывать срабатывания основных механизмов санитизации приложения. Например, фильтрация стандартных специальных символов HTML, таких как `< > & ;`, не защитит от атак на JSON API, где к специальным символам относятся `/ { } :`.

Существуют сотни доступных для использования в приложениях баз данных NoSQL, предоставляющих API на множестве языков и поддерживающих различные модели связей. Каждая из них предлагает собственный набор возможностей и ограничений. Поскольку единого общего языка между ними не существует, примеры кода инъекций неприменимы универсально ко всем NoSQL-базам данных. По этой причине любому специалисту, тестирующему систему на атаки NoSQL Injection, необходимо ознакомиться с синтаксисом, моделью данных и базовым языком программирования целевой СУБД для построения специфических тестов.

Атаки NoSQL Injection могут выполняться в иных областях приложения по сравнению с традиционной SQL-инъекцией. Если SQL-инъекция выполняется внутри движка базы данных, то варианты NoSQL могут исполняться на уровне приложения или на уровне базы данных, в зависимости от используемого API NoSQL и модели данных. Как правило, атаки внедрения NoSQL-кода выполняются в том месте, где строка атаки разбирается, интерпретируется или конкатенируется в вызов NoSQL API.

Дополнительные атаки по времени (timing attacks) могут быть обусловлены отсутствием проверок параллелизма (конкурентности) в базе данных NoSQL. Они не рассматриваются в рамках тестирования на инъекции. На момент написания данного документа MongoDB является наиболее широко используемой NoSQL-базой данных, поэтому все примеры построены на базе API MongoDB.

## Методика тестирования

### Уязвимости инъекции NoSQL в MongoDB

API MongoDB ожидает вызовы в формате BSON (Binary JSON) и включает безопасный инструмент сборки BSON-запросов. Однако, согласно документации MongoDB, несериализованный JSON и [выражения JavaScript](https://docs.mongodb.org/manual/faq/developers/#javascript) разрешены в ряде альтернативных параметров запросов. Наиболее часто используемым вызовом API, допускающим произвольный ввод JavaScript, является оператор `$where`.

Оператор MongoDB `$where` обычно используется в качестве простого фильтра или проверки, аналогично условиям в SQL:

`db.myCollection.find( { $where: "this.credits`` ``==`` ``this.debits" } );`

Кроме того, поддерживается выполнение кода JavaScript для задания более сложных условий:

`db.myCollection.find( { $where: function() { return obj.credits - obj.debits < 0; } } );`

### Пример 1

Если атакующий способен манипулировать данными, передаваемыми в оператор `$where`, он может внедрить произвольный JavaScript-код, который выполнится в рамках запроса MongoDB. Пример уязвимости представлен в следующем коде при передаче пользовательского ввода напрямую в запрос MongoDB без предварительной санитизации:

`db.myCollection.find( { active: true, $where: function() { return obj.credits - obj.debits < $userInput; } } );;`

Как и при тестировании других типов инъекций, для подтверждения наличия проблемы нет необходимости проводить полную эксплуатацию уязвимости. Внедряя специальные символы целевого языка API и наблюдая за результатами, тестировщик может определить, правильно ли приложение очищает входные данные. Например, в MongoDB передача без санитизации строки, содержащей любой из следующих спецсимволов, приведет к ошибке базы данных:

`' " \ ; { }`

При обычной SQL-инъекции аналогичная уязвимость позволила бы атакующему выполнять произвольные команды SQL, просматривая или изменяя данные по своему усмотрению. Однако поскольку JavaScript является полнофункциональным языком программирования, это позволяет злоумышленнику не только манипулировать данными, но и выполнять произвольный программный код. Например, вместо простой генерации ошибки при тестировании полноценный эксплойт использовал бы специальные символы для составления валидного кода JavaScript.

Передача значения `0;var date=new Date(); do{curDate = new Date();}while(curDate-date<10000)` в переменную `$userInput` в приведенном выше примере приведет к выполнению следующей функции JavaScript. Эта конкретная строка атаки вызовет 100% загрузку процессора всего инстанса MongoDB в течение 10 секунд:

`function() { return obj.credits - obj.debits < 0;var date=new Date(); do{curDate = new Date();}while(curDate-date<10000); }`

### Пример 2

Даже если входные данные, используемые в запросах, полностью санитизируются или параметризуются, существует альтернативный способ вызова NoSQL-инъекции. Многие экземпляры NoSQL имеют собственные зарезервированные имена переменных, независимые от языка программирования приложения.

Например, в MongoDB синтаксис `$where` сам по себе является зарезервированным оператором запроса. Он должен передаваться в запрос в точности в указанном виде; любое его изменение приведет к ошибке базы данных. Однако поскольку `$where` также является допустимым именем переменной в PHP, атакующий может внедрить код в запрос, создав PHP-переменную с именем `$where`. Документация PHP по MongoDB прямо предупреждает разработчиков:

> Пожалуйста, убедитесь, что для всех специальных операторов запроса (начинающихся с `$`) вы используете одинарные кавычки, чтобы PHP не пытался заменить `$exists` значением переменной `$exists`.

Даже если запрос не зависит от пользовательского ввода (как в следующем примере), атакующий может проэксплуатировать MongoDB, подменив оператор вредоносными данными:

`db.myCollection.find( { $where: function() { return obj.credits - obj.debits < 0; } } );`

Одним из способов потенциального присвоения значений переменным PHP является загрязнение HTTP-параметров (см. раздел [HTTP Parameter Pollution](04.%20HTTP%20Parameter%20Pollution.md)). Создав переменную `$where` с помощью Parameter Pollution, можно вызвать ошибку MongoDB, указывающую на некорректность запроса. Любое значение `$where`, отличное от самой строки `$where`, будет достаточным доказательством наличия уязвимости. Полноценный эксплойт злоумышленника строится путем внедрения следующей конструкции:

`$where: function() { //arbitrary JavaScript here }`
