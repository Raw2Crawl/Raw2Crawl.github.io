# Массовое присваивание (Mass Assignment)

| ID |
| --- |
| WSTG-INJT-20 |

## Резюме

Современные веб-приложения практически всегда строятся на базе фреймворков. Многие веб-фреймворки поддерживают автоматическую привязку пользовательского ввода (в виде параметров входящего HTTP-запроса) к полям внутренних объектов модели. Этот механизм обычно называется автоматическим связыванием (autobinding или mass assignment).
Данная функциональность может быть проэксплуатирована для модификации внутренних полей объектов, изменение которых извне изначально не предполагалось разработчиками, что приводит к повышению привилегий (Privilege Escalation), подделке данных, обходу проверок безопасности и другим рискам.
В подобных сценариях диагностируется уязвимость массового присвоения (Mass Assignment).

Примеры чувствительных свойств объектов:

- **Свойства, определяющие права доступа**: должны задаваться только привилегированными пользователями (например, `is_admin`, `role`, `approved`).
- **Свойства, зависящие от бизнес-процесса**: должны вычисляться и обновляться исключительно внутренней логикой по завершении определенного этапа (например, `balance`, `status`, `email_verified`).
- **Служебные системные свойства**: должны формироваться исключительно инфраструктурой приложения (например, `created_at`, `updated_at`).

## Цели тестирования

- Идентифицировать запросы, изменяющие состояние объектов модели.
- Оценить возможность модификации полей, изменение которых извне не предполагалось бизнес-логикой.

## Методика тестирования

Ниже приведен классический пример, наглядно иллюстрирующий проблему.

Предположим, что в веб-приложении на Java определен класс `User`, аналогичный следующему:

```java
public class User {
   private String username;
   private String password;
   private String email;
   private boolean isAdmin;

   //Getters & Setters
}
```

Для создания нового пользователя `User` в веб-приложении реализована следующая форма представления:

```html
<form action="/createUser" method="POST">
     <input name="username" type="text">
     <input name="password" type="text">
     <input name="email" text="text">
     <input type="submit" value="Create">
</form>
```

Контроллер, обрабатывающий запрос на создание (фреймворк Spring обеспечивает автоматическое связывание параметров запроса с моделью `User`):

```java
@RequestMapping(value = "/createUser", method = RequestMethod.POST)
public String createUser(User user) {
   userService.add(user);
   return "successPage";
}
```

При отправке HTML-формы браузер формирует следующий запрос:

```http
POST /createUser
[...]
username=bob&password=supersecretpassword&email=bob@domain.test
```

Однако в силу включенного автосвязывания злоумышленник может добавить в запрос параметр `isAdmin`, который контроллер автоматически сопоставит с полем модели:

```http
POST /createUser
[...]
username=bob&password=supersecretpassword&email=bob@domain.test&isAdmin=true
```

В результате создается учетная запись с установленным флагом `isAdmin` в значении `true`, что наделяет пользователя административными полномочиями в приложении.

### Тестирование методом «черного ящика»

#### Обнаружение обработчиков

Чтобы определить, какие компоненты приложения подвержены массовому присвоению, необходимо перечислить все эндпоинты, принимающие входящие пользовательские данные и потенциально сопоставляющие их с объектами модели. Сюда входят все HTTP-запросы (преимущественно методов GET, POST и PUT), которые инициируют создание или обновление сущностей на стороне бэкенда.
Одним из наиболее очевидных индикаторов поддержки mass assignment является использование синтаксиса квадратных скобок в именах параметров, например:

```html
<input name="user[name]" type="text">
```

При обнаружении подобных паттернов попробуйте передать параметр с заведомо несуществующим атрибутом (например, `user[nonexistingattribute]`) и проанализируйте ответ и поведение приложения.
Если в приложении отсутствуют механизмы фильтрации (например, список разрешенных полей), сервер, скорее всего, вернет ошибку (например, с кодом 500) из-за невозможности сопоставить неизвестный атрибут с целевым объектом. Более того, информативные сообщения об ошибках часто раскрывают реальные имена полей и ожидаемые типы данных, необходимые для эксплуатации уязвимости, даже без доступа к исходному коду.

#### Определение конфиденциальных полей

Поскольку при тестировании методом «черного ящика» исходный код недоступен, тестировщику необходимо использовать косвенные методы сбора сведений об атрибутах моделей.
Внимательно анализируйте ответы, возвращаемые бэкендом, обращая особое внимание на:

- Исходный код HTML-страниц
- Кастомные клиентские скрипты JavaScript
- Ответы REST/GraphQL API

Например, очень часто обработчики, возвращающие подробные сведения об объекте, содержат подсказки о структуре полей.
Рассмотрим обработчик, возвращающий профиль пользователя (например, `GET /profile`), который может содержать расширенный набор атрибутов (в данном примере особый интерес представляет поле `isAdmin`):

```json
{"_id":12345,"username":"bob","age":38,"email":"bob@domain.test","isAdmin":false}
```

После этого проверьте обработчики, позволяющие редактировать или создавать пользователей, добавив в тело запроса параметр `isAdmin` со значением `true`.

Другой подход заключается в применении словарей для автоматизированного перебора потенциальных атрибутов (фаззинг через wfuzz, Burp Intruder, ZAP Fuzzer и т. д.). Утилита sqlmap содержит встроенный словарь [common-columns.txt](https://github.com/sqlmapproject/sqlmap/blob/master/data/txt/common-columns.txt), отлично подходящий для идентификации потенциально чувствительных полей.
Примеры распространенных чувствительных параметров:

- `is_admin`
- `is_administrator`
- `isAdmin`
- `isAdministrator`
- `admin`
- `administrator`
- `role`

Если в приложении реализовано несколько ролей пользователей, сравните структуру запросов, выполняемых учетными записями с разными уровнями привилегий (обращая особое внимание на действия администратора). Если в запросах администратора передаются дополнительные параметры, попробуйте передать их в контексте непривилегированного или анонимного пользователя.

#### Оценка последствий

Влияние уязвимости массового присвоения существенно зависит от контекста бизнес-логики. Поэтому для каждого отправленного тестового ввода проанализируйте результат и определите практическое воздействие на безопасность приложения.
Например, изменение поля `id` объекта может привести к отказу в обслуживании (Denial of Service, DoS) или горизонтальному повышению привилегий. Возможность изменения статуса или роли пользователя (например, `role` или `isAdmin`) приводит к вертикальному повышению привилегий (Vertical Privilege Escalation).

### Тестирование методом «серого ящика»

При анализе методом «серого ящика» используется та же методология, однако доступ к архитектурным сведениям позволяет быстрее выявлять уязвимые фреймворки и контроллеры.
При наличии доступа к исходному коду поиск точек входа становится существенно быстрее и точнее. В процессе аудита исходного кода используйте простые поисковые утилиты (например, `grep`) для поиска характерных паттернов автосвязывания.
Доступ к схеме базы данных и исходникам также позволяет сразу определить полный список чувствительных полей.

#### Java

Spring MVC автоматически связывает параметры запроса с полями объектов. Найдите контроллеры, обрабатывающие запросы, изменяющие состояние (например, проанализируйте вхождения `@RequestMapping`), а затем проверьте наличие ограничений связывания (как на уровне контроллера, так и на уровне используемых моделей). Ограничения на эксплуатацию mass assignment реализуются, например, следующими способами:

- Задание списка разрешенных к связыванию полей через метод `setAllowedFields` класса `DataBinder` (например, `binder.setAllowedFields(["username","password","email"])`)
- Задание списка запрещенных к связыванию полей через метод `setDisallowedFields` класса `DataBinder` (например, `binder.setDisallowedFields(["isAdmin"])`)

Также обратите внимание на использование аннотации `@ModelAttribute`, позволяющей переопределять имена и ключи привязки.

#### PHP

В Laravel Eloquent ORM метод `create` поддерживает массовое присвоение атрибутов. Однако актуальные версии Eloquent по умолчанию защищены от уязвимостей массового присвоения: они требуют явного объявления разрешенных атрибутов через массив `$fillable` либо списка защищенных от связывания атрибутов через массив `$guarded`. Анализируя модели (классы, наследующие `Model`), можно быстро определить разрешенные и запрещенные атрибуты, выявив потенциальные бреши.

#### .NET

Механизм связывания моделей (Model binding) в ASP.NET автоматически сопоставляет пользовательский ввод со свойствами объектов. Это работает и для сложных составных типов данных: если имена полей во входящем запросе совпадают со свойствами объекта, они будут автоматически заполнены.
Идентифицируйте контроллеры и проверьте наличие ограничений связывания. Ограничения могут быть реализованы следующими способами:

- Объявление свойств модели со спецификатором `ReadOnly`
- Задание разрешенных полей через атрибут `Bind` (например, `[Bind(Include = "FirstName, LastName")] Student std`), через параметр `includeProperties` (например, `includeProperties: new[] { "FirstName, LastName" }`) или вызов `TryUpdateModel`
- Задание запрещенных полей через атрибут `Bind` (например, `[Bind(Exclude = "Status")] Student std`) или через параметр `excludeProperties` (например, `excludeProperties: new[] { "Status" }`)

## Рекомендации по устранению

Используйте встроенные механизмы фреймворков для четкого разграничения разрешенных и запрещенных к связыванию полей. Подход, основанный на списках разрешений (allowlist / bindable), в котором явно перечисляются только те свойства, которые пользователю разрешено обновлять, является наиболее надежным.
Архитектурным решением для полного предотвращения проблемы является использование паттерна *Data Transfer Object* (DTO), исключающего прямое связывание параметров с сущностями доменной модели. Объект DTO должен содержать исключительно те поля, которые допустимо редактировать пользователю.
