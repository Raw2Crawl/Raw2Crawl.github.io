# Обзор тестирования API

## Введение в Web API

Веб-интерфейс прикладного программирования (Web Application Programming Interface, API) обеспечивает взаимодействие и обмен данными между различными программными системами по локальной сети или через интернет. Веб-API позволяют различным приложениям взаимодействовать друг с другом стандартизированным и эффективным способом, давая им возможность использовать функционал и данные друг друга.

Распространение таких технологий, как облачные вычисления, микросервисные архитектуры и одностраничные приложения (Single Page Applications, SPA), способствовало повсеместному переходу к API как ключевой архитектурной концепции.

Как и при внедрении любых новых концепций, здесь могут возникать недостатки и уязвимости, требующие проведения тестирования. В противном случае недостаточно защищенные API могут предоставить злоумышленникам прямой неограниченный доступ к конфиденциальным данным.

Эта глава призвана помочь исследователю безопасности освоить концепции, необходимые для тестирования API. В частности, данный раздел посвящен исследованию различных технологий API и истории их развития.

## Какая технология API используется?

Прежде чем делать предположения о типе тестируемого API, полезно представлять весь спектр предметной области, с которой может столкнуться исследователь безопасности. Сюда входят:

1. API на базе Representational State Transfer (REST)
2. API на базе Simple Object Access Protocol (SOAP)
3. API GraphQL
4. Удаленные вызовы процедур gRPC (gRPC Remote Procedure Calls)
5. API WebSockets

## REST (Representational State Transfer) API

### Что такое REST?

REST — это набор правил и соглашений для взаимодействия с веб-ресурсами. Ключевые компоненты — URI, методы HTTP, заголовки и коды состояния — обеспечивают реализацию принципов REST.

### История

Благодаря своей простоте, масштабируемости и совместимости с существующей веб-инфраструктурой архитектура REST на момент написания этого документа стала наиболее распространенной архитектурой API в интернете. API на базе REST появились не сразу, пройдя долгий путь от академических исследований до всеобщего признания.

В 1994 году Рой Филдинг (Roy Fielding), один из основных авторов спецификации HTTP, начал работу над REST в рамках своей докторской диссертации в Калифорнийском университете в Ирвайне. К 2000 году он опубликовал диссертацию [Architectural Styles and the Design of Network-based Software Architectures](https://ics.uci.edu/~fielding/pubs/dissertation/top.htm), где впервые представил и определил REST как архитектурный стиль. REST был разработан с целью использования преимуществ существующих возможностей HTTP с упором на масштабируемость, взаимодействие без сохранения состояния (stateless) и унифицированный интерфейс.

В 2010-х годах REST стал стандартом де-факто для веб-API благодаря своей простоте и совместимости с базовой архитектурой веба. Широкому распространению RESTful API способствовал бурный рост мобильных приложений, облачных вычислений и микросервисной архитектуры. Разработка таких инструментов и спецификаций, как Swagger/OpenAPI, RAML и API Blueprint, существенно упростила проектирование, документирование и тестирование REST API.

К 2020-м годам современные разработки обогатили экосистему REST такими технологиями, как GraphQL. Кроме того, спецификация OpenAPI/Swagger стала общепринятым стандартом для описания REST API, обеспечив улучшенные возможности интеграции и автоматизации.

### Унифицированные идентификаторы ресурсов (URI)

REST API используют унифицированные идентификаторы ресурсов (Uniform Resource Identifiers, URI) для доступа к ресурсам. URI являются важнейшим элементом архитектуры REST. URI представляет собой строку символов, однозначно идентифицирующую конкретный ресурс. URI широко используются в интернете для поиска ресурсов и взаимодействия с ними (веб-страницами, файлами, сервисами).

URI состоит из нескольких компонентов, каждый из которых выполняет определенную задачу. Общий синтаксис URI, определенный в [RFC3986](https://tools.ietf.org/html/rfc3986), приведен ниже:

> `URI = scheme "://" authority "/" path [ "?" query ] [ "#" fragment ]`

Для REST **схема (scheme)** обычно представляет собой `HTTP` или `HTTPS`, но в общем случае указывает на протокол или метод, используемый для доступа к ресурсу. К другим распространенным схемам относятся `ftp`, `mailto` и `file`.

**Управляющая часть (authority)** задает доменное имя или IP-адрес сервера, на котором размещен ресурс, и может включать номер порта. Она также может содержать информацию о пользователе (userinfo) в качестве подкомпонента.

**Путь (path)** указывает конкретное расположение ресурса на сервере. С точки зрения безопасности нас интересует путь URI как отражение взаимосвязи между пользователем и ресурсами. Например, `https://api.example.com/admin/testing/report` может возвращать отчет о тестировании. Здесь прослеживается связь между пользователем `admin` и его отчетами.

Путь любого URI определяет модель ресурсов REST API. Ресурсы разделяются косой чертой (слэшем) и строятся по принципу нисходящего проектирования (Top-Down design).

Например:

- `https://api.example.com/admin/testing/report`
- `https://api.example.com/admin/testing/`
- `https://api.example.com/admin/`

**Строка запроса (query)** передает дополнительные параметры для ресурса. Она начинается со знака `?` и состоит из пар «ключ-значение», разделенных символом `&`.

**Фрагмент (fragment)** указывает на определенную часть ресурса, например на раздел внутри веб-страницы. Он начинается со знака `#`. Стоит отметить, что идентификаторы фрагментов обрабатываются исключительно на стороне клиента и не передаются на сервер.

### HTTP-методы

REST API используют стандартные методы HTTP для выполнения операций над ресурсами в соответствии с [методами HTTP-запросов](https://datatracker.ietf.org/doc/html/rfc9110#section-9), определенными в [RFC 9110](https://datatracker.ietf.org/doc/html/rfc9110). Эти методы соответствуют парадигме CRUD — четырем базовым функциям постоянного хранения данных в информатике. CRUD расшифровывается как Create (создание), Read (чтение), Update (обновление) и Delete (удаление) — четыре операции, которые могут выполняться над данными.

Методы HTTP-запросов включают:

| Methods | Description                                   |
|---------|-----------------------------------------------|
| GET     | Получение представления состояния ресурса     |
| POST    | Создание нового ресурса                       |
| PUT     | Обновление ресурса                            |
| DELETE  | Удаление ресурса                              |
| HEAD    | Получение метаданных состояния ресурса        |
| OPTIONS | Получение списка доступных методов            |

#### Заголовки

REST опирается на заголовки для передачи дополнительной информации в запросе или ответе. К ним относятся:

- `Content-Type`: указывает медиа-тип ресурса (например, `application/json`).
- `Authorization`: содержит учетные данные для аутентификации (например, токены).
- `Accept`: задает типы данных (медиа-типы), допустимые для ответа.

#### Коды состояния

Интерфейсы API, соответствующие принципам REST, используют коды состояния HTTP-ответа для уведомления клиента о результатах обработки его запроса.

| Response Code | Response Message      | Description   |
|---------------|-----------------------|--------------------------------------------------------------------------------------------------------|
| 200           | OK                    | Успешная обработка клиентского запроса                                                                 |
| 201           | Created               | Создан новый ресурс                                                                                    |
| 301           | Moved Permanently     | Постоянное перенаправление                                                                             |
| 304           | Not Modified          | Ответ, связанный с кэшированием, возвращаемый, когда клиент располагает той же копией ресурса, что и сервер |
| 307           | Temporary Redirect    | Временное перенаправление ресурса                                                                      |
| 400           | Bad Request           | Некорректно сформированный запрос клиента                                                              |
| 401           | Unauthorized          | Клиенту запрещено отправлять запросы или получать доступ к данному ресурсу                             |
| 403           | Forbidden             | Клиенту запрещен доступ к ресурсу                                                                      |
| 404           | Not Found             | Ресурс не существует или указан неверно в запросе                                                      |
| 405           | Method Not Allowed    | Использован недопустимый или неизвестный метод                                                         |
| 500           | Internal Server Error | Сервер не смог обработать запрос из-за внутренней ошибки                                               |
