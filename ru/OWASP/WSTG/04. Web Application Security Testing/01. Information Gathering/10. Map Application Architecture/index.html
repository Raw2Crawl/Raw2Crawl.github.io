    Составление карты архитектуры приложения¶

    ID
    WSTG-INFO-10

    Резюме¶

    Для эффективного тестирования приложения и предоставления содержательных рекомендаций по устранению выявленных проблем крайне важно понимать, что именно подвергается тестированию. Кроме того, это помогает определить, какие конкретные компоненты следует исключить из области оценки (out-of-scope).

    Современные веб-приложения могут существенно различаться по сложности — от простейшего скрипта, выполняющегося на единственном сервере, до высококомплексных распределенных систем, охватывающих десятки различных сервисов, языков программирования и компонентов. Также в инфраструктуре могут присутствовать сетевые компоненты, такие как межсетевые экраны (файрволы) или системы защиты от вторжений, способные оказать значительное влияние на ход тестирования.

    Цели тестирования¶

    • Изучить архитектуру приложения и используемый стек технологий.

    Методика тестирования¶

    При тестировании методом «черного ящика» (black-box) важно составить четкую картину того, как функционирует приложение и какие технологии и компоненты в нем задействованы. В некоторых случаях удается напрямую протестировать наличие определенных компонентов (таких как межсетевой экран веб-приложений / WAF), тогда как другие компоненты выявляются путем анализа поведения приложения.

    В подразделах ниже представлен высокоуровневый обзор типовых архитектурных компонентов и способов их идентификации.

    Компоненты приложения¶

    Веб-сервер¶

    Простые приложения могут работать на отдельном сервере, параметры которого определяются с помощью шагов, описанных в разделе руководства Fingerprint Web Server.

    Платформа как услуга (PaaS)¶

    В модели «платформа как услуга» (Platform-as-a-Service, PaaS) веб-сервер и базовая инфраструктура находятся под управлением поставщика облачных услуг, а клиент отвечает исключительно за развернутое на них приложение. С точки зрения тестирования здесь имеются два ключевых отличия:

    • Владелец приложения не имеет прямого доступа к базовой инфраструктуре, а значит, не сможет самостоятельно устранить инфраструктурные уязвимости.
    • Тестирование инфраструктуры, скорее всего, будет находиться за рамками области оценки (out-of-scope) для данного аудита.

    В ряде случаев использование PaaS можно выявить по доменному имени приложения (например, приложения, развернутые в Azure App Services, по умолчанию получают домен вида *.azurewebsites.net, хотя могут использовать и кастомные домены). В других ситуациях определить применение PaaS бывает затруднительно.

    Бессерверные вычисления (Serverless)¶

    В бессерверной модели (Serverless) разработчики предоставляют код, который выполняется на хостинг-платформе в виде отдельных функций, вместо развертывания традиционного монолитного приложения в корневом каталоге веб-сервера. Это решение идеально подходит для микросервисной архитектуры. Как и в случае со средой PaaS, тестирование инфраструктуры обычно исключается из области оценки.

    В некоторых случаях на использование бессерверного кода указывает наличие специфических HTTP-заголовков. Например, функции AWS Lambda обычно возвращают следующие заголовки:

    X-Amz-Invocation-Type
X-Amz-Log-Type
X-Amz-Client-Context

    Функции Azure Functions выявить сложнее. Обычно они возвращают заголовок Server: Kestrel, однако одного этого признака недостаточно, чтобы однозначно подтвердить использование Azure App Function, поскольку на Kestrel может выполняться любой другой сервис.

    Микросервисы¶

    В микросервисной архитектуре API приложения состоит из множества дискретных сервисов вместо единого монолитного приложения. Сами сервисы часто запускаются внутри контейнеров (как правило, под управлением Kubernetes) и могут использовать различные операционные системы и языки программирования. Хотя они обычно скрыты за единым API-шлюзом (API Gateway) и общим доменом, использование нескольких языков (что часто заметно по подробным сообщениям об ошибках) может свидетельствовать о наличии микросервисов.

    Статическое хранилище¶

    Многие приложения хранят статический контент на специализированных платформах хранения данных, а не отдают его напрямую с основного веб-сервера. Двумя наиболее распространенными платформами являются бакеты Amazon S3 и учетные записи хранения Azure Storage Accounts; их легко идентифицировать по доменным именам:

    • BUCKET.s3.amazonaws.com или s3.REGION.amazonaws.com/BUCKET для бакетов Amazon S3
    • ACCOUNT.blob.core.windows.net для учетных записей Azure Storage Accounts

    Эти хранилища нередко приводят к раскрытию конфиденциальных файлов, о чем подробно рассказывается в разделе Cloud Storage.

    База данных¶

    Большинство нетривиальных веб-приложений используют базы данных для хранения динамического содержимого. В ряде случаев тип СУБД можно определить однозначно. Часто это достигается за счет:

    • Сканирования портов сервера и поиска открытых сетевых портов, характерных для конкретных СУБД.
    • Провоцирования сообщений об ошибках SQL (или NoSQL) (либо поиска уже проиндексированных ошибок через поисковые системы).

    Если однозначно определить базу данных не удается, тестировщик может выдвинуть обоснованное предположение на основе косвенных признаков:

    • Windows, IIS и ASP.NET часто используют Microsoft SQL Server
    • Встраиваемые (embedded) системы чаще всего применяют SQLite
    • Стек PHP обычно опирается на MySQL или PostgreSQL
    • Oracle APEX работает с СУБД Oracle

    Это не жесткие правила, однако они дают разумную отправную точку при отсутствии более точных сведений.

    Аутентификация¶

    В большинстве приложений предусмотрена аутентификация пользователей. Для этого могут применяться различные механизмы (бэкенды):

    • Конфигурация веб-сервера (включая файлы .htaccess) или жестко закодированные пароли в скриптах
      • Обычно проявляется как базовая HTTP-аутентификация (HTTP Basic), сопровождаемая всплывающим окном в браузере и заголовком ответа WWW-Authenticate: Basic.
    • Локальные учетные записи пользователей в базе данных
      • Обычно интегрированы в веб-форму или эндпоинт API приложения.
    • Существующий централизованный источник аутентификации, такой как Active Directory или сервер LDAP
      • Может использовать аутентификацию NTLM, о чем свидетельствует заголовок WWW-Authenticate: NTLM.
      • Может быть встроен в веб-форму приложения.
      • Может требовать ввода имени пользователя в формате ДОМЕН\пользователь или предоставлять выпадающий список доступных доменов.
    • Технология единого входа (Single Sign-On, SSO) с внутренним или внешним провайдером идентификации
      • Как правило, использует протоколы OAuth, OpenID Connect или SAML.

    Приложения могут предоставлять пользователям несколько способов аутентификации (например, регистрацию локального аккаунта или вход через существующий профиль Facebook), а также использовать различные механизмы для рядовых пользователей и администраторов.

    Сторонние сервисы и API¶

    Практически все веб-приложения подключают сторонние ресурсы, которые загружаются клиентом или с которыми взаимодействует браузер. К ним относятся:

    • Активный контент (скрипты, таблицы стилей, шрифты и теги iframe)
    • Пассивный контент (изображения и видео)
    • Внешние API
    • Кнопки социальных сетей
    • Рекламные сети
    • Платежные шлюзы

    Эти ресурсы запрашиваются напрямую браузером пользователя, что облегчает их выявление с помощью инструментов разработчика или перехватывающего прокси. Хотя их важно идентифицировать (поскольку они могут влиять на безопасность приложения), помните, что они обычно находятся вне рамок согласованной области тестирования, так как принадлежат сторонним организациям.

    Сетевые компоненты¶

    Обратный прокси-сервер (Reverse Proxy)¶

    Обратный прокси-сервер (reverse proxy) размещается перед одним или несколькими бэкенд-серверами и перенаправляет запросы к соответствующему адресату. Он может выполнять различные функции:

    • Выступать в роли балансировщика нагрузки или межсетевого экрана веб-приложений.
    • Позволять размещать несколько приложений на одном IP-адресе или домене (в подпапках).
    • Реализовывать фильтрацию по IP или другие ограничения доступа.
    • Кэшировать статический и динамический контент бэкенда для повышения производительности.

    Обнаружить обратный прокси удается не всегда (особенно если за ним скрыто только одно приложение), однако на его присутствие могут указывать:

    • Несоответствие между сервером фронтенда и приложением бэкенда (например, заголовок Server: nginx при работе с приложением ASP.NET)
      • Подобная конфигурация иногда может приводить к уязвимостям контрабанды HTTP-запросов (HTTP Request Smuggling).
    • Дублирующиеся заголовки (особенно заголовок Server).
    • Множество приложений, размещенных на одном IP-адресе или домене (особенно если они написаны на разных языках).

    Балансировщик нагрузки¶

    Балансировщик нагрузки (load balancer) располагается перед пулом серверов бэкенда и распределяет входящие запросы между ними для обеспечения отказоустойчивости и повышения пропускной способности приложения.

    Балансировщики бывает трудно обнаружить, однако иногда их можно идентифицировать, отправляя серию запросов и анализируя различия в ответах:

    • Несовпадающее системное время в заголовках.
    • Различные внутренние IP-адреса или имена хостов в подробных сообщениях об ошибках.
    • Различные адреса, возвращаемые при эксплуатации уязвимостей подделки запросов на стороне сервера (Server-Side Request Forgery, SSRF).

    На их наличие также могут указывать специфические cookie (например, балансировщики F5 BIG-IP создают файл cookie с именем BIGipServer).

    Сеть доставки контента (CDN)¶

    Сеть доставки контента (Content Delivery Network, CDN) — это географически распределенная сеть кэширующих прокси-серверов, предназначенная для оптимизации скорости загрузки сайта.

    Обычно CDN настраивается путем направления публичного DNS-домена на серверы CDN с последующей настройкой подключения CDN к целевым серверам бэкенда (часто называемым «источником» / origin).

    Простейший способ определить использование CDN — выполнить WHOIS-запрос для IP-адресов, в которые разрешается домен. Если они принадлежат CDN-провайдеру (такому как Akamai, Cloudflare или Fastly — более полный список см. на Википедии), высока вероятность того, что используется CDN.

    При тестировании ресурса за CDN следует учитывать следующие аспекты:

    • IP-адреса и пограничные серверы принадлежат провайдеру CDN и, вероятнее всего, исключены из области тестирования инфраструктуры.
    • Многие CDN включают встроенные механизмы защиты от ботов, ограничения частоты запросов (rate limiting) и функции WAF.
    • CDN кэширует контент, поэтому изменения на бэкенде могут не сразу отображаться на страницах сайта.

    Если сайт находится за CDN, крайне полезно выявить реальные серверы бэкенда. Если на бэкенде не настроен должный контроль доступа, тестировщик сможет обойти CDN (и все ее механизмы защиты), обратившись к серверам напрямую. Существует ряд методов, позволяющих идентифицировать реальный сервер (origin):

    • Электронные письма, отправляемые приложением, могут исходить напрямую с бэкенд-сервера, раскрывая его IP-адрес.
    • Перебор DNS (DNS grinding), передача зон или списки Certificate Transparency для домена могут раскрыть адрес на поддомене.
    • Сканирование диапазонов IP-адресов, принадлежащих целевой компании, может помочь найти сервер бэкенда.
    • Эксплуатация уязвимостей подделки запросов на стороне сервера (SSRF) может раскрыть внешний или внутренний IP-адрес origin-сервера.
    • Детализированные сообщения об ошибках приложения могут выдавать реальные IP-адреса или имена хостов.

    Компоненты безопасности¶

    Сетевой межсетевой экран¶

    Большинство веб-серверов защищены пакетными фильтрами или межсетевыми экранами с контролем состояния соединений (stateful inspection firewall), блокирующими любой неразрешенный сетевой трафик. Чтобы выявить файрвол, выполните сканирование портов сервера и проанализируйте полученные результаты.

    Если подавляющее большинство портов определяются как «closed» (то есть возвращают пакет RST в ответ на начальный пакет SYN), это указывает на то, что сервер, возможно, не защищен брандмауэром. Если же порты отображаются как «filtered» (то есть при отправке пакета SYN на неиспользуемый порт ответ вообще не поступает), на сервере с высокой вероятностью установлен файрвол.

    Кроме того, если во внешнюю сеть выставлены не предназначенные для этого сервисы (такие как SMTP, IMAP, MySQL и т. д.), это говорит либо об отсутствии межсетевого экрана, либо о грубых ошибках в его настройке.

    Система обнаружения и предотвращения сетевых вторжений¶

    Сетевая система обнаружения вторжений (Intrusion Detection System, IDS) предназначена для фиксации подозрительной или вредоносной сетевой активности (например, сканирования портов или поиска уязвимостей) и генерации оповещений. Система предотвращения вторжений (Intrusion Prevention System, IPS) выполняет аналогичные задачи, но дополнительно принимает активные меры по блокировке активности, обычно закрывая доступ для исходного IP-адреса.

    Наличие IPS обычно определяется путем запуска автоматизированных инструментов сканирования (например, сканера портов) по целевому объекту с последующей проверкой, был ли заблокирован исходный IP-адрес. Однако многие инструменты прикладного уровня могут не фиксироваться сетевой IPS (особенно если она не выполняет расшифровку TLS-трафика).

    Межсетевой экран уровня веб-приложений (WAF)¶

    Межсетевой экран веб-приложений (Web Application Firewall, WAF) инспектирует содержимое HTTP-запросов и блокирует запросы, которые выглядят подозрительными или вредоносными. WAF также может применяться для динамического внедрения других механизмов защиты, таких как CAPTCHA или ограничение частоты запросов. Обычно они используют набор известных сигнатур вредоносной активности и регулярных выражений — таких как OWASP Core Rule Set — для идентификации атак. WAF эффективны для защиты от определенных классов атак, таких как внедрение SQL-кода (SQL injection) или межсайтовый скриптинг (Cross-Site Scripting, XSS), однако менее эффективны против проблем контроля доступа или недостатков бизнес-логики.

    WAF может быть развернут в различных конфигурациях:

    • Непосредственно на самом веб-сервере в виде модуля.
    • На отдельной виртуальной машине или аппаратном устройстве.
    • В облаке перед серверами бэкенда (Cloud WAF).

    Поскольку WAF блокирует вредоносные запросы, его присутствие можно обнаружить, подставляя типовые строки атак в параметры и наблюдая за реакцией сервера. Например, попробуйте передать параметр с именем foo со значением ' UNION SELECT 1 или ><script>alert(1)</script>. Если эти запросы блокируются, высока вероятность наличия WAF. Кроме того, текст и оформление страниц блокировки могут выдать конкретную используемую технологию. Наконец, некоторые WAF добавляют в ответы собственные cookie или HTTP-заголовки, раскрывающие их работу.

    Если используется облачный WAF, его можно попытаться обойти путем прямого обращения к исходному серверу бэкенда (origin) методами, описанными в подразделе Content Delivery Network.
