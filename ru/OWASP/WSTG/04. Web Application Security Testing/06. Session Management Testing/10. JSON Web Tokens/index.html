    JSON Web Tokens¶

    ID
    WSTG-SESS-10

    Резюме¶

    Веб-токены JSON (JSON Web Tokens, JWT) представляют собой криптографически подписанные токены формата JSON, предназначенные для обмена утверждениями (клеймами — claims) между системами. Они часто используются в качестве токенов аутентификации или токенов сессий, особенно в REST API.

    JWT являются распространенным источником уязвимостей, возникающих как из-за ошибок их реализации в приложениях, так и в базовых библиотеках. Поскольку они применяются для аутентификации, наличие уязвимости может легко привести к полной компрометации приложения.

    Цели тестирования¶

    • Определить, раскрывают ли JWT конфиденциальную информацию.
    • Определить, могут ли JWT подвергаться фальсификации или модификации.

    Методика тестирования¶

    Обзор¶

    JWT состоят из трех компонентов:

    • Заголовок (header)
    • Полезная нагрузка (payload или body)
    • Подпись (signature)

    Каждый компонент закодирован в base64, и они разделяются точками (.). Имейте в виду, что кодирование base64, используемое в JWT, удаляет символы равенства (=), поэтому для декодирования секций может потребоваться добавить их обратно (padding).

    Анализ содержимого¶

    Заголовок¶

    Заголовок определяет тип токена (обычно JWT) и алгоритм, используемый для вычисления подписи. Пример декодированного заголовка показан ниже:

    {
  "alg": "HS256",
  "typ": "JWT"
}

    Существует три основных типа алгоритмов, используемых для вычисления подписей:

    Algorithm Description
    HSxxx HMAC с использованием секретного ключа и SHA-xxx.
    RSxxx and PSxxx Подпись с открытым ключом с использованием RSA.
    ESxxx Подпись с открытым ключом с использованием ECDSA.

    Существует также широкий спектр других алгоритмов, которые могут применяться для зашифрованных токенов (JWE), хотя они встречаются реже.

    Полезная нагрузка¶

    Полезная нагрузка JWT содержит фактические данные. Пример полезной нагрузки показан ниже:

    {
  "username": "administrator",
  "is_admin": true,
  "iat": 1516239022,
  "exp": 1516242622
}

    Полезная нагрузка обычно не шифруется, поэтому изучите ее, чтобы определить, содержатся ли в ней какие-либо конфиденциальные или потенциально неуместные данные.

    Данный JWT содержит имя пользователя и статус администратора, а также два стандартных клейма (iat и exp). Эти клеймы определены в RFC 7519, краткая информация о них приведена в таблице ниже:

    Claim Full Name Description
    iss Issuer Идентификатор стороны, выдавшей токен.
    iat Issued At Временная метка Unix, указывающая время выдачи токена.
    nbf Not Before Временная метка Unix, указывающая самую раннюю дату, когда токен может быть использован.
    exp Expires Временная метка Unix, указывающая время истечения срока действия токена.

    Подпись¶

    Подпись вычисляется с использованием алгоритма, определенного в заголовке JWT, затем кодируется в base64 и добавляется к токену. Модификация любой части JWT должна приводить к недействительности подписи и отклонению токена сервером.

    Чтобы прочитать эти три части из токена, декодируйте его с помощью инструмента для работы с JWT. Вкладка JWT в Gori декодирует токен при его вставке и оставляет клеймы доступными для редактирования с целью повторного подписания. Команда gori run jwt выводит аналогичные декодированные данные:

    $ gori run jwt "$TOKEN"
// header
{
  "typ": "JWT",
  "alg": "RS256"
}

// payload
{
  "data": {
    "id": 25,
    "email": "alice@wstg.test",
    "password": "646e613efcfc1317061b1df9340e3726",
    "role": "customer",
    // ... profile fields omitted
  },
  "bid": 6,
  "iat": 1789655485
}

// signature (not verified)
wcaY3SC6taMCJUH8F4CEcF2a1rUa8bjYetKAo3s8DO3yjt3D4GFmz2SyJR3151np…

    Этот токен был выдан приложением OWASP Juice Shop. Его полезная нагрузка содержит роль пользователя и хеш пароля. Поскольку полезная нагрузка не зашифрована, относитесь к каждому значению в ней как к доступному для чтения любому лицу, владеющему токеном.

    Анализ использования¶

    Помимо собственной криптографической стойкости, JWT также должен безопасно храниться и передаваться. Это должно включать проверки того, что:

    • Он всегда передается по зашифрованным соединениям (HTTPS).
    • Если он хранится в cookie, для него должны быть установлены надлежащие атрибуты.

    Срок действия JWT также должен быть проверен на основе клеймов iat, nbf и exp, чтобы убедиться, что:

    • JWT имеет разумное время жизни для данного приложения.
    • Просроченные токены отклоняются приложением.

    Проверка подписи¶

    Одной из наиболее серьезных уязвимостей, встречающихся при работе с JWT, является отсутствие проверки корректности подписи со стороны приложения. Обычно это происходит, когда разработчик использует функцию наподобие jwt.decode() в Node.js, которая просто декодирует тело JWT, вместо jwt.verify(), проверяющей подпись перед декодированием токена.

    Это можно легко проверить, изменив тело JWT без каких-либо изменений в заголовке или подписи и отправив его в запросе, чтобы проверить, примет ли его приложение.

    Вкладка JWT в Gori также содержит готовые к отправке пейлоады для описанных ниже уязвимостей. Команда gori run jwt --attacks выводит тот же набор: варианты алгоритма none, подбор слабых секретных ключей и пейлоады внедрения заголовков (header injection).

    Алгоритм none¶

    Наряду с алгоритмами на основе открытых ключей и HMAC, спецификация JWT также определяет алгоритм подписи с именем none. Как следует из названия, это означает, что подпись у JWT отсутствует, что позволяет модифицировать токен.

    Это можно протестировать, изменив алгоритм подписи (alg) в заголовке JWT на none, как показано в примере ниже:

    {
        "alg": "none",
        "typ": "JWT"
}

    Затем заголовок и полезная нагрузка повторно кодируются в base64, а подпись удаляется (при этом замыкающая точка сохраняется). При использовании приведенного выше заголовка и полезной нагрузки из раздела payload получится следующий JWT:

    eyJhbGciOiAibm9uZSIsICJ0eXAiOiAiSldUIn0K.eyJ1c2VybmFtZSI6ImFkbWluaW5pc3RyYXRvciIsImlzX2FkbWluIjp0cnVlLCJpYXQiOjE1MTYyMzkwMjIsImV4cCI6MTUxNjI0MjYyMn0.

    Некоторые реализации пытаются предотвратить это путем явной блокировки использования алгоритма none. Если эта проверка чувствительна к регистру (отклоняется только точная строка none), но используемая библиотека сопоставляет имена алгоритмов без учета регистра, проверку можно обойти, указав алгоритм вида NoNe. Значение alg чувствительно к регистру в соответствии с RFC 7515, поэтому соответствующая стандарту библиотека должна отклонить NoNe как неизвестный алгоритм.

    Уязвимость «психических подписей» (Psychic Signatures) в ECDSA¶

    В Java версий с 15 по 18 была обнаружена уязвимость, из-за которой при определенных обстоятельствах некорректно проверялись подписи ECDSA (CVE-2022-21449, известная как «мистические подписи» — psychic signatures). Если одна из этих уязвимых версий используется для разбора JWT с алгоритмом ES256, этим можно воспользоваться для полного обхода проверки подписи путем модификации тела токена и последующей замены подписи следующим значением:

    MAYCAQACAQA

    В результате получается JWT, выглядящий примерно так:

    eyJhbGciOiJFUzI1NiIsInR5cCI6IkpXVCJ9.eyJhZG1pbiI6InRydWUifQ.MAYCAQACAQA

    Слабые ключи HMAC¶

    Если JWT подписан с использованием алгоритма на основе HMAC (например, HS256), безопасность подписи целиком зависит от криптостойкости секретного ключа, используемого в HMAC.

    Если приложение использует готовое коммерческое (off-the-shelf) или открытое программное обеспечение, первым шагом должно стать исследование кода на предмет наличия используемого по умолчанию ключа подписи HMAC.

    Если ключ по умолчанию отсутствует, может оказаться возможным подобрать или перебрать (brute-force) ключ по словарю. Простейший способ сделать это — использовать скрипт crackjwt.py, которому требуются только JWT и файл словаря.

    Более мощным вариантом является преобразование JWT в формат, поддерживаемый John the Ripper, с помощью скрипта jwt2john.py. Затем John можно использовать для проведения гораздо более сложных атак на ключ.

    Если размер JWT велик, он может превысить максимальный размер, поддерживаемый John. Это можно обойти, увеличив значение переменной SALT_LIMBS в файле /src/hmacSHA256_fmt_plug.c (или эквивалентном файле для других форматов HMAC) и перекомпилировав John, как описано в этом issue на GitHub.

    Если этот ключ удается получить, становится возможным создавать и подписывать произвольные JWT, что обычно приводит к полной компрометации приложения.

    Путаница алгоритмов HMAC и открытого ключа¶

    Если приложение использует JWT с подписями на основе открытых ключей, но не проверяет корректность указанного алгоритма, атакующий потенциально может использовать это в атаке типа путаницы подписей (signature type confusion attack). Для успеха атаки должны выполняться следующие условия:

    1. Приложение должно ожидать, что JWT подписан алгоритмом на основе открытого ключа (т. е. RSxxx или ESxxx).
    2. Приложение не должно проверять, какой именно алгоритм фактически используется в JWT для создания подписи.
    3. Открытый ключ, используемый для проверки JWT, должен быть доступен атакующему.

    Если все эти условия соблюдены, злоумышленник может использовать открытый ключ для подписания JWT с помощью алгоритма на основе HMAC (например, HS256). Например, библиотека Node.js jsonwebtoken использует одну и ту же функцию как для токенов с открытым ключом, так и для токенов на основе HMAC, как показано в примере ниже:

    // Verify a JWT signed using RS256
jwt.verify(token, publicKey);

// Verify a JWT signed using HS256
jwt.verify(token, secretKey);

    Это означает, что если JWT подписан с использованием publicKey в качестве секретного ключа для алгоритма HS256, подпись будет признана сервером валидной.

    Для эксплуатации этой проблемы необходимо получить открытый ключ. Чаще всего это происходит, если приложение повторно использует один и тот же ключ как для подписания JWT, так и в составе TLS-сертификата. В этом случае ключ можно загрузить с сервера с помощью команды, подобной следующей:

    openssl s_client -connect example.org:443 | openssl x509 -pubkey -noout

    Кроме того, ключ может быть доступен в публичном файле на сайте в стандартном расположении, например /.well-known/jwks.json.

    Для тестирования измените содержимое JWT, а затем используйте ранее полученный открытый ключ для подписания JWT по алгоритму HS256. Это часто сложно выполнить при тестировании без доступа к исходному коду или деталям реализации, поскольку формат ключа должен быть абсолютно идентичен используемому сервером: проблемы с пробелами или кодировкой символов перевода строки (CRLF) могут привести к несовпадению ключей.

    Открытый ключ, предоставленный злоумышленником (встроенный JWK)¶

    Стандарт JSON Web Signature (JWS) (RFC 7515 §4.1.3) позволяет встраивать открытый ключ, используемый для проверки подписи, непосредственно в заголовок с помощью параметра jwk. Если серверная библиотека проверки слепо принимает этот встроенный ключ без сопоставления его с хранилищем доверенных ключей (truststore) или списком разрешенных открытых ключей (allowlist), атакующий может встроить свой собственный открытый ключ и подписывать поддельные токены соответствующим приватным ключом.

    Например, атакующий может внедрить свой открытый ключ прямо в заголовок:

    {
  "alg": "RS256",
  "typ": "JWT",
  "jwk": {
    "kty": "RSA",
    "e": "AQAB",
    "use": "sig",
    "kid": "attacker-inline-key",
    "n": "u1SucjA342W..."
  }
}

    Существует множество скриптов и расширений, позволяющих генерировать и внедрять встроенные заголовки jwk, такие как jwt_tool или JSON Web Tokens Burp Extension.

    Манипуляция идентификатором ключа (kid)¶

    Параметр заголовка kid обычно используется для извлечения ключа, необходимого для проверки подписи, из файловой системы или базы данных. Он может быть уязвим для различных атак типа внедрения (инъекций).

    Обход каталогов (Directory Traversal)¶

    Если приложение использует параметр kid для чтения файла ключа из файловой системы, злоумышленник может указать путь к заведомо пустому файлу, например ../../../../dev/null (в Linux) или nul (в Windows).

    Например, атакующий может изменить заголовок так, чтобы он указывал на пустой файл:

    {
  "alg": "HS256",
  "typ": "JWT",
  "kid": "../../../../../dev/null"
}

    Поскольку содержимое /dev/null пустое, атакующий может подписать вредоносный токен, используя пустую строку в качестве секретного ключа. Если сервер уязвим, он прочитает пустой файл, применит пустую строку для проверки подписи и примет поддельный токен.

    Внедрение команд и SQL-инъекции¶

    Если значение kid передается без фильтрации в запрос к базе данных или системную команду для извлечения ключа, оно может быть уязвимо к SQL-инъекциям или внедрению команд операционной системы.

    Например, атакующий может внедрить SQL-пейлоад в параметр kid, чтобы контролировать ключ, возвращаемый базой данных:

    {
  "alg": "HS256",
  "typ": "JWT",
  "kid": "invalid-key' UNION SELECT 'attacker-controlled-key'--"
}

    Это позволяет атакующему принудить приложение использовать известный ключ (например, «attacker-controlled-key») для проверки, что позволяет подделывать валидные токены.

    Инъекция в заголовки JWKS URL (jku) и X.509 URL (x5u)¶

    Спецификация JSON Web Signature (JWS) (RFC 7515 §4.1.2, §4.1.5) поддерживает параметры заголовка, указывающие на внешние хранилища открытых ключей:

    • jku (JWK Set URL): URI, указывающий на ресурс с набором открытых ключей в формате JSON (JWKS).
    • x5u (X.509 URL): URI, указывающий на ресурс с набором сертификатов открытых ключей X.509.

    Если библиотека проверки автоматически загружает открытые ключи по URI, указанному в заголовке, без применения строгого разрешающего списка (allowlist) доменов, атакующий может направить jku/x5u на контролируемый им сервер, разместить там свой ключ и подписывать поддельные токены соответствующим приватным ключом, которые сервер примет как валидные.

    Процедура тестирования¶

    1. Сгенерируйте пару ключей RSA на тестовой машине.

    2. Разместите соответствующий открытый ключ в формате JSON Web Key Set (JWKS) на публичном сервере:

      {
  "keys": [
    {
      "kty": "RSA",
      "e": "AQAB",
      "use": "sig",
      "kid": "test-key-01",
      "alg": "RS256",
      "n": "u1SucjA342W..."
    }
  ]
}

    3. Измените полезную нагрузку целевого JWT с модифицированными клеймами (например, изменив user_id или role).

    4. Обновите заголовок JWT параметром jku, указывающим на размещенную конечную точку JWKS, и соответствующим kid:

      {
  "alg": "RS256",
  "typ": "JWT",
  "jku": "https://attacker.example.com/.well-known/jwks.json",
  "kid": "test-key-01"
}

    5. Подпишите поддельный токен с помощью приватного ключа и отправьте его в аутентифицированном запросе.

    6. Если прямые внешние имена хостов заблокированы, проверьте способы обхода фильтрации URL:
      • Проверьте наличие уязвимостей открытого перенаправления (open redirect) на разрешенных доменах (например, https://trusted.example.com/oauth/redirect?url=https://attacker.example.com/jwks.json).
      • Проверьте несоответствия парсеров URL или ошибки нормализации путей (например, https://trusted.example.com@attacker.example.com/jwks.json).
      • Проверьте, пытается ли сервер выполнять разрешение во внутренней сети (SSRF) при указании в jku локального интерфейса (http://127.0.0.1/) или конечных точек метаданных облачных провайдеров (http://169.254.169.254/).

    Параметр x5u можно тестировать аналогичным образом: вместо документа JWKS разместите по целевому URL цепочку сертификатов X.509 (в кодировке PEM), подписанную ключом атакующего. Многие библиотеки извлекают открытый ключ из конечного сертификата (leaf certificate) без проверки того, является ли цепочка доверенной или завершается ли она на привязанном (pinned) корневом центре сертификации (root CA), поэтому проверьте, принимается ли самоподписанная или иная недоверенная цепочка.

    Путаница параметров аудитории (aud) и издателя (iss) токена¶

    В распределенных микросервисных и мультиарендных (multi-tenant) архитектурах множество различных сервисов часто используют централизованного поставщика удостоверений (Identity Provider, IdP). Распространенная ошибка авторизации возникает, когда нижестоящий сервис проверяет криптографическую подпись токена с помощью IdP, но не проверяет, что токен был явно выпущен для этого конкретного сервиса.

    • aud (Audience): определяет получателей, для которых предназначен JWT (RFC 7519 §4.1.3).
    • iss (Issuer): определяет субъекта (эмитента), выпустившего JWT (RFC 7519 §4.1.1).

    Если Сервис B доверяет подписи IdP, но пропускает проверку клейма aud, атакующий с валидными учетными данными в низкопривилегированном Сервисе A может перехватить свой токен и воспроизвести его при обращении к Сервису B.

    Процедура тестирования¶

    1. Аутентифицируйтесь в низкопривилегированном приложении или арендаторе (tenant), зарегистрированном у Identity Provider целевой организации.
    2. Перехватите и извлеките выданный валидный JWT.
    3. Проанализируйте клеймы полезной нагрузки для определения целевых aud (например, aud: "client-portal") и iss (например, iss: "https://auth.example.com/").
    4. Воспроизведите неизмененный токен в запросе к высокопривилегированному сервису, административному API или отдельному тенанту (например, https://internal-admin.example.com/api/v1/users).
    5. Если высокопривилегированный сервис принимает токен и выполняет действие, он уязвим к межсервисному повторному воспроизведению токена (Cross-Service Token Replay) из-за отсутствия валидации audience.
    6. Протестируйте подмену поставщика (issuer confusion) отдельно: если IdP является мультиарендным или обслуживает несколько сред (например, тестовую — staging и производственную — production) с общей конечной точкой JWKS, получите токен, выданный для другого, менее доверенного арендатора или приложения, и воспроизведите его на целевом сервисе. Принятие токена указывает на то, что iss либо не валидируется вовсе, либо проверяется слабым сравнением (например, сопоставлением префикса или подстроки) вместо строгого строкового равенства ожидаемому доверенному эмитенту.

    Рекомендации по устранению¶

    • Используйте безопасную и актуальную библиотеку для работы с JWT.
    • Убедитесь, что подпись валидна и использует ожидаемый алгоритм.
    • Не доверяйте непроверенным параметрам заголовков, таким как jku, x5u или jwk, без сверки со строгим разрешающим списком (allowlist) доменов/URI.
    • Всегда валидируйте стандартные клеймы: проверяйте, что exp находится в будущем, nbf — в прошлом, iss соответствует доверенному серверу авторизации, а aud строго совпадает с ожидаемым идентификатором сервиса.
    • Используйте надежный ключ HMAC или уникальный закрытый ключ для подписания токенов.
    • Убедитесь, что в полезной нагрузке не раскрывается конфиденциальная информация.
    • Обеспечьте безопасное хранение и передачу JWT.
    • См. OWASP JSON Web Tokens Cheat Sheet.
