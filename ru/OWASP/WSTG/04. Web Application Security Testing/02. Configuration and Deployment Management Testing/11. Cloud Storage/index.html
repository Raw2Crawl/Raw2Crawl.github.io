    Облачное хранилище¶

    ID
    WSTG-CONF-11

    Резюме¶

    Сервисы облачного объектного хранения данных (AWS S3, Azure Blob Storage, Google Cloud Storage и аналогичные платформы) позволяют веб-приложениям сохранять и получать объекты без необходимости развертывания и сопровождения собственных файловых серверов. Однако некорректная настройка контроля доступа способна приводить к раскрытию конфиденциальной информации, нарушению целостности данных или несанкционированному доступу. По умолчанию хранилища всех трех ведущих провайдеров являются закрытыми (private) и доступны исключительно явно авторизованным субъектам. Тем не менее, корзина/контейнер целиком либо отдельные объекты внутри них могут быть сделаны публичными — как намеренно (с чрезмерно широким скоупом), так и по ошибке конфигурации, — позволяя неавторизованным пользователям читать, загружать или модифицировать данные.

    Помимо публичной доступности на уровне корзин, данная категория проблем включает: некорректную настройку списков контроля доступа (ACL) и политик IAM, предоставляющих избыточные полномочия субъектам; уязвимости подписанных и предварительно подписанных URL (signed / presigned URLs), используемых для ограниченного по времени доступа без передачи полных учетных данных; а также настройки версионирования объектов и политик жизненного цикла (lifecycle policies), которые могут оставлять доступными устаревшие или якобы удаленные конфиденциальные данные, либо перемещать их в хранилища со слабыми механизмами контроля доступа.

    Цели тестирования¶

    • Убедиться, что механизмы контроля доступа к сервисам хранения данных (публичный доступ на уровне корзины/контейнера, ACL и политики IAM на уровне объектов или субъектов) настроены корректно.
    • Проверить, что подписанные и предварительно подписанные URL имеют жестко ограниченный скоуп действий, минимальное время жизни и обрабатываются безопасно.
    • Оценить, способны ли версионирование объектов и правила жизненного цикла раскрывать устаревшие или удаленные конфиденциальные данные.

    Методика тестирования¶

    В первую очередь определите URL-адрес корзины/контейнера: в рамках тестирования методом «черного ящика» (black-box) адреса обычно выявляются через ссылки в HTTP-ответах (теги <img>, <script>, бандлы JavaScript, ответы API), а при тестировании методом «серого ящика» (gray-box) — из консоли облачного провайдера, исходного кода или проектной документации. Затем выполните три базовые проверки для каждого провайдера: листинг (раскрывает ли корзина/контейнер свой список файлов без аутентификации?), чтение (можно ли получить конкретный или подобранный по словарю объект?) и запись (возможно ли загрузить произвольный файл или перезаписать существующий?). Проверки листинга и чтения следует проводить даже тогда, когда точное имя корзины неизвестно: техники перебора типовых и предсказуемых имен детально описаны в подразделе Cloud Object Storage Artifacts.

    В приведенных ниже таблицах сопоставлены проверки методом «черного ящика» (с помощью утилиты curl без учетных данных) и проверки методом «серого ящика» (с помощью CLI-утилит провайдеров при наличии учетных записей). Используйте curl для тестирования неаутентифицированного доступа; используйте CLI провайдеров при наличии учетных данных для прямой верификации сконфигурированных прав.

    Amazon S3¶

    Форматы URL: стиль виртуального хостинга (https://<bucket>.s3.<region>.amazonaws.com/<key>) или путь (https://s3.<region>.amazonaws.com/<bucket>/<key>); устаревший глобальный эндпоинт без указания региона также продолжает работать для ряда регионов.

    Проверка curl AWS CLI
    Листинг (List) curl "https://<bucket>.s3.amazonaws.com/" aws s3 ls s3://<bucket>
    Чтение (Get) curl "https://<bucket>.s3.amazonaws.com/<key>" aws s3 cp s3://<bucket>/<key> -
    Запись (Write) curl -X PUT -d 'test' "https://<bucket>.s3.amazonaws.com/test.txt" aws s3 cp test.txt s3://<bucket>/test.txt

    Успешный неаутентифицированный листинг возвращает XML-тело с корневым элементом <ListBucketResult>; отказ в записи сопровождается ошибкой AccessDenied в теле ответа или выводе CLI.

    Azure Blob Storage¶

    Формат URL: https://<account-name>.blob.core.windows.net/<container-name>/<blob-name>.

    Проверка curl Azure CLI (тестирование методом «серого ящика»)
    Листинг (List) curl "https://<account>.blob.core.windows.net/<container>?restype=container&comp=list" az storage blob list --container-name <container>
    Чтение (Get) curl "https://<account>.blob.core.windows.net/<container>/<blob>" az storage blob download --container-name <container> --name <blob>
    Запись (Write) curl -X PUT -d 'test' -H "x-ms-blob-type: BlockBlob" -H "x-ms-version: <current>" "https://<account>.blob.core.windows.net/<container>/test.txt" az storage blob upload --container-name <container> --name test.txt

    Возврат статуса 200 OK с XML-ответом <EnumerationResults> при проверке листинга означает, что для контейнера установлен уровень доступа Container (публичное чтение и листинг), а не Private или Blob (чтение только по точно известным именам файлов). Команда az storage container show-permission позволяет напрямую проверить заданный уровень доступа при наличии прав.

    Google Cloud Storage (GCS)¶

    Формат URL (публичный XML-эндпоинт): https://storage.googleapis.com/<bucket-name>/<object-name>.

    Проверка curl gsutil (тестирование методом «серого ящика»)
    Листинг (List) curl "https://storage.googleapis.com/storage/v1/b/<bucket>/o" gsutil ls gs://<bucket>
    Чтение (Get) curl "https://storage.googleapis.com/<bucket>/<object>" gsutil cat gs://<bucket>/<object>
    Запись (Write) curl -X POST --data-binary @test.txt "https://storage.googleapis.com/upload/storage/v1/b/<bucket>/o?uploadType=media&name=test.txt" gsutil cp test.txt gs://<bucket>/test.txt

    Возврат статуса 200 OK со списком объектов в формате JSON при проверке листинга свидетельствует о включенном публичном просмотре, чаще всего обусловленном привязкой ролей allUsers или allAuthenticatedUsers в IAM либо устаревшими списками ACL. Команда gsutil iam get gs://<bucket> подтверждает действующие привязки политик при тестировании методом «серого ящика».

    В операционной системе Windows замените одинарные кавычки (') на двойные (") в приведенных выше командах curl.

    Ошибки конфигурации политик ACL и IAM¶

    Помимо бинарного переключателя «публичный/приватный доступ», все три провайдера поддерживают гибкое разграничение прав, которое легко настроить избыточно мягко:

    • AWS S3: проанализируйте политики корзин (bucket policies) и ACL на предмет предоставления прав группам AllUsers или AuthenticatedUsers (аналог публичного доступа в терминологии AWS), а также на наличие разрешений s3:* или s3:GetObject/s3:PutObject для группового субъекта ("Principal": "*") или стороннего аккаунта AWS, которому этот доступ не требуется. Убедитесь, что механизм S3 Block Public Access активирован на уровне аккаунта и корзины (он служит страховочным эшелоном защиты, даже если отдельная политика корзины настроена ошибочно). Команды aws s3api get-bucket-acl и aws s3api get-bucket-policy позволяют просмотреть действующую конфигурацию в рамках gray-box анализа.
    • Azure Blob Storage: проверьте уровень публичного доступа контейнера (Private, Blob или Container), а также политики Shared Access Signature (SAS) и назначения ролей RBAC (Storage Blob Data Reader/Contributor), привязанные к учетной записи хранения, на предмет избыточных прав.
    • GCS: изучите привязки IAM (gsutil iam get gs://<bucket>) и устаревшие ACL объектов/корзин на наличие субъектов allUsers (публичный доступ) или allAuthenticatedUsers (любой пользователь с аккаунтом Google, а не только пользователи данного приложения: последнюю группу часто ошибочно принимают за «закрытый доступ», что не соответствует действительности).

    Во всех случаях отделяйте объекты, публичные по задумке разработчиков (статические ресурсы фронтенда, открытые материалы для скачивания), от файлов конфигураций, резервных копий или пользовательских документов, оказавшихся публичными по недосмотру: именно назначение объекта, а не только факт сетевой доступности, определяет реальную опасность уязвимости.

    Уязвимости подписанных и предварительно подписанных URL (Signed/Presigned URL)¶

    Подписанные URL (предварительно подписанные URL в S3, токены SAS в Azure, подписанные URL в GCS) позволяют приложению предоставлять ограниченный по времени доступ к закрытому объекту без передачи мастер-ключей и учетных данных сервиса. Проверяйте:

    • Срок действия (Expiry): убедитесь, что время жизни ссылки (X-Amz-Expires для S3, параметр se= для Azure SAS, Expires/X-Goog-Expires для GCS) минимально и соответствует решаемой задаче. Подписанный URL со сроком действия в несколько дней или лет фактически становится постоянным учетным атрибутом в случае утечки (через историю браузера, заголовок Referer, логи прокси-серверов или пересылку третьим лицам).
    • Область действия (Scope): убедитесь, что подпись ограничена только конкретным объектом и необходимым действием (например, в GCS и S3 подпись можно выдать строго на один файл и один HTTP-метод; маркеры Azure SAS могут быть сгенерированы на уровне всей учетной записи хранения вместо точечного контейнера или блоба — проверяйте используемый уровень гранулярности).
    • Утечка и повторное использование: проверьте, не регистрируются ли подписанные URL открытым текстом в промежуточных прокси, CDN или логах веб-приложения, и не используется ли один и тот же URL для множества пользователей вместо генерации уникальной одноразовой ссылки на каждый запрос. Утекший URL валиден для любого держателя до момента истечения срока жизни, а механизмы досрочного отзыва одиночного URL в большинстве платформ отсутствуют (требуется полная ротация мастер-ключа учетной записи).
    • Валидация подписи: в качестве базовой проверки целостности измените путь к объекту или параметры запроса в действующем подписанном URL (например, укажите другой файл при неизменной подписи) и убедитесь, что сервер отклоняет модифицированный запрос, а не отдает запрошенный ресурс.

    Проблемы версионирования и жизненного цикла¶

    Версионирование объектов (сохранение предыдущих версий файла при перезаписи или удалении) и политики жизненного цикла (автоматическое перемещение между уровнями хранения или удаление по расписанию) часто включаются для отказоустойчивости и соответствия стандартам, однако могут нарушать ожидание того, что «удаленные» данные действительно уничтожены:

    • Если версионирование активно, убедитесь, что «удаленный» объект (например, файл с персональными данными, удаленный по запросу пользователя, или старый файл с учетными данными после ротации) невозможно восстановить через идентификатор предыдущей версии. Для S3: aws s3api list-object-versions --bucket <bucket>; для GCS: gsutil ls -a gs://<bucket>/<object>; для Azure: моментальные снимки, версии и мягко удаленные блобы через команду az storage blob list --include svd (параметр v отдельно выводит только версии).
    • Убедитесь, что параметры контроля доступа применяются согласованно ко всем версиям объектов: исправление прав на корзину или контейнер после инцидента безопасности может затронуть только текущую версию, оставляя исторические версии доступными, если версионный доступ тарифицируется или разграничивается провайдером отдельно.
    • Проанализируйте правила жизненного цикла, переводящие объекты на другие уровни хранения или в другие учетные записи/регионы (архивные холодные уровни, межрегиональная репликация): убедитесь, что целевое хранилище имеет аналогичные средства защиты, поскольку перемещение данных может незаметно перенести конфиденциальную информацию в контур, не проходивший исходный аудит безопасности.
    • Если приложение задействует операцию «удаления» для стирания конфиденциальных данных, убедитесь, что это приводит к полному физическому уничтожению объекта (включая все исторические версии и реплицированные копии), а не просто скрывает текущую версию из листинга.
