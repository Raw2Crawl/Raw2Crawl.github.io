    Захват поддоменов (Subdomain Takeover)¶

    ID
    WSTG-CONF-10

    Резюме¶

    Успешная эксплуатация данного типа уязвимости позволяет злоумышленнику зарегистрировать на себя и получить полный контроль над поддоменом жертвы. Проведение атаки опирается на следующие факторы:

    1. Запись для поддомена на внешнем DNS-сервере жертвы указывает на несуществующий или деактивированный ресурс, внешний сервис или эндпоинт. Бурное развитие облачных сервисов XaaS («все как услуга») и публичных платформ создает огромное количество потенциальных целей.
    2. Сторонний провайдер услуг, хостивший ресурс, внешний сервис или эндпоинт, не выполняет надлежащую верификацию прав владения поддоменом при повторной регистрации.

    В случае успешного захвата поддомена атакующему открывается широкий спектр векторов атак (размещение вредоносного контента, фишинг, кража сессионных cookie пользователей, перехват учетных данных и т. д.). Уязвимость может эксплуатироваться для различных типов ресурсных записей DNS, включая A, CNAME, MX, NS, TXT и др. С точки зрения критичности наибольшую опасность представляет захват записей NS (делегирования зоны): хотя он встречается реже, успешная атака приводит к полному перехвату всей DNS-зоны и основного домена жертвы.

    GitHub¶

    1. Жертва (victim.com) использует сервис GitHub для разработки и настроила DNS-запись (coderepo.victim.com) для доступа к ресурсу.
    2. Жертва решает перенести свой репозиторий с GitHub на коммерческую платформу, однако забывает удалить запись coderepo.victim.com со своего DNS-сервера.
    3. Злоумышленник обнаруживает, что запись coderepo.victim.com указывает на сервис GitHub, и регистрирует это имя через GitHub Pages с помощью собственной учетной записи GitHub.

    Истекший домен¶

    1. Жертва (victim.com) владеет другим доменом (victimotherdomain.com) и использует запись CNAME (поддомен www) для перенаправления на него (www.victim.com --> victimotherdomain.com).
    2. В определенный момент срок регистрации домена victimotherdomain.com истекает, и он становится доступным для покупки любым желающим. Поскольку запись CNAME не была удалена из DNS-зоны victim.com, лицо, зарегистрировавшее освободившийся домен victimotherdomain.com, получает полный контроль над www.victim.com до тех пор, пока запись в DNS не будет удалена или изменена.

    Цели тестирования¶

    • Перечислить все возможные поддомены (актуальные и исторические), включая имена, попадающие под маску (wildcard).
    • Идентифицировать забытые или некорректно настроенные домены, а также любые признаки неактивных служб («висячих» записей), не покрытые стандартными сигнатурами ответов.
    • Выявить ссылки и ресурсы, указывающие на внешние домены, облачные корзины или сторонние учетные записи, которые больше не существуют и могут быть заняты атакующим.
    • При подтверждении возможности захвата оценить, распространяется ли доверие родительского приложения (cookie, политики CORS, валидация redirect_uri в OAuth, белый список CSP) на скомпрометированный поддомен.

    Методика тестирования¶

    Тестирование методом «черного ящика»¶

    Тестирование на предмет захвата поддоменов состоит из трех этапов: перечисление поддоменов (subdomain enumeration), автоматизированный поиск по сигнатурам (fingerprint-based detection) и ручная верификация (manual validation).

    «Висячая» DNS-запись (dangling DNS record) возникает в том случае, когда запись DNS продолжает указывать на внешний ресурс, который был удален или деактивирован у провайдера. Например, запись CNAME, указывающая на сайт GitHub Pages, удаленный владельцем, по-прежнему разрешается в IP-адреса сервиса, но сам ресурс не привязан ни к одной учетной записи. Злоумышленник может зарегистрировать соответствующий ресурс в сервисе и получить полный контроль над поддоменом.

    Перечисление поддоменов¶

    Используйте утилиту subfinder для обнаружения поддоменов целевого домена: subfinder -d victim.com -o subdomains.txt

    Команда сформирует базовый список поддоменов для последующего этапа обнаружения уязвимостей.

    Перед переходом к поиску сигнатур разрешите (resolve) и отфильтруйте полученный список, оставив только поддомены с записями CNAME, NS или MX, поскольку именно они чаще всего оказываются «висячими». Утилита dnsx позволяет автоматизировать эту операцию: dnsx -l subdomains.txt -cname -resp -o resolved.txt

    Обнаружение на основе отпечатков (Fingerprinting)¶

    Метод обнаружения по сигнатурам (отпечаткам — fingerprints) основан на сопоставлении HTTP-ответов каждого поддомена с базой данных известных ответов уязвимых сервисов. Проект can-i-take-over-xyz поддерживает открытую базу данных, каталогизирующую специфические строки ответов, возвращаемые поставщиками услуг (такими как GitHub Pages, AWS S3, Heroku, Fastly), когда запрашиваемый ресурс не занят.

    Используйте сканер subzy для быстрого экспресс-сканирования: subzy run --targets subdomains.txt

    Для получения более точных результатов выполните проверку с помощью утилиты nuclei с использованием специализированных шаблонов захвата: nuclei -l subdomains.txt -t takeovers/

    Положительный результат работы любого из этих инструментов указывает на совпадение ответа поддомена с известной сигнатурой уязвимого сервиса, что свидетельствует о наличии «висячей» DNS-записи, указывающей на свободный ресурс на сторонней платформе.

    Например, поддомен, указывающий на незанятый сайт GitHub Pages, возвращает следующий ответ:

    HTTP/1.1 404 Not Found
...
<p>There isn't a GitHub Pages site here.</p>

    Данная строка зафиксирована в базе can-i-take-over-xyz как эталонный отпечаток GitHub Pages. Когда subzy или nuclei обнаруживают эту строку, поддомен помечается как потенциально уязвимый.

    Ручная проверка¶

    Автоматизированные средства дают ложноположительные срабатывания. Обязательно проверяйте каждую обнаруженную уязвимость вручную перед внесением в отчет.

    1. Подтвердите тип DNS-записи и целевой хост: dig CNAME subdomain.victim.com
    2. Убедитесь, что полученный HTTP-ответ совпадает с ожидаемой сигнатурой провайдера из базы can-i-take-over-xyz: curl -i http://subdomain.victim.com
    3. Убедитесь, что ресурс свободен на платформе соответствующего провайдера. Не регистрируйте ресурс на себя.

    В отношении записей NS проверьте, доступен ли для свободной регистрации сам делегированный сервер имен: выполните dig NS subdomain.victim.com, после чего проверьте, свободен ли домен полученного nameserver. Незарегистрированный домен DNS-сервера означает, что любой желающий может купить его и отвечать на DNS-запросы для всей делегированной зоны — это наиболее опасный сценарий захвата.

    Захват ресурсов, специфичный для облачных сред¶

    Ведущие облачные провайдеры, платформы PaaS и JAMstack имеют характерные особенности захвата поддоменов. Поскольку поставщики периодически совершенствуют механизмы верификации, перед формированием отчета обязательно сверяйтесь с актуальным состоянием в базе can-i-take-over-xyz:

    • AWS S3: запись CNAME, указывающая на URL-адрес корзины S3 (например, bucket.s3.amazonaws.com), для которой корзина была удалена, возвращает ответ NoSuchBucket. Любой пользователь, создавший корзину с аналогичным именем в любом аккаунте AWS, захватывает поддомен.
    • Azure: «висячие» записи CNAME, указывающие на деактивированные службы Azure (App Services, точки Azure CDN/Front Door или профили Traffic Manager), могут быть захвачены путем регистрации ресурса с тем же именем в любой другой подписке Azure.
    • GCP: аналогичные сценарии возможны для корзин Cloud Storage и эндпоинтов Firebase Hosting.
    • GitHub Pages: детально рассмотрен выше в подразделе GitHub; по-прежнему остается одной из наиболее частых находок на практике.
    • Vercel и Netlify: запись CNAME, указывающая на домен проекта (*.vercel.app, *.netlify.app), который был удален или переименован, обычно может быть захвачена путем создания нового проекта с соответствующим именем.
    • Пользовательские домены Cloudflare Pages / Workers: «висячие» записи CNAME на *.pages.dev иногда могут быть захвачены в зависимости от политик на уровне учетных записей (следует проверять текущую логику, так как Cloudflare постоянно ужесточает проверки).
    • Heroku: запись CNAME на *.herokuapp.com для удаленного приложения возвращает статус «No such app» и позволяет перехватить трафик при создании приложения с тем же именем (с учетом правил именования Heroku).
    • Fastly и Shopify: оба сервиса регулярно фигурируют в отчетах об уязвимостях из-за некорректно отключенных пользовательских доменов; проверяйте сигнатуры согласно can-i-take-over-xyz аналогично другим провайдерам.

    Неиспользуемые («висячие») сигнатуры сервисов¶

    Помимо сопоставления строковых сигнатур в теле HTTP-ответов, наличие «висячей» записи может быть выявлено по косвенным сетевым признакам:

    • Ответы NXDOMAIN, SERVFAIL или пустой ответ записи A при попытке разрешения целевого хоста, на который ссылается CNAME жертвы (когда сам целевой хост сервиса не резолвится). Это более надежный признак, чем совпадение строки в HTTP, поскольку доказывает полное удаление вышестоящего ресурса.
    • Ошибки сертификатов TLS (несовпадение имени хоста, сертификат выдан для постороннего домена) на поддомене, который должен обслуживаться конкретным провайдером. Это часто указывает на то, что сервис больше не выпускает сертификат для данного имени из-за деактивации ресурса.
    • Специфические страницы ошибок поставщиков, сигнатуры которых еще не внесены в базу can-i-take-over-xyz (для новых или редких сервисов). Они также требуют ручной валидации с помощью dig и curl; воспринимайте базу сигнатур как ориентир, а не исчерпывающий перечень.

    Риски подстановочных записей CNAME (Wildcard CNAME)¶

    Символьная подстановочная запись DNS (wildcard record, например *.victim.com CNAME target.example-paas.com), указывающая на уязвимый сторонний сервис, многократно усиливает ущерб от единичной конфигурационной ошибки: любой поддомен, запрошенный злоумышленником (anything.victim.com, admin.victim.com, login.victim.com), будет успешно разрешаться через маску. Захват целевого ресурса на сервисе предоставляет контроль над неограниченным множеством поддоменов организации сразу. В ходе разведки целенаправленно проверяйте наличие wildcard-записей (dig CNAME nonexistent-random-string.victim.com, сравнивая результат с известным легитимным поддоменом), поскольку имена под маской не обнаруживаются пассивными методами разведки и выявляются только прямым запросом заведомо случайного имени.

    Последствия, выходящие за рамки контроля содержимого¶

    Последствия успешного захвата поддомена не исчерпываются возможностью публикации собственного контента на скомпрометированном узле. Поскольку поддомен разделяет периметр доверия родительского домена в ряде протоколов и браузерных механизмов, ущерб может распространяться на основное приложение:

    • Файлы Cookie: cookie, установленные с атрибутом Domain, охватывающим родительский домен, автоматически передаются браузером на захваченный поддомен, что позволяет злоумышленнику перехватывать сессии основного приложения (session hijacking). Кроме того, с захваченного поддомена можно устанавливать собственные cookie для родительского домена («подбрасывание cookie» — cookie tossing), которые будут передаваться на основной сайт, что открывает векторы фиксации сессий (session fixation) или перезаписи токенов CSRF. Изолированные host-only cookie (установленные без явного указания атрибута Domain) возвращаются только тому хосту, который их установил, и не могут быть перехвачены с соседнего поддомена; применение префикса __Host- гарантирует это поведение на уровне браузера.
    • CORS: если политика совместного использования ресурсов между источниками (CORS) основного приложения разрешает запросы с поддоменов по маске (например, доверие к *.victim.com или динамическое отражение заголовка Origin с проверкой суффикса), атакующий может инициировать аутентифицированные межсайтовые запросы к основному приложению из контекста захваченного поддомена.
    • OAuth: если в конфигурации клиента OAuth адрес перенаправления (redirect_uri) указывает на захваченный поддомен (либо валидация URI проверяет только совпадение родительского домена), атакующий сможет перехватывать коды авторизации и маркеры доступа, предназначенные для легитимного приложения.
    • CSP: если политика Content-Security-Policy основного приложения разрешает родительский домен с подстановочным знаком (*.victim.com) в директивах script-src или connect-src, атакующий сможет подключать вредоносные скрипты или эксфильтровать данные через разрешенный политикой источник.

    При формировании отчета о захвате поддомена обязательно анализируйте применимость указанных сценариев: они переводят уязвимость из разряда «подмена содержимого на изолированном узле» в категорию «компрометация сессий, авторизации и скриптового контекста основного веб-приложения».

    Перехват неработающих ссылок¶

    Аналогичный паттерн угроз возникает в отношении внешних ресурсов, на которые ссылается или которые загружает приложение, даже без использования собственных DNS-записей. Если сторонний домен, облачная корзина, репозиторий кода, пакет зависимостей или профиль в социальной сети прекращают свое существование, злоумышленник может зарегистрировать их на себя и перехватить трафик.

    Выполните краулинг приложения, соберите все внешние URL-адреса и проверьте, какие из них не разрешаются в DNS или возвращают ошибку «не найдено» на платформах, допускающих повторную регистрацию имен. Расставляйте приоритеты в зависимости от роли ресурса:

    • Скрипты, таблицы стилей и другие ресурсы, подгружаемые в страницу (<script src>, <link href>, <iframe src>): захват источника позволяет злоумышленнику исполнять произвольный код в контексте веб-приложения, что по масштабу последствий эквивалентно хранимому межсайтовому скриптингу (Stored XSS).
    • Ссылки на профили в социальных сетях, каналы технической поддержки или документацию: захват учетной записи позволяет злоумышленнику выдавать себя за официального представителя организации.
    • Домены или корзины, упомянутые в шаблонах электронных писем, документации или исходных кодах мобильных приложений: их легко упустить, поскольку они не обнаруживаются прямым обходом веб-сайта.

    Как и при тестировании захвата поддоменов, подтвердите фактическую возможность регистрации ресурса на платформе провайдера перед включением в отчет и не занимайте ресурсы без письменного согласования с заказчиком.

    Тестирование методом «серого ящика»¶

    В распоряжении специалиста по тестированию находится файл DNS-зоны, поэтому этап перечисления поддоменов не требуется. В остальном методика тестирования полностью аналогична.

    Рекомендации по устранению¶

    • Для устранения риска захвата поддоменов необходимо своевременно удалять неиспользуемые ресурсные записи из DNS-зоны при деактивации внешних сервисов. Рекомендуется внедрить процедуры непрерывного мониторинга и периодического аудита DNS.
    • Для предотвращения перехвата неработающих ссылок (Broken Link Hijacking) удаляйте или обновляйте внешние ссылки при закрытии сторонних сервисов, сохраняйте контроль над упоминаемыми доменами и аккаунтами, а также внедряйте механизм проверки целостности подресурсов (Subresource Integrity, SRI) для скриптов и таблиц стилей, загружаемых со сторонних площадок.
