    Загрязнение HTTP-параметров (HTTP Parameter Pollution)¶

    ID
    WSTG-INJT-04

    Резюме¶

    Тестирование на загрязнение HTTP-параметров (HTTP Parameter Pollution, HPP) проверяет реакцию приложения на получение нескольких HTTP-параметров с одинаковым именем; например, если параметр username передается в параметрах GET или POST дважды.

    Передача нескольких одноименных HTTP-параметров может привести к тому, что приложение интерпретирует их значения непредвиденным образом. Эксплуатируя эти эффекты, атакующий может обойти валидацию входных данных, спровоцировать ошибки приложения или изменить значения внутренних переменных. Поскольку загрязнение HTTP-параметров (сокращенно HPP) затрагивает базовый компонент всех веб-технологий, существуют векторы атак как на стороне сервера, так и на стороне клиента.

    Действующие стандарты HTTP не содержат рекомендаций относительно интерпретации нескольких входных параметров с одинаковым именем. Например, RFC 3986 просто определяет термин строка запроса (Query String) как последовательность пар «поле-значение», а RFC 2396 определяет классы зарезервированных и незарезервированных символов строки запроса. В отсутствие единого стандарта различные компоненты веб-приложений обрабатывают эту пограничную ситуацию по-разному (подробнее см. таблицу ниже).

    Само по себе это не обязательно свидетельствует об уязвимости. Однако если разработчик не осведомлен о данной проблеме, наличие дублирующихся параметров может привести к аномальному поведению приложения, которое потенциально может быть проэксплуатировано атакующим. Как это часто бывает в информационной безопасности, неожиданное поведение системы служит распространенным источником слабостей, приводящих в данном случае к атакам класса HTTP Parameter Pollution. Чтобы лучше понять этот класс уязвимостей и последствия HPP-атак, полезно рассмотреть несколько практических примеров, обнаруженных в прошлом.

    Обход валидации входных данных и фильтров¶

    В 2009 году, сразу после публикации первых исследований по HTTP Parameter Pollution, данная методика привлекла пристальное внимание сообщества специалистов по безопасности как потенциальный способ обхода межсетевых экранов веб-приложений (Web Application Firewall, WAF).

    Одна из таких уязвимостей, затронувшая правила ядра ModSecurity по противодействию SQL-инъекциям (ModSecurity SQL Injection Core Rules), представляет собой классический пример рассогласования логики интерпретации (impedance mismatch) между приложениями и фильтрами. Фильтр ModSecurity корректно применял черный список (deny list) к строке: select 1,2,3 from table, блокируя обработку веб-сервером следующего примера URL: /index.aspx?page=select 1,2,3 from table. Однако, эксплуатируя конкатенацию нескольких HTTP-параметров, злоумышленник мог заставить сервер приложений объединить строки уже после того, как фильтр ModSecurity пропустил входные данные. Например, URL /index.aspx?page=select 1&page=2,3 from table не вызывал срабатывания фильтра ModSecurity, но на уровне приложения переданные части конкатенировались обратно в полную вредоносную строку.

    Другая уязвимость HPP затронула Apple CUPS, известную систему печати, используемую во многих Unix-системах. Эксплуатируя HPP, атакующий мог легко вызвать уязвимость межсайтового скриптинга (Cross-Site Scripting), используя следующий URL: https://127.0.0.1:631/admin/?kerberos=onmouseover=alert(1)&kerberos. Проверку валидации в приложении можно было обойти путем добавления дополнительного аргумента kerberos, содержащего допустимую строку (например, пустую строку). Поскольку контрольная точка валидации проверяла только второе вхождение, первый параметр kerberos не подвергался должной санитизации перед генерацией динамического HTML-контента. Успешная эксплуатация приводила к выполнению кода JavaScript в контексте целевого сайта.

    Обход аутентификации¶

    Еще более критическая уязвимость HPP была обнаружена в популярной платформе ведения блогов Blogger. Данная ошибка позволяла злоумышленникам захватить контроль над блогом жертвы с помощью следующего HTTP-запроса (https://www.blogger.com/add-authors.do):

    POST /add-authors.do HTTP/1.1
[...]

security_token=attackertoken&blogID=attackerblogidvalue&blogID=victimblogidvalue&authorsList=goldshlager19test%40gmail.com(attacker email)&ok=Invite

    Уязвимость заключалась в механизме аутентификации веб-приложения: проверка безопасности выполнялась для первого параметра blogID, тогда как фактическая бизнес-операция использовала второе вхождение.

    Ожидаемое поведение со стороны сервера приложений¶

    Способ обработки дублирующихся параметров зависит от используемого фреймворка, сервера и того, как приложение считывает значение (например, первое значение, последнее значение или всю коллекцию целиком). Любую таблицу значений по умолчанию следует рассматривать лишь как отправную точку: обязательно проверяйте фактическое поведение целевого стека, включая обратные прокси-серверы (reverse proxies), межсетевые экраны веб-приложений (WAF) и шлюзы API (API gateways), которые могут нормализовать строки запросов по-разному.

    Для заданного URL и строки запроса: https://example.com/?color=red&color=blue

    Typical Stack Common Default Parsing Example
    ASP.NET / IIS All occurrences concatenated with a comma color=red,blue
    ASP.NET Core / Kestrel All occurrences available (StringValues; comma-joined when stringified) color=red,blue
    PHP (Apache / php-fpm / Nginx) Last occurrence only color=blue
    Java Servlet (Tomcat, Jetty, and similar) First occurrence only color=red
    Node.js / Express First occurrence only color=red
    Python (Django, Flask, and similar) All occurrences in a list / MultiDict color=['red','blue']

    Поведение других серверов и более старых платформ может отличаться; всегда проверяйте его на тестируемой системе. Исторические исследования по этой теме включают доклад AppSec EU 2009 (Carettoni & di Paola).

    Цели тестирования¶

    • Идентифицировать используемый бэкенд и метод парсинга параметров.
    • Оценить точки внедрения и попытаться обойти входные фильтры с использованием HPP.

    Методика тестирования¶

    Уязвимость конкретной страницы или эндпоинта API к HPP зависит от взаимодействия между несколькими компонентами, включая само приложение, веб-сервер, межсетевой экран веб-приложений и промежуточное программное обеспечение (middleware). Если в различных частях приложения (например, в микросервисной архитектуре) эти компоненты различаются, это может привести к тому, что одни компоненты приложения окажутся уязвимыми, а другие — нет.

    Поскольку для обнаружения уязвимости требуется глубокое понимание бизнес-логики, тестирование на HPP проводится вручную. Автоматизированные средства могут лишь частично помочь аудиторам, поскольку склонны генерировать слишком много ложных срабатываний (false positives). Кроме того, атаки HPP могут проявляться как в серверных, так и в клиентских компонентах.

    Серверное загрязнение параметров HTTP (Server-Side HPP)¶

    Для проверки на уязвимости HPP определите любую форму или действие, принимающее пользовательский ввод. Параметры строки запроса в HTTP GET-запросах легко модифицировать прямо в адресной строке браузера. Если действие формы отправляет данные через POST, тестировщику потребуется перехватывающий прокси-сервер для модификации POST-данных при их отправке на сервер. Идентифицировав целевой параметр ввода, можно отредактировать GET- или POST-данные путем перехвата запроса либо изменить строку запроса после загрузки страницы ответа. Чтобы протестировать приложение на HPP, достаточно добавить к GET- или POST-данным тот же параметр, но с другим значением.

    Например, если тестируется параметр search_string в строке запроса, URL запроса будет содержать имя этого параметра и его значение:

    https://example.com/?search_string=kittens

    Нужный параметр может находиться среди нескольких других параметров, однако подход остается прежним: оставьте остальные параметры без изменений и добавьте дубликат:

    https://example.com/?mode=guest&search_string=kittens&num_results=100

    Добавьте тот же параметр с другим значением:

    https://example.com/?mode=guest&search_string=kittens&num_results=100&search_string=puppies

    Для эндпоинтов на основе JSON полезная нагрузка будет выглядеть следующим образом:

    POST /search HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "search_string": "kittens",
  "search_string": "puppies"
}

    и отправьте новый запрос.

    Проанализируйте страницу ответа, чтобы определить, какое значение (или значения) было обработано. В приведенном примере результаты поиска могут отобразить kittens, puppies, комбинацию обоих значений (kittens,puppies, kittens~puppies или ['kittens','puppies']), вернуть пустой результат или страницу ошибки.

    Свидетельствует ли такое поведение по умолчанию о наличии потенциальной уязвимости, зависит от механизмов валидации и фильтрации входных данных конкретного приложения. Общее правило таково: если существующая валидация ввода и другие механизмы безопасности достаточны для единичных параметров, и если сервер присваивает только первый или последний из дублирующихся параметров, то загрязнение параметров не создает уязвимости. Если же дублирующиеся параметры конкатенируются, различные компоненты веб-приложения используют разные вхождения, либо тестирование приводит к возникновению ошибки, вероятность успешного использования HPP для вызова уязвимостей безопасности существенно возрастает.

    Более глубокий анализ требует отправки трех HTTP-запросов для каждого HTTP-параметра:

    1. Отправить HTTP-запрос со стандартным именем и значением параметра и зафиксировать HTTP-ответ. Например, page?par1=val1
    2. Заменить значение параметра на модифицированное тестовое значение, отправить запрос и зафиксировать HTTP-ответ. Например, page?par1=HPP_TEST1
    3. Отправить новый запрос, объединяющий шаги (1) и (2). Снова сохранить полученный HTTP-ответ. Например, page?par1=val1&par1=HPP_TEST1
    4. Сравнить ответы, полученные на всех предыдущих этапах. Если ответ из шага (3) отличается от (1) и одновременно отличается от (2), имеет место рассогласование логики (impedance mismatch), которое потенциально может быть использовано для эксплуатации уязвимостей HPP.

    Создание полноценного эксплойта на основе недостатков обработки параметров выходит за рамки данного документа. Примеры и подробности см. в списке литературы.

    Загрязнение HTTP-параметров (HPP) на стороне клиента¶

    Как и в случае с серверным HPP, ручное тестирование является единственным надежным способом аудита веб-приложений для обнаружения уязвимостей загрязнения параметров, затрагивающих клиентские компоненты. Если в серверном варианте злоумышленник использует уязвимое веб-приложение для доступа к защищенным данным или выполнения действий, которые запрещены либо не предполагались разработчиками, то клиентские атаки направлены на нарушение логики работы клиентских компонентов и технологий.

    Для проверки уязвимостей клиентского HPP найдите любую форму или действие, принимающее пользовательский ввод и возвращающее результат этого ввода обратно пользователю. Страница поиска подходит идеально, тогда как форма входа может не подойти (так как может не возвращать некорректное имя пользователя обратно клиенту).

    Аналогично тестированию серверного HPP внедрите в каждый HTTP-параметр значение %26HPP_TEST и найдите декодированные (URL-decoded) вхождения переданной полезной нагрузки:

    • &HPP_TEST
    • &amp;HPP_TEST
    • и т. д.

    В частности, обращайте внимание на ответы, содержащие векторы HPP внутри атрибутов data, src, href или действий форм (form actions). Опять же, указывает ли такое поведение по умолчанию на наличие потенциальной уязвимости, зависит от механизмов валидации, фильтрации и бизнес-логики конкретного приложения. Это также может влиять на параметры строки запроса, используемые в XMLHttpRequest (XHR), fetch и при динамическом создании атрибутов во время выполнения программы.
