    MySQL¶

    Резюме¶

    Уязвимости внедрения SQL-кода (SQL Injection) возникают всякий раз, когда пользовательский ввод используется при построении SQL-запроса без достаточных ограничений или санитизации. Использование динамического SQL (построение SQL-запросов путем конкатенации строк) открывает возможность для данных уязвимостей. SQL-инъекция позволяет злоумышленнику получить доступ к SQL-серверам и выполнять SQL-код с привилегиями учетной записи, используемой для подключения к базе данных.

    Сервер MySQL обладает рядом специфических особенностей, из-за которых некоторые эксплойты требуют специальной адаптации под данную систему. Этому и посвящен данный раздел. Поскольку MariaDB является форком MySQL, материалы этой страницы актуальны и для MariaDB.

    Методика тестирования¶

    При обнаружении уязвимости SQL Injection в приложении, работающем с базой данных MySQL, существует ряд атак, которые могут быть выполнены в зависимости от версии MySQL и привилегий пользователя в СУБД.

    В промышленной эксплуатации по всему миру встречается как минимум четыре основных версии MySQL: 3.23.x, 4.0.x, 4.1.x и 5.0.x. Каждая версия предоставляет набор возможностей, пропорциональный номеру версии:

    • Начиная с версии 4.0: UNION
    • Начиная с версии 4.1: подзапросы (Subqueries)
    • Начиная с версии 5.0: хранимые процедуры (Stored procedures), хранимые функции (Stored functions) и системное представление INFORMATION_SCHEMA
    • Начиная с версии 5.0.2: триггеры (Triggers)

    Следует отметить, что для версий MySQL до 4.0.x применимы только атаки Blind Injection на основе булевых условий или задержек времени, так как функционал подзапросов или инструкции UNION в них не были реализованы.

    Далее будем предполагать наличие классической уязвимости SQL-инъекции, которая может быть вызвана запросом, аналогичным описанному в разделе SQL Injection.

    https://www.example.com/page.php?id=2

    Проблема одинарных кавычек¶

    Прежде чем использовать функционал MySQL, необходимо учитывать, как представляются строки в SQL-инструкции, поскольку веб-приложения часто экранируют одинарные кавычки.

    Экранирование кавычек в MySQL выглядит следующим образом:

    'A string with \'quotes\''

    То есть MySQL интерпретирует экранированные апострофы \' как символы данных, а не как метасимволы.

    Поэтому, если приложению для корректной работы требуются строковые константы, различают два случая:

    1. Веб-приложение экранирует одинарные кавычки ' => \'
    2. Веб-приложение не экранирует одинарные кавычки ' => '

    В MySQL существует стандартный способ обойти необходимость использования одинарных кавычек, позволяющий объявлять строковую константу без их применения.

    Предположим, мы хотим узнать значение поля password в записи с условием следующего вида:

    1. password like 'A%'
    2. Значения ASCII в виде конкатенированного шестнадцатеричного представления (hex): password LIKE 0x4125
    3. Функция char(): password LIKE CHAR(65,37)

    Множественные смешанные запросы¶

    Библиотечные коннекторы MySQL не поддерживают множественные запросы, разделенные точкой с запятой (;), поэтому в MySQL невозможно внедрить несколько разнородных SQL-команд в рамках одной точки уязвимости, как это делается в Microsoft SQL Server.

    Например, следующая инъекция приведет к ошибке:

    1 ; update tablename set code='javascript code' where 1 --

    Сбор информации¶

    Снятие отпечатков MySQL¶

    Разумеется, первым делом необходимо определить, используется ли СУБД MySQL в качестве серверной базы данных. В MySQL реализована функция, позволяющая другим СУБД игнорировать инструкции в диалекте MySQL. Когда блок комментариев '/**/' содержит восклицательный знак '/*! sql here*/', он интерпретируется MySQL и воспринимается как обычный комментарий другими СУБД, как описано в руководстве по MySQL.

    Пример:

    1 /*! and 1=0 */

    Если используется MySQL, инструкция внутри блока комментариев будет выполнена.

    Версия¶

    Существует три способа получить эту информацию:

    1. Использование глобальной переменной @@version
    2. Использование функции VERSION()
    3. Использование фингерпринтинга через комментарии с указанием номера версии /*!40110 and 1=0*/

    что означает

    if(version >= 4.1.10)
   add 'and 1=0' to the query.

    Эти методы эквивалентны, так как приводят к одинаковому результату.

    Внутриполосная инъекция (in-band):

    1 AND 1=0 UNION SELECT @@version /*

    Слепая логическая инъекция (inferential):

    1 AND @@version like '4.0%'

    Ответ будет содержать строку следующего вида:

    5.0.22-log

    Вход пользователя в систему¶

    В MySQL Server различают два типа пользователей:

    1. USER(): пользователь, подключившийся к серверу MySQL.
    2. CURRENT_USER(): внутренний пользователь, от имени которого выполняется запрос.

    Между 1 и 2 существует различие. Основное заключается в том, что анонимный пользователь может подключиться (если это разрешено) под любым именем, но внутренним пользователем MySQL будет пустое имя (''). Другое отличие состоит в том, что хранимая процедура или хранимая функция выполняются с привилегиями создавшего их пользователя, если не указано иное. Это можно узнать с помощью CURRENT_USER.

    Внутриполосная инъекция:

    1 AND 1=0 UNION SELECT USER()

    Слепая логическая инъекция:

    1 AND USER() like 'root%'

    Ответ будет содержать строку вида:

    user@hostname

    Имя используемой базы данных¶

    Используется встроенная функция DATABASE()

    Внутриполосная инъекция:

    1 AND 1=0 UNION SELECT DATABASE()

    Слепая логическая инъекция:

    1 AND DATABASE() like 'db%'

    Ожидаемый результат — строка следующего вида:

    dbname

    INFORMATION_SCHEMA¶

    Начиная с MySQL 5.0 было добавлено представление INFORMATION_SCHEMA. Оно позволяет извлекать всю информацию о базах данных, таблицах и столбцах, а также о процедурах и функциях.

    Tables_in_INFORMATION_SCHEMA DESCRIPTION
    SCHEMATA All databases the user has (at least) SELECT_priv
    SCHEMA_PRIVILEGES The privileges the user has for each DB
    TABLES All tables the user has (at least) SELECT_priv
    TABLE_PRIVILEGES The privileges the user has for each table
    COLUMNS All columns the user has (at least) SELECT_priv
    COLUMN_PRIVILEGES The privileges the user has for each column
    VIEWS All columns the user has (at least) SELECT_priv
    ROUTINES Procedures and functions (needs EXECUTE_priv)
    TRIGGERS Triggers (needs INSERT_priv)
    USER_PRIVILEGES Privileges connected User has

    Вся эта информация может быть извлечена с использованием известных техник, описанных в разделе SQL Injection.

    Векторы атак¶

    Запись в файл¶

    Если у подключенного пользователя есть привилегия FILE и одинарные кавычки не экранируются, для экспорта результатов запроса в файл можно использовать конструкцию into outfile.

    Select * from table into outfile '/tmp/file'

    Примечание: обойти одинарные кавычки, обрамляющие имя файла, невозможно. Поэтому, если к одинарным кавычкам применяется санитизация вроде экранирования \', использовать предложение into outfile не удастся.

    Этот тип атаки может применяться как внеполосная техника для получения результатов запроса или для записи файла, который может быть выполнен внутри директории веб-сервера (веб-шелл).

    Пример:

    1 limit 1 into outfile '/var/www/root/test.jsp' FIELDS ENCLOSED BY '//'  LINES TERMINATED BY '\n<%jsp code here%>';

    Результаты сохраняются в файле с правами rw-rw-rw, владельцем которого являются пользователь и группа MySQL.

    Где /var/www/root/test.jsp будет содержать:

    //field values// <%jsp code here%>

    Чтение из файла¶

    load_file — это встроенная функция, позволяющая читать файл, если это разрешено правами файловой системы. Если у подключенного пользователя есть привилегия FILE, ее можно использовать для получения содержимого файлов. Экранирование одинарных кавычек можно обойти с помощью описанных ранее техник.

    load_file('filename')

    Файл целиком станет доступен для экспорта стандартными методами.

    Стандартная атака с использованием SQL-инъекции¶

    В стандартной SQL-инъекции результаты могут отображаться непосредственно на странице в виде обычного вывода или ошибки MySQL. Применяя ранее упомянутые векторы SQL-инъекций и описанные возможности MySQL, можно легко реализовать прямую SQL-инъекцию, глубина которой зависит главным образом от версии MySQL, с которой столкнулся пентестер.

    Хорошим вектором атаки является получение данных путем принуждения функции/процедуры или самого сервера к генерации ошибки. Список ошибок, генерируемых MySQL и, в частности, встроенными функциями, можно найти в руководстве по MySQL.

    Внеполосная SQL-инъекция¶

    Внеполосная инъекция может быть реализована с помощью конструкции into outfile.

    Слепая SQL-инъекция¶

    Для слепых SQL-инъекций MySQL Server предоставляет набор полезных встроенных функций:

    • Длина строки:
      • LENGTH(str)
    • Извлечение подстроки из заданной строки:
      • SUBSTRING(string, offset, #chars_returned)
    • Слепая инъекция на основе задержек времени:
      • BENCHMARK и SLEEP BENCHMARK(#ofcycles,action_to_be_performed) Функция benchmark может использоваться для проведения атак по времени, когда слепая инъекция на основе булевых значений не дает результатов. См. SLEEP() (MySQL > 5.0.x) в качестве альтернативы benchmark.

    Полный список функций см. в руководстве по MySQL.
