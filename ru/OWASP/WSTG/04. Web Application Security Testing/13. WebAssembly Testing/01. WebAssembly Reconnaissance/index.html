    Разведка WebAssembly¶

    ID
    WSTG-WASM-01

    Резюме¶

    WebAssembly (Wasm) представляет собой бинарный формат инструкций, доставляемый в браузер в виде скомпилированного модуля. Поскольку на первый взгляд он не предназначен для чтения человеком, его часто ошибочно воспринимают как полностью непрозрачный и, следовательно, более безопасный, чем JavaScript. На практике, как и традиционные исполняемые файлы для настольных операционных систем, модули Wasm можно обнаружить, идентифицировать (снять цифровые отпечатки) и проанализировать.

    Разведка (Reconnaissance) является первым этапом тестирования безопасности WebAssembly. Данный этап направлен на обнаружение модулей Wasm в составе веб-приложения, определение цепочки инструментов (toolchain), с помощью которой они были собраны, проверку наличия открытых артефактов отладки, таких как карты исходного кода (source maps), информация DWARF (Debugging With Attributed Record Formats) и секция name, а также на сопоставление поверхности атаки на инфраструктуру (URL, эндпоинты API, хосты), которую раскрывают данные модули.

    На данном этапе выполняется исключительно сбор информации о цели. Он намеренно останавливается перед декомпиляцией кода, анализом логики его работы или запуском модуля под отладчиком. Успешный сбор этих разведывательных данных формирует базовую карту, необходимую для последующих фаз тестирования.

    В этой главе основное внимание уделяется Wasm-модулям, доставляемым в браузер (browser-delivered). Разведка модулей Wasm, выполняемых вне браузера (в средах WASI, граничных или бессерверных платформах), отличается тем, что модули обычно не передаются клиенту и должны быть получены иными путями. Различия подробно описаны в разделе WebAssembly Testing Overview.

    Цели тестирования¶

    • Обнаружить все модули WebAssembly, загружаемые целевым приложением, включая модули без расширения .wasm, сжатые, загружаемые отложенно (lazy-loaded), загружаемые через fetch и ручную инициализацию либо встроенные непосредственно в JavaScript.
    • Идентифицировать компиляторный тулчейн и исходный язык программирования (например, C/C++, Rust, Go, .NET) по метаданным секций, импортам, экспортам и связующему коду (glue code).
    • Выявить оставленные артефакты отладки: карты исходного кода (source maps), отладочную информацию DWARF и пользовательскую секцию name.
    • Составить карту поверхности атаки на инфраструктуру путем извлечения встроенных URL, эндпоинтов API, внутренних имен хостов или IP-адресов.

    Методика тестирования¶

    Поиск модулей WebAssembly¶

    Бинарные файлы WebAssembly загружаются с помощью JavaScript, как правило, асинхронно. Самый прямой способ их обнаружения — использование инструментов разработчика браузера (DevTools) и анализ клиентского JavaScript-кода.

    Инструменты разработчика в браузере¶

    1. Откройте инструменты разработчика (Developer Tools) и перейдите на вкладку Network («Сеть»).
    2. Перезагрузите целевое приложение и выполните действия в интерфейсе, чтобы инициировать отложенную загрузку компонентов.
    3. В браузерах Chrome и Edge выберите фильтр Wasm, чтобы отобразить только запросы WebAssembly. В Firefox специального фильтра Wasm нет, поэтому выполните поиск по списку запросов по ключевому слову .wasm и проверьте столбец типа контента на наличие application/wasm.
    4. Проверьте также фоновые процессы Web Workers и Service Workers. Они часто используются для выполнения кода Wasm, и их сетевой трафик может отображаться в отдельных вкладках DevTools.

    Анализ кода JavaScript¶

    Если в приложении используется отложенная загрузка или бандлинг, выполните поиск по файлам JavaScript на предмет вызовов API загрузки WebAssembly:

    • WebAssembly.instantiate / WebAssembly.instantiateStreaming
    • WebAssembly.compile / WebAssembly.compileStreaming
    • new WebAssembly.Module / new WebAssembly.Instance

    Приложения не всегда загружают Wasm по прямому URL с расширением .wasm. Модуль может запрашиваться через fetch или XMLHttpRequest, а затем инициализироваться вручную из ArrayBuffer, распаковываться в JavaScript перед созданием экземпляра или собираться из нескольких фрагментов (чанков). В таких ситуациях на вкладке Network отображается лишь стандартный HTTP-запрос, поэтому поиск по указанным функциям API является более надежным методом.

    Если модуль формируется динамически во время выполнения и не загружается отдельным файлом, его можно перехватить в момент инициализации. Например, скрипт, внедренный до выполнения основного кода приложения (с использованием Local Overrides в DevTools, сниппета перед загрузкой страницы или расширения для пользовательских скриптов), может переопределить API и сохранить копию переданных байтов:

    const _instantiate = WebAssembly.instantiate;
window.__wasmDumps = [];
WebAssembly.instantiate = function (source, ...rest) {
  if (source instanceof ArrayBuffer || ArrayBuffer.isView(source)) {
    window.__wasmDumps.push(new Uint8Array(source.buffer || source).slice());
  }
  return _instantiate.call(this, source, ...rest);
};

    Аналогичный подход к перехвату применим к WebAssembly.compile, WebAssembly.Module и потоковым методам (streaming), которые принимают объект Response вместо массива байтов и требуют его клонирования. Перехваченные байты затем можно сохранить в файл для последующего анализа.

    Встроенные модули¶

    Бинарные файлы Wasm также могут быть встроены непосредственно в JavaScript во избежание отправки дополнительного HTTP-запроса. Обращайте внимание на:

    • Крупные строки Base64, передаваемые через atob или кастомный декодер в объект Uint8Array.
    • URI схемы data:, такие как data:application/octet-stream;base64,.
    • Очень длинные строковые литералы, часто содержащие экранированные символы или символы за пределами ASCII, которые декодируются вспомогательной функцией при запуске и передаются в один из вышеупомянутых API.

    Подобный подход применяется в сборках Emscripten с опцией SINGLE_FILE. В современных версиях Emscripten бинарный файл по умолчанию встраивается с использованием кастомной кодировки UTF-8 (Base64 применяется только при отключении SINGLE_FILE_BINARY_ENCODE), поэтому второй и третий шаблоны наиболее типичны для актуальных сборок. Подробности см. в справочнике параметров Emscripten. Ввиду различий кодировок между версиями перехват в момент инициализации, показанный выше, зачастую оказывается проще, чем ручное декодирование строки.

    Идентификация файлов Wasm по содержимому¶

    Не следует полагаться исключительно на расширение файла или MIME-тип. Модули могут отдаваться с расширениями .bin, .dat, вовсе без расширения или в сжатом виде — .wasm.gz или .wasm.br. Сжатые файлы перед анализом заголовка необходимо распаковать (например, с помощью gunzip или brotli -d). Браузеры прозрачно распаковывают ответы с заголовком Content-Encoding, поэтому файл, сохраненный через DevTools, обычно уже распакован, в то время как файл, загруженный консольной утилитой, может оставаться сжатым.

    Каждый бинарный файл Wasm начинается с одинакового 8-байтового заголовка (сигнатура «магических байтов» \0asm, за которой следует номер версии):

    00 61 73 6D 01 00 00 00

    Загруженный файл можно проверить с помощью команд file module.bin или od -An -tx1 -N8 module.bin. В исходном коде JavaScript этот заголовок отображается в начале Base64-строки как префикс AGFzbQ.

    Если файл, загружаемый приложением как модуль, не начинается с этих байтов и не сжат, приложение может кодировать или шифровать его с последующим декодированием в JavaScript перед загрузкой. В таком случае изучите функцию декодирования в связующем коде (glue code) и примените ее к скачанному файлу для получения исходного бинарного файла.

    После подтверждения сигнатуры заголовка проверьте корректность модуля с помощью утилиты wasm-validate из пакета WebAssembly Binary Toolkit (WABT):

    wasm-validate module.wasm

    Если валидация завершается ошибкой из-за использования модулем новых возможностей языка (например, сборщика мусора garbage collection), повторите запуск с флагом --enable-all.

    Обратите внимание, что методы WebAssembly.instantiateStreaming и WebAssembly.compileStreaming требуют от сервера передачи MIME-типа application/wasm, поэтому передача Wasm-файла с другим типом может свидетельствовать о некорректной конфигурации сервера.

    Анализ пользовательских секций¶

    После загрузки модуля выведите список его секций с помощью утилиты wasm-objdump (входит в состав WABT). Большинство дальнейших задач разведки решаются анализом этого вывода:

    wasm-objdump -h module.wasm

    Ищите следующие пользовательские секции:

    Section What it reveals Covered in
    producers Исходный язык и инструменты, использованные для сборки модуля Identifying the Compiler and Toolchain
    sourceMappingURL URL внешней карты исходного кода Source Maps
    .debug_*, external_debug_info Отладочная информация DWARF (встроенная или в отдельном файле) DWARF Debug Information
    name Исходные имена функций и переменных Name Section

    Пользовательские секции являются необязательными и могут быть удалены на любом этапе. Полное отсутствие пользовательских секций — обычная практика для релизных продуктивных сборок.

    Определение компилятора и набора инструментов¶

    Информация о том, был ли модуль скомпилирован из C/C++, Rust, Go или другого языка, помогает тестировщику понять его модель памяти, соглашения о вызовах, особенности времени выполнения и структуру сопутствующего JavaScript-кода (glue code).

    Эти данные также помогают расставить приоритеты при последующем тестировании безопасности. Например, использование нативных языков компиляции указывает на необходимость более пристального анализа безопасности памяти, работы с линейной памятью, небезопасных операций и границ взаимодействия между нативным кодом и JavaScript, тогда как специализированные фреймворки привлекают внимание к соответствующим средам выполнения и поверхностям интеграции.

    Идентификацию компилятора следует использовать для выбора направлений тестирования и приоритизации проверок, а не в качестве доказательства наличия конкретной уязвимости.

    Автоматизированное обнаружение¶

    Такие инструменты, как WASM-Hunter, позволяют оперативно идентифицировать компилятор и инструментарий сборки, сканируя бинарный файл Wasm на наличие характерных строк, символов, импортов и маркеров среды выполнения:

    wasm-hunter -compiler -i target_module.wasm

    Автоматическое определение носит эвристический, а не абсолютный характер. Оптимизированные, очищенные от отладочных символов (stripped) или обфусцированные модули могут не содержать характерных маркеров, поэтому полученный результат следует рассматривать как предварительную классификацию и по возможности проверять вручную.

    Ручная идентификация¶

    Если автоматическое определение недоступно или выдает неопределенный результат, проанализируйте несколько признаков, не полагаясь на одну-единственную сигнатуру.

    Пользовательская секция producers зачастую является наиболее прямым индикатором, поскольку тулчейны фиксируют в ней языки и инструменты сборки, такие как clang, rustc или wasm-bindgen. Просмотреть ее можно с помощью wasm-objdump из состава WABT:

    wasm-objdump -s -j producers module.wasm

    Секция producers опциональна и часто удаляется из оптимизированных или защищенных сборок. В таком случае исследуйте импорты и экспорты модуля, строки среды выполнения, связанный связующий код JavaScript и сопутствующие файлы сборки. Список импортов и экспортов можно получить командами wasm-objdump -x -j Import module.wasm и wasm-objdump -x -j Export module.wasm. Рассматривайте отдельные признаки как подсказки и по возможности подтверждайте выводы вторым независимым показателем:

    • Emscripten (C/C++): Импорты функций вида emscripten_resize_heap, __syscall_* или invoke_*. Импорт универсального модуля env не является достаточным доказательством, так как он используется и другими тулчейнами. Релизные сборки обычно минифицируют имена импортов (например, модуль с именем a), что скрывает эти паттерны.
    • WASI: Импорт модулей wasi_snapshot_preview1 или wasi_unstable свидетельствует об использовании системных вызовов WASI. Это не определяет исходный язык напрямую (модули Emscripten также могут их импортировать), поэтому требуются дополнительные проверки.
    • Rust (wasm-bindgen): Импорты или экспорты, начинающиеся с __wbindgen_ или __wbg_, импортируемый модуль с именем wbg, а также сгенерированный файл *_bg.wasm рядом со связующим файлом *_bg.js. Секция producers обычно явно содержит записи rustc и wasm-bindgen.
    • Go: Связующий файл wasm_exec.js, модуль импорта с именем gojs (в Go 1.21 и новее) или go (в более старых версиях), а также строки вида runtime.wasmExit, runtime.gopanic или Go build ID. Современные версии Go также добавляют пользовательскую секцию go:buildid.
    • .NET (Blazor WebAssembly): Файлы dotnet.wasm или dotnet.native.wasm, загружаемые из каталога _framework/. До версии .NET 10 также присутствует манифест blazor.boot.json. Начиная с .NET 10 начальная конфигурация загрузки встраивается внутрь dotnet.js.
    • AssemblyScript: В релизных сборках маркеры практически отсутствуют: как правило, присутствует единственный импорт env.abort и экспорт memory. В отладочных сборках сохраняются пути вида ~lib/rt/ в секции name, а модули, собранные с флагом --exportRuntime, экспортируют функции __new и __pin.

    Ни один маркер не должен рассматриваться как окончательный вердикт. Наиболее надежный результат достигается объединением нескольких независимых признаков: метаданных producers, runtime-символов, импортов/экспортов, связующего кода и файлов развертывания.

    Очистка отладочной информации (stripping) и обфускация могут скрыть большинство приведенных маркеров. Удаление секций producers и name, минификация имен импортов и экспортов, а также удаление неиспользуемого кода (tree-shaking) вспомогательных компонентов среды выполнения являются стандартом для релизных сборок, и тестировщик может вовсе не суметь определить тулчейн. Неопределенный результат является абсолютно валидным итогом данного этапа и должен фиксироваться как таковой, без необоснованных догадок.

    Проверка наличия карт исходного кода (Source Maps) и отладочных символов¶

    Разработчики иногда оставляют артефакты отладки в продуктивных сборках. Само по себе это является уязвимостью конфигурации (информационной утечкой) и при этом предоставляет тестировщику обширный контекст для анализа.

    Карты исходного кода (Source Maps)¶

    Аналогично JavaScript модуль WebAssembly может ссылаться на внешнюю карту исходного кода (source map). Ссылка размещается в пользовательской секции sourceMappingURL, содержимым которой является URL-адрес файла карты (например, module.wasm.map).

    Если данная секция отсутствует, выполните прямой запрос по вероятным путям, таким как module.wasm.map. Связующий JavaScript-код также может содержать ссылку на собственную карту исходников через комментарий //# sourceMappingURL= или заголовок ответа SourceMap. Эта карта относится к JavaScript, а не к модулю Wasm, однако она также может раскрывать исходные файлы проекта.

    При наличии доступа к карте исходного кода откройте вкладку Sources (или Debugger) в браузере. Браузер обработает карту и отобразит исходную структуру каталогов и файлов. Объем восстанавливаемых данных зависит от содержимого карты:

    • Если карта содержит свойство sourcesContent либо файлы исходного кода доступны для загрузки по указанным путям, можно прочитать исходный код целиком.
    • В противном случае восстанавливаются только пути к файлам и сопоставления строк, что тем не менее раскрывает структуру проекта, названия зависимостей и внутренние пути среды разработки.

    Отладочная информация DWARF¶

    Для языков C, C++ и Rust отладочные данные чаще формируются в стандарте DWARF, чем в виде карт source maps. На этапе разведки необходимо лишь проверить их наличие: либо в виде секций .debug_* внутри самого модуля, либо в виде секции external_debug_info, указывающей на отдельный отладочный файл («разделительный DWARF», split DWARF), который может быть доступен для загрузки с сервера.

    Секция имен¶

    Даже при полном удалении карт исходников и данных DWARF в модуле иногда оставляют пользовательскую секцию name. Она содержит исходные имена функций, а в некоторых случаях — локальных переменных. Проверьте ее наличие в списке секций и извлеките данные командой:

    wasm-objdump -x -j name module.wasm

    Имена функций для Rust и C++ обычно представлены в искаженном виде (mangled). Восстановленные имена, такие как check_license_key или encrypt_password, сразу становятся приоритетными целями для детального реверс-инжиниринга.

    Картирование поверхности атаки (URL, API и IP-адреса)¶

    Модули WebAssembly часто содержат «вшитые» (hardcoded) данные об инфраструктуре. Типичные примеры включают:

    • Базовые URL и пути эндпоинтов бэкенд-API (https://api.example.com/v2/, /internal/admin/).
    • Эндпоинты WebSocket и других не-HTTP протоколов (wss://realtime.example.com).
    • Имена хостов тестовых сред (staging), сред разработки или внутренней сети (build-server.corp.local, staging-api.example.com).
    • Приватные IP-адреса и порты (10.x.x.x, 172.16-31.x.x, 192.168.x.x).
    • URL-адреса сторонних сервисов, таких как серверы аналитики, проверки лицензий или обновлений.

    Извлечение этой маршрутной информации позволяет восстановить карту архитектуры бэкенда и обнаружить эндпоинты, не упоминаемые в открытом коде JavaScript.

    Автоматизированное извлечение¶

    Утилита wasm-hunter позволяет автоматизировать извлечение данных из локального файла или по удаленному URL:

    wasm-hunter -i target_module.wasm

    Ручное извлечение¶

    Ту же информацию можно собрать стандартными системными утилитами, что удобно при отсутствии специализированного инструментария. Строковые литералы хранятся в сегментах данных модуля и могут быть найдены напрямую в бинарном файле:

    # URLs and endpoints
strings -n 6 module.wasm | grep -Eio '(https?|wss?|ftp)://[^[:space:]"'"'"']+'

# Common internal hostname patterns and API paths
strings -n 6 module.wasm | grep -Ei '\.(internal|local|corp|lan)\b|/api/|/v[0-9]+/'

# Private IPv4 addresses
strings -n 6 module.wasm | grep -Eo '\b(10\.[0-9]{1,3}|172\.(1[6-9]|2[0-9]|3[01])|192\.168)\.[0-9]{1,3}\.[0-9]{1,3}\b'

# Same search for UTF-16 strings (used by some toolchains such as .NET)
strings -n 6 -el module.wasm | grep -Ei 'https?://'

    Необработанные сегменты данных можно просмотреть с помощью команды wasm-objdump -s -j Data module.wasm. Строки, сжатые, зашифрованные или формируемые динамически во время выполнения, не отобразятся в этих результатах. Строки, найденные в связующем коде JavaScript или в сопутствующих конфигурационных файлах, также должны быть включены в отчет.

    (Примечание: Извлечение фактических учетных данных, токенов и криптографических ключей из бинарного файла выходит за рамки этапа разведки.)

    Рекомендации по устранению¶

    • Не публикуйте в продуктивной среде карты исходного кода (source maps), данные DWARF или разделенные отладочные файлы (split debug files). Храните отладочную и символьную информацию на защищенном сервере символов или в изолированной среде.
    • Удаляйте избыточные отладочные метаданные и метаданные сборки из релизных версий. Например, утилита wasm-strip (WABT) удаляет все пользовательские секции, а wasm-opt --strip-debug --strip-producers (Binaryen) удаляет отладочную информацию и секцию producers. Настройте компилятор и компоновщик на создание очищенных (stripped) релизных артефактов там, где это поддерживается.
    • Не зашивайте в код модулей, доставляемых на сторону клиента, внутренние имена хостов, IP-адреса, учетные данные или чувствительные эндпоинты. Любой ресурс, передаваемый в браузер, следует рассматривать как публично доступный.
    • Отдавайте Wasm с корректным MIME-типом application/wasm и убедитесь, что карты исходного кода, отладочные артефакты и другие файлы непродуктивных сборок недоступны для публичной загрузки.

    Инструменты¶

    • WebAssembly Binary Toolkit (WABT) — включает wasm-objdump для просмотра секций, импортов, экспортов и символов, а также wasm-strip. Также содержит инструменты wasm2wat и wasm-decompile, применяемые на последующих этапах анализа.
    • wasm-tools — инструментарий от Bytecode Alliance для вывода структуры секций (wasm-tools objdump) и парсер, выступающий альтернативой WABT.
    • Binaryen — предоставляет утилиту wasm-opt, используемую для очистки отладочной информации и секции producers, а также wasm-dis для дизассемблирования.
    • WASM-Hunter — инструмент статического анализа для сопоставления поверхности атаки (Attack Surface Mapping) и экспресс-определения компилятора с возможностью сканирования удаленных URL.
    • strings, od, file, grep — стандартные системные утилиты, достаточные для проверки заголовков и базового извлечения строк.
